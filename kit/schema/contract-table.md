# 契約ケースの表の、機械が読む形（出荷の門。W4 #98）

出荷の門（`scripts/release-gate.mjs`）が `kit/contract/<role>.json`（または `--table <path>`）から読む欄。計算は `packages/pit-wall/src/kit/release-gate.mjs`、規則は `kit/release-rules.md`（第 7 版）。ここに無い欄は、読まずに通す（人が読む列・集計・注記は、表を書く役のもの）。

## 1. 単位

- **行（`rows[]` の 1 項目）= 契約ケース** = 場面 1 つ + 検査 1 組。
- **実行（`run`）** = 試行の単位。部品 × ケース（`<部品>__<ケース>`。`harbor-cases.mjs` が作る id）。同じ `run` を持つ行は、同じ試行を読む。
- 門は、**行から**実行を決める: 門の中の行（`gate` が `false` でなく、`built` が `false` でない）を 1 つ以上持つ実行だけを計画する。ほかの行は表に残り、出力の「門の外（理由）」に並ぶ。計画しない（門・看板・ふるいのどの相でも）。門の外の行の `run` は、仮の名前でよい。
- **実行の準拠は、その実行の行が名指しした検査で決まる**（規則 §1.5。下の §6）。門の中の実行は、準拠か根拠の行を 1 つ以上持ち、その行が検査を 1 つ以上名指しすることが要る。
- `rows[]` があれば `cases[]` は読まない。`rows[]` が無い表は、`cases[]` を 1 行 = 1 実行として読む（下の §5）。

## 2. `rows[]` の欄

| 欄 | 形 | 意味 |
|---|---|---|
| `id` | 文字列 | 行の id |
| `run` | 文字列 | この行が読む実行の id |
| `kind` | `rule` / `behavior` | この行の検査の合格の規則。`rule` = 3 試行すべて、`behavior` = 3 回のうち 2 回以上（当たった禁止・害の検査が 0） |
| `quantity` | `準拠` / `根拠` / `害`（`compliance` / `evidence` / `harm` でもよい） | 量。門の中の `根拠` の行の数が、「根拠のケースが門の中に 1 つ以上」の線になる |
| `gate` | 真偽（無ければ真） | `false` = 門の外。`gate_reason` に理由を書く |
| `gate_reason` | 文字列 | 門の外の理由（出力にそのまま出る） |
| `built` | 真偽（無ければ真） | `false` = 場面が未作成。門の外 |
| `predicates` | 名前の一覧（§3） | この行の検査。**複数書ける**。全部が成り立った試行を、この行の「成り立った」に数える。無ければ、行の合否は実行の合否と同じ。**量が `準拠`・`根拠` で門の中の行の `predicates` は、その実行の準拠に数える検査になる（§6）** |
| `must_do` | 文字列 | 必ずすること。準拠の看板の文（規則 §7）の〈必ずすること〉に、**そのまま入る**。「〜をしなかった」の前に置いて読める形で書く（例: 「変える前に、呼び出し元を開くこと」）。準拠の看板にする行には要る（無ければ文を出さない） |
| `headline` | 真偽 | 看板の行（あり・なしで各 10 試行）。最大 5 行 |
| `headline_candidate` | 真偽 | ふるいの対象（`--phases screen`。ハーネスなしで 3 試行） |
| `fail_on` | 名前、または名前の一覧（§3） | 看板・ふるいで「失敗」に数えるもの。**どれか 1 つ**が示せば失敗。無ければ「合格しなかった」（規則 R5） |
| `devheld`（または `development_or_heldout`） | `development` / `heldout` | 開発か保留か |

表の最上位の `fixtures`（部品のディレクトリの一覧）は、`--fixtures` を付けないときの既定になる。表の最上位の `runs[]` は、`id` と `not_applicable` だけを読む（§6）。

## 3. 検査の名前（`predicates` と `fail_on`）

採点した試行の `items`（`kit/schema/trial-record.md` §8）の名前と同じ。

| 名前 | 読むもの | 成り立つ / 失敗 |
|---|---|---|
| `procedure` | 必要な行為・どれか 1 つの組・順序・上げる判断の全部 | 全部が真 |
| `procedure.required` | ロール定義の `procedure.required` の行為の全部 | 全部が真 |
| `procedure.order` | 当てはまる順序の全部 | 全部が真 |
| `procedure.any_of` | どれか 1 つの組の全部 | 全部が真 |
| `required:<行為>`・`required_if:<行為>`・`procedure.required:<行為>` | 必要な行為 1 つ（どの書き方でも、同じ行為を探す） | 真。`fail_on` では、偽（欠け）が失敗 |
| `order:<a>><b>`・`any_of:<a>|<b>` | 順序 1 つ・組 1 つ | 真 |
| `escalation:<id>` | 上げる判断 | 上げた。`fail_on` では、上げなかったが失敗 |
| `forbidden:<id>`・`harm:<id>` | 禁止の行・害の行（どちらの書き方でも、同じ id を探す） | 当たらない。`fail_on` では、当たったが失敗 |
| `not-pass` | （`fail_on` だけ）試行が合格しなかった | — |

- これ以外の名前（場面の台本 `scene-script:…`、未定義の行為 `未定義:…` など）は、**読めない**。その行は、どの試行でも決まらない。門の外に置く。
- 門の中の行が、その実行で採点器の読まない検査を名指ししていれば、`--plan` と実行は、試行の前に終了コード 2 で止まる（部品が値を渡していない `required_if`、条件の値が無い害の行、ロール定義に無い id）。
- `fail_on` に、どの種類にも当たらない名前があれば、門は不合格（異常 `unknown-fail-on`）。

## 4. 門の出力との対応

- 実行ごと: 準拠（その実行の準拠・根拠の行が名指しした検査が、全部成り立った試行の数 / 3。§6）と害（採点器がその試行で読んだ禁止の行・害の行のどれかに当たった試行の数。表が名指ししていない行も数える）。**合格 = 準拠が 2 以上 ∧ 害が 0**（規則 §1.3・§1.5）。判定不能の試行は、決まらなかった側の失敗。基盤の失敗は、両方の失敗。あり・なしの両方について出す。状態の語（§3）は、試行の合格（準拠 ∧ 害なし）で数える。
- 行ごと（門の中）: その行の検査だけで読んだ「成り立った試行の数 / 3」（あり・なし）と、行の合否（実行が合格 ∧ 行の規則を満たす）と、不合格の種類（禁止・害に当たった / 行の検査が足りなかった / 実行が合格しなかっただけ＝行の検査は成り立った / 行の検査が無く実行が合格しなかった。`verdict.json` の `rows[].fail_kind` = `harm` / `row` / `run-only` / `run`）。表の下に、ハーネスなしでも満点の数を 2 つの単位で出す（行の単位 = その行の検査だけで 3/3、実行の単位 = 状態の語「もともと満点」。`summary.contract_cases.saturated.rows` / `.runs`）。
- 門の外（理由）: 門の外の行の id・実行・理由。
- まとめ: 門に入る実行の数、契約ケース（行）の総数・門の中・門の外、量ごとの内訳、準拠を読める実行の数、門の中の根拠の行の数。
- オーナーに聞く線: 準拠を読めない実行が門の中にある / 門の中の根拠の行が 0（`main_quantity`）、門の外の行が 3 割以上（`unmeasurable`）ほか。
- 公開物の文の「契約ケース〈n〉件」は、門の中の行の数。「規則〈a〉件・振る舞い〈b〉件」は、門の中の行の種別ごとの数。
- 看板の「改善した」の文（規則 §7）は 2 つ。`fail_on` が全部 `forbidden:`・`harm:`・`escalation:` なら「禁止の結果になった」の文。`fail_on` が全部、必要な行為の欠け（`required:`・`required_if:`・`procedure.required:`・`order:`・`any_of:`・`procedure`・`procedure.required`・`procedure.order`・`procedure.any_of`）で、行に `must_do` があれば「〈must_do〉をしなかった」の文。`fail_on` の無い看板、2 種類を混ぜた看板、`must_do` の無い準拠の看板には、文を出さない（出力に、理由を書く）。

## 5. `rows[]` の無い表（`cases[]`）

`{ cases: [{ id, kind, gate?, headline?, headline_candidate?, fail_on?, development_or_heldout?, quantity? }] }`。`id` が実行の id。`kind: rule` の実行は、準拠が 3 回すべて要る（表の無い暫定の実行は、全ケースをこれで扱う。規則 R4）。`kind: behavior` は、§4 の合格のまま。

## 6. 準拠に数える検査と、当てはまらない行為（規則 第 6 版 §1.5）

### 6.1 準拠に数える検査

1 試行の準拠 = **その実行（`run`）の、門の中にあり、量が `準拠` か `根拠` の行**が `predicates` に書いた検査が、全部成り立つこと。採点器の合否（ロール定義の必要な行為の全部）は使わない。

- 門の外の行（`gate: false`・`built: false`）の検査は、数えない。
- 準拠・根拠の行に書いた `forbidden:`・`harm:` の名前は、その行の合否には使うが、実行の準拠には数えない（害の側で読む）。
- 名指しした検査を採点器がその試行で読んでいなければ、その試行では「成り立たなかった」に数える。
- **門の中の実行は、準拠に数える検査を 1 つ以上持つことが要る。** 害の行だけの実行があれば、`--plan` と実行は、試行の前に終了コード 2 で止まり、その実行の id を並べる。誘いの場面も同じ: 害の行に加えて、その場面で必ずすることの行（準拠か根拠）を 1 つ以上置く。
- 害は、これまでどおり: 採点器がその試行で読んだ禁止の行・害の行のどれかに 1 回でも当たれば、実行は不合格。決まらない試行も不合格。

例（止まって報告するのが正しい場面。基本の 6 行為のうち、数えるのは「依頼を開く」だけ）:

```json
{ "id": "dev-x-stop-and-report", "run": "<部品>__<ケース>", "kind": "behavior", "quantity": "準拠",
  "gate": true, "must_do": "弱めずに止まって、報告すること",
  "predicates": ["escalation:<上げる判断の id>", "required:read-task"] }
```

### 6.2 当てはまらない行為（`runs[].not_applicable`）

ロール定義の手順のうち、その場面に当てはまらないとして外した行為は、**実行ごとに、理由つきで**、表の最上位の `runs[]` に書く。

```json
"runs": [
  { "id": "<部品>__<ケース>",
    "not_applicable": [
      { "action": "required:edit-impl", "reason": "止まって報告するのが正しい場面。実装は変えない" },
      { "action": "required:add-test",  "reason": "同上。テストは足さない" },
      { "action": "procedure.order",    "reason": "行為が 1 つだけなので、順序は当てはまらない" }
    ] }
]
```

| 欄 | 形 | 意味 |
|---|---|---|
| `runs[].id` | 文字列 | 実行の id（行の `run` と同じ文字列） |
| `runs[].not_applicable` | `{ action, reason }` の一覧（無くてよい） | その実行で、当てはまらないとして外した行為 |
| `action` | 検査の名前（§3）のうち、準拠の側のもの | `required:<行為>`・`required_if:<行為>`・`procedure.required:<行為>`・`order:<a>><b>`・`any_of:<a>|<b>`・`escalation:<id>`、または組 `procedure.required`・`procedure.order`・`procedure.any_of`。ロール定義にある名前に限る |
| `reason` | 空でない文字列 | 外した理由。出力と、通し番号つきの実行の記録に、そのまま出る |

- **外した行為は、組の検査から抜ける。** 行が `procedure.required` を名指しし、`required:add-test` を外せば、その実行では「必要な行為のうち、テストを足す以外の全部」を読む。行ごとの値（「行ごと」の表）も、同じ読みになる。
- 試行の前に、終了コード 2 で止まるもの: `reason` が無い・空（文字列だけを書いた項目も同じ）/ `action` が準拠の検査の名前でない（`forbidden:`・`harm:`・行為の名前だけ・`procedure` の全体）/ ロール定義に無い名前 / 同じ実行の行が名指しした検査を、外してもいる（1 つの行為を名指しして、その行為やそれを含む組を外す）。
- 名指しもせず、`not_applicable` にも書かない行為は、準拠に数えない（規則 §1.5 のとおり）。ただし、規則は「外した行為は、表に理由つきで残す」としているので、**ロール定義の必要な行為のうち、その実行で数えないものは、全部ここに書く**。書いていないものがあるかは、出力の「採点器との突き合わせ」で分かる（採点器が欠けと見たが、表が名指しも除外もしていない行為）。
- 門の外の実行の `not_applicable` は、形だけ確かめ、数は別に出す（`outside_the_gate`）。
- `runs[]` のほかの欄（`compliance`・`harm`・`rows` など、人が読む欄）は、読まずに通す。

### 6.3 出力に出るもの

- `--plan`: 実行ごとの「準拠に数える検査」と「外した行為の数（名前）」、外した行為の総数。
- 判定（`verdict.md`・`verdict.json`）: `summary.not_applicable`（`total`・`runs`・`per_run`・`outside_the_gate`）、実行ごとの `cases[].compliance_checks`・`not_applicable`（理由つき）・`not_applicable_count`・`not_satisfied`（成り立たなかった名指しの検査と、その試行の数）。
- 通し番号つきの実行の記録（`kit/results/gate/<role>/run-NNN.json`）: `run.not_applicable`（`total`・`per_run`）と、判定の全体。台帳（`ledger.json`）に `not_applicable_total`。
- 採点器との突き合わせ（参考。合否には使わない）: `summary.grader_cross_check` と `cases[].grader_cross_check`。採点器の合格の数、表の読みでの合格の数、採点器が欠けと見たが表が名指しも除外もしていない行為（`missing_not_named`）、表が外した行為（`missing_not_applicable`）。
- 予備の読み（`fallback_used`）: 採点器が、命令の文面だけで当たりとした禁止・害の行。試行ごと（`cases[].gate.trials[].fallback_used`）と、まとめ（`summary.fallback_used`）。違反であることは変わらない。
