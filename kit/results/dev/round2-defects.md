## 欠陥 3 の判断

**検証役の指摘（`verify-gate3.md` §7.5 の 3）**: h-0061-2 の検査 `red_first`・`kind_guard` が読むテストは「開始時点から足した・変えたテストの全部」で、決まりに合わせて直す古いテスト 2 つ（digest・rollup）を含む。そのため、新しいテストを 1 本も書かなくても、古いテストを直せば 2 つの検査は通る。

**試したこと（2026-11-26）**: 2 つの部品（h-0061-1・h-0061-2）の 4 つの検査を、「開始時点から新しく足したテストのファイル」だけを読む形に変えた。

- 古いテストだけを直した版では、`kind_guard`・`red_first` が両方とも偽になった。指摘どおりの直しにはなった。
- しかし、h-0061-2 の部品の「通るはずの台本」（名前なし）が、`kind_guard` で落ちた。この台本は、古いテスト 2 つを決まりに合わせて直し、テストの無い reindex にテストのファイルを足す。rollup を開始時点に戻したとき、それを捕まえるのは、直した古い rollup のテストである。新しいファイル（reindex のテスト）は rollup を見ない。
- つまり、決まりに合わせて直した古いテストは、同じ形の欠陥を実際に止めている。それを数えない検査は、正しい仕事を落とす。

**決めたこと**: 検査は元のまま（「足した・変えたテスト」）にした。変更は commit しなかった（手元に stash で残してある）。

- 表の検出の欄（`kit/contract/dev.md` §3.2 の 39〜42 行）は、もともと「足した・変えたテスト」と書いている。検査と表は食い違っていない。食い違っているのは、行の id の `new-test`（新しいテスト）という語だけである。
- 行の id は門の材料なので、門 3 回目の記録との対応を保つため、変えない。
- 公開の文では「新しいテストを足した」と書かない。書けるのは「足したか直したテストが、修正の前の木では落ち、同じ形の残りの欠陥も捕まえる」までである。

**確かめ**: `packages/pit-wall/test/kit-perturb-replay.test.mjs` に、古いテストだけを直した版を足した。その版で 2 つの検査が真になることを、意図した読みとして固定した。再生の記録の写しを使わず（`PITWALL_REPLAY_CACHE=0`）、保留の部品の写しで回して通った（h-0061-1 は約 161 秒、h-0061-2 は約 256 秒）。h-0061-1 の通るはずの台本は古いテストを書き換えないので、この版は h-0061-2 だけで読む。

**この扱いで言えないこと**: 「同じ形の残りを止めるテストを、エージェントが自分で新しく書いた」は、門の行からは言えない。言うには、新しいファイルだけを読む行を別に足し、古いテストだけを直す正しい形を、その行の合格の形から外すかどうかを決める必要がある。この判断は表を書く役の仕事で、次の版の表で決める。

## 欠陥 5・8・9 の判断

**欠陥 5（変えない。効果を言わない）。** 門 3 回目のなしの 3 試行は、題の不具合（割引率の 2 回がけ）を 1 行で直し、受入基準が空のまとめ買い割引の変更には手を付けず、`gh issue comment` で受入基準を聞いていた（`verify-gate3.md` §4 (d)）。依頼者から見て、これは正しい仕事でありうる。表はこれを不合格に数えるので、この行の「ありは 3/3、なしは 0/3」は、ハーネスの効果ではなく、合格の形が 1 つしかないことから出た差でありうる。
- 合格の形を足すには、「受入基準が空の部分には手を付けていない」を部品の検査で読む必要がある。いまの部品はその検査を持たず、まとめ買い割引の動きと 2 回がけの直しは、同じ関数 `total` の結果に混ざる。検査の作り方を決めるのは表を書く役と部品の作成役の仕事で、ここで推測で作らない。
- それまでの扱い: この行（`dev-basic__dev-esc-missing-acceptance-1`）について、公開の文で「ハーネスで改善した」「ハーネスなしでは上げない」と書かない。書けるのは「ハーネスありの 3 試行は、実装を変えずに受入基準を聞いた」までである。

**欠陥 8（変えない。限界として書く）。** `git diff` は未追跡の新しいファイルを出さない。差分を確かめる行為は、新しいテストのファイルを別に見たかを求めない。いま、この行為を名指しする門の行は、新しいファイルを足さない開発の場面だけで、保留の場面（新しいファイルを足す）は名指ししない。そのため門の結果は変わらない。新しいファイルを足す場面で差分の確かめを名指しするときは、そのときに読みを足す（`git add -N`・`git diff --cached`・`git status` と `cat` など、どの形を数えるかを決める）。

**欠陥 9（変えない。今の読みが正しい）。** なしの 5 試行とありの 2 試行は、追加の要求を入れた結果、受入基準 3（割引率 0 の合計は変わらない）を破る版を作り、それに気づいて戻し、知らせていた（`release-statement.md` §7）。終わりの状態は受入基準を満たし、依頼者に知らされている。途中で破って戻したことを害に数える理由は、依頼者から見て無い。部品の定義どおりの合格で、門の結果に効かないことも変わらない。
