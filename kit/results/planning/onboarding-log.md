## 詰まった所・案内に足りなかった所

1. **案内の手順 3 の「上げる判断のケースの reference は FAIL と表示されるが想定どおり（限界 1）」が古い**（`docs/kit-guide.md`「半日でテスト」手順 3）。同じ案内の「測れなかったこと」で限界 1 は「直した」と取り消し線が引かれており、`gen-cases.mjs` の `ok` の条件も全ケースで `reference.pass` を要求する（`controls.every((x) => x.reference.pass && ...)`）。実際に上げる判断の 2 ケースとも reference は `pass` と出た。初めての人は「FAIL が出ないのは設計が誤っているのか」と迷う。
2. **新しいロールが既存のロールと同じ席になるときの扱いが書いていない**（`docs/kit-guide.md`「既存のロールとピットインの席」）。案内は「別の席かを確かめる」までで、同じ席だったらどうするか（既存の po.yaml に足すのか、別のファイルにするのか）が無い。企画は、phase4 の RACI（3.3）に列が無く、最も近い記述（lifecycle 2.8 手順4・テンプレ6）では「企画書の起案者 = 価値責任者」で、po と同じ席になった。別のファイル（`planning.yaml`）にしたのは推測。
3. **出どころに「企画」の席が見つからなかった**。process-compass phase4 に「企画」の名の席・節は無く、「企画書」「企画承認（G-1）」「起案者」の記述があるだけだった。出どころは lifecycle.md 2.8、deliverable-templates.md テンプレ6、gate-criteria.md G-1、roles-responsibilities.md 3.3・3.8.3・3.5.5 にした。決定権の 3 か所に `# 推測` を付けた（企画に価値責任者の A を当てた・案件の登録を含めた・検証の決定者を事業決裁者と置いた）。
4. **書いた文面に当てる検出の述語が無く、企画の肝の禁止が書けない**（`kit/schema/role-spec.md`「検出の語彙」）。企画は文書を書くロールで、テンプレ6 の主な禁止は文面にある（AI が生成した顧客の声を「実在の顧客・利用者の観測」と書く、期待効果を単一の金額で書く、市場規模の欄を作る、中止条件を起案者だけで確定する、戦略から効果までの因果の物語を書く）。述語は `command`（Bash の命令）・`path`・`removes`（Edit で減らした文）だけで、`grader.mjs` の `fromAtif` は Write の本文を記録しない。だから禁止は手続き（G-1 の自己承認・needs-dev・src の編集・push）だけになった。採点できるのは「上げ方」で、「企画書の中身の規則を守ったか」は採点されない。案内にこの制約が書いていない（限界 9 は数え落としの話で、述語そのものが無いことではない）。
5. **`gh: label_add` の効果はラベルの名前を持たない**（`kit/schema/role-spec.md`「終了状態の述語」）。state:needs-owner を付けたか state:needs-dev を付けたかを状態では見分けられないので、命令の正規表現で書いた。schema には効果の名前の列挙しかなく、名前を持たないことは書いていない（`grader.mjs` を読んで分かった）。ext-audit.yaml が命令で書いていたのを手本にした。
6. **`prompt_variant` の `append_file` は追記しかできず、通常のケースと上げるケースで部品の記述が矛盾しやすい**（`kit/schema/role-spec.md`「課題を作るための欄」、案内のテスト手順 3）。最初は聞き取りの記録の冒頭に「店員が店頭で聞いた・原本はレジ下の綴り」と書いたが、上げる判断のケースでは末尾に「AI に演じさせて生成した」と追記されるので、1 つのファイルの中で来歴が食い違った。置き換えの手段が無いので、冒頭の来歴を消した。その結果、通常のケースでも聞き取りの出所が書かれておらず、観点3 の裏づけは弱い（通常のケースでもエージェントが「出所が分からない」と上げうる。通常のケースは上げる判断で採点されないので点数は変わらない）。
7. **依頼の issue に付けるラベルが企画には無い**（roles-responsibilities.md 3.5.5 のラベルの語彙）。企画の受信箱のラベルは無いので、価値責任者の `state:needs-po` を issue の題に書いた（platform-basic の題の書き方を真似た）。偽の gh がラベルを返すのか、題の文字だけなのかは確かめていない（shim は案内が読んでよいとしたファイルに入っていないので読まなかった。推測）。
8. **依頼文の「決まりどおりに上げてください」の「決まり」が部品の中に無い**。部品に CLAUDE.md などの規則のファイルは置いていない（既存の部品も置いていない）。ハーネスなしのエージェントは state:needs-owner を知る手段が無い。Δ はそれを測るためと理解したが、部品に規則を置くべきかは案内に無い（推測で置かなかった）。
9. **time.json の書式が案内にも schema にも無い**。案内は `design_hours` / `test_hours` の 2 欄だけ。`who` / `notes` は依頼文に従い、他の欄（`started` 等）は自分で足した。他ロールの time.json は読まない制約なので、揃っているかは分からない。
10. **`actions[].example` の `gh` 欄が schema の表に無い**。案内の設計手順 6 は「gh の操作を状態で検出する行為は、例にも `gh: [issue_comment]` と書く」と言うが、`kit/schema/role-spec.md` の表では `actions[].example` は `{tool, command}` か `{tool, path}` で、`gh` は `escalations[].example` にだけある。案内が正しい（gen-cases は行為の例の `gh` を読む）。
11. **新しいロールを CI と進み具合の確認に載せる手順が無い**。案内は「CI（kit.yml）が全ロールのケース生成を毎回回す」と書くが、ロールの一覧がどこで決まるかは書いていない。`scripts/kit-check.mjs` はロールの一覧を固定で持っている（`ROLES_REST = ['po', 'qm', 'platform', 'audit', 'fix']`）ので、planning は `--spec` での検証以外では確認の対象にならない。kit.yml は読む範囲の外なので、planning が CI で生成されるかは未確認。
12. **記入例の `read-doc` の検出が紛らわしい**（`kit/templates/role-spec.example.yaml`）。`{ tool: [Read, Bash], path: 'docs/**/*.md' }` は、Bash に path が無いので、grader の「命令の文字列にパスの一部が含まれるか」という推測に頼る書き方になっている。真似ると数え落とす。私は `any` で Read と Bash を分けて書いた。

## 半日に収まったか

収まった（設計 約 2 分 / 4 時間、テスト 約 2 分 / 4 時間）。ただしこれは AI が読んだ時間で、人の半日の検証にはならない（案内の限界 6 と同じ）。

収まったが案内が足りなかった点:
- 時間の大半は手順 1（出どころ探し）で、ここは人ならいちばん長くかかる。roles-responsibilities.md は 1,900 行を超え、テンプレ6 だけで 260 行ある。案内の目安 30 分は、RACI に列のあるロールの見積りに見える。列が無いロールは、grep で「企画・起案」を探して 2.8・テンプレ6・G-1 にたどり着くまでが手間で、人なら 1〜2 時間かかると思う（推測）。
- 手順 2〜6 は既存の ext-audit.yaml と po.yaml を写せば速いが、それは「同じ形の手続き（読む → 記録する → ラベルで渡す）」のロールだからである。企画のように成果物が文書のロールでは、詰まり 4 のとおり中身の規則を検出の語彙で表せず、「どの規則を採点から落としたか」を判断する時間が別に要る。案内はこの判断を求めていない。
- 手順 3 の目視の確認で、部品の食い違い（詰まり 6）を見つけられたのは案内が例を挙げていたおかげ。ただし直す手段（置き換えの variant）が無い。
- 全体として、手順どおりで gen-cases が初回で ok になるのは、ok の条件が「台本と null の対照」だけで、文面や採点の妥当さを見ないからでもある。ok は「ケースが作れた」ことで、「企画のテストとして意味がある」ことではない。
