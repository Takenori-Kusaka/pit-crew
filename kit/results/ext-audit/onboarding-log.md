## 詰まった所（1 件ずつ）

1. **出どころに「外部監査」が無い**（指示された process-compass phase4 配下）。`grep 外部監査` は adoption-guide.md の採用判断者の紹介文（監査法人の言及）だけに当たった。最も近い記述として、roles-responsibilities.md 3.4 の「監査担当（プロセス内部監査の実施者）」の要件 1〜4（案件に関与していない・開発部門の長が差し戻せない報告線・置けなければ外部への委託）、3.5.5 の `state:needs-audit` → `state:needs-po`、assurance-case.md「内部監査で確かめる観点」を使った。案内（kit-guide 設計 1）は「RACI で A・R を書き出す」としか書いておらず、**RACI（3.3）の表に監査担当の列が無い**ロールの決定権をどこから取るかの指示が無い。決定権（decides: 監査の所見）は 3.5.5 の「監査担当が監査の判定を終える」からの**推測**。
2. **既存の `audit` ロールと名前が近く、別の席だと分かるまでに既存定義を読む必要があった**（kit-guide の 6 ロールの表は「Audit」とだけ書く）。kit/roles/audit.yaml の冒頭の注で、GQ の Audit がピットインの出荷判定者（G-7）に当たると分かった。案内にロールの一覧と、それぞれがピットインのどの席かの対応が無い。
3. **gh の効果（`gh:` 述語）は通常・誘いのケースの参照台本では空になる**。`gen-cases.mjs` の `referenceState` が `gh: []` を固定で返すため、必要な行為を `gh: issue_comment` で検出すると、正しい台本でも fail する。schema（role-spec.md「終了状態の述語」）にも kit-guide にも書いていない。既存ロールがすべて命令の正規表現で検出していたので真似て避けたが、理由はコードを読むまで分からなかった。上げる判断のケースだけは `example.gh` が状態に入る。
4. **正規表現の `.` は改行に当たらない**。採点器は `new RegExp(...)` を旗なしで使う。`gh issue comment 41 --body "…\n- 観点 6 …"` のような複数行の本文で `.*観点` が外れた（手作りの記録を採点器に当てて確かめた）。`[\s\S]*` に直した。schema の「書くときの規則」に無い。既存ロール（audit / po）の `.*G-7` も同じ穴を持つと思われる（**推測**。既存ロールは直していない）。
5. **`--body-file` や、本文をファイルに書いてから投稿する書き方では、所見の記録を検出できない**（命令の文字列に「観点」が無い、または heredoc の本文が `gh issue comment` より前に来る）。直していない。限界 5・9（gh は命令から推定・正規表現）の一例として残す。
6. **テスト 3 の合格条件が読み取りにくい**。kit-guide は「reference が pass・null が 0」と書くが、(a) null の何が 0 か（conformance か pass の数か）が書いていない、(b) 上げる判断のケースは reference が pass にならない（0.40）のに gen-cases は `ok` を返す。`gen-cases.mjs` の判定（上げる判断のケースは reference の違反 0、全ケース null の conformance 0）を読んで、FAIL 表示が想定どおりだと分かった。限界 1 に書いてあるが、テスト 3 の表からはそこへの参照が無い。
7. **設計 7「`scripts/kit-check.mjs` の `validateSpec` が見る項目も同じ」の意味が取れない**。kit-check.mjs はロールの一覧（`ROLES_REST`）を固定で持ち、新しいロールの定義を引数で検証する方法が無い。実行しても ext-audit は検査されず、既存のマイルストーンの `ALL PASS` が出るだけ。新しいロールでは gen-cases が読めたかだけが検証になる。
8. **環境の部品の `issue` の書き方が schema に無い**。role-spec.md は「`issue`（任意）」とだけ書く。`number` / `title` / `body` / `acceptance_heading` の欄は dev-basic の部品と gen-cases.mjs を見て知った。`task.issue` のように依頼の番号を `${task.x}` で使う場合、`issue.number` とは別に `task` にも書く必要がある（二重に書く。**推測**で両方に書いた）。
9. **上げる判断の場面の文面が、部品と矛盾していないかを確かめる手順が無い**。最初に「あなたは F-07 の G-6 を担当していた」と書いたが、部品の記録では G-6 の判定者は sato なので、エージェントが自分を sato と読む余地があった。生成された prompt.md を目で読んで気づき、「仕様 PR #20 の起案に関与」に変えた。gen-cases は文面の整合を見ない。
10. **Δ の「あり」の側に何を選ぶかの指示が無い**。kit-guide 手順 5 は `<harness dir> /<entry>` とだけ書く。6 ロールの表から GQ v0 は `subjects/ganbari-quest-v0` だろうと**推測**し、`kit/run-all-delta-wsl.sh` で確かめた。新しいロールに対応するハーネスが無いときにどうするか（既存の近い席を使う、ハーネスなしどうしにする等）は書いていない。
11. **禁止の一部は検出の語彙で書けなかった**。附属書の「監査の抽出の対象を、監査される当事者に選ばせてはならない」は、「全部の記録を読まなかった」ことを出来事・終了状態の述語で表しにくく、forbidden に入れていない（`after` と `not` を組めば書けるかもしれないが、試していない）。
12. **キットの内部（gen-cases.mjs・grader.mjs・shim）を読まないと分からないことがあった**（3・6・8）。案内は「部品は packages/pit-wall/src/kit/ にある」と言うだけで、読む必要があるとは言っていない。初めての人がコードを読まない場合、3 は gen-cases の FAIL として現れ、原因に行き着きにくい。

## 半日に収まったか

- 収まった。実測は設計・テスト合わせて約 4 分（エージェントの時間）。ただしこれは、(a) 既存の audit の部品（カートの JS・records/）をほぼそのまま流用できた、(b) 出どころの文書を grep で一気に引けた、(c) キットのコードを読んで 3・6・8 を自分で解けた、ためである。
- 人が初めて使う場合は、詰まり 1（出どころの席が RACI に無い）と 3（gh の効果が参照台本に入らない）で時間を使うと思われる（**推測**）。特に 3 は、案内どおり書くと gen-cases が FAIL を返し、原因がコードにしか書いていない。
- 案内が足りなかった点の要約: RACI の外にある席の決定権の取り方、`gh:` 述語を必要な行為に使えないこと、正規表現の改行、テスト 3 の合格条件の書き方、kit-check が新ロールを検証しないこと、`issue` の欄、Δ の「あり」の選び方。
- 対照（reference pass・null 0）は、採点器と部品が噛み合っていることしか示さない。例の命令は検出の正規表現に合わせて書いたので、reference pass はほぼ同語反復である。実際のエージェントの書き方（複数行・`--body-file`・ラベルの引用符）で検出が外れないかは、手作りの記録を採点器に当てて一部だけ確かめた（詰まり 4・5）。
