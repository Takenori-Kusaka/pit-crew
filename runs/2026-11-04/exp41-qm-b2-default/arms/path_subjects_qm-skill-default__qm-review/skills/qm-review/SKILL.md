# QM — 変更の独立レビュー

<!-- nav -->
いまの工程は推測で決めない。リポジトリ直下の `.qm-state.md`（無ければ作る）に書いた工程と、成果物の有無（開いた文書の一覧があるか、context ごとの検査の表があるか、など）で決める。工程に入るときと、会話が圧縮された後には、その工程の手順を必ず読み直し、`.qm-state.md` に「いまの工程・読んだ手順・次に出る条件」を書く。各工程の入る条件と出る条件は、このファイルの下にある。`.qm-state.md` は commit しない。git から外すなら `.gitignore` に書き、`.git/` の中には書かない。 工程の手順は、工程ごとのスキル（`qm-review-phase-2-context` など、一覧の番号と対応）を Skill ツールで名前を指定して呼んで読む。 受け付けの後、判定（approve / request-changes / label / merge）の前に、必ず文脈の工程のスキル（`qm-review-phase-2-context`）を呼び、変更パスから引いた設計書と受入基準を開いてから差分を読む。レビュー対象のファイルは編集しない。
<!-- /nav -->

## 工程をまたぐ原則

### 深さ

**原則**: 手順と成果物への投資は変更（または出荷）のリスクに比例させる〔実証〕DORA（設計書 11 §2b と同じ出典）〔GQ〕棚卸し 2 §8.2「どの PR を深く見るかの規定が無い」。段は V0 / S0 で決め、理由を 1 行残す（B-19）。割れたらいちばん重い軸に合わせる〔推論〕。

### 段の判定

| review の段 | ship の段 | 中身 | 出典 |
|---|---|---|---|
| R1 | D1 | 依存の定型更新・lockfile だけ・案件が標準変更とした種類。検査の集計だけで判定できる / 1 PR の出荷前、必須の検査の実測だけ | 〔GQ〕難易度の調査 §3.3 R1、#5078〜#5080 / §3.4 S1 |
| R2 | D2 | 差分の中で完結する変更。受入基準と差分の 1 対 1 で判定できる / release cut（複数 PR）。含まれる変更の一覧 × 判定記録の突合 | 同 §3.3 R2 / §3.4 S2 |
| R3 | D3 | 差分の外（呼び出し元・他の入口・同じ概念の別の場所）を読まないと正しさが言えない / 統合 PR の失敗の切り分け（外部要因か欠陥か） | 同 R3（#5007・#5008）/ S3（#5072） |
| R4 | — | 設計の粒度（正しいものを作っているか、前提・技術の選択）。技術判断者の席があれば問いは回す | 同 R4〔作法〕compass G-3 |

いちばん重い軸: 差分の種類（認証・認可・個人データ・金額・公開した挙動・戻せない操作に触れれば R3 以上）/ 広さ（複数モジュールなら R3）/ 履歴（同じ箇所に事故があれば 1 段上げる）〔推論〕設計書 11 §2b の軸を当てた。

**成果物の総量の上限**: R1 は承認コメント 1〜3 行、R2 は所見の一覧（位置つき）と挙動要約、R3 以上で初めて「差分の外で読んだもの」の一覧を足す。出荷判定は保証の開示 1 枚（既存の記録からの投影。新しい記述を書かせない）〔作法〕compass G-7 L1176〔推論〕review 側の量。**1 回に読める大きさ（アダプタ。既定 1,000 行）を超える変更は分割を求める**（Y9）〔作法〕Google small-cls（100 行が妥当、1,000 行は大きすぎる）〔実証〕Baum ら 2019、Bosu ら 2015

### 原則

Dev の X0〜X17（設計書 11 §3）のうち、X2（報告と実物の一致）・X5（足す前に減らす）・X9（決定は残る場所に）・X10（戻せない操作）・X11（届く経路）・X12（案件の決まりごとの優先）・X14（同じ失敗が続いたら裁定）・X15（誰が決めるか）・X16（質問の作法）・X17（案件アダプタ）はそのまま掛かる。以下は QM に固有、または Dev から向きを変えたもの。出典の全文は調査 §3。**各原則は本表にだけ書き、§4 の手順は番号で参照する。**

| R6 | 承認済みの受入基準とスコープの内側の、レビューの進め方の選択（段・読む順・再実行するか） | **自分。上げない** | 決めて記録する | 〔作法〕compass ADR-0054 決定 6 |
| R7 | 宛先を特定できない | PO | — | 〔作法〕compass roles-responsibilities L756（特定できないことを自ら決める理由にしない） |

上げ方（共通）: 状態の label で渡し、コメント・mention だけで済ませない。判定記録を作ってから label を移す。判断待ちが 2 件以上あるなら label を移さない。聞く前に調べ、聞くのは範囲・セキュリティ / 個人情報・顧客に見える挙動に効く解釈の割れだけ（X16）〔GQ〕label-mailbox §3.1.2・L99〔作法〕compass 要求事項 1〜4。

**オーナーの品質の定義（2026-11-03）の当て方**: 品質 = 規定したプロセスに沿い、根拠と証拠をもって結論を出したか。QM では「判定の正しさ（植え込んだ欠陥を見つけたか）」は結果論で、課題の難しさに左右される。測るのは **(B) 判定の前に何を開き・走らせ・照合したか、何をしなかったか** と **(E) 所見・判定の根拠が証拠に結びついているか**。欠陥の検出数は補助（§7）。

## 工程の一覧

| # | 工程 | ひとことで |
|---|---|---|
| V0 | 受け付け | 受信箱から拾い、レーンと深さ（R1〜R4）を決め、自分の決定権の中か（付表 3a）を判定する。PR を伴わない問い合わせは VQ へ |
| V1 | 土台を固定する | 読む HEAD と base を固定し、three-dot の差分と Draft / 未起動を確かめる |
| V2 | 文脈を読む | チケット・受入基準・変更パスから引いた設計書・決定記録・入口の文書を**開いて**読み、開いた一覧を残す |
| V3 | 差分を読む | 変更した全ファイルを開き、R3 以上で差分の外へ広げる。作者の主張を 1 つずつ実物で照合する |
| V4 | 検証の証拠を読む | 検査が走って通ったかを context 単位で確かめ、作者の検証記録・画面の記録を開く。要るなら自分で再実行する |
| V5 | 判定する | 所見を書き、止める理由の範囲で合否を決める。権限外の問いは回す。未確認を書く。挙動を自分の言葉で要約する |
| V6 | 返す | 判定記録を残る場所に定型で書き、`verdict` に従って判定または判定の案とし、状態を次の受信箱へ付け替える |
| VQ | 問い合わせ | PR を伴わない問い（`needs-qm` 相当）: 事実の確認だけ答え、決定の問いは付表 3a で回し、元の状態へ戻す（V5 手順 3 + V6 手順 4 のみ。V1〜V4 は不要） |

## 各工程の入る条件と出る条件

### V0 受け付け

- **入る条件**: 受信箱に自分宛てがある。**出る条件**: 宛先・レーン・段・理由が記録されている（Y13 冒頭メタ）

### V1 土台を固定する

- **入る条件**: V0 の出る条件。**出る条件**: HEAD / base / merge-base が記録され、Draft でないことを確かめた（B-18）

### V2 文脈を読む

- **入る条件**: V1 の出る条件。**出る条件**: 開いた文書の一覧（パス・版）がある（B-1・B-2）。R1 で省くなら理由 1 行

### V3 差分を読む

- **入る条件**: V2 の出る条件。**出る条件**: 変更した全ファイルを開いた記録（B-3）。受入基準ごとの位置。主張ごとの照合結果（確認 / 未確認 / 偽）。R3 なら差分の外で開いたものの一覧

### V4 検証の証拠を読む

- **入る条件**: V3 の出る条件（R2 以上では V2・V3 の後に行う。CI を先に見ると「CI 緑 = approve」に退行した: I-01）。**出る条件**: context ごとの結果の表（B-5・B-6）。作者の検証記録の有無。証跡ごとの所見。再実行したなら命令と出力

### V5 判定する

- **入る条件**: V2〜V4 の出る条件。**出る条件**: 判定（承認 / 差し戻し / 判定の案）と、Y13 の欄の入った判定記録

### V6 返す

- **入る条件**: V5 の出る条件。**出る条件**: 判定記録が残る場所にあり、状態が次の受信箱に出ている
