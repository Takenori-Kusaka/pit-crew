### V2 文脈を読む

**目的**: 変更が何のためで、何に従うべきかを、作者の要約ではなく一次の文書（チケット・受入基準・設計書・決定記録）で知る。開いた一覧を証拠として残す（Y1 を V2 で当てる）。手順 1〜4 が段階。

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | チケットと受入基準を開く | PR が閉じるチケットの受入基準・採択条件・履歴（コメント・関連 PR）を開く。PR 本文の要約で代用しない（Y2）。決裁が要る PR はチケット側の条件と PR 側のブリーフを両方読む | 〔事故〕I-01・I-24〔GQ〕qm-session 手順 1 |
| 2 | 変更パスから設計書を引く | 変更したパスに対応する設計書・決定記録・入口の文書を**機械的に**引いて開く。対応表はアダプタ（GQ の例: `docs/CLAUDE.md` の更新ルール表、`pr-review` Step 0）。**対応表が無い案件の既定**: 変更パスの各ディレクトリの入口文書（CLAUDE.md / README）を開き、`docs/` を変更ファイル名・モジュール名・公開名で検索して当たった文書を開く。当たらなければ「対応する設計書なし」を未確認に書く。開いた一覧を判定記録に残す | 〔オーナー〕会社の型（対応表の無い新しい案件で起きた）〔GQ〕`research-inventory.md` §(2) 不足「手順 0」〔実証〕Bacchelli & Bird 2013（理解が中心）〔推論〕対応表が無いときの既定 |
| 3 | 決定記録の状態を見る（R3 以上） | 日付と状態（置き換え済みか）を確かめる。古い記録に基づく所見を書かない。コア機能では設計意図の記録の完備を確かめる | 〔作法〕Nygard（設計書 11 §4.1 手順 5）、compass G-6 基準 3 |
| 4 | 意図的な設計かを確かめる | 差分が設計書と食い違うとき、「設計書が古い」「意図的に変えた（決定の記録がある）」「逸脱」のどれかを決める前に、根拠（決定記録・チケットの合意）を探す | 〔GQ〕`research-inventory.md` §(2)（policy-compliance の段が PR ごとに無い） |

- **考え方**: レビューの中心は欠陥の発見より「変更の理解」で、文脈の知識が有用率を倍にする〔実証〕Bacchelli & Bird 2013、Bosu ら 2015。差分だけを見るレビューは会社で実際に詰まった〔オーナー〕
- **調査の範囲と深さ**: 対応表が指す文書と、チケットから 1 ホップ（関連 PR・置き換えた決定）まで。それ以上は R3 の V3 手順 4 で広げる〔推論〕
- **背景・目的が不明なとき**: チケットの目的・受入基準自体が曖昧なら、推測で埋めずに「受入基準が曖昧」を所見にし、付表 3a R2（PO）へ回す。GQ にはこの規定が無かった〔GQ〕棚卸し 2 §8.2
- **矛盾するとき（文書と差分）**: 黙ってどちらかに合わせない。①食い違いを所見に書く ②意図的な変更の記録があるか探す ③無ければ「設計書の修正か差分の修正か」を作成者に返し、裁けないなら付表 3a R3（技術判断者）へ。GQ では「設計書同期なしはマージ不可」（pr-review F）と「3 類型に当たらなければ QM が直す」（憲章 §0）が食い違っていた〔GQ〕棚卸し 2 §8.2・§8.6。核は「食い違いの所見 + 裁定の経路」、どちらを採るかはアダプタ〔推論〕
- **成果物**: 開いた文書の一覧（判定記録の欄「開いたもの」）
- **典型的な失敗**: 設計書を読まずに差分だけでレビュー（会社の型）/ PR 本文の要約を仕様の代わりに読む（I-21 と同型）
