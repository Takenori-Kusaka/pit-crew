### 3 テスト設計

**目的**: 完了の条件と、誤ったときの損失が大きい所を、**それを最も安く確実に確かめられる層**で確かめる最小のテストの一覧を作る。網羅を目標にしない。何を書かないかも決める。

**前提にする事実**（`research-testing-practice-evidence.md`）:
- テストの形（ピラミッド・トロフィー・ハニカム）の比率に、実証の裏付けは無い。どの比率も実務家の経験から出た数字である〔作法〕Fowler、Dodds、Google（いずれも実証なし）
- カバレッジを上げても、テストの効き目はあまり上がらない（テスト数をそろえると相関は低〜中程度、出荷後の不具合とは有意な相関が無い）。ただし低いカバレッジは問題の印にはなる〔実証〕Inozemtseva & Holmes 2014、Kochhar ら 2017、Gopinath ら 2014（設計者は本文未照合）
- 単体テストと結合テストで、見つかる欠陥の種類に差は無かった（Java OSS の 38,782 件）。単体テストの利点は欠陥の場所を特定しやすいこと〔実証〕Trautsch ら 2020（要旨で照合済み）
- テストには保守費用がある: CI の flaky でない失敗の 26% はテスト自体が古い・誤っていることが原因〔実証〕Labuschagne ら 2017。Google では全テスト実行の約 1.5% が flaky〔実証〕Micco 2016
- AI エージェントは「テストを書かない」より「何も確かめていないテストを量産する」方向に偏る（テストのパッチの 80.2% は期待値の検査が弱いか無い）。異常系が最もテストされない〔実証〕Banik ら 2026、Dipongkor ら 2026（要旨で照合済み）
- テストのコードも負債である。正味の価値がプラスのテストだけを残す〔作法〕Khorikov（実証なし、実務家の体系）。一定の確信に届くまでで止める〔作法〕Kent Beck（Stack Overflow 2008、帰属は [二次]）

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **T1 何を確かめるか** | 1 | 確かめるものを挙げる | ①完了の条件に書かれた振る舞い（正常系と、仕様が定める失敗の扱い）②誤ったときの損失が大きい所（お金・データの消失・権限・個人情報）③分岐の多いロジック ④過去に壊れた所・間違えやすい所 ⑤外部の失敗（タイムアウト・相手のエラー・制約違反）への応答を代表 1 件ずつ。これ以外は挙げない | 〔作法〕Spec Kit（受け入れ条件）、Kent Beck（自分が普段しない誤りはテストしない、複雑な条件分岐に注意）、Google SWE 11 章（壊したくないものにはテストを）〔実証〕Dipongkor ら（異常系が最も落ちる）〔推論〕5 つにまとめたこと |
| | 2 | テストリストを書く | 1 で挙げたものを、振る舞いの一文の一覧にする。実装の判断（クラス名・関数の分け方）を混ぜない。各行に「どの完了の条件・どのリスクを確かめるか」を付ける。**付けられない行は書かない** | 〔両氏〕t-wada 訳 Canon TDD（テストリストに実装の判断を混ぜない）〔作法〕Khorikov（正味の価値）〔推論〕付けられない行は書かない |
| **T2 どの層で確かめるか** | 3 | 層を、確かめるものごとに選ぶ | 比率では決めない。既定はコードの種類で決める: ①ドメインのロジック・アルゴリズム（計算する・分岐が多い）→ プロセス内の小さいテスト ②つなぎのコード（コントローラ・ハンドラ・CRUD）→ 公開 API の層で、自分専用の DB は実物を使うテスト ③自明なコード（ロジックの無い取り出し・委譲だけ）→ 書かない ④分岐も外部への依存も多いコード → テストの前に分割を考える | 〔作法〕Khorikov の 4 象限（[二次]）・「最も重要な部分に集中」、DHH「コントローラは結合テストで」、Fowler（比率の議論は本質でない）。いずれも実証なし（実務家の意見） |
| | 4 | 製品の性質で、主になる層を決める | 複雑さがドメインの計算にある製品（料金計算・規則の判定）は小さいテストが主。複雑さがサービスや外部とのつなぎ目にある製品（API 中心の Web アプリ・マイクロサービス）は API の層のテストが主。どちらと判断したかと根拠（どこに複雑さと過去の不具合があるか）を 1 行書く。案件アダプタに既定があればそれに従う | 〔作法〕Spotify の Testing Honeycomb（マイクロサービスという条件つき）、Khorikov（「ほとんどのアプリで」という条件つき）〔推論〕判断を 1 行書く |
| | 5 | テストの境界を決める | アプリと自分専用の DB までは実物にし、自分が制御できない外部（他のサービス・メール・決済）だけを置き換えるか契約テストにする。内部の構造・private な関数・呼び出し順は確かめない（状態を変える外への呼び出しを除く） | 〔作法〕Khorikov "When to Mock"、Google SWE 12・13 章（公開 API 経由、実物を優先）、Pact、Testcontainers〔両氏〕t-wada（リクエストとレスポンスのあたりを狙う、private メソッド） |
| | 6 | 大きいテストは理由があるものだけ | 実ネットワーク・ブラウザ・複数サービスにまたがるテストは、設定・つなぎ目・利用者の主要な経路など、中くらいのテストでは原理的に確かめられないものにだけ使い、1 本ずつ理由を書く | 〔作法〕Google SWE 14 章〔両氏〕t-wada「テストサイズ」（大を足すなら理由を、言い換えは〔推論〕） |
| | 7 | 変更の種類で最初の 1 本を決める | 不具合 → 症状を再現できる、外側に近い安定した層で再現テスト（調査で書いたもの）／ 新しい振る舞い → 完了の条件を確かめる外側（API・受け入れ）のテストを 1 本 ／ 振る舞いを変えないリファクタリング → **新しいテストを書かない**。既存の振る舞いのテストが通り続けることで確かめる（無ければ先に今の挙動を固定する） | 〔両氏〕t-wada「不具合にテストを書いて立ち向かう」〔作法〕Freeman & Pryce（外側から、[二次]）、Google SWE 12 章（変わらないテスト）、Feathers〔推論〕「外側に近い安定した層」 |
| **T3 書かないものを決める** | 8 | 書かないテストを確かめる | 次は書かない: 自明なコードのテスト／フレームワーク・ライブラリ自体の挙動／内部の構造・private・呼び出し順／自分専用の DB をモックするテスト／上の層のテストが既に確かめていて、足しても失敗の場所の特定も速さも増えないテスト／起こりえない状況（型や入力の検査で既に排除されている）のテスト／カバレッジの数字のためだけのテスト／現在の出力をそのまま期待値に固定するテスト（今の挙動を固定する目的で意図して書く場合を除く） | 〔作法〕Khorikov、Google SWE 12・13 章、Kent Beck Test Desiderata（構造に左右されない）、Claude Code best practices（「起こりえない場合のテスト」を名指し）〔両氏〕t-wada 訳 Canon TDD（アサーションの無いテスト、実際の出力を期待値に貼る）〔推論〕フレームワーク自体のテスト |
| | 9 | 時間の予算を確かめる | 手元で回す範囲と CI の必須の検査が、それぞれ 10 分以内に結果を返すか。超えそうなら、足す前に遅いテストを速くする・まとめる・消すを考える。足すテストの実行時間の桁を書く | 〔作法〕DORA（10 分以内、調査方法は未照合）、t-wada「SMURF」（速さと本番との近さの両替）〔推論〕桁を書く |
| **T4 見せる** | 10 | テストリストを見せる（人と進めるとき） | 人と一緒に進める作業なら、実装の前にテストリストを見せる。見せるのは一覧（何を確かめるか）で、テストのコードではない | 〔両氏〕t-wada（Claude Code に「テストリストは若干足りない」と差し戻した記録）〔作法〕Kent Beck "Augmented Coding"（次のテストを人が指定）〔推論〕見せる対象を一覧に限る |

#### 考え方

- **テストは確信を買うための費用。** 一定の確信に届いたら止める。テストのコードも本番のコードと同じく負債で、正味の価値がプラスのものだけを残す〔作法〕Kent Beck（帰属は [二次]）、Khorikov
- **網羅を目標にしない。カバレッジは穴を探す道具。** 数字を上げても効き目はあまり上がらない〔実証〕Inozemtseva & Holmes、Kochhar
- **層の比率に正解は無い。** 確かめたいものごとに、最も安く確実に確かめられる層を選ぶ〔作法〕Fowler、Google（比率はいずれも当て推量と自認）
- **振る舞いをテストする。** 内部の構造に結びついたテストは、作り直しを妨げ、保守費用を生む〔作法〕Google SWE 12 章、Kent Beck Test Desiderata〔両氏〕t-wada〔実証〕Labuschagne（失敗の 26% がテスト自体の問題）
- **絞るとき、異常系を落とさない。** エージェントは異常系を最も落としやすい。最小化の対象は「何も足さないテスト」であって、確かめる範囲ではない〔実証〕Dipongkor ら〔推論〕
- **テストのために設計が複雑になるなら、やりすぎ。** そのときは外側のテストで確かめる〔両氏〕t-wada「テスト容易性設計」〔作法〕DHH「Test-induced design damage」

#### 調査の範囲と深さ

- 既存のテストの層・書き方・実行時間・flaky の状況を読む。案件アダプタのテストの方針（主になる層、時間の予算）を読む〔推論〕
- 変更が触れる領域に、重い検査でしか見つからない不具合の履歴があれば、関係する重い検査を手元で走らせてから設計する〔GQ〕dev-session §重量 e2e 敏感領域
- 技法（同値分割・境界値・決定表・状態遷移）は、手順 1 の ②〜④（損失が大きい・分岐が多い・過去に壊れた）に当たる所にだけ当てる。調査の深さではなく、その箇所のリスクで決める〔作法〕Khorikov（重要な部分に集中）、Kent Beck〔推論〕

#### 背景・目的が不明なとき

- 完了の条件がテストできる形にならない: テストを書けないのは理解が足りないしるし。調査に戻り、仮定を記録するか、原則 X16 の作法で聞く〔作法〕INVEST の T、Spec Kit

#### 矛盾するとき

- 完了の条件と設計が食い違う（条件を満たすテストが設計では書けない）: 設計に戻す〔GQ〕dev-process/completion-principles §7
- 既存のテストが、今回の完了の条件と逆の挙動を期待している: どちらが正かを、調査の「矛盾するとき」の裁定手順で決める。既存のテストを黙って書き換えない〔GQ〕ADR-0006（アサーションの弱体化禁止）〔推論〕
- 案件のカバレッジの閾値と「書かないテスト」がぶつかる: 閾値を下げない。閾値を満たすためだけのテストも書かない。ぶつかったことを報告し、閾値の見直しを提案する〔GQ〕カバレッジ閾値の引き下げ禁止〔推論〕

#### 成果物と受け渡し

- テストリスト（振る舞い・確かめる条件かリスク・層・大きいテストの理由）と、書かないテストの一覧。次の工程（テスト実装）は自分〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 技法を全部の入力に当て、テストの数と実行時間だけが増える | 〔実証〕Inozemtseva & Holmes（数を増やしても効き目はあまり上がらない）〔作法〕DORA（10 分） |
| 内部の構造に結びついた単体テストを書き、作り直しのたびにテストを直す | 〔作法〕Google SWE 12 章〔実証〕Labuschagne |
| 自分専用の DB をモックし、本番でだけ失敗するクエリを通す | 〔作法〕Khorikov、Testcontainers |
| 絞った結果、異常系（外部の失敗への応答）を落とす | 〔実証〕Dipongkor ら |
| テストリストに実装の判断を書き、振る舞いの抜けに気づかない | 〔両氏〕t-wada 訳 Canon TDD |
