### 6 テスト評価

**目的**: 「通った」「できた」と言う前に、その主張を証明する検査を今の変更（正しい HEAD）に対して実行し、結果を読む。独立の確認は、後段のレビューと重ならない条件のときだけ入れる。

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **V1 対象を確かめる** | 1 | 検査する HEAD を確かめる | 検査を走らせる作業ツリーの HEAD が、報告する変更の HEAD と同じかを確かめて記録する | 〔事故〕I-13〔GQ〕agents/dev-session（gate 実行前の HEAD 確認） |
| **V2 主張ごとに証明する** | 2 | 主張を証明するコマンドを決めて今実行する | 「通った」「直した」の主張ごとに、それを証明するコマンドを決め、今実行し、出力を読む。出力を報告に添える | 〔作法〕superpowers verification-before-completion、Claude Code best practices |
| | 3 | 関係するテストを手元で、全体を CI で回す | 変更に関係するテストを手元で走らせる。全体の判定は CI で取る（修正が他を壊していないか） | 〔両氏〕t-wada「不具合にテストを書いて立ち向かう」（手順 7、全テストの実行）〔GQ〕dev-session §並行セッション前提（フルスイートは CI を正とする） |
| | 4 | 動かして見る（利用者に見える挙動を変えたとき） | 利用者に見える挙動を変えたなら、単体テストと型検査で終えず、アプリを動かして結果を見る（画面・API の応答）。内部だけ・型だけ・文書だけの変更では行わない | 〔作法〕Anthropic「長時間エージェントのハーネス」、Claude Code best practices〔GQ〕dev-session（UI は自分の目で） |
| | 5 | 完了の条件を確かめる | 完了の条件ごとに、確かめた証拠（コマンドの結果・画面の記録・検索の件数）を言えるようにする。条件 × 証拠の表を作るのは、条件が複数あるとき・「全部」と主張するとき・T2 のとき。「全部」と書く前に全範囲を検索する | 〔GQ〕ADR-0060（「全対応完了」宣言の検証）、agents/dev-session §Fix 完遂検証 log〔事故〕I-14。がんばりクエストの「AC 検証マップ」（4 列の表）は撤去済み（dev-open-pr SKILL.md、#4305）なので、表の形は取り込まず、条件と証拠を対応させる考え方だけを採った |
| **V3 CI を読む** | 6 | 検査が「通った」のか「走らなかった」のかを分ける | CI の各検査が pass か（skip・未起動・下書きのため未実行ではないか）を 1 つずつ確かめる。まとめの検査が緑でも、それを根拠にしない | 〔GQ〕qm-session（skipping を pass と読まない）、CLAUDE.md（ci-gate は skipped を failure に数えない）〔事故〕I-22 |
| | 7 | 不安定なテストを再実行で済ませない | 不安定なテストは隔離して原因を記録する。手元で並行して走らせた検証の「落ちた」「通った」は、負荷で偽の結果が出るので根拠にしない（全体の検査は CI を正とする） | 〔両氏〕t-wada（不安定なテストはスイートの価値を下げる、[二次]）〔作法〕Fowler「非決定性」〔GQ〕dev-session §並行セッション前提・§PR 作業時 |
| **V4 独立に確かめる（条件つき）** | 8 | 独立の確認を入れるかを決める | 入れるのは、①T2 ②後段に人や QM のレビューが無い ③同じ文脈で作ったものを同じ文脈で「完了」とし、しかも複数の条件を「全部できた」と主張する、のどれかのとき。T0 と、後段に QM のレビューがある T1 では入れず、実行の証拠と「確かめていないこと」を報告に書いて後段に任せる。入れる前に、後段のどの検査と重なるか、何を後段に任せるかを書く | 〔実証〕DORA（高リスクの変更に追加の精査）、Czerwonka ら（初めて見るレビュアの指摘の有用率 33%）、McIntosh ら（レビューが薄い部品は欠陥が増える、[二次]）〔作法〕apenwarr（レビュー層を 1 つ足すたびに 10 倍遅くなる。本人も理論的根拠が無いと認める経験則）〔事故〕I-14〔推論〕3 条件への整理 |
| | 8b | 入れるときは範囲を絞る | 作業の文脈を持たない別のエージェント（または人）に、仕様と照らして**正しさに関わる欠落だけ**を報告させる。見た目の好みと「念のため」のテスト追加の提案は除く。指摘を全部は採らず、採否は自分が判断する | 〔作法〕Claude Code best practices（問題を探せと言われたレビュアは必ず何か見つけ、全部直すと起こりえない場合のテストが増える）〔GQ〕dev-session §多観点セルフレビュー |
| | 9 | カバレッジは差分の穴を探す道具として使う | 変更した行のうちどのテストにも実行されない行、実行されないエラー処理を探して報告する。全体の数字を目標にしない。閾値を下げない | 〔実証〕Inozemtseva & Holmes、Kochhar（カバレッジの数字と効き目の相関は弱い）、Dipongkor ら（エージェントの PR の 64.8% で変更行が未実行、エラー処理が最も未実行）〔作法〕Fowler「TestCoverage」〔GQ〕カバレッジ閾値の引き下げ禁止〔事故〕I-05 |
| | 9b | テストの効き目を疑うときは壊してみる | 変更行を 1 か所わざと壊して、テストが落ちるかを確かめる（差分に限ったミューテーション）。落ちなければ足りないテストの候補として読む | 〔作法〕Google のミューテーションテストの実務（Petrović ら 2021、差分に限る） |
| **V5 判定** | 10 | 「グリーン」の範囲を書く | 全部通ったことを「正しい」とは書かない。「テストに書いた想定の範囲で動く」と書き、範囲外は未検証と書く。テストの件数を成果として書かない。何を確かめたか、何を確かめていないか、どのテストを書かなかったかを書く | 〔両氏〕t-wada「オールグリーン」〔実証〕Banik ら（テストファイルの数を数えると検証の強さを過大評価する） |
| | 11 | 時間と不安定さを報告する | テストの実行時間（手元・CI）と、不安定なテストの状況を報告に含める。予算（§4.3 手順 9）を超えていれば、そのことを書く | 〔作法〕DORA（10 分以内）、Google SWE 11 章（flaky が 1% に近づくと価値を失う）〔推論〕 |

#### 考え方

- **証拠のない「通った」は、偽の「通った」と同じ**〔GQ〕dev-process/qm-fix §Self-Review HONESTY〔作法〕superpowers
- **テストの結果は、判断と行動を促す情報。** 何が失敗し、だから次に何をするかまで書く〔両氏〕t-wada「自動テスト実行結果の目的」
- **人の理解を関所にする。** 長い説明で理解した気にさせず、要点を人が自分で確かめられる形（具体的な入出力の例、図）で示す〔両氏〕t-wada（[二次]）

#### 調査の範囲と深さ

- 手元の事前検査（pre-ready 等）は、CI が落とす検査のごく一部しか見ていない。CI 側の検査の一覧（案件アダプタ）を読み、個別に確かめる〔GQ〕CLAUDE.md §CI で hard-fail する検査、#4390（pre-ready の PASS は CI 緑ではない）
- 独立の確認の要否は手順 8 の条件で決める。後段の QM のレビュー・監査が何を見るか（案件アダプタ）を読み、重ねない〔推論〕〔作法〕apenwarr、DORA（手続きを足すと待ち時間とバッチが増える悪循環）

#### 背景・目的が不明なとき

- 完了の条件のどれかを確かめる方法が分からない: 確かめていない条件を「未検証」と書く。確かめたことにしない〔GQ〕dev-process/completion-principles §5（実画面未確認の完了は検証偽装）

#### 矛盾するとき

- 手元では通り、CI で落ちる（またはその逆）: CI を正とし、差の原因（環境・負荷・版）を調べる〔GQ〕dev-session §並行セッション前提、branch-strategy §4.1
- 自分の変更が原因でない CI の失敗: 放置しない。原因を特定し、その場で直す変更を出す。「原因調査中」「自分のせいではない」で済ませない〔GQ〕dev-process/anti-patterns §7
- 独立の確認の指摘が、仕様と食い違う: 仕様と実物で照らし、誤っていれば根拠を示して退ける〔作法〕superpowers receiving-code-review

#### 成果物と受け渡し

- 検証の記録（主張・コマンド・出力・判定）。完了の条件 × 証拠の表は手順 5 の条件のときだけ。次の工程（報告と受け渡し）は自分 〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| CI が緑というだけで、完了の条件を見ずに完了とする | 〔事故〕I-01、I-21 |
| 走っていない検査・下書きのため未実行の検査を緑と読む | 〔事故〕I-22 |
| 別の HEAD で検査し、その結果を報告する | 〔事故〕I-13 |
| カバレッジの閾値を下げて通す | 〔事故〕I-05 |
| アサーションを消して成功したふりをする | 〔両氏〕t-wada 訳 Canon TDD |
| 独立の確認を全変更に重ね、後段のレビューと同じことを見て待ち時間だけを増やす | 〔作法〕apenwarr、DORA |
