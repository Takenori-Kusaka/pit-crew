### 5 実装

**目的**: 失敗しているテストを、最小の変更で通し（Green）、通った状態のまま設計を整える（Refactor）。範囲の外に手を出さない。

**TDD（テストから始める周回）を当てる範囲**

| 場合 | 当て方 | 出典 |
|---|---|---|
| 振る舞いを足す・変える変更（期待値を先に書けるもの） | 失敗するテストを先に書き、期待した理由で失敗するのを確かめてから実装する | 〔両氏〕t-wada 訳 Canon TDD〔作法〕Thoughtworks の合宿報告（エージェントが誤りを追認するテストを書くのを防ぐ）、Willison |
| 不具合の修正 | 再現テストを先に（失敗を確かめる）→ 修正 → 通る → 関係するテスト | 〔両氏〕t-wada「不具合にテストを書いて立ち向かう」 |
| 設定・文言・純粋な削除・依存の定型更新・振る舞いを変えない機械的なリファクタリング | 失敗するテストから始めない。既存のテストを変更の前後で走らせる（テストが無ければ、変更の前にいまの挙動を固定する） | 〔作法〕Willison "First run the tests"、Feathers〔両氏〕t-wada「自動テストとテスト駆動開発、その全体像」（自動テストは必須、TDD は個人が選ぶスタイル） |
| 机上で決まらない試作（スパイク） | テストから始めることを課さない。時間枠を決め、結論が出たら捨てるか、テストを書いて作り直す | 〔作法〕スパイク〔両氏〕t-wada（テストファーストの範囲が広がりすぎる問題、同上） |
| Red / Green / Refactor ごとの記録（コミット） | 人と一緒に進める伴走モードでは既定にする（人が流れを制御するため）。任せる委託モードと、PR を 1 コミットにまとめて取り込む案件では、案件アダプタで省いてよい | 〔両氏〕t-wada「AI 時代の TDD」（伴走パターン）、Claude Code との TDD の記録（勉強会） |

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **I1 通す（Green）** | 1 | テストを通す最小の変更をする | いま書いたテストと、それまでのすべてのテストを通す。整理を混ぜない。テストに合わせて値をハードコードしない | 〔両氏〕t-wada 訳 Canon TDD（ステップ 3 とその過ち）〔作法〕Anthropic prompting best practices |
| | 2 | 気づいたことは一覧へ | 途中で見つけた別の課題は、その場で直さずテストリストかチケットに残す | 〔両氏〕t-wada 訳 Canon TDD（「その過程で気づいたことはテストリストに追加する」） |
| | 3 | 範囲を守る | 頼まれた変更と、明らかに必要な変更だけをする。不具合の修正で周りを掃除しない。1 回しか使わない処理に補助関数を作らない。起こりえない状況の防御を書かない（検査は外との境界で） | 〔作法〕Anthropic prompting best practices（overengineering）〔推論〕miyagawa の "does nothing else"（道具の機能範囲についての発言）を、変更の範囲に当てはめたもの |
| | 4 | 同じ概念の他の場所にも同じ変更をする | 調査で挙げた並行実装の組すべてに同じ変更を入れ、検索の件数で確かめる（「1 画面だけ直って他が壊れている」が最も多い苦情の型） | 〔GQ〕dev-session §並行実装、dev-process/feature-change-lateral-spread §1 |
| | 5 | 既存の解を使う | フレームワークや標準の機能を包まずに使う。依存を足すなら版を固定し、変わった依存の一覧を示す | 〔作法〕Spec Kit Article VIII〔両氏〕miyagawa（Carmel: 版の固定と差分の確認） |
| | 6 | 記録する | 通したら、その段階を記録する。段階ごとに分けるかは上の表（伴走モードは既定、委託モードは案件アダプタで決める） | 〔両氏〕t-wada（TDD のステップごとのコミット） |
| **I2 整える（Refactor）** | 7 | 通った状態のまま整える | 重複・名前・責務を整える。今の作業に必要な範囲だけ。2 つ目の重複で共通化しない（重複は合図であって命令ではない）。抽象化するなら理由を書く | 〔両氏〕t-wada 訳 Canon TDD（ステップ 4 とその過ち）〔GQ〕dev-session §3 つ目の類似 |
| | 8 | 学んだことをコードに映す | 後から分かったことは、整理でコードに映す。「負債」を雑なコードの言い訳にしない。「後で直す」と書くならチケットを作り、作らないなら今直す | 〔両氏〕t-wada 訳「Ward が語る負債のメタファー」、「質とスピード」（[二次]） |
| | 9 | テストを走らせ、記録する | 整理の後に、手元で走らせられる範囲のテストを走らせ、通ったら記録する（全体の判定は 4.6 で CI を正とする） | 〔両氏〕t-wada 訳 Canon TDD |
| **I3 次へ** | 10 | テストリストが空になるまで繰り返す | 4.4 の U1 に戻る | 〔両氏〕t-wada 訳 Canon TDD（ステップ 5） |
| | 11 | 設計書を同じ変更で直す | 仕様が変わったら、設計書の更新を同じ変更に入れる（別のチケットに切り出さない） | 〔GQ〕ADR-0001、docs/CLAUDE.md §設計書更新ルール |
| | 12 | 画面を変えたら自分の目で見る | 画面の変更は、実際に動かして見るまで完成ではない | 〔GQ〕dev-session §あなたの 6 ロール（ローカルで触っていない UI 変更は未完成） |

#### 入る条件

- 失敗するテストが 1 件あり、期待した理由で失敗した記録がある（テスト実装の出る条件）〔両氏〕t-wada
- 合意が要る設計は、承認の記録がある〔GQ〕dev-session §設計ポリシー先行確認
- 作業の土台（branch・base）が最新で、記録してある〔GQ〕dev-session §PR 作業時 ①〔事故〕I-12

#### 考え方

- **「動く」と「きれい」を同時に狙わない。** 順に達成する〔両氏〕t-wada「動作するきれいなコード」
- **1 つの変更は 1 つの目的。** 混ざったら分ける〔両氏〕t-wada（Claude Code との記録で自分が混ぜた 2 つの内容を 2 つの PR に分けた）〔作法〕Google small CLs
- **はりぼての合図で止まる。** 「shim として」「足場として」「ひとまず動く」「とりあえず」「同等性は別のチケットで」と書き始めたら、型をごまかす書き方（any・強制的な型変換）をし始めたら、その場で止めて設計に戻る〔GQ〕dev-process/completion-principles §4
- **行き詰まったら、同じ変更の中で作り直す。** 修正を重ねるより、最後に緑だった記録まで戻して作り直す方が速いことが多い（同じ branch・同じ PR の中のこと）。変更（PR）そのものを閉じて別に作り直すのは最後の手段で、理由を変更に残す〔両氏〕t-wada（「ダメだったらブランチを廃棄する」、[二次]）〔作法〕Cursor〔GQ〕dev-process/completion-principles §3（close & restart は最後の手段。同節の「PO の明示承認」は憲章 §0 ルール 4 と食い違う（棚卸し C9）ため、承認ではなく理由の記録とした）

#### 調査の範囲と深さ

- 実装中も調査の範囲（並行実装・派生物）を保つ。触ったコードの書き方が古いと気づいたら、一次資料 2 件以上で確かめてから直す〔GQ〕dev-session §実装モダン性、dev-process/feature-change-lateral-spread
- 調査で想定していない問いが出たら、調査に戻る〔推論〕

#### 背景・目的が不明なとき

- 実装の途中で、完了の条件の解釈が 2 通りに割れた: 実装を止め、調査の「背景・目的が不明なとき」に戻る（仮定して記録するか、顧客に見える挙動なら PO に聞く）〔作法〕Spec Kit〔推論〕

#### 矛盾するとき

- テストが誤っていると思った: テストを回避・書き換えせず、理由を書いて報告する〔作法〕Anthropic prompting best practices（テストが誤っていると思ったら知らせよ）
- 同じ問題への修正が 3 回失敗した: 4 回目に進まず、設計を疑って設計に戻る〔作法〕superpowers systematic-debugging
- 範囲外の問題に気づいた: 軽く同じ目的なら同じ変更で直す。目的が混ざるなら、いま別の変更（PR）にして直す。チケットにするのは、いま直せないと分かったときだけで、そのときは理由と担当を書く（「別のチケットとして提案」はこの場合）。チケットにして放置しない〔GQ〕dev-process/anti-patterns §1、憲章 §0 ルール 7・8（直せないと分かったときだけ起票）〔両氏〕t-wada（1 PR 1 目的）

#### 出る条件

- テストリストが空で、全テストが通った記録（コマンドと出力）がある〔両氏〕t-wada 訳 Canon TDD
- 並行実装の組すべてに変更が入ったことを、検索の件数で確かめた〔GQ〕dev-process/feature-change-lateral-spread
- 仕様が変わったなら、設計書が同じ変更で直っている〔GQ〕ADR-0001
- 仮置き（stub・何もしない実装・TODO）が残っていない〔GQ〕dev-session §段階的リリース禁止

#### 成果物と受け渡し

- テスト・実装・整理を分けて記録した変更、設計書の差分、並行実装の検索結果。次の工程（テスト評価）は自分 〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 通す変更と整理を混ぜ、どちらで壊れたか分からなくなる | 〔両氏〕t-wada 訳 Canon TDD |
| 1 画面だけ直り、同じ概念の他の場所が古いまま | 〔GQ〕dev-process/feature-change-lateral-spread §1 |
| 本番に必要な設定を配らずに起動時の検査を足し、反映が連続で失敗する | 〔事故〕I-06 |
| 規則を字面どおりに当てはめ、動いている検査を消す | 〔事故〕I-26 |
