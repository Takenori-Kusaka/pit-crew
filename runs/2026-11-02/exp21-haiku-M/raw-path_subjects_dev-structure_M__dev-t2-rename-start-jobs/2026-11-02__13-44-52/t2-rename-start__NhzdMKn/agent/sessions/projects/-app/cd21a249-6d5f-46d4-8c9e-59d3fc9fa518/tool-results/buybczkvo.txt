### 2 設計

**目的**: 調査で分かった事実・品質の順位・トレードオフ点の候補をもとに、根本的に違う案を 2 つ以上比べて 1 つを選び、選んだ理由と捨てた案を残し、実装できる単位の計画に分ける。

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **S1 要否** | 1 | 設計を書くかを決める | 解が一つに決まり、トレードオフが小さいなら設計書は書かず、計画（S5）だけを書く。代替案の無い「実装手順書」を設計書と呼ばない。新しいデータの形・新しいインターフェース・セキュリティ・課金・外部資源の追加・数日以上の作業なら、設計を書く。誰の合意が要るかは原則 X10（戻せない操作）と X15（誰が決めるか）で決まる | 〔作法〕Design Docs at Google〔GQ〕dev-session §設計ポリシー先行確認（設計を書く対象の列挙。合意の相手は §0 と食い違うため X15 を採る） |
| **S2 判断基準** | 2 | 判断基準に順位を付ける | 調査の品質の順位（重要度・難しさ）と、事業上の目的を、案を比べる基準として順位つきで並べる。どの案でも満たせる基準は比較から外す | 〔作法〕MADR の Decision Drivers、ATAM（設計者は逐語未照合）、Heuer の診断性 |

| **S3 案を出す** | 4 | 案を比べる（自明に 1 つでないとき） | 妥当な案が自明に 1 つでないときだけ、根本的に違う案を 2 つ以上出す。数より「捨てた案と理由を 1 つ以上書けるか」で足りる。「最小の変更 / きれいな構造 / 中間」の 3 方向は新しい機能で構造の判断が要るときだけ。既存の解（調査の手順 13）を案に含める | 〔作法〕Ousterhout「Design it Twice」（[二次]）、feature-dev〔両氏〕miyagawa「Steal Good Ideas」 |
| | 5 | 誤りにくい形を先に考える | 実行時の検査を足す前に、型・列挙・値の型で不正な値を作れなくできないかを考える。生成した時点で不変条件が成り立つ形にし、状態を書き換えるより新しい値を返す形を選ぶ。外から入る値は境界で早く失敗させる（型で保証していても外からの値には実行時の検査を残す） | 〔両氏〕t-wada「誤りにくい設計」（目次 [一次]・各論 [二次]）、Claude Code との TDD 記録（fail fast） |
| | 6 | テストしやすさで点検する | 時刻・乱数・外部 I/O を外から差し込めるか。テストのために設計を変えたら、責務が単純になったかを確かめる（複雑になったらやりすぎ）。private を直接テストしたくなったら、クラスの抽出を考える | 〔両氏〕t-wada「テスト容易性設計」「private メソッドをテストすべきか」 |
| | 7 | 相手への義務を最小にする | インターフェースは、使う側・実装する側に求める義務を最小にし、便利な機能は上の層に置く。公開インターフェースに特定のライブラリの型を漏らさない。既存の仕組みと互換にし、互換を壊すなら明示して理由を書く | 〔両氏〕miyagawa（PSGI FAQ "as simple as possible"、"minimize the requirements on backends"、CGI との互換） |
| **S4 選ぶ** | 8 | 案を比べて選ぶ | 順位つきの基準で各案を比べ、推奨と理由を書く。トレードオフ点（1 つの選択で品質が逆向きに動く点）をどちらに倒したかと、その理由を書く。セキュリティと運用の健全性を既定では譲らない | 〔作法〕Design Docs at Google（代替案の節が最も重要）、ATAM、AWS Well-Architected |
| | 9 | 3 つ目で型を考える | 似た仕組みが 3 つ目になるときに、共通の型（Strategy・Factory・Registry 等）を当てるかを判断する。当てないなら理由を 1 行。2 つ目までは共通化しない（重複は合図であって命令ではない） | 〔GQ〕dev-session §3 つ目の類似〔両氏〕t-wada 訳 Canon TDD（早すぎる抽象化） |
| | 10 | 脅威への対処を決める | 調査で挙げた脅威（該当するとき）について、どう対処するかを決める | 〔作法〕Threat Modeling Manifesto の問い 3 |
| **S5 計画** | 11 | 実装の単位に分ける | 1 つの変更（PR）は 1 つの目的にする。その中の刻みはテストリストに任せる。分単位のタスクの一覧（触るファイルと確かめ方つき）は、別のエージェント・人に実装を渡すときだけ作る。1 つの変更（PR）は 1 つの目的にする。途中の段階を出すなら、各段階が単独で動く形にし、仮置き（stub・何もしない実装・TODO）を出さない | 〔作法〕superpowers writing-plans（文脈の無い別の実行者に渡す前提の雛形）、Google small CLs〔両氏〕t-wada（1 つの PR に 2 つの内容を混ぜて分け直した記録）〔GQ〕dev-session §段階的リリース禁止 |
| **S6 合意と記録** | 12 | 決定を残す | 決定記録（文脈・決定・状態・結果）を書くのは、①後から覆すときに背景の理解が要り、案件の残りの進み方に影響する重要な決定 ②既存の決定記録と矛盾する新しい判断（古い記録を置き換え済みにする）③機械で強制できない判断原則、のどれかのときだけ。それ以外は PR 本文の 1 段落に書く。覆すときは古い記録を消さず置き換え済みにする。根拠・目標・制約を決めたその場で書く | 〔作法〕Nygard ADR〔両氏〕t-wada「意図負債」（明示的な根拠・目標・制約が存在しない状態）〔GQ〕ADR-0001（設計書は SSOT）、docs/decisions/README §新規 ADR 追加 gate（3 条件。がんばりクエストは ADR の増殖で上限と削除主義を定めた） |
| | 13 | 合意を取る（要るとき） | 原則 X10・X15 で承認が要るものは、着手前に承認を取り、その記録（GitHub 上のコメント・label・決定記録）を残す。それ以外は Dev が決め、決定記録に理由を残す | 〔作法〕feature-dev「承認なしに始めない」〔GQ〕憲章 §0 ルール 4・§4.4〔事故〕I-25 |

#### 考え方

- **最も単純な案から始め、必要なときだけ複雑にする**〔作法〕Anthropic「Building effective agents」
- **TDD は設計しないことではない。** コードを書く前に、設計の方針とテストリストを示す〔両氏〕t-wada（Canon TDD 訳者コメント、「まだコードは書かないでください」と指示した記録）
- **要望に No と言う。** 中核でないもの、他と組み合わせて実現できるものは足さない。足さない理由を書く〔両氏〕miyagawa（t-wada の引用経由、[二次]）
- **複雑さを減らす主語は使う人。** 内部の作りの数ではなく、使う人から見た複雑さで比べる〔GQ〕dev-process/anti-patterns §11
- **誤りを検出するより、誤りにくくする**〔両氏〕t-wada

#### 調査の範囲と深さ

- 設計のために新たに調べるのは、案の比較に必要な範囲だけ（各案の前例・制約・費用）。調査の工程に戻るほどの新しい問いが出たら、調査に戻る〔推論〕
- 重さは軌道（§2b）で決まる。戻せない決定・公開インターフェース・データの形は T2〔作法〕Bezos、Hyrum's Law

#### 背景・目的が不明なとき

- 案を選ぶのに、顧客に見える方針・backlog の順序の判断が要る（原則 X15）: 案と推奨を付けて PO に聞く（作法は原則 X16）〔作法〕feature-dev（推奨を示し明示的な確認を取る）〔GQ〕憲章 §0 ルール 4
- 技術の進め方で迷う: Dev が決めて理由を残す。PO に技術の決定を預けない〔GQ〕憲章 §0 ルール 4。がんばりクエストの completion-principles §4「選択肢を 2〜3 個用意して PO に明示質問」は憲章 §0 と衝突している（`research-ganbari-role-process-inventory.md` §1.3 D3）。本設計は §0 の側を採る（原則 X15）

#### 矛盾するとき

- 選んだ案が既存の設計・決定記録と食い違う: 決定記録を置き換える（古いものを置き換え済みにして新しいものを書く）。黙って違う作りにしない〔作法〕Nygard ADR
- 設計の途中で、要件・データの形・規約の不備が分かった: 元の工程（調査・要件）に戻して先に直す。大きな巻き戻しは合意を取る〔GQ〕dev-process/completion-principles §7

#### 成果物と受け渡し

- 設計の成果物は軌道で決める（§2b）: 書かない（理由 1 行）/ PR 本文に数行（推奨と、捨てた案 1 つと理由）/ 設計書（1〜3 ページ: 背景と範囲・ゴールと非ゴール・設計・検討した代替案・セキュリティ・個人情報・観測性）。設計書は T2、または新しい公開インターフェース・新しい機能のときだけ〔作法〕Design Docs at Google、feature-dev README〔推論〕軌道との対応
- 計画（タスクの一覧）。次の工程（テスト設計）は自分 〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 案を 1 つしか出さず、比べないまま作る | 〔作法〕Design Docs at Google、Ousterhout（[二次]） |
| 2 つ目の重複で共通化して、早すぎる抽象を作る | 〔両氏〕t-wada 訳 Canon TDD |
| 仮置き（stub・TODO）のまま出し、残りが別のチケットに流れる | 〔GQ〕dev-session §段階的リリース禁止 |
| 合意がセッション上の発言だけで、出典が GitHub に無い | 〔事故〕I-25 |
| PO の規則を字面どおりに当てはめ、動いている検査を消す | 〔事故〕I-26 |

### 3 テスト設計

**目的**: 完了の条件と、誤ったときの損失が大きい所を、**それを最も安く確実に確かめられる層**で確かめる最小のテストの一覧を作る。網羅を目標にしない。何を書かないかも決める。

**前提にする事実**（`research-testing-practice-evidence.md`）:
- テストの形（ピラミッド・トロフィー・ハニカム）の比率に、実証の裏付けは無い。どの比率も実務家の経験から出た数字である〔作法〕Fowler、Dodds、Google（いずれも実証なし）
- カバレッジを上げても、テストの効き目はあまり上がらない（テスト数をそろえると相関は低〜中程度、出荷後の不具合とは有意な相関が無い）。ただし低いカバレッジは問題の印にはなる〔実証〕Inozemtseva & Holmes 2014、Kochhar ら 2017、Gopinath ら 2014（設計者は本文未照合）
- 単体テストと結合テストで、見つかる欠陥の種類に差は無かった（Java OSS の 38,782 件）。単体テストの利点は欠陥の場所を特定しやすいこと〔実証〕Trautsch ら 2020（要旨で照合済み）
- テストには保守費用がある: CI の flaky でない失敗の 26% はテスト自体が古い・誤っていることが原因〔実証〕Labuschagne ら 2017。Google では全テスト実行の約 1.5% が flaky〔実証〕Micco 2016
- AI エージェントは「テストを書かない」より「何も確かめていないテストを量産する」方向に偏る（テストのパッチの 80.2% は期待値の検査が弱いか無い）。異常系が最もテストされない〔実証〕Banik ら 2026、Dipongkor ら 2026（要旨で照合済み）
- テストのコードも負債である。正味の価値がプラスのテストだけを残す〔作法〕Khorikov（実証なし、実務家の体系）。一定の確信に届くまでで止める〔作法〕Kent Beck（Stack Overflow 2008、帰属は [二次]）

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **T1 何を確かめるか** | 1 | 確かめるものを挙げる | ①完了の条件に書かれた振る舞い（正常系と、仕様が定める失敗の扱い）②誤ったときの損失が大きい所（お金・データの消失・権限・個人情報）③分岐の多いロジック ④過去に壊れた所・間違えやすい所 ⑤外部の失敗（タイムアウト・相手のエラー・制約違反）への応答を代表 1 件ずつ。これ以外は挙げない | 〔作法〕Spec Kit（受け入れ条件）、Kent Beck（自分が普段しない誤りはテストしない、複雑な条件分岐に注意）、Google SWE 11 章（壊したくないものにはテストを）〔実証〕Dipongkor ら（異常系が最も落ちる）〔推論〕5 つにまとめたこと |
| | 2 | テストリストを書く | 1 で挙げたものを、振る舞いの一文の一覧にする。実装の判断（クラス名・関数の分け方）を混ぜない。各行に「どの完了の条件・どのリスクを確かめるか」を付ける。**付けられない行は書かない** | 〔両氏〕t-wada 訳 Canon TDD（テストリストに実装の判断を混ぜない）〔作法〕Khorikov（正味の価値）〔推論〕付けられない行は書かない |
| **T2 どの層で確かめるか** | 3 | 層を、確かめるものごとに選ぶ | 比率では決めない。既定はコードの種類で決める: ①ドメインのロジック・アルゴリズム（計算する・分岐が多い）→ プロセス内の小さいテスト ②つなぎのコード（コントローラ・ハンドラ・CRUD）→ 公開 API の層で、自分専用の DB は実物を使うテスト ③自明なコード（ロジックの無い取り出し・委譲だけ）→ 書かない ④分岐も外部への依存も多いコード → テストの前に分割を考える | 〔作法〕Khorikov の 4 象限（[二次]）・「最も重要な部分に集中」、DHH「コントローラは結合テストで」、Fowler（比率の議論は本質でない）。いずれも実証なし（実務家の意見） |
| | 4 | 製品の性質で、主になる層を決める | 複雑さがドメインの計算にある製品（料金計算・規則の判定）は小さいテストが主。複雑さがサービスや外部とのつなぎ目にある製品（API 中心の Web アプリ・マイクロサービス）は API の層のテストが主。どちらと判断したかと根拠（どこに複雑さと過去の不具合があるか）を 1 行書く。案件アダプタに既定があればそれに従う | 〔作法〕Spotify の Testing Honeycomb（マイクロサービスという条件つき）、Khorikov（「ほとんどのアプリで」という条件つき）〔推論〕判断を 1 行書く |
| | 5 | テストの境界を決める | アプリと自分専用の DB までは実物にし、自分が制御できない外部（他のサービス・メール・決済）だけを置き換えるか契約テストにする。内部の構造・private な関数・呼び出し順は確かめない（状態を変える外への呼び出しを除く） | 〔作法〕Khorikov "When to Mock"、Google SWE 12・13 章（公開 API 経由、実物を優先）、Pact、Testcontainers〔両氏〕t-wada（リクエストとレスポンスのあたりを狙う、private メソッド） |
| | 6 | 大きいテストは理由があるものだけ | 実ネットワーク・ブラウザ・複数サービスにまたがるテストは、設定・つなぎ目・利用者の主要な経路など、中くらいのテストでは原理的に確かめられないものにだけ使い、1 本ずつ理由を書く | 〔作法〕Google SWE 14 章〔両氏〕t-wada「テストサイズ」（大を足すなら理由を、言い換えは〔推論〕） |
| | 7 | 変更の種類で最初の 1 本を決める | 不具合 → 症状を再現できる、外側に近い安定した層で再現テスト（調査で書いたもの）／ 新しい振る舞い → 完了の条件を確かめる外側（API・受け入れ）のテストを 1 本 ／ 振る舞いを変えないリファクタリング → **新しいテストを書かない**。既存の振る舞いのテストが通り続けることで確かめる（無ければ先に今の挙動を固定する） | 〔両氏〕t-wada「不具合にテストを書いて立ち向かう」〔作法〕Freeman & Pryce（外側から、[二次]）、Google SWE 12 章（変わらないテスト）、Feathers〔推論〕「外側に近い安定した層」 |
| **T3 書かないものを決める** | 8 | 書かないテストを確かめる | 次は書かない: 自明なコードのテスト／フレームワーク・ライブラリ自体の挙動／内部の構造・private・呼び出し順／自分専用の DB をモックするテスト／上の層のテストが既に確かめていて、足しても失敗の場所の特定も速さも増えないテスト／起こりえない状況（型や入力の検査で既に排除されている）のテスト／カバレッジの数字のためだけのテスト／現在の出力をそのまま期待値に固定するテスト（今の挙動を固定する目的で意図して書く場合を除く） | 〔作法〕Khorikov、Google SWE 12・13 章、Kent Beck Test Desiderata（構造に左右されない）、Claude Code best practices（「起こりえない場合のテスト」を名指し）〔両氏〕t-wada 訳 Canon TDD（アサーションの無いテスト、実際の出力を期待値に貼る）〔推論〕フレームワーク自体のテスト |
| | 9 | 時間の予算を確かめる | 手元で回す範囲と CI の必須の検査が、それぞれ 10 分以内に結果を返すか。超えそうなら、足す前に遅いテストを速くする・まとめる・消すを考える。足すテストの実行時間の桁を書く | 〔作法〕DORA（10 分以内、調査方法は未照合）、t-wada「SMURF」（速さと本番との近さの両替）〔推論〕桁を書く |
| **T4 見せる** | 10 | テストリストを見せる（人と進めるとき） | 人と一緒に進める作業なら、実装の前にテストリストを見せる。見せるのは一覧（何を確かめるか）で、テストのコードではない | 〔両氏〕t-wada（Claude Code に「テストリストは若干足りない」と差し戻した記録）〔作法〕Kent Beck "Augmented Coding"（次のテストを人が指定）〔推論〕見せる対象を一覧に限る |

#### 考え方

- **テストは確信を買うための費用。** 一定の確信に届いたら止める。テストのコードも本番のコードと同じく負債で、正味の価値がプラスのものだけを残す〔作法〕Kent Beck（帰属は [二次]）、Khorikov
- **網羅を目標にしない。カバレッジは穴を探す道具。** 数字を上げても効き目はあまり上がらない〔実証〕Inozemtseva & Holmes、Kochhar
- **層の比率に正解は無い。** 確かめたいものごとに、最も安く確実に確かめられる層を選ぶ〔作法〕Fowler、Google（比率はいずれも当て推量と自認）
- **振る舞いをテストする。** 内部の構造に結びついたテストは、作り直しを妨げ、保守費用を生む〔作法〕Google SWE 12 章、Kent Beck Test Desiderata〔両氏〕t-wada〔実証〕Labuschagne（失敗の 26% がテスト自体の問題）
- **絞るとき、異常系を落とさない。** エージェントは異常系を最も落としやすい。最小化の対象は「何も足さないテスト」であって、確かめる範囲ではない〔実証〕Dipongkor ら〔推論〕
- **テストのために設計が複雑になるなら、やりすぎ。** そのときは外側のテストで確かめる〔両氏〕t-wada「テスト容易性設計」〔作法〕DHH「Test-induced design damage」

#### 調査の範囲と深さ

- 既存のテストの層・書き方・実行時間・flaky の状況を読む。案件アダプタのテストの方針（主になる層、時間の予算）を読む〔推論〕
- 変更が触れる領域に、重い検査でしか見つからない不具合の履歴があれば、関係する重い検査を手元で走らせてから設計する〔GQ〕dev-session §重量 e2e 敏感領域
- 技法（同値分割・境界値・決定表・状態遷移）は、手順 1 の ②〜④（損失が大きい・分岐が多い・過去に壊れた）に当たる所にだけ当てる。調査の深さではなく、その箇所のリスクで決める〔作法〕Khorikov（重要な部分に集中）、Kent Beck〔推論〕

#### 背景・目的が不明なとき

- 完了の条件がテストできる形にならない: テストを書けないのは理解が足りないしるし。調査に戻り、仮定を記録するか、原則 X16 の作法で聞く〔作法〕INVEST の T、Spec Kit

#### 矛盾するとき

- 完了の条件と設計が食い違う（条件を満たすテストが設計では書けない）: 設計に戻す〔GQ〕dev-process/completion-principles §7
- 既存のテストが、今回の完了の条件と逆の挙動を期待している: どちらが正かを、調査の「矛盾するとき」の裁定手順で決める。既存のテストを黙って書き換えない〔GQ〕ADR-0006（アサーションの弱体化禁止）〔推論〕
- 案件のカバレッジの閾値と「書かないテスト」がぶつかる: 閾値を下げない。閾値を満たすためだけのテストも書かない。ぶつかったことを報告し、閾値の見直しを提案する〔GQ〕カバレッジ閾値の引き下げ禁止〔推論〕

#### 成果物と受け渡し

- テストリスト（振る舞い・確かめる条件かリスク・層・大きいテストの理由）と、書かないテストの一覧。次の工程（テスト実装）は自分〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 技法を全部の入力に当て、テストの数と実行時間だけが増える | 〔実証〕Inozemtseva & Holmes（数を増やしても効き目はあまり上がらない）〔作法〕DORA（10 分） |
| 内部の構造に結びついた単体テストを書き、作り直しのたびにテストを直す | 〔作法〕Google SWE 12 章〔実証〕Labuschagne |
| 自分専用の DB をモックし、本番でだけ失敗するクエリを通す | 〔作法〕Khorikov、Testcontainers |
| 絞った結果、異常系（外部の失敗への応答）を落とす | 〔実証〕Dipongkor ら |
| テストリストに実装の判断を書き、振る舞いの抜けに気づかない | 〔両氏〕t-wada 訳 Canon TDD |
=====4
### 4 テスト実装

**目的**: テストリストから 1 件ずつ、仕様から導いた期待値で確かめるテストにし、期待した理由で失敗することを確かめる。テストのコードも最小にする。

#### 工程の内部の段階とやること（順に）

この工程は、実装（4.5）と 1 件ずつ交互に回す。効くのは「テストを先に書くこと」そのものより「小さく一定の歩幅」であることを示す実証がある〔実証〕Fucci ら 2017（設計者は本文未照合）〔両氏〕t-wada 訳 Canon TDD（ステップ 2〜5）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **U1 1 件選ぶ** | 1 | テストリストから 1 件だけ選ぶ | 外側（完了の条件を確かめる層）から始める。内側の小さいテストは、外側のテストを通す途中で複雑なロジックが要ると分かったときにだけ足す | 〔両氏〕t-wada 訳 Canon TDD〔作法〕Freeman & Pryce（外側から内側へ、[二次]）、Kent Beck "Augmented Coding"（最も単純な失敗するテストを先に、1 度に 1 つ） |
| **U2 書く** | 2 | 期待値を仕様から書く | 期待値は仕様から導いた具体的な値にし、根拠（仕様の箇所・計算）を示せるようにする。実際に動かした値を貼らない。本番と同じ式で期待値を計算しない | 〔両氏〕t-wada 訳 Canon TDD（実際の出力を貼る過ち）、自動テストの講演（自作自演、[二次]） |
| | 3 | 期待値の検査を強くする | 例外が出ないことだけ・真偽だけ・件数だけ、で済ませない。失敗したとき期待値と実際の値が出る比べ方にする | 〔実証〕Banik ら（エージェントのテストの 80.2% は検査が弱いか無い）〔両氏〕t-wada（失敗時の情報量、power-assert の新形式についての発言 2025） |
| | 4 | 非決定性を固定し、テストどうしを独立させる | 時刻・乱数・並行性に依存するなら、値を決め打ちするか外から差し込む。順序に依存させない | 〔両氏〕t-wada（レガシーコード改善、テスト容易性設計、F.I.R.S.T） |
| | 5 | テストのコードも最小にする | 1 つの振る舞いに 1 つのテスト。テストのためだけの間接層（テスト専用のインターフェースやフック）を足さない。準備のコードは読みやすさを損なわない範囲で共有する | 〔作法〕Khorikov（テストのコードも負債）、Google SWE 12 章（振る舞いごとに 1 テスト）、DHH〔推論〕本番の「最小の変更」をテストに当てたもの |
| **U3 失敗を見る** | 6 | 走らせて、期待した理由で失敗することを確かめる | コマンドと出力を残す。最初から通るテストは何も確かめていない。予期しない理由で失敗したら、テストか理解を直す | 〔両氏〕t-wada 訳 Canon TDD、「不具合にテストを書いて立ち向かう」（手順 4）〔作法〕superpowers TDD |
| | 7 | 仕組み（guard）なら外して落ちることを確かめる | 規則を守る仕組みを書いたら、その仕組みを外すと落ちることを実行して記録する | 〔GQ〕dev-session §過去に 2 度以上受けた指摘 |
| **U4 残す** | 8 | テストを記録する | 失敗するテストを、実装と区別できる形で残す（コミットを分けるか、同じ変更の中で区別するかは案件の運用で決める）。実装のときにテストを書き換えない | 〔作法〕Cursor（テストを先にコミットし、実装でテストを変えない）〔両氏〕t-wada（TDD のステップごとのコミット、勉強会の記録）〔推論〕分け方を案件の運用に任せたこと |

#### 考え方

- **一度に一つだけ**〔両氏〕t-wada 訳 Canon TDD
- **テストは正しさの検証であって、解の定義ではない。** テストに合わせて値をハードコードしない〔作法〕Anthropic prompting best practices
- **アサーションを弱めない。** 置き換え（真偽だけを見る形に変える・待ち時間を延ばして不安定扱いにする・期待値の差し替え・テストを飛ばす・何でも通す比較）をしない。弱めるなら理由と代わりの確かめ方を書き、承認を得る〔両氏〕t-wada 訳 Canon TDD（アサーションを消して成功したふりをする過ち。承認を得るのは言い換え〔推論〕）〔GQ〕ADR-0006、dev-process/anti-patterns §3
- **消すこととごまかすことは違う。** 高価で信頼されていないテストを消す・置き換えるのは、理由と代わりの確かめ方を書けば正当。期待値を緩めて通すのはごまかし〔作法〕DORA（信頼できないスイートは剪定してよい）〔推論〕区別

#### 調査の範囲と深さ

- 既存のテストの書き方・補助（fixture・ヘルパ）を読み、合わせる。案件のテストの決まり（案件アダプタ）を読む〔GQ〕dev-session §新規実装時 ④〔推論〕

#### 背景・目的が不明なとき

- 期待値を仕様から導けない: 根拠の無いまま値を決めない。調査に戻り、仮定として記録するか、原則 X16 の作法で聞く〔両氏〕t-wada（実際の出力を期待値に貼らない）〔推論〕

#### 矛盾するとき

- 書いたテストが、修正前にも通ってしまう: テストの誤りか、原因の理解不足を疑い、調査に戻る〔両氏〕t-wada「不具合にテストを書いて立ち向かう」
- 落ちたテストが、実装が無いことを教えている: テストを消さず、実装を直す〔GQ〕dev-session §QM から返ってくるもの

#### 成果物と受け渡し

- 失敗するテスト 1 件と、その実行の記録。次は実装（4.5）〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 何も確かめていないテスト（例外が出ないことだけ）を量産する | 〔実証〕Banik ら |
| テストリストを全部先にテストにしてから、1 つずつ通そうとする | 〔両氏〕t-wada 訳 Canon TDD |
| 実際の出力を期待値に貼り、誤った挙動を正として固定する | 〔両氏〕t-wada 訳 Canon TDD |
| 失敗を見ないまま実装に進み、最初から通っていたテストが何も確かめていない | 〔作法〕superpowers TDD |
