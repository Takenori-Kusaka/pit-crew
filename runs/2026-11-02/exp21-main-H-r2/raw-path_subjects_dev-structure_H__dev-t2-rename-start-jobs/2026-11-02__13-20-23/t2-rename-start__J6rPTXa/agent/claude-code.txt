**読んだこと・動かしたことだけを事実として書く。** それ以外は「未確認」か「推論」と書き分ける。開いていないコードについて語らない〔作法〕Anthropic prompting best practices〔GQ〕po-session\n- **報告は実物ではない。** 他の人やサブエージェントの報告、label、CI の要約を、事実の代わりにしない。実物（diff・ログ・API Issue）を確かめてから変える〔作法〕Chesterton's fence〔二次〕\n- **正しい問いを立てる。** 一般論ではなく、この製品の前提（実行基盤・顧客・開発体制・段階・制約）から問いを立て、顧客に害が出る失敗の型から逆算する〔GQ〕dev-process/research-discipline §1-2\n- **仮説に中立に調べる。** 「裏付けよ」と探すのではなく事実を並べて評価する。結論を覆しうる観測を 1 つ挙げ、それを取りに行く。他社の事例は補強であって決定の根拠ではない〔GQ〕dev-process/research-discipline §2（同節の「反証 3 件」の数字には根拠が無いので、数に依存しない形にした〔推論〕）〔作法〕Heuer の診断性\n- **調査は手段。** 完了に要る問いに答えられたら止める。存在しない資料を探し続けない〔作法〕Anthropic 研究エージェントの停止規則\n- **推測した原因は、テストで確かめるまで「仮説」と書く。** 再現テストが修正前に失敗して初めて、推測した原因が正しいと言える〔両氏〕t-wada「不具合にテストを書いて立ち向かう」\n- **1 つ見つけたら、同じ型を探す。** テストをすり抜けた不具合は、見落としていた視点を示している。同じ種類の誤りが他にないかを確かめ、検索した結果（件数と場所）を残す〔両氏〕同上（要旨）〔GQ〕dev-process/feature-change-lateral-spread\n- **理解は外注できない。** サブエージェントやツールに調べさせても、結論を自分が説明できるところまで読む。確かめたこと・推測したこと・確かめていないことを分けて書く〔両氏〕t-wada「思考は外注できるが、理解は外注できない」（Agentic Software Engineering 2026-07、[二次]: スライドの取得ツール要約）、cognitive surrender の紹介（負債のメタファー 2026-09、[一次]）\n- **頑張りではなく仕組みで気づく。** 調査で見つけた「人が気をつければ防げる」穴は、注意書きを足すより、テスト・型・CI で検出できる形にすることを次の工程の候補に挙げる〔両氏〕t-wada「「人間が頑張る」ではなく…「仕組みで気づける」にしないとつらい」（AI 時代の TDD 2026-04）\n- 両氏の資料の偏り:
