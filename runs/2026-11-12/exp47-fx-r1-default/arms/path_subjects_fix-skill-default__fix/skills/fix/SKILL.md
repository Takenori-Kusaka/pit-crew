# fix — 指摘の解消

<!-- nav -->
いまの工程は推測で決めない。リポジトリ直下の `.fix-state.md`（無ければ作る）に書いた工程と、成果物の有無（指摘ごとの仕分け表があるか、落ちた検査を変更後に再実行した記録があるか、対応表を書いたか、など）で決める。工程に入るときと、会話が圧縮された後には、その工程の手順を必ず読み直し、`.fix-state.md` に「いまの工程・読んだ手順・次に出る条件」を書く。`.fix-state.md` は **Write / Edit ツールで書く**（shell のリダイレクトや heredoc では書かない）。`.fix-state.md` は commit しない: commit するファイルは `git add <ファイル名>` で名前を挙げて選び（`git add -A` / `git add .` は使わない）、`.gitignore` や `.git/` の下（`.git/info/exclude` など）は触らない。 工程の手順は、工程ごとのスキル（`fix-phase-0-intake` など、一覧の番号と対応）を Skill ツールで名前を指定して呼んで読む。 差し戻しを受けたら、どのファイルも編集する前に、必ず受け付けの工程のスキル（`fix-phase-0-intake`）を呼び、指摘を全部開いて 1 件ずつ「直す / 退ける / 回す」を決めてから、直すと決めたものだけを直す。回すと決めた指摘に関わるファイルは触らない。
<!-- /nav -->

## 受ける上限（1 つでも外れたら編集せず回す）


fix が 1 件の指摘を**自分で直す**のは、次の 4 条件を全部満たすとき。1 つでも外れたら FX-6 で回す（編集しない）〔オーナー〕11-06 ②。

| 条件 | 中身 | 根拠 |
|---|---|---|
| 具体性 | 指摘に位置（`path:line` または関数名）と、期待する挙動または直し方がある。無ければ QM に問い返す（FX-5 の「確かめられない」） | 〔実証〕Guo 2024: 失敗の 52% はドメイン知識の不足、15〜21% は位置の不明。指摘の約半数（105/200）は曖昧 |
| 局所性 | 変更が 1 モジュール内・1〜数ファイル。呼び出し元を変える必要が無い | 11 §2b 広さの軸、Bosu 2015（ファイル数で有用率が下がる） |
| 領域 | 認証・認可・個人データ・金額・公開した挙動・戻せない操作に触れない（触れる修正は Dev の T2） | 11 §2b T2 の列 |
| 種類 | 書式・文言・型・lint・テストの不備・再現手順つきの小さな不具合・生成物の同期・定型の依存更新。**設計の変更・新しい公開インターフェース・受入基準の解釈は不可** | 〔GQ〕修正 subagent と CI Fix の判断表（qm-session L130、qm-agent-templates L113-121） |

- **11 §2b との整合**: 不具合修正は T1 以上。fix は T1 のうち「調査の結果（位置・原因）を指摘が既に持っている」ものだけを受け、調査 I1〜I4 を「指摘の位置と呼び出し元を開く」に縮める。縮めた分は B-F13（位置を開いた）と B-F5（再実行）を必須にして補う〔推論〕
- **Dev へ戻す閾値**: 4 条件 / ADR-0022 の 2 線 / 同じ指摘の 2 周目 / 修正を試みて落ちた検査が 3 回続く。回数はアダプタ（compass RC-05 参考値: 連続失敗 3 回・無進捗 2 回）
- **モデルの既定**: Haiku 級。ローカル 7〜8B は無理筋（SWE-bench Verified 15% 前後、OmniCode Review-Response で 32B 17.7%）。24〜32B は実験の arm としてだけ。**どのモデルでも B は同じ基準で測り、害の差で「安いモデルで足る範囲」を後から決める**〔オーナー〕④

## 工程をまたぐ原則


| # | 原則 | 測り方 |
|---|---|---|
| Z1 | **全指摘に 1 行**: 直した（証拠）/ 退けた（根拠）/ 回した（宛先と理由）。黙って無視しない | B-F2 |
| Z2 | **症状でなく事由**。検査を黙らせる（skip・assertion 削除・閾値引き下げ・guard の warn 化・再試行の追加）ことで通さない。例外は owner と期限の記載があるときだけ（ADR-0006） | B-F6 / H2 |
| Z3 | **範囲は指摘が名指しした箇所 + 同じ型 + そのテスト**。「ついで」の整理をしない。同じ型を直したら件数と場所を宣言する | B-F4 |
| Z4 | **方針・設計・統制を変えて指摘を消さない**。設計書・ADR・lint / CI 設定・閾値・強制層に触れる修正は FX-6 で回す | B-F11 / H3 |
| Z5 | **落ちた検査は、変更後に、push する HEAD と同じ作業ツリーで再実行する**。CI に丸投げしない、別 HEAD の結果を報告しない | B-F5 |
| Z6 | **履歴を壊さない**。amend しない、`--force` しない（`--force-with-lease` のみ）。受け取った HEAD は最終 HEAD の祖先のまま | B-F7 |
| Z7 | **返す**: 対応表を PR の残る場所に書き、差し戻し状態を外してレビュー待ちを付ける。自分で承認・merge しない。承認を自分のサブエージェントにもさせない | B-F9 / B-F10 |
| Z8 | **2 周で止める**。同じ id の指摘が 2 回目に来たら 3 周目を直さず、食い違いを名指しして裁定へ回す | B-F12（多段。最初の評価では測らない） |
| Z9 | **指摘を鵜呑みにしない**: 位置を開き、実物と照らしてから直す。食い違えば退ける（Z1） | B-F13 / B-F3 |

## 出る条件（全体）

- すべての指摘について「直した（証拠つき）/ 退けた（根拠つき）/ 確かめている（何を待っているか）」のどれかが書かれている〔作法〕Google、superpowers
- 指摘 × 検証コマンド × 件数の表がある〔GQ〕agents/dev-session
- CI がすべて pass で、状態がレビュー待ちに戻っている〔GQ〕label-mailbox §3.1.1
- 修正の変更（履歴を壊さない形）、指摘ごとの対応と検証の表、撮り直した証跡。渡す先: レビュアの受信箱 〔推論〕工程の並びから
