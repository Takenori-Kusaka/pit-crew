### 2 設計

**目的**: 調査で分かった事実・品質の順位・トレードオフ点の候補をもとに、根本的に違う案を 2 つ以上比べて 1 つを選び、選んだ理由と捨てた案を残し、実装できる単位の計画に分ける。

#### 工程の内部の段階とやること（順に）

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **S1 要否** | 1 | 設計を書くかを決める | 解が一つに決まり、トレードオフが小さいなら設計書は書かず、計画（S5）だけを書く。代替案の無い「実装手順書」を設計書と呼ばない。新しいデータの形・新しいインターフェース・セキュリティ・課金・外部資源の追加・数日以上の作業なら、設計を書く。誰の合意が要るかは原則 X10（戻せない操作）と X15（誰が決めるか）で決まる | 〔作法〕Design Docs at Google〔GQ〕dev-session §設計ポリシー先行確認（設計を書く対象の列挙。合意の相手は §0 と食い違うため X15 を採る） |
| **S2 判断基準** | 2 | 判断基準に順位を付ける | 調査の品質の順位（重要度・難しさ）と、事業上の目的を、案を比べる基準として順位つきで並べる。どの案でも満たせる基準は比較から外す | 〔作法〕MADR の Decision Drivers、ATAM（設計者は逐語未照合）、Heuer の診断性 |
| | 3 | 単純さの関門を置く | 将来のための仕組みを作らない / フレームワークの機能を包まずに使う / 抽象を足さない。破るなら理由を書く | 〔作法〕Spec Kit（簡素性ゲート）、Anthropic「最も単純な案から始める」 |
| **S3 案を出す** | 4 | 案を比べる（自明に 1 つでないとき） | 妥当な案が自明に 1 つでないときだけ、根本的に違う案を 2 つ以上出す。数より「捨てた案と理由を 1 つ以上書けるか」で足りる。「最小の変更 / きれいな構造 / 中間」の 3 方向は新しい機能で構造の判断が要るときだけ。既存の解（調査の手順 13）を案に含める | 〔作法〕Ousterhout「Design it Twice」（[二次]）、feature-dev〔両氏〕miyagawa「Steal Good Ideas」 |
| | 5 | 誤りにくい形を先に考える | 実行時の検査を足す前に、型・列挙・値の型で不正な値を作れなくできないかを考える。生成した時点で不変条件が成り立つ形にし、状態を書き換えるより新しい値を返す形を選ぶ。外から入る値は境界で早く失敗させる（型で保証していても外からの値には実行時の検査を残す） | 〔両氏〕t-wada「誤りにくい設計」（目次 [一次]・各論 [二次]）、Claude Code との TDD 記録（fail fast） |
| | 6 | テストしやすさで点検する | 時刻・乱数・外部 I/O を外から差し込めるか。テストのために設計を変えたら、責務が単純になったかを確かめる（複雑になったらやりすぎ）。private を直接テストしたくなったら、クラスの抽出を考える | 〔両氏〕t-wada「テスト容易性設計」「private メソッドをテストすべきか」 |
| | 7 | 相手への義務を最小にする | インターフェースは、使う側・実装する側に求める義務を最小にし、便利な機能は上の層に置く。公開インターフェースに特定のライブラリの型を漏らさない。既存の仕組みと互換にし、互換を壊すなら明示して理由を書く | 〔両氏〕miyagawa（PSGI FAQ "as simple as possible"、"minimize the requirements on backends"、CGI との互換） |
| **S4 選ぶ** | 8 | 案を比べて選ぶ | 順位つきの基準で各案を比べ、推奨と理由を書く。トレードオフ点（1 つの選択で品質が逆向きに動く点）をどちらに倒したかと、その理由を書く。セキュリティと運用の健全性を既定では譲らない | 〔作法〕Design Docs at Google（代替案の節が最も重要）、ATAM、AWS Well-Architected |
| | 9 | 3 つ目で型を考える | 似た仕組みが 3 つ目になるときに、共通の型（Strategy・Factory・Registry 等）を当てるかを判断する。当てないなら理由を 1 行。2 つ目までは共通化しない（重複は合図であって命令ではない） | 〔GQ〕dev-session §3 つ目の類似〔両氏〕t-wada 訳 Canon TDD（早すぎる抽象化） |
| | 10 | 脅威への対処を決める | 調査で挙げた脅威（該当するとき）について、どう対処するかを決める | 〔作法〕Threat Modeling Manifesto の問い 3 |
| **S5 計画** | 11 | 実装の単位に分ける | 1 つの変更（PR）は 1 つの目的にする。その中の刻みはテストリストに任せる。分単位のタスクの一覧（触るファイルと確かめ方つき）は、別のエージェント・人に実装を渡すときだけ作る。1 つの変更（PR）は 1 つの目的にする。途中の段階を出すなら、各段階が単独で動く形にし、仮置き（stub・何もしない実装・TODO）を出さない | 〔作法〕superpowers writing-plans（文脈の無い別の実行者に渡す前提の雛形）、Google small CLs〔両氏〕t-wada（1 つの PR に 2 つの内容を混ぜて分け直した記録）〔GQ〕dev-session §段階的リリース禁止 |
| **S6 合意と記録** | 12 | 決定を残す | 決定記録（文脈・決定・状態・結果）を書くのは、①後から覆すときに背景の理解が要り、案件の残りの進み方に影響する重要な決定 ②既存の決定記録と矛盾する新しい判断（古い記録を置き換え済みにする）③機械で強制できない判断原則、のどれかのときだけ。それ以外は PR 本文の 1 段落に書く。覆すときは古い記録を消さず置き換え済みにする。根拠・目標・制約を決めたその場で書く | 〔作法〕Nygard ADR〔両氏〕t-wada「意図負債」（明示的な根拠・目標・制約が存在しない状態）〔GQ〕ADR-0001（設計書は SSOT）、docs/decisions/README §新規 ADR 追加 gate（3 条件。がんばりクエストは ADR の増殖で上限と削除主義を定めた） |
| | 13 | 合意を取る（要るとき） | 原則 X10・X15 で承認が要るものは、着手前に承認を取り、その記録（GitHub 上のコメント・label・決定記録）を残す。それ以外は Dev が決め、決定記録に理由を残す | 〔作法〕feature-dev「承認なしに始めない」〔GQ〕憲章 §0 ルール 4・§4.4〔事故〕I-25 |

#### 考え方

- **最も単純な案から始め、必要なときだけ複雑にする**〔作法〕Anthropic「Building effective agents」
- **TDD は設計しないことではない。** コードを書く前に、設計の方針とテストリストを示す〔両氏〕t-wada（Canon TDD 訳者コメント、「まだコードは書かないでください」と指示した記録）
- **要望に No と言う。** 中核でないもの、他と組み合わせて実現できるものは足さない。足さない理由を書く〔両氏〕miyagawa（t-wada の引用経由、[二次]）
- **複雑さを減らす主語は使う人。** 内部の作りの数ではなく、使う人から見た複雑さで比べる〔GQ〕dev-process/anti-patterns §11
- **誤りを検出するより、誤りにくくする**〔両氏〕t-wada

#### 調査の範囲と深さ

- 設計のために新たに調べるのは、案の比較に必要な範囲だけ（各案の前例・制約・費用）。調査の工程に戻るほどの新しい問いが出たら、調査に戻る〔推論〕
- 重さは軌道（§2b）で決まる。戻せない決定・公開インターフェース・データの形は T2〔作法〕Bezos、Hyrum's Law

#### 背景・目的が不明なとき

- 案を選ぶのに、顧客に見える方針・backlog の順序の判断が要る（原則 X15）: 案と推奨を付けて PO に聞く（作法は原則 X16）〔作法〕feature-dev（推奨を示し明示的な確認を取る）〔GQ〕憲章 §0 ルール 4
- 技術の進め方で迷う: Dev が決めて理由を残す。PO に技術の決定を預けない〔GQ〕憲章 §0 ルール 4。がんばりクエストの completion-principles §4「選択肢を 2〜3 個用意して PO に明示質問」は憲章 §0 と衝突している（`research-ganbari-role-process-inventory.md` §1.3 D3）。本設計は §0 の側を採る（原則 X15）

#### 矛盾するとき

- 選んだ案が既存の設計・決定記録と食い違う: 決定記録を置き換える（古いものを置き換え済みにして新しいものを書く）。黙って違う作りにしない〔作法〕Nygard ADR
- 設計の途中で、要件・データの形・規約の不備が分かった: 元の工程（調査・要件）に戻して先に直す。大きな巻き戻しは合意を取る〔GQ〕dev-process/completion-principles §7

#### 成果物と受け渡し

- 設計の成果物は軌道で決める（§2b）: 書かない（理由 1 行）/ PR 本文に数行（推奨と、捨てた案 1 つと理由）/ 設計書（1〜3 ページ: 背景と範囲・ゴールと非ゴール・設計・検討した代替案・セキュリティ・個人情報・観測性）。設計書は T2、または新しい公開インターフェース・新しい機能のときだけ〔作法〕Design Docs at Google、feature-dev README〔推論〕軌道との対応
- 計画（タスクの一覧）。次の工程（テスト設計）は自分 〔推論〕工程の並びから

#### 典型的な失敗

| 失敗 | 出典 |
|---|---|
| 案を 1 つしか出さず、比べないまま作る | 〔作法〕Design Docs at Google、Ousterhout（[二次]） |
| 2 つ目の重複で共通化して、早すぎる抽象を作る | 〔両氏〕t-wada 訳 Canon TDD |
| 仮置き（stub・TODO）のまま出し、残りが別のチケットに流れる | 〔GQ〕dev-session §段階的リリース禁止 |
| 合意がセッション上の発言だけで、出典が GitHub に無い | 〔事故〕I-25 |
| PO の規則を字面どおりに当てはめ、動いている検査を消す | 〔事故〕I-26 |
