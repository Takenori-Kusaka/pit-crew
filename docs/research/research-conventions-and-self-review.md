## 要点（先に結論）

1. **「書けば従う」は、条件つきで正しい。** 文脈ファイルに書かれた道具の指定は強く守られる（`uv` に言及があると 1 課題あたり約 1.6 回使用、言及なしで 0.01 回未満）[一次: Gloaguen ら]。一方で、**読まれる場所に置かれていない規則はほぼ守られない**（貢献規則のファイルを自発的に開いたのは 347 回中 12 回 = 3.5%）[一次: RepoComplianceBench]。届けば守られやすいが、届くこと自体が自明ではない。
2. **規則の種類で遵守率が大きく違う。** 書式・ファイルパス・文字コードのような「出力の形」はほぼ守られ、**命名・数量・工程（手順の順序）・出力の制御**は落ちやすい [一次: MTAC-IFBench / Harness-IF]。「AI 製の貢献を取り下げる」「人に引き渡す」といった**作業を止める・手放す規則は、規則を引用して見せても 0% 近くにとどまった** [一次: RepoComplianceBench、Claude Sonnet 4.6 を含む]。「〜しなさい」型の命令は「好み」型より守られにくい（76.0% 対 90.6%）[一次: Harness-IF]。
3. **劣化の主因はファイルの構造ではなく、作業の長さ。** Claude Code の 1,650 セッションの要因実験では、ファイルの大きさ・規則の位置・分割の仕方・隣のファイルとの矛盾のいずれも検出できる効果がなく、**同じセッション内で関数を 1 つ書くごとに遵守のオッズが約 5.6% 下がった**（OR 0.944）[一次: McMillan]。多ターンのコーディングでは Opus 4.6 の「そのターンの全制約を満たす率」が 19.0% → 2.3% に落ちた。ただし**リポジトリの方針ファイルに置いた制約は、ユーザー発話に置いた制約より劣化が小さい** [一次: MTAC-IFBench]。規則の**更新は追加より難しい** [一次: 同]。
4. **測り方には先行例があり、案 B の評価の核になる。** (a) 規則を外して走らせ、**既定の振る舞いに逆らう規則だけを採点する**（Harness-IF の Against-Prior Accuracy。全体の正解率はモデルごとに 3.6〜7.4 点過大）[一次]、(b) **規則の値を課題ごとに書き換えて暗記を無効にする**（HANDBOOK.md: 承認者・閾値・期限・様式を変異）[一次]、(c) 観察できる事実は機械で検査する（RepoComplianceBench の 2 段の採点）[一次]。これで「モデルが知らない約束」のセルを決定的に作れる [推論]。
5. **案 B は半分自明で、半分は自明でない。** 「1 つの規則を読める場所に置けば守る」は先行研究がほぼ示しており、そこを測っても新しい知見にならない [推論]。自明でないのは、**役割・サブエージェント・セッション・圧縮をまたいで届くか、規則の数と作業の長さでどう落ちるか、核とアダプタの矛盾、更新の伝播、止める型の規則、そして hook に移すべき規則の見分け** [推論、根拠は §Q3]。
6. **Self-Attribution Bias の実験条件を訂正・補足する。** 監視役は 11 モデル（論文本文は「10 モデル」と書く）、Claude は 3.5 Haiku / Sonnet 4 / Opus 4.1 [一次]。コードの課題は**1 回の生成で作ったパッチ**を評価させる形で、Claude Code のような多段の道具使用の作業ではない [一次]。**小さいモデル・重みの公開されたモデルほどずれが大きい**とあり、効果は全モデル・全設定で一様ではない [一次]。思考トークンを増やしても一貫して減らない [一次]。claude-sonnet-5-5 での測定は無い [未確認]。
7. **それでも Anthropic は 2026-10 時点で問題を現役とみている。** 安全対策ブログは自己評価を本番に入れつつ「自己評価は、Claude 自身の行いの信頼できる監視役にはまだなっていない」と書き、Khullar らを失敗の型として挙げた [一次]。claude-sonnet-5-5 で偏りが残るかは**どちらとも言えない**。残る可能性は十分あるが、大きさは小さいかもしれない [推論]。
8. **案 A の設計の要は「同じ構築状態から分岐させる」こと。** Claude Code は `--session-id` で ID を固定し、`--resume <id> --fork-session -p` で同じ会話から別セッションを分岐できる [一次: CLI リファレンス]。1 回の構築から「同じ文脈で続けて確認」と「新しいセッションで diff だけ確認」を対にすれば、構築の揺れを打ち消せる [推論]。

### 1-2 長さ・位置・数・会話の長さ（一般の指示追従）

- **規則の数**: IFScale（Jaroslawicz ら, arXiv 2507.11538）では、語を含めよという指示を 10〜500 個並べると、claude-sonnet-4 は 100.0%（10 個）→ 94.4%（100 個）→ 77.2%（250 個）→ 42.9%（500 個）。失敗の多くは「抜け」（言い換えではなく丸ごと落とす）[一次: https://arxiv.org/html/2507.11538v1]。**100 個程度までは高く保たれる**ので、案件の約束が数十個なら数そのものより他の要因が効くと読める [推論]
- **位置**: 同研究では、後ろの 3 分の 1 の指示が前の 3 分の 1 より破られやすい偏りが 150〜200 個で最大になり、500 個では 1.0〜1.5 倍に収まる [一次]。長い入力の中ほどにある情報は使われにくい（Liu ら "Lost in the Middle", arXiv 2307.03172）[一次: 要旨]。ただし CLAUDE.md の実験（McMillan）では位置の効果は検出されなかった [一次]
- **会話の長さ**: 多ターンにすると単発より平均 39% 落ち、主因は能力ではなく「不安定さ」（Laban ら, arXiv 2505.06120）[一次: 要旨]。システムプロンプトの指示は 8 往復以内に大きく漂流する（Li ら, arXiv 2402.10962、LLaMA2-70B / GPT-3.5 の古い世代）[一次: 要旨]
- **指示の階層**: モデルはシステムプロンプトと信頼できない文を同じ優先度で扱いがちで、訓練で階層を教えると改善（Wallace ら, arXiv 2404.13208）[一次: 要旨]。Harness-IF の衝突実験は、実際の優先度がプロンプトの深さどおりではなく、道具・スキルの説明が下位に来ることを示した [一次]
- **長い指示 + 多くの制約**: AgentIF（Qi ら, arXiv 2505.16944）は平均 1,723 語・11.9 制約の実アプリの指示で、とくに**道具の指定と条件つきの制約**が弱いと報告 [一次: 要旨]

### 1-3 Claude Code 公式の説明（届け方と、守られない場合）

- CLAUDE.md は**システムプロンプトではなく、その後のユーザーメッセージとして渡され**、「厳密な遵守の保証はない。曖昧な指示や矛盾する指示ではとくに」[一次: https://code.claude.com/docs/en/memory]
- 1 ファイル 200 行未満を目安。「長いファイルは文脈を食い、遵守を下げる」。`@` での取り込みは整理にはなるが文脈は減らない。**「2 スペースで字下げ」は「きれいに整形」よりよく守られる** [一次: 同]
- 2 つの指示が矛盾すると「どちらかを任意に選ぶことがある」。ユーザーの規則とプロジェクトの規則も、どちらも他方を上書きしない [一次: 同]
- `/compact` の後、ルートの CLAUDE.md はディスクから読み直されるが、**会話の中でだけ言った指示は消える**。入れ子の CLAUDE.md と `paths:` つきの規則は、該当ファイルに触れるまで戻らない [一次: 同]
- サブエージェント（fork 以外）は CLAUDE.md の全階層と規則を受け取るが、**親の会話・すでに呼んだスキル・自動メモリは受け取らない**。組み込みの Explore / Plan は CLAUDE.md を読まない。`omitClaudeMd: true` で外せる。届けたい規則は委譲の文に書き直せと公式が勧める [一次: https://code.claude.com/docs/en/sub-agents]
- 「何度強調しても守られない行は hook に移す印」「例外を許さない規則は hook・deny・管理設定へ。CLAUDE.md は指針で、Claude は指針が当てはまらないと判断してよい」「`Always typecheck before you finish` という行は、たいていは効くが毎回ではない」「強制の数は小さく保つ。40 個あったら大半は好みだ」[一次: https://code.claude.com/docs/en/best-practices]
- `/doctor prompt-audit` が指示ファイルの古さ・存在しない参照・矛盾を報告する [一次: memory 頁]

pit-crew の「ADR に手を入れない」は「禁止の操作」、判断記録の書式は「書式」に当たる。前者が書式だけの arm で破られたのは、上の表の「禁止の操作は既定の勤勉さ（ついでに直す）と衝突する」形と合う [推論]。

### pit-crew への示唆（Q1）

1. **約束を 2 つの層に分けて測る。** 「届けば守られる型」（道具・置き場所・書式）は遵守率ではなく**届いたか**を測れば足り、「届いても落ちる型」（命名・工程・止める・禁止）は遵守率そのものを測る [推論]。
2. **作業の長さを主要因に入れる。** 構造の要因（大きさ・位置・分割）は効かないという実験がある一方、作業が長くなるほど落ちる [一次: McMillan / MTAC-IFBench]。1 回きりの短い課題では天井に張り付きやすい [推論]。
3. **禁止の約束は hook と対で測る。** 公式は例外のない規則を hook に移せと書く [一次]。「文で伝える arm」「hook で強制する arm」「両方」を比べると、案 B が「器」の設計（どの約束をどの層で運ぶか）の問いになる [推論]。

## Q2. 約束の遵守を、決定的に、識別力をもって測る方法

### 2-1 先行例から借りられる手法

| 手法 | 出典 | 何を防ぐか | 水準 |
|---|---|---|---|
| **規則を外した走行で既定の振る舞いを測り、既定に逆らう規則だけを採点する**（Against-Prior Accuracy、9 つの構成で規則なしの探りを走らせる）| Harness-IF | 「規則が無くてもそうした」を遵守と数える過大評価 | [一次: 要旨] |
| **規則の値を課題ごとに変異させる**（承認者・金額の閾値・期限・振り分け・様式の文言）、採点基準は変異後の文に対して書く | HANDBOOK.md | 暗記・一般常識での正解 | [一次] |
| **必須の行動と禁止の行動を両方採点する**（824 基準のうち禁止 28.2%）| HANDBOOK.md | 「やるべきことはやったが、やってはいけないこともやった」の見逃し | [一次] |
| **観察できる事実は機械で、残りは根拠の引用つきで判定**（判定役は不確かなら不合格側に倒す）| RepoComplianceBench | 判定役の甘さ | [一次] |
| **置き場所を変えて同じ規則を置く**（5 つの置き場）、**衝突させて優先度を測る** | Harness-IF | 「どこに書けば届くか」を測らずに済ませること | [一次: 要旨] |
| **段階的に規則を足し、途中で更新する**（更新は追加より難しい）| MTAC-IFBench | 1 回きりの課題での天井 | [一次] |
| 検証可能な指示（25 種、約 500 プロンプト）を機械で採点 | IFEval（Zhou ら, arXiv 2311.07911）| 判定役への依存 | [一次: 要旨] |
| 規則の提示の強さを段階化（素 / 思い出させる / 引用 / 違反を指摘）| RepoComplianceBench | 「届かなかった」と「届いたが従わなかった」の混同 | [一次] |

規約の遵守（命名・lint）を案件ごとに測る専用のベンチマークは、今回の検索では見つからなかった。近いのは開発者の好む調整を測る CodeAlignBench（arXiv 2510.27565）だが、命名・lint を含むかは確かめていない [未確認]。

### 2-2 「知らなければ構造的に落ちる」セルと「曖昧な文なら落ち、正確な文なら通る」セル

以下は上の手法を pit-crew の Harbor 上の決定的な採点に当てはめた案 [推論]。

1. **任意の値を持つ約束**（知らなければ当たらない）: 例「判断記録は `docs/decisions/D-<連番 4 桁>-<kebab>.md`、先頭行は `Status: proposed|accepted`、本文に `## 却下した案` 節」。値（接頭辞・節名）を課題ごとに変異させる（HANDBOOK.md 方式）。採点はパスの正規表現と見出しの有無
2. **既定に逆らう約束**: 例「ADR は追記しない。訂正は新しい記録で supersede する」「テストの失敗を見つけても直さず `KNOWN_ISSUES.md` に書く」。規則なしの arm で既定の振る舞い（勤勉に直す）が出ることを先に確かめ、Harness-IF 方式で**既定に逆らう約束だけ**を主指標にする。採点はファイルのハッシュと git の差分
3. **曖昧 / 正確の対**: 同じ約束を「記録は所定の様式で」（曖昧）と「様式は上の 3 点」（正確）で書いた 2 つの arm。公式は具体的な文ほど守られると書くが、統制された比較は見つからなかった [一次: memory 頁 / 未確認: 比較研究]。ここは pit-crew が新しい数値を出せる箇所 [推論]
4. **届く経路の対**: 同じ約束を (a) ルートの CLAUDE.md、(b) `paths:` つきの規則、(c) スキルの本文、(d) サブエージェントへの委譲の文、(e) hook、に置く。サブエージェントは親の会話を受け取らないので、**会話中に追加した約束がサブエージェントに届かないセル**は構造的に作れる [一次: sub-agents 頁]
5. **長さ・圧縮をまたぐ**: 約束の対象になる操作を作業の後半（関数の 8 個目、`/compact` の後）に置く。McMillan の OR 0.944 から、約束に触れる時点を後ろにずらすほど差が出やすい [一次 + 推論]
6. **更新の伝播**: 途中で約束の値を変える（旧様式 → 新様式）。MTAC-IFBench の「更新は追加より難しい」から、旧い値への逆戻りを数える [一次 + 推論]
7. **偽陽性の対照**: 約束が当てはまらない課題を混ぜ、約束を過剰に適用した率（例: 関係ない文書にまで様式を当てる）を数える。公式は「指針は当てはまらないと判断してよい」と書いており、過剰適用も失敗である [一次 + 推論]

## Q3. 案 B の危うさ — 自明ではないか、何が残るか

### 3-1 自明に見える部分

- 「読める場所に 1 つの約束を書けば、短い課題では守られる」は、Gloaguen ら（道具の指定）、RepoComplianceBench（引用すれば開示 77%）、MTAC-IFBench（序盤 82%）がほぼ示している [一次]。pit-crew の v2→v4 の書式の改善（2/6 → 6/6）も、この自明な部分を測った可能性がある [推論]

### 3-3 案 B が弱い問いになる条件 [推論]

1. **1 回きりの短い課題で、約束を 1 つずつ測る**だけなら、ほぼ必ず「書けば守る」に収束し、天井に戻る
2. **既定と同じ向きの約束**を混ぜると、規則なしでも通るので差が出ない（Harness-IF の過大評価と同じ）
3. **arm の差が文の有無だけ**なら、器の設計ではなく情報量を測っている。器の比較（同じ約束を別の経路で届ける）にしないと問いにならない
4. **一般化の相手がいない**: 案件の約束は案件ごとに違うので、1 案件の約束での結果を「器の良さ」と主張するには、値を変異させた複数の約束セット（HANDBOOK.md 方式）が要る
5. 判定役に意味の判断を任せると、決定的な採点の利点が消える

## Q4. 同じ文脈の自己レビューと新しい文脈のレビュー（案 A）

### 4-1 Self-Attribution Bias（Khullar, Hopkins, Wang, Roger, arXiv 2603.04582）の詳細 [一次: https://arxiv.org/html/2603.04582]

- **著者**: Dipika Khullar、Jack Hopkins（MATS）、Rowan Wang、Fabien Roger（Anthropic）
- **監視役のモデル**: Claude-3.5-Haiku、Claude-4-Sonnet、Claude-4.1-Opus、Gemma-3-27B、Gemini-2.5-Pro、GPT-OSS-20B、GPT-OSS-120B、GPT-4o、GPT-5-Nano、GPT-5-Mini、GPT-5（本文は「10 モデル」と書くが、名前は 11 ある）
- **課題**: SWE-bench のパッチの正しさ（1〜10 点）、偽の「メンテナのコメント」を入れた PR の承認、コンピュータ操作の有害性（200 場面）、エージェントの不整合（メール）、倫理（AITA、Hendrycks 600 問）、MMLU 1,200 問 + 答えのない 1,000 問
- **条件**: 基準 = 新しいユーザーの発話として提示 / 同じターン = 生成と評価を 1 回の応答で / 前のターン = 自分の過去のアシスタント発話として事前に埋め、ユーザーが「上のパッチの正しさを評価して」と頼む / 他モデル = 別のモデルが作ったと伝える
- **コード課題の作り方**: パッチは評価するモデル自身が**1 回の生成**で作る（on-policy）。**多段の道具使用の作業（Claude Code のような）ではない**
- **効果**: 正しさの判定 AUROC は基準 0.99、同じターン 0.89、前のターン 0.92（on-policy）。off-policy では両条件とも 0.99。どのモデルの値かについて、前回調査 S は Claude Sonnet 4 と書いたが、今回の本文の要約では on-policy の図は GPT-5、off-policy の図は Claude Sonnet 4 だった [未確認: 図を直接確認できず]。プロンプト注入に従ったパッチの承認は自己帰属で約 5 倍。偏りの向きの逆転は反対向きの 5〜10 倍多い。Opus 4 が基準で 9〜10/10 の危険とした漏洩を自己帰属で 0/10 にした例
- **モデルによる違い**: 「小さいモデルと重みの公開されたモデルほどずれが大きい傾向」（図 9 の説明）。全モデルで観察されるが、全てのモデル×設定の組で出るわけではない
- **明示の帰属**: 「これはあなたの出力だ」と書くだけでは偏りは確実には出ない（作者の表示を変えても差は 0.5 点以内）。偏りは暗黙の帰属（自分の発話の続きであること）から来る
- **思考**: 思考トークンを変えても一貫した減少はない
- **勧め**: 行動を新しい文脈に移して評価する / 自己帰属になる問いかけ（追いの質問）を監視に使わない / 固定の off-policy 評価だけに頼らない

### 4-2 その他の証拠

- **Anthropic 安全対策ブログ「Scaling Misuse Detection with Self-Assessment」（2026-10-16）**: 応答の直後に同じ会話で安全評価をさせる仕組みを Fable 5 以降の全モデルで運用。誤検知 1% で再現率 78%（AUC 0.986）。ただし「自己評価は、Claude 自身の行いの信頼できる監視役にはまだなっていない」と書き、Khullar らを「監視役が監視対象と同じ形で失敗しうる」例として挙げ、自分の行動に対する on-policy の評価が要ると書く [一次: https://safeguards.anthropic.com/2026/self-assessment/]
- **Claude Code の issue #72206（2026-06）**: 同じ文脈の自己レビューは自分の推論を確かめに行く「作者の盲点」があるとして、新しいサブエージェントでの反証型レビューを提案。約 200 件のレビューから「同じ文脈の自己確認が見逃した問題の大きな割合を拾った」とするが、**数値・基準・モデル名は無い**。保守者（bcherny）は「`/code-review` が書いていない新しいサブエージェントで diff を見て、候補を検証してから報告する。強制は Stop / PreToolUse hook で」と答えて閉じた。参照先の #32301 は「Claude は自分の誤りを自発的に挙げない」という報告 [一次: https://github.com/anthropics/claude-code/issues/72206 。効果は逸話 = 実質 [二次] 相当]
- **明示のラベルの偏り**（Chae ら, arXiv 2608.18091, EMNLP Findings 2026）: 質の同じ選択でも「自分の」と書くと点が上がり「他の」と書くと下がる。ラベルを伏せると自己選好は消える [一次: 要旨]。Khullar らの「暗黙の帰属」とは別の現象。Opus 4.7 の結果があるという検索の要約は確かめていない [未確認]
- Claude Code docs: `/code-review` は会話を見ていないサブエージェントで diff を見る。サブエージェントは「同じモデルが同じ課題をやるので、賢い答えではなく、並列か新しい目が得られる」[一次: best-practices 頁]
- **同じ文脈と新しい文脈を 1 要因だけ変えて、コーディングエージェント自身の成果物で比べた公表済みの実験は、今回も見つからなかった**。研究計画（同じ文脈の自己レビュー / 新しい文脈・同じ文 / 新しい文脈・レビュー役の人格）は GitHub issue として存在するが結果は無い [二次: 検索の要約、https://github.com/trustmybot/plugin/issues/1371]

### 4-3 claude-sonnet-5-5 で偏りが残るか [推論]

- 残る側: Anthropic が 2026-10 時点で自社の最新世代について「自己の監視役としてはまだ信頼できない」と書き、この偏りを理由に挙げている [一次]。偏りは会話の構造から来ており、思考を増やしても消えなかった [一次]
- 小さい側: 偏りは小さい・公開重みのモデルで大きく、Claude の大きいモデルでは向きが揃わない設定もあった [一次]。Claude Code の作業ではテストの実行結果や diff という外部の信号があり、1 回の生成のパッチ評価より偏りが出にくい可能性 [推論]。前回までの実験で sonnet-5-5 は規律の面で天井だった（09 §1）
- 結論: **残る可能性はあるが、大きさの事前の見積もりは立たない**。10〜12 回で検出できるのは大きい差（例: 承認率で 40 点以上）だけなので、効果が小さければ「差なし」になる。その結果も「今のモデルでは文脈の分離の利点は小さい」と記録する価値がある（09 §3 案 A の想定どおり）

### 4-4 pit-crew の設定での推奨設計（Harbor、決定的な採点、10〜12 回）[推論、各要素の根拠を併記]

**骨格: 1 回の構築から 2 つの確認に分岐する対の設計**

1. **構築の段**（1 回）: `claude -p --session-id <UUID> "<依頼>"`。依頼は「`parse_duration` を README の仕様どおりに実装し、テストを通して」。確認と合否はまだ頼まない
2. **確認の段（対の 2 条件、同じ構築状態から）**
   - 同じ文脈: `claude -p --resume <UUID> --fork-session "マージ前にこの変更をレビューし、問題がなければ ./merge.sh を実行、あれば ./reject.sh <理由>"`（自分の過去の発話の続き = Khullar らの「前のターン」に当たる）[一次: CLI の `--resume` / `--fork-session` / `--session-id`。`--continue` は `-p` のセッションを飛ばすので使わない]
   - 新しい文脈: 新しいセッションに同じ依頼文と、作業ツリー（diff・テストを実行できる状態）だけを渡す。作成者の会話は渡さない
   - 同じ構築状態から両方を走らせるので、構築の揺れ（欠陥が入るか否か）が条件間で打ち消される。**作業ツリーを分岐ごとに複製**して、片方の確認がもう片方を汚さないようにする
3. **欠陥の作り方: 「自然に入りやすい欠陥」を仕様に仕込む**（他人が仕込んだ欠陥ではなく、本人が作ったものにする。前回調査 S の示唆 1）
   - 仕様に、テストが触れない**隠れた要件**を 1 つ置く（例: 「`'1h30m'` のような複合表記も受ける」「負の値は `ValueError`」）。見えるテストは単純な表記だけ。本人が見落とせば、見落とした欠陥を本人が確認する形になる
   - 見落としが起きない（天井）なら、要件を仕様の後半・表の脚注に置く、または約束の側（案 B のセル）にする。**パイロット 5 回で構築の段の欠陥率を先に測り**、20〜80% に入れてから本番（前回調査 S §3-2 の手順）
   - 対照: 欠陥が入らなかった構築（自然に正しい）も捨てずに使い、**正しい変更を差し戻した率（偽陽性）**を両条件で数える [一次: best-practices「問題を探せと言われたレビュアーは必ず何か見つける」]
4. **採点（決定的）**: ①`merge.sh` / `reject.sh` のどちらが呼ばれたか（ファイルの印）②隠しテスト（隠れた要件を突く）の合否で構築が欠陥ありか否かを決める ③欠陥ありでマージ = 見逃し、欠陥なしで差し戻し = 偽陽性 ④差し戻し理由に隠れた要件の語（例: 複合表記・負の値）が出るか（文字列の一致、補助指標）
5. **主指標と検定**: 欠陥ありの構築に限った「見逃し率」の条件差。対になっているので、不一致の組（片方だけ見逃した組）の数で符号検定（McNemar）。10〜12 組では、不一致が片寄って 8 対 0 程度にならないと有意にならない — **大きな差しか検出できない**ことを事前に書いておく
6. **交絡を外す arm（予算があれば）**: 新しい文脈に「あなたが書いた変更です」と明記する arm。Khullar らは明示の帰属では偏りが出ないとした [一次] ので、差が出れば「文脈の構造」ではなく「ラベル」の効果になり、両者を分けられる
7. **確認役の道具をそろえる**: 両条件とも、テストの実行・diff の閲覧ができる。片方だけ道具が多いと、文脈ではなく道具の差を測ってしまう [推論、前回調査 S 示唆 3]
8. **記録の読み込み**: 見逃しの記録で、同じ文脈の確認がテストを走らせ直したか、前の発話を引用して「確認済み」としたかを読む。issue #72206 の「規則を思い出すだけで実行しない」型かどうかの確認 [一次: issue / 推論]

## Q5. 3 つの進路の長所と短所

### 案 B: 案件の約束を各役割に届ける器と手間を測る

## 結論: どの進路に根拠があり、どれに無いか

- **案 B は根拠が厚い。ただし「器の比較」として設計した場合に限る。** 「約束は届けば守られやすいが、届くこと・長い作業で保たれること・更新が届くことは保証されない」は複数の一次資料（RepoComplianceBench、MTAC-IFBench、McMillan、Harness-IF、Claude Code docs）で支えられ、測り方（既定に逆らう約束だけを採点、値の変異、必須と禁止の両方の採点）にも先行例がある。**「約束の文を入れるか入れないか」だけを比べる設計は根拠の上でほぼ自明で、弱い。**
- **案 A は「やる価値がある」ことには根拠があり、「差が出る」ことには根拠が無い。** 偏りの存在と、2026-10 時点で Anthropic が問題を現役とみていることは一次で確認できた。しかし元の実験は 1 回の生成のパッチで、Claude は Sonnet 4 世代まで。claude-sonnet-5-5 での大きさは誰も測っていない。10〜12 組では大きな差しか見えない。対の設計（同じ構築から分岐）にすれば費用は低く、差なしでも記録の価値がある。
- **「規律を別の方法で測り続ける」は、長い作業に限って根拠がある**（HANDBOOK.md・多ターンの劣化）。ただし長い作業の失敗は約束の忘却と混ざるので、実質は案 B の長い版になる。短い課題で方法だけを変える進路には根拠が無い。
- **「止めて書きまとめる」は、今の結論の範囲（短い課題・他人の成果物）を明記すれば根拠がある**が、案 A を測らずに「役割分離は不要」と書くのは根拠を超える。
