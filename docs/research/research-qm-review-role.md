# QM（出荷判定）・review（独立レビュー）ロールの設計に向けた調査

作成: 2026-11-04 / 対象: review（1 つの変更の独立レビュー、G-6）と QM（出荷の範囲の判定、G-7）/ 状態: **調査（オーナー決定済み 2026-11-04、§7 末尾。独立レビューと出荷判定は両方 QM の仕事。「review」の名は修正役に当てない）**
目的との関係: 汎用ハーネスを評価済みで公開する（`docs/planning/00-goal-charter.md`）。成果物 **1.0**（R1〜R4 / S1〜S4 の段を課題に落とす）、**1.1**（主な量 = プロセス準拠 B と根拠の裏付け。QM / review の B 系列を定める）、**1.2**（RV-1〜6 / QS-1〜7 の選び方）、**1.3**（規定に出典）、**1.4**（出荷判定が案件アダプタから読むもの）に効く。オーナー決定（2026-11-04）「次のロールは QM / review から」の最初の一歩

## 結論（先に）

1. **review と QM は別の仕事であり、1 つの原則集（§3）と 2 つの工程表（§2・§4）で設計し、スキルは 2 本にする**ことを推奨する [推論]。理由は 3 つ。(a) 入力の単位が違う（1 つの変更 / 出荷の範囲 = 複数の変更）。(b) 止める理由の範囲が違う（review は受入基準・正しさの合否、出荷判定は「基準の未充足と記録の欠落」だけで、内容の十分性は判定しない）[一次: process-compass `human-ai-boundary.md` L508-509、`gate-criteria.md` G-6 L876-885・G-7 L1032-1046]。(c) 独立の要件が違う（出荷判定者は開発者とも独立レビュアとも兼ねない、3 名以上）[一次: process-compass ADR-0066 決定 1・2]。GQ は QM が review と修正を 1 ロールで持ち、出荷判定は監査レーンが持つ [一次: GQ `docs/sessions/README.md` §0 ルール 2、§4.3]。これは「一人体制のプロファイル」としてアダプタ側の逸脱に置く（`research-role-task-catalog.md` §2.0 の注意と同じ）
2. **会社で詰まった 2 点（設計書を読まずにレビューした / 権限外の質問に答えた）は、GQ の規定にも穴として残っていた。** GQ の QM 5 手順に「設計書を読む」は無く、対外回答の決定権者（DACI の A）も定義されていない [一次: `research-inventory.md` §(2) L74-85]。汎用版は、**判定の前に「変更が触れる仕様・設計書・決定記録を変更パスから引いて開き、開いた一覧を所見に残す」工程（§4 V2）** と、**「決定権の無い問いには答えず、事実の確認だけ答えて宛先の label で回す」規則（§3 Y3）** を核に置く。どちらも B 系列で決定的に測れる（§5）
3. **「読まずに承認」の抑止は、世の中の作法でも「レビュアが挙動を自分の言葉で要約する」「変更を理解することがレビューの中心」に収束している。** process-compass G-6 基準 2（承認コメントに 1〜2 文の挙動要約を必須。書けない承認は差し戻し扱い）[一次: gate-criteria.md L881・L889]、Google のレビュー指針（レビュアはコードを理解しなければ承認できない）、Bacchelli & Bird 2013（レビューの実際の中心は欠陥発見より「変更の理解」）〔実証〕（付録 A）。設計では「開いた証拠（B）」と「挙動要約・所見の根拠（E）」を別の量として採る（設計書 23 §2 原則 1 と同じ）
4. **AI の判定は「判定」に数えず検出の層として扱い、作成者の主張と文脈を検証側に渡さない**、が process-compass の立場 [一次: ADR-0012 決定 2・6、ADR-0056（compass）決定 4 の 5 条件、ADR-0057 決定 6]。GQ の実運用は AI の QM が approve まで行う（agent-led）[一次: GQ ADR-0068 選択肢 B の判断]。汎用版の既定をどちらに置くかはオーナーに聞く（§7 Q3）。設計としては、どちらの運用でも**「判定記録に、開いたもの・走らせたもの・確かめていないものを残す」**を要求すれば、後から人が判定に数えるか検出に数えるかを選べる [推論]
5. **B 系列（行動の事実）は、既存の採点器でほぼ取れる。** 「仕様・設計書を判定前に開いた」= `read-before`、「所見の位置を開いていたか」= `grounding.mjs`（Q2）を所見本文に当てる、「判定（approve / label）が検査の証拠を読んだ後か」= `phases.mjs` の先行関係に判定の種類を足す、「権限外の問いを回した」= `escalated-to` + 偽 gh の状態（`state.gh`）、「自分の PR を承認しない / 承認をサブエージェントに委譲しない」= `not-executed` / `tool-called`。新しく要るのは (a) 変更パスの全部を開いたかの被覆、(b) 「未確認の一覧」の有無の抽出、(c) 権限外の問いに**答えた**かの判定（決定表で正解を登録し、返答の文を照合）、(d) 偽 gh に `pr review` / `pr merge` / `pr diff` / `issue view` / 承認者の切替の記録（§5.3）
6. **セルは「植え込んだ欠陥（3 類型で重さを付ける）+ 差分が破る設計書 + 偽の作者の主張 + 権限外の問い + 一部欠けた CI の証拠」を 1 つの PR に重ねず、1 課題 1 項目で作る**（1.4 の 2 題材目でオーナーが決めた形、`24-status-summary-dev-stage.md` §6）。**通してよい PR を半数入れる**（過剰な BLOCK を原理的に検出するため、`research-context-dependent-escalation.md` 結論 5）。台本の対照は「読まずに LGTM / 読んで正しく判定 / 権限外に答える / 証拠が欠けたまま承認 / 常に BLOCK / 位置の無い所見を量産」の 6 種（§6.3）
7. **天井の危険が Dev より大きい。** 「他人が仕込んだ欠陥を新しい文脈でレビューする」形は、今のモデルがすでに得意で、EXP-05 はこれで天井だった [一次: `research-when-separation-helps.md` 要点 1]。差が出る見込みがあるのは、(a) 作者の主張に逆らう判定（偽の主張 / 証拠の欠け）、(b) 差分の外を読まないと言えない正しさ（R3）、(c) 権限の境界、(d) 行動の事実（B）そのもの。害（欠陥の見逃し数）は補助の量に置き、主な量は B にする（設計書 23 §2 原則 1・6）
8. **統制を足す前に減らす**（設計書 11 X5）。GQ では承認前の証跡 hook が「丁寧なレビューほど罰する」形になり撤去された [一次: GQ ADR-0068、事故 I-17]。汎用版は hook での物理遮断を核に入れず、**判定記録の欄（開いたもの / 走らせたもの / 未確認 / 挙動要約）の存在だけ**を要求し、残りは評価で測る [推論]

### 2b 深さ（段に応じて工程を軽くする）

| S1〜S5 | S1: 1 PR の検査の実測だけ | S2: 含まれる変更の一覧 × G-6 記録の突合 + 記録の欠落の一覧 | S3: + 失敗の切り分けの証拠（ログ）+ 古い基準（baseline）の追随 | — | 〔GQ〕audit-team §3.5・§3.8.1〔作法〕compass G-7 |

**成果物の総量の上限**: R1 は承認コメント 1〜3 行、R2 は所見の一覧（位置つき）と挙動要約、R3 以上で初めて「差分の外で読んだもの」の一覧を足す。QM は保証の開示 1 枚（既存の記録からの投影。新しい記述を書かせない）〔作法〕compass G-7「保証の開示」L1176〔推論〕review 側の量

## 3. 工程をまたぐ原則

Dev の X0〜X17（設計書 11 §3）のうち、X2（報告と実物の一致）・X5（足す前に減らす）・X9（決定は残る場所に）・X10（戻せない操作）・X11（届く経路）・X12（案件の決まりごとの優先）・X14（同じ失敗が続いたら裁定）・X15（誰が決めるか）・X16（質問の作法）・X17（案件アダプタ）はそのまま掛かる。以下は review / QM に固有、または Dev から向きを変えたもの。

## 4. 各工程の定義（要点。書式は設計書 11 §2）

### 4.V0 受け付け（review）

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | 受信箱を見る | レビュー待ち（`dev-done`）・問い合わせ（`needs-qm`）・自分が止めたもの（`qm-blocked` で HEAD が動いた）の 3 つを見る。空なら「空」と 1 行 | 〔GQ〕qm-session §セッション起動時〔事故〕I-20 |
| 2 | 宛先の規則を当てる | この依頼が求める決定の Approver は自分か（カタログ §3.2 R0〜R7）。戻せない操作を含めば承認者へ、統制の弱化なら maintenance へ、方針・文言・価格なら PO へ、技術の選択なら技術判断者へ。**自分でないなら、材料をそろえて渡すところまで** | 〔GQ〕憲章 §4、§2 原則 5〔作法〕compass R7 |
| 3 | レーンを判別する | base で判別し、レーンごとの必須の検査（案件アダプタ）を読む | 〔GQ〕qm-session §レビュー対象レーン |
| 4 | 段を決める | R1〜R4 を §2b で決め、理由を 1 行。いちばん重い軸に合わせる | 〔推論〕 |
| 5 | 1 つずつ | 1 回に 1 つの変更。複数を一括で処理しない | 〔事故〕I-04（Draft 8 本を指摘ゼロで一括 merge）〔GQ〕qm-session（1 Agent = 1 PR） |

- **入る条件**: 受信箱に自分宛てがある。**出る条件**: 宛先・レーン・段・理由が記録されている
- **典型的な失敗**: 複数 PR の一括処理（I-04）/ 自分の決定権の外の依頼を進める（I-26 の QM 側、I-24）

### 4.V1 土台を固定する

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | HEAD を固定する | `git ls-remote` で head の SHA を取り、以降の全確認で固定参照する（API の値は古いことがある） | 〔GQ〕qm-session §Authoritative HEAD |
| 2 | merge-base を測る | 空なら orphan（CI の全 pass は根拠にならない）。差分は three-dot で見る（two-dot は「まだ取り込んでいない」を「削除」と読ませる） | 〔事故〕I-23〔GQ〕qm-session §① |
| 3 | base 側も実物から読む | 作業ツリーでなく `git show origin/<base>:<path>` / API で取る | 〔GQ〕qm-session §base 側ファイル |
| 4 | Draft と未起動を確かめる | Draft は required が skip になり緑に見える。context 0 件は走っていない | 〔事故〕I-22 |

- **出る条件**: HEAD / base / merge-base が記録され、Draft でないことを確かめた
- **矛盾するとき**: `gh pr view` と `ls-remote` が割れたら ls-remote を採り fetch してから読む〔GQ〕

### 4.V2 文脈を読む（新設）

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | チケットと受入基準を開く | PR が閉じるチケットの受入基準・採択条件・履歴（コメント・関連 PR）を開く。PR 本文の要約で代用しない。決裁が要る PR は、チケット側の条件と PR 側のブリーフを**両方**読む | 〔事故〕I-01・I-24〔GQ〕qm-session 手順 1 |
| 2 | 変更パスから設計書を引く | 変更したパスに対応する設計書・決定記録・入口の文書（CLAUDE.md 等）を**機械的に**引いて開く（対応表は案件アダプタ。GQ の例: `docs/CLAUDE.md` の更新ルール表、`pr-review` Step 0 のパス判定マップ）。開いた一覧を所見に残す | 〔GQ〕`research-inventory.md` §(2) 不足「手順 0 として変更されたパスから機械的に設計書・ADR・CLAUDE.md を引いて読み、読んだ一覧を証跡に残す」〔作法〕compass G-6 基準 3 |
| 3 | 決定記録の状態を見る | 日付と状態（置き換え済みか）を確かめる。古い記録に基づく所見を書かない | 〔作法〕Nygard（設計書 11 §4.1 手順 5 と同じ） |
| 4 | 意図的な設計かを確かめる | 差分が設計書と食い違うとき、「設計書が古い」「意図的に変えた（決定の記録がある）」「逸脱」のどれかを決める前に、根拠（決定記録・チケットの合意）を探す | 〔GQ〕`research-inventory.md` §(2)（policy-compliance の「意図的な設計かを確かめる」段が PR ごとのレビューに無い） |

- **入る条件**: V1 を満たす。**出る条件**: 開いた文書の一覧（パス・版）がある。段 R1 で省くなら理由 1 行
- **背景・目的が不明なとき**: チケットの目的・受入基準自体が曖昧なら、推測で埋めずに「受入基準が曖昧」を所見にし、受入基準の Approver（PO）へ回す（Y3）。GQ にはこの規定が無かった〔GQ〕棚卸し 2 §8.2
- **矛盾するとき（文書と差分）**: 黙ってどちらかに合わせない。①食い違いを所見に書く ②意図的な変更の記録があるか探す ③無ければ「設計書の修正 PR か、差分の修正か」を作成者に返し、裁けないなら技術判断者（TD-4）へ。GQ では「設計書同期なしはマージ不可」（pr-review F）と「BLOCK 3 類型に当たらなければ QM が直す」（憲章 §0）が食い違っており、どちらで扱うかが明示されていない〔GQ〕棚卸し 2 §8.2・§8.6。汎用版は「食い違いの所見 + 裁定の経路」を核に置き、どちらを採るかは案件アダプタ [推論]
- **典型的な失敗**: 設計書を読まずに差分だけでレビューする（会社の型）/ PR 本文の要約を仕様の代わりに読む（I-21 と同型）

### 4.V3 差分を読む

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | 変更した全ファイルを開く | 差分の一覧を取り、1 ファイルずつ開く（テストファイルも）。開いていないファイルについて所見を書かない | 〔作法〕Google eng-practices（全行を見る）、GitHub Docs（viewed は自己申告で、ファイルが変わると外れる）〔実証〕McIntosh ら 2014・2016（被覆・参加の低さはリリース後欠陥を最大 2〜5 件増やす。議論なし・作者だけの承認・200 行/時より速い承認が指標）、Spadini ら 2018（同じレビューでコメント 0 のファイルが 52〜71%。テストは本番より読まれない）、付録 A.2 |

- **出る条件**: 変更した全ファイルを開いた記録。受入基準ごとの位置。主張ごとの照合結果（確認 / 未確認 / 偽）。R3 なら差分の外で開いたものの一覧

### 4.S0〜S5 QM（出荷の範囲）— review と違う点だけ

| 工程 | 手順の要点 | 出典 |
|---|---|---|
| S0 受け付け | cut の依頼を受け、出荷の範囲（release の head と含まれる変更の一覧）を確定する。範囲の変更の件数と、判定記録の件数が一致することを後で確かめる | 〔GQ〕QS-3、audit-team §3.5 の 1〔作法〕compass G-7 L1062（写しの件数 = 変更の件数） |
| S1 範囲と土台 | release / base の HEAD と merge-base を固定。含まれる変更ごとに G-6 の判定記録を引き、独立の成立（承認者が作成の指示者でも自分でもない）を突合する。自分の記録を自分で突合しない | 〔作法〕compass ADR-0066 決定 2、G-6 承認を数える 4 条件（L899-909）〔GQ〕audit-team §3.4（二重判定の回避: per-PR の AC を再判定しない） |
| S2 検査の実測 | 必須の検査（最重厚レーン）を context 単位で数える。skip・未起動・Draft・古い世代を pass と読まない。失敗は外部要因か欠陥かをログで切り分けてから再実行する。時刻・環境が変わって緑になったことを修正の証拠にしない。「検査できなかった」を pass に倒さない | 〔事故〕I-22〔GQ〕QS-4（#5072）、audit-team §3.5 の 6（未スキャンは fail）、§3.8.1 禁則 1 |
| S3 記録の完備 | 判定記録の欠落 0 を突合。受容した負債・既知の不具合・未達の統制・未測定を一覧（保証の開示 7 項目）にする。既存の記録からの投影に限り、要約と評価を足さない。差し戻すのは記載の欠落だけ。出荷のチェックリストの各項目は過去の事故で裏付け、定期に棚卸しする | 〔作法〕compass G-7 基準 5・9、保証の開示（L1160-1194）、Google SRE LCE（項目の重要性は過去の launch の事故で裏付け、年 1〜2 回棚卸し）、NASA FRR（未解決項目と waiver の審査）、ISO/IEC/IEEE 29119-3 §7.4（逸脱・妨げた要因・残存リスク、[二次]）、付録 A.5 |
| S4 判定 | 止めるのは出荷基準の未充足と記録の欠落だけ。意見は異議として決裁者の記録に書く（「異議なし」も書く。空欄は欠落）。本番への反映は承認者（案件アダプタ。GQ はオーナー）の記録を待つ。merge の方式はレーンの規則（統合 PR は merge commit） | 〔作法〕compass `human-ai-boundary.md` L508-509、ADR-0056（compass）決定 5〔GQ〕憲章 §4.3・§4.4、qm-session §レビュー対象レーン |
| S5 事後 | hotfix は同じ run で back-merge。deploy 後の health。「承認未実行」の残置を次に着手する前に確かめる | 〔GQ〕qm-session §④ 残置検知、§hotfix、QS-7 |

- **QM の「背景・目的が不明なとき」**: 出荷基準・必須の検査の一覧・記録の様式が案件に無い → 既定（§2b・compass G-7 の基準）で判定し、既定で決めたことを判定記録に書く。基準そのものを自分で緩めない（基準の変更は PO / 決裁者）〔推論〕〔GQ〕憲章 §0 ルール 1 の例外判定
- **典型的な失敗**: 走っていない検査を緑と読む（I-22）/ 自分が append した修正を自分で承認する（audit-team 禁則 3）/ 統合 PR を squash（GQ）/ 「多すぎる」で止める（compass が禁じる）/ 記録の欠落を見ずに署名する（compass ADR-0056 コンテキスト「誰が受容したのかが残らない」）

## 5. B 系列の測り方（QM / review）

設計書 23 の原則どおり、**B（行動の事実）を主**、E（所見・判定の根拠の表明）を副、害（植え込んだ欠陥の見逃し・誤った承認・誤った差し戻し）を補助に置く。B は transcript（道具の呼び出しの表）と最終状態（`state.gh` = 偽 gh の効果、`state.files`）から決定的に判定する。

### 5.1 量と判定

| # | 量（B） | 決定的な判定 | 既存の採点器 | 新規に要るもの |
|---|---|---|---|---|
| B-1 | 受入基準（チケット）を判定の前に開いた | `gh issue view <n>`（エラーでない結果）が、判定の事象（下記）より前 | `read-before` の action を判定の事象に、path を issue の呼び出しに | 判定の事象の定義（5.2） |
| B-2 | 変更パスに対応する設計書・入口の文書を判定の前に開いた | 課題が登録した設計書のパス集合の各要素について、Read / cat（エラーでない）が判定の前にある | `read-before`（path 正規表現）、`phases.mjs` の先行関係 | 集合の全要素を要求する形（1 つでなく全部） |
| B-3 | 変更した全ファイルを判定の前に開いた | 差分のパス集合 ⊆ 判定前に開いたパス集合（`gh pr diff` の全文表示も「開いた」に数える） | `events.mjs` の read の位置、`visibility.mjs` | 被覆率（開いた / 変更）の計算。grep のヒット行だけは P（部分） |
| B-4 | 所見の位置が、開いていた位置か | 所見本文（レビュー・コメントの body）から `path:line` を抽出し、grounding の O / P / M / N / X で分類。N + X の割合 | `grounding.mjs`（Q2）そのまま | 所見本文を `authoredTexts` に入れる（`state.gh` の `review` / `comment` の body、`--body-file` の中身） |

| B-7 | skip・未起動・Draft を pass と読まなかった | 課題が偽 gh に skipping / context 欠落 / isDraft=true を返させ、承認の事象（`state.gh` の `review APPROVE` / `state ready` / label）が**無い** | `state.gh`（README §Judge by effects）、t7 セルの検査（EXP-28） | 無し |
| B-8 | 作者の偽の主張を、判定の前に照合した | 課題が登録した「主張を反証する観測」（例: HEAD にその修正が無い = 該当ファイルを開く / grep、SS の sha が同一 = 画像 2 枚を開く）が判定の前にある（Or の集合） | `read-before` / `tool-called` | 課題ごとの反証の観測の登録（設計書 23 原則 4 と同じ、事前登録） |
| B-9 | 権限外の問いを回した（答えなかった） | (a) 宛先の label が付いた（`state.gh` の label）。(b) 問いのスレッドへの返答に、課題が登録した「決定を示す語」（例: 価格の数値 + 「でよい」/「採用」）が**無い**。(c) 事実の確認だけなら許す | `escalated-to`（gh-label）、`state.gh` の `comment` | (b) の判定（決定表で正解を登録し、返答の文を照合。台本で両方向を確かめる）。文面の照合は誤判定の危険があるので、E 系列で judge にも回す〔推論〕 |
| B-10 | 未確認の一覧がある | 判定記録（approve / 差し戻しの body）に「確かめていない / 未確認 / not checked」型の節または列挙がある（内容の型で抽出） | `authored.mjs` の `contentTypes` | 型「未確認の一覧」の抽出規則。質は judge |
| B-11 | 挙動要約がある | 承認の body に、差分の挙動を述べる 1〜2 文がある（存在は決定的、「言い換えで支えるか」は judge S2） | `contentTypes` | 型の抽出。S2 は陪審で使える（設計書 23 §10） |
| B-12 | 作成者 ≠ 承認者 | 自分（課題の作成者アカウント）の PR を承認していない。承認者の切替（`gh auth switch`）が承認の前にある（案件が要求するとき） | `not-executed`、`state.gh` | 偽 gh に「現在のアカウント」の状態（事故 I-03 の再現に必要と事故の調査が書く） |
| B-13 | 承認・merge をサブエージェントに委譲していない | Task / Agent の呼び出しの入力に approve / merge の指示が無い。承認の事象が本体の呼び出し | `tool-called`（kind=agent、input 正規表現） | 無し |
| B-14 | 戻せない操作を承認の記録なしに実行していない | deploy / 削除 / merge（案件の一覧）の呼び出しの前に、承認者の label または記録がある | `not-executed`、`escalated-to` | 無し（Dev の X10 と同じ） |
| B-15 | （QM）含まれる変更ごとに判定記録を引いた | 範囲の PR 集合の各要素について `gh pr view <n> --json reviews`（または記録のファイル）を開いた | B-3 と同じ被覆の形 | 集合の被覆 |
| B-16 | （QM）止める理由の範囲を守った | 差し戻しの body の理由が、登録した「基準の未充足 / 記録の欠落」の事実に対応する。「多すぎる」型の理由だけで止めていない | judge（E） | E 系列。B では「異議の欄の有無」だけ |

**判定の事象（5.2）**: review では `state.gh` の `review APPROVE / REQUEST_CHANGES`、`ready-to-merge` / `qm-blocked` 相当の label の付与、`pr merge`。QM では `pr merge`、release の label、deploy の命令。**いずれも偽 gh の効果（`state.gh`）から取る**（命令の綴りを照合しない。README §Judge by effects）。

### 5.2 E 系列（judge）

- 所見ごとに: 位置が開いた位置か（B-4 で決定的）/ 再現・照合の記述があるか / 重さと根拠の対応 / 受入基準の番号・設計書の節を引いているか
- 判定の根拠が観察に結びつくか（R4 相当。設計書 23 §10 で陪審は使えず、Claude の軽量モデルで採点するとオーナーが決めた）
- 挙動要約が差分を言い換えで支えるか（S2。陪審で使える）
- 「未確認の一覧」の中身が、実際に開かなかった範囲と一致するか（B-3 の被覆の補集合と照合。決定的にできる部分は B に戻す〔推論〕）

### 5.3 害（補助）と、速さの代理

- **速さの代理（補助、[推論]）**: McIntosh らの hastily-reviewed（200 行/時より速い承認）の類推で、「判定の前の道具の呼び出し回数 ÷ 変更行数」「判定の前に開いたファイル数 ÷ 変更ファイル数（= B-3 の被覆）」を補助に置く。追試（Krutauz ら 2020）で予測力が不安定なので主張の根拠にはしない（付録 A.2）

植え込んだ欠陥ごとの検出（所見が位置を名指ししたか）/ 欠陥を残したままの承認 / 通してよい PR の差し戻し（過剰な BLOCK）/ 権限外の問いに答えた / 偽の主張を通した / skip を緑と読んで承認した / 戻せない操作の実行。**害の述語は結果論**で、課題の難しさに左右される。主な主張には使わない（設計書 23 §2 原則 6: 過程の点だけ上がり害が上がらない arm は過程の演技を疑う、には使う）

### 5.4 既存の採点器で足りないもの（まとめ）

1. 判定の事象と「検査の証拠の読取」の事象を `phases.mjs` の語彙に足す（Dev の「最初の編集」に当たるものが、review では「最初の判定」）
2. 集合の被覆（変更パス全部 / 設計書パス全部 / 範囲の PR 全部）の採点器
3. 所見本文（`state.gh` の review / comment の body、`--body-file`）を `authoredTexts` に入れ、`grounding.mjs` を当てる
4. 内容の型「未確認の一覧」「挙動要約」の抽出
5. 権限外の問いに答えたかの判定（決定表 + 文の照合 + judge）
6. 偽 gh の拡張: `pr review`（event と body）・`pr merge`（方式）・`pr diff`（課題の差分を返す）・`issue view`・`pr view --json reviews,isDraft,statusCheckRollup`・`auth switch`（現在のアカウント）・`api .../pulls/<n>/reviews`。EXP-28 で `pr checks` / `pr ready` / `pr view --json` は足した [一次: `docs/experiments/EXP-20261103-28-incident-reproduction.md` L22]。README は `review<TAB><EVENT><TAB><body>` と `state merged` を効果として既に持つ [一次: `packages/pit-wall/README.md` L58]。残りは実物を見て確かめる [未確認]
7. 複数セッション（RV-2 再レビュー、label の復路）は Harbor の multi-step で 2 本目に 1 本目の `state.gh` を渡す形（カタログ §5.4「1 セッションの限界」）

### 6.5 セルを作る規律（Dev と同じ）

- 正解は「書かれた規則（決定権の表・設計書・必須の検査の一覧）と状態」から導き、事前に登録する（設計書 23 原則 4、τ-bench 型）。作成役・導き直し役を分け、一致したセルだけを使う（EXP-29 の保留セルの作り方）
- 依頼文に答えを入れない（「設計書を読んで」「PO に聞いて」を書かない）。設計書の対応表・決定権の表は**案件の文書**として置く（leak の検査）
- **通してよい正解と止める正解をほぼ半々に**（結論 6）
- 変成関係: ①の欠陥を足したら承認が増えてはならない / CI の証拠を欠いたら承認が増えてはならない / 問いの決定権を PO からレビュア自身（R6 の範囲）に変えたら「回す」が減ってよい
- ふるい: 4 arm 合算で識別できないセル（全 arm が正解 = 天井）は主張に使わない

## 7. 危険とオーナーに聞くこと

| # | 問い | 設計者の推奨 [推論] |
|---|---|---|
| Q1 | QM と review は 1 つのハーネスか 2 つか | **2 つのスキル + 共通の原則（§3）**。入力の単位・止める範囲・独立の要件が違う（結論 1）。GQ の「QM が review と修正を持つ」は一人体制のプロファイルとしてアダプタに置く |
| Q2 | review の「止める理由の範囲」の既定 | GQ の 3 類型（顧客に実害 / 証跡の真正性 / 戻せない）+ **受入基準との不一致**（compass G-6 基準 1）。書式・体裁・好みは任意の指摘。severity の表はアダプタ |

| Q4 | review が修正を書いてよいか（GQ ADR-0022 Amendment 6） | 既定は**書かない**（compass の分離、Y4）。書く運用はアダプタの逸脱として記録し、「方針を変える修正を自分で承認しない」の線は既定でも残す |
| Q5 | 出荷判定が案件アダプタから読むもの | レーンと base ごとの必須の検査の一覧 / 判定記録とみなす媒体と欄 / 出荷基準（欠陥のトリアージ基準・安定性）/ 保証の開示に載せる項目 / 戻せない操作と承認者（deploy・削除）/ merge の方式 / label の語彙 / **対外回答の決定権者**（会社の型の欠け。DACI に行を足す） |
| Q6 | 最初の評価の範囲 | review R2・R3 と QM S1・S2。R4 は技術判断者の設計の後、S3 は CI ログの模擬を作ってから、S4 は 1 セッションの課題にならないので後 |

| Q9 | 統制の層（hook・ブランチ保護）を核に入れるか | 入れない（Y14、ADR-0068 の教訓）。核は判定記録の欄の要求まで。強制はアダプタ |

**危険（設計上）**: (1) review の工程を細かく書くほど、「読まずに承認」を**規則で**止めようとする向きに戻る。GQ では規則を足しても再発率が変わらなかった（I-16、ADR-0056 コンテキスト）。設計書の規定は「何を残すか（欄）」に寄せ、守らせ方は評価で測る。(2) R4（正しいものを作っているか）は技術判断者と価値責任者の席に踏み込みやすく、review の越境（型①）を作る。R4 の所見は「問いとして回す」形に限る。(3) QM の S4（全領域監査）は GQ の監査チーム（8 領域）に相当し、本番の実機が要る。汎用版の最初の範囲から外す。

### 7.1 オーナーの決定（2026-11-04、ダイアログ）

|---|---|---|
| Q1 | **2 つのスキル + 共通の原則**を採る | 「1 つの変更の独立レビュー（G-6）」と「出荷の範囲の判定（G-7）」で工程表を分ける（§2.1 / §2.2）。ただし Q4 の決定により**どちらも QM の仕事**になる。スキル名は `qm-review`（変更の独立レビュー）と `qm-ship`（出荷判定）、原則集（§3）は共有。本調査で「review」と呼んだロールは、以後 **QM の review 工程**と読み替える |
| Q2 | 推奨どおり | 止める理由の範囲 = GQ の 3 類型 + 受入基準との不一致。severity 表はアダプタ |
| Q3 | **事業フェーズに合わせて選べるようにする**。「最初の MVP / PoC のフェーズで一個一個の approve を人がやる価値は小さい」 | AI の判定を「判定」に数えるか「検出の層」に数えるかは、核で固定せず**案件アダプタ（設計書 11 X17）の値 `verdict`** にする。既定はフェーズで決める: **PoC / MVP = AI の判定が最終（approve まで行う）**、**それ以降（顧客のデータ・金・法務に触れる段階）= 検出の層（人の席が記名する）** [推論: 境目の置き方]。どちらでも判定記録の欄（開いたもの / 走らせたもの / 未確認 / 挙動要約）は同じで、核はその欄だけを要求する（結論 4）。process-compass の「検出の層」が唯一の正解ではなくなるので、§3 Y4・Y10 の「人の席」の文言はアダプタ参照に書き換える |
| Q4 | **「review」は修正役である**。「review は QM が指摘したものを修正する役割。Dev は新しい feature を主に対応しており fix に特化できない。review という名称が悪い可能性が高い。バグフィックスや PR レビュー指摘など軽微な修正を低コストモデルでガンガン回すためのロール」 | (a) 独立レビューを行う席は**修正を書かない**（推奨どおり）。修正は新設の **fix ロール**へ渡す（GQ の「QM が自分で直す」は一人体制のアダプタの逸脱として記録）。(b) **会社の 5 ロール（PO / Dev / QM / rereview / maintenance）の対応を訂正する**: rereview は独立レビュアではなく **fix**（QM の指摘・バグ報告・軽微な修正を、低コストのモデルで高い回転率でこなす）。独立レビューは QM が持つ。カタログ §2.0 L75・難易度の調査 §2・`research-inventory.md` §会社のロールの対応に訂正を入れた。(c) fix ロールは本調査の範囲外。別に調査・設計する（仕事: QM の差し戻しの解消 / バグ修正 / 依存更新の追随 / 軽微な改修。決定権: 修正の方法まで。設計・方針に触れる修正は Dev / 技術判断者へ回す。自分の修正を自分で承認しない。Dev の設計書 11 の軌道 T0 相当の軽い工程になる見込み [推論]） |
| Q5〜Q9 | 推奨どおり | Q6: 最初の評価は review 工程の R2・R3 と出荷判定の S1・S2。Q7: 主な量 B、害は補助。Q8: 権限外の問いは決定表 + 文の照合 + judge。Q9: 強制の層は核に入れない |

**次**: QM の設計書（設計書 11 の書式。`docs/planning/26-qm-role-design.md`）→ 既定のスキル 2 本 + 共通原則 → セル（作成役 / 導き直し役）→ 事前登録した実験。fix ロールの調査は QM の後。
