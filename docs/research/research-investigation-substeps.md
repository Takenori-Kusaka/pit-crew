## 結論の要約

1. **どの作法も「集める前に、何を問い、何を基準に選び・重み付けし、いつ止めるかを決める」段を持つ。** 系統的文献レビュー（Kitchenham）は計画 → 実施 → 報告の 3 段で、実施の前に「プロトコル」（問い・探す範囲・採否の基準・質の評価表・統合のしかた）を書く。理由は「研究者の期待で選択や分析が歪むのを防ぐため」[一次]。意思決定の作法（Kepner-Tregoe、MADR の Decision Drivers）も、選択肢を評価する前に基準と重みを決める [二次 / 一次]。ATAM は事業上の目的を先に聞き、品質の目標を順位付けしてから構造を分析する [一次]。11 §4.1 にはこの「基準を先に決める」段が無い。
2. 共通の骨格は **問いの設計 → 調査計画（基準・範囲・止め方を先に）→ 収集 → 整理 → 評価 → 統合 → 記録と受け渡し** の 7 段に収まる。11 §4.1 の手順 1〜10 は主に「収集」に当たり、「計画」「評価」「統合」が薄い（§5.2 の対応表）。
3. **食い違うインプットの重み付け**で既存調査（`research-phase-practices.md` §Q2、`research-evidence-strength.md`）に無かった点は 4 つ。①**診断性**: どの仮説とも矛盾しない証拠は判断の役に立たない（Heuer の ACH）[一次] ②**三角測量**: 種類の違う出所・方法・観察者・理論で同じ結論が出るかを見る（Runeson & Höst）[一次] ③**外部資料の格付け表**: 発信者の権威・方法・客観性（利害）・日付・他資料との関係・新規性・影響・媒体の種類（Garousi ら）[一次] ④**結論の感度**: 決め手になった少数の証拠が誤っていたら結論がどう変わるか（ACH 手順 6）[一次]。
4. **品質特性のトレードオフ**は、調査の段階では「解く」のではなく**洗い出して順位を付ける**のが作法。ATAM の効用木（utility tree）は品質目標を具体的なシナリオまで分解し、「システムの成功への重要度」と「達成の難しさ（リスク）」をそれぞれ H/M/L で付ける [一次]。性能とセキュリティのように 1 つの設計パラメータで両方が動く点を「トレードオフ点」と呼び、記録して設計で扱う [一次]。成果物は「事業上の目的 → 品質シナリオの順位表」「脅威の一覧（4 つの問い）」「数値の予算（性能予算・エラーバジェット）」。
5. **トレードオフの既定値として外部に明文があるもの**: AWS Well-Architected は「柱の間のトレードオフは事業の文脈で決める。ただしセキュリティと運用上の優秀性は一般に他の柱とのトレードオフにしない」[一次]。Google SRE は「100% はほぼ決して正しい信頼性の目標ではない」とし、許容する不信頼性をエラーバジェットとして数値で持つ [一次]。
6. 和田さん・宮川さんの公開資料に、**調査の内部段階や証拠の重み付けを直接論じたものは見つからなかった**。関係するのは、和田さんの「不具合調査は仮説をテストで確かめる」「品質とスピードはトレードオフではない（犠牲になるのは内部品質＝保守性）」[二次]、宮川さんの「良い考えは他から盗む」「PSGI はできるだけ単純に。速さは仕様ではなく実装の性質」[一次] など、限られた点だけ（§Q4）。
7. Q5 として、調査工程を **R0 問いの設計 / R1 調査計画 / R2 収集 / R3 整理 / R4 評価 / R5 統合 / R6 記録と受け渡し** の 7 段に分け、各段の目的・入る条件・やること・出る条件・成果物を案にした（§Q5.1）。優先度付けの規則の候補を 18 本、出典つきで挙げた（§Q5.3）。

## Q1. 確立した作法は調査をどんな内部段階に分けているか

### Q1.2 作法に共通する骨格 [推論]

上の作法は、名前や細部は違うが、次の 7 段に並べ直せる。

| 段 | 何をするか | 主な出典 |
|---|---|---|
| 問いの設計 | 実務上の問題から問いを立て、分解する（何が分かれば決められるか） | Kitchenham「問いの特定」、Cartaxo「実務上の問題」、Double Diamond の Discover、Issue Tree |
| 調査計画 | **集める前に**、探す範囲・採否の基準・質の評価のしかた・重み付けの基準・止め方・時間枠を決める | Kitchenham のプロトコル、Anthropic の計画保存、KT の重み、ATAM の効用木、MADR の Decision Drivers |
| 収集 | 計画に沿って探し、読み、動かす | Kitchenham「探索」「選択」 |
| 整理 | 集めたものを同じ形に抜き出し、問い・仮説ごとに並べる | Kitchenham「抽出」、ACH の表 |
| 評価 | 個々の証拠の質と、仮説を見分ける力（診断性）を評価し、食い違いを裁く | Kitchenham「質の評価」、ACH ③④、Garousi の表、既存の L1〜L6 |
| 統合 | 結論を出す。反証を試み、結論の感度と残るリスク・トレードオフ点を書く | Kitchenham「統合」、ACH ⑤⑥、ATAM のリスク・感度点・トレードオフ点 |
| 記録と受け渡し | 結論・限界・省略した手順・見直しの目印を、次の工程が使える形で残す | Kitchenham「報告」、Cartaxo の透明性と Evidence Briefing、ACH ⑦⑧ |

**ここから言える一番大事な点** [推論、根拠は上表]: オーナーの指摘にある「情報をどう優先度付けして整理するかを事前に決める」は、どの作法にも独立した段として存在する（SLR のプロトコル、KT の重み、ATAM の効用木、MADR の Drivers）。理由も明示されている — 先に決めないと、集めた材料や気に入った案に合わせて基準が作られる（Kitchenham の researcher bias）。

### Q1.3 各段の入る / 出る条件（作法に明文があるもの）

| 段 | 入る条件 | 出る条件 | 出典・印 |
|---|---|---|---|
| 計画 | 問いが特定されている | プロトコルが書かれ、（可能なら）独立に評価されている。SLR ではプロトコルの評価は推奨だが必須ではない | [一次] Kitchenham §5（「必須でない段」に Evaluating the review protocol を挙げる） |
| 収集 | プロトコルがある | 停止基準（飽和 / 労力上限 / 網羅）のどれかに達した | [一次] Garousi Guideline 8 |
| 評価 | 採否が決まった材料がある | 質の評価が済んだ。迅速レビューでは省いてよいが、省いたことと妥当性への脅威を書く | [一次] Kitchenham §6.3、Cartaxo §4.2.3 |
| 統合 | 評価済みの材料 | 反証を試みた。結論が少数の証拠にどれだけ依存するかを書いた。全仮説の相対的な確からしさを書いた | [一次] Heuer ch.8 手順 5〜7 |
| 記録 | 結論 | 限界・省略が書かれている。見直しの目印がある | [一次] Cartaxo「Transparency …」、Heuer 手順 8 |
| （設計判断の前段） | 事業上の目的が分かっている | 品質シナリオが H/M/L で順位付けされ、分析の対象が絞られている | [一次] ATAM Step 2・5・6 |

## Q2. 食い違うインプットの重み付け（既存調査にない点）

既存の規則は参照する: 「いま何をしているか」は実際の挙動、「何をすべきか」は意図を記録した文書（`research-phase-practices.md` §2-2）。根拠の段 L1 外部の拘束 → L6 理由のない記述、新しさは段を決めない、同点決着（`research-evidence-strength.md` §5）。以下はそれに足す点。

### Q2.1 診断性（diagnosticity）

- 定義: 「ある証拠が、対立する仮説の相対的な確からしさを決める助けになる度合い」。例として、高熱は患者が病気であることは強く示すが、どの病気かを決めるのにはほとんど役立たない（多くの仮説と整合するため）[一次] Heuer ch.4「Failure To Consider Diagnosticity of Evidence」
- 対立する仮説の集合がそろっていないと、診断性は評価できない [一次] 同上
- ACH は、診断性のない証拠を表から除いてから結論を出す（手順 4）[一次] 同 ch.8
- **ソフトウェアの調査への当てはめ** [推論]: 不具合の原因候補が 3 つあるとき、「ログにエラーが出ている」はどの候補とも整合するなら判断材料にならない。候補 A でだけ起きる観測（例: 設定を変えると消える）を探す。設計の選択でも、「どちらの案でも満たせる要求」は案を選ぶ基準にならないので、比較表から外す

### Q2.2 三角測量（triangulation）

- Runeson & Höst（2009、SE の事例研究の指針）は Stake（1995）に依って 4 種を挙げる: データ（出所）の三角測量＝複数の出所、または同じデータを別の機会に集める / 観察者の三角測量＝複数の観察者 / 方法の三角測量＝質的・量的など異なる収集方法の組み合わせ / 理論の三角測量＝別の理論・視点 [一次] Empirical Software Engineering 14:131–164 §2.2 https://www.cse.chalmers.se/~feldt/advice/runeson_2009_emse_case_study_guidelines.pdf
- 「同じ結論が複数の情報源から引き出せるなら、その結論は単一の情報源による結論より強い」（§4.1）[一次] 同上
- **当てはめ** [推論]:
  - 方法の三角測量 = 「コードを読んだ解釈」と「実行した観測」と「テストの結果」が同じことを示すか
  - 観察者の三角測量 = 作業したエージェントとは別のエージェント（作業の文脈を見ていない）に同じ問いを独立に調べさせる
  - データの三角測量 = チケット・設計書・利用者の声のように**独立に作られた**出所。設計書の値をチケットに写しただけなら、出所は 1 つと数える（Admiralty の「他の情報源で確認済み」を数えるときの注意。`research-evidence-strength.md` §2.4 の補足）

### Q2.3 外部資料（グレー文献）の格付け

## Q3. 品質特性のトレードオフを調査の段階でどう把握し、順位を付けるか

### Q3.1 品質特性の語彙: ISO/IEC 25010

- ISO/IEC 25010 の製品品質モデルは 9 つの品質特性からなる（2023 年版）: 機能適合性 / 性能効率性 / 互換性 / 相互作用能力（旧「使用性」）/ 信頼性 / セキュリティ / 保守性 / 柔軟性（旧「移植性」）/ 安全性 [二次] https://iso25000.com/en/iso-25000-standards/iso-25010 （**規格本文は有料で読んでいない**。解説ページでも確認できたのは前半 5 特性とその副特性まで。版の明記も無かった）
- 確認できた副特性の例: 性能効率性 = 時間効率性・資源効率性・容量。信頼性 = 無障害性・可用性・障害許容性・回復性 [二次] 同上
- 使い方 [推論]: 調査の段階では、**漏れの点検表**として使う（「この変更は 9 特性のどれに効くか」）。9 特性を全部評価するのではない。順位は Q3.2 の方法で付ける

### Q3.2 品質特性シナリオと ATAM の効用木

- **品質特性シナリオ**（SEI / Bass・Clements・Kazman）: 品質要求を 6 要素で書く — 刺激の発生源 / 刺激 / 環境 / 対象（成果物）/ 応答 / 応答の測定値。「速く」「安全に」ではなく、測れる形にする [二次] 講義資料・解説の要約（『Software Architecture in Practice』本文は未読）
- **効用木**（ATAM Step 5）[一次] CMU/SEI-2000-TR-004 §5.3:
  - 事業上の目的を具体的な品質特性シナリオに変換する、上から下への仕組み。根は「効用」、その下に性能・変更容易性・セキュリティ・可用性など、さらに副要素、葉が具体的なシナリオ
  - 順位は 2 軸で付ける: 「各ノードのシステムの成功への重要度」と「そのノードの達成に伴うと感じられるリスク（どれだけ容易に達成できるか）」。例: (M,L) は重要度中・リスク低、(H,M) は重要度高・リスク中
  - 0〜1 の尺度より H/M/L を好む。理由: "we find that the stakeholders cannot reliably and repeatably make finer distinctions than High, Medium, and Low"
  - 効用木を作ると、当初は挙がっていなかった品質（例ではセキュリティと変更容易性だけが挙がっていたが、性能と可用性も重要と分かった）が見つかる
  - 出力は「順位付けしたシナリオの一覧」で、残りの評価で時間をどこに使うかの計画になる
- **リスク・感度点・トレードオフ点**（同 §3）[一次]:
  - リスク = 重要なのにまだ決まっていない決定、または決めたが結果が十分に理解されていない決定
  - 感度点 = ある測定可能な品質の応答と強く相関する構造上のパラメータ
  - トレードオフ点 = 1 つのパラメータが複数の感度点を持ち、そのパラメータを変えると品質ごとに逆向きに効く点（例: 通信路の速度を上げるとスループットは上がるが信頼性が下がる）
  - これらは「将来の懸念の領域」で、試作・設計・分析の対象にする
- **調査工程への当てはめ** [推論]: 調査の段階では、効用木を軽く作り（変更が効く品質特性ごとに 1〜3 本のシナリオ、H/M/L × H/M/L）、トレードオフ点の**候補**を挙げるところまで。どちらを取るかは設計工程で決める。(H,H) の葉が、調査を深くする対象になる（11 §4.1 の深さの判定とつながる）

### Q3.3 アーキテクチャ上重要な要求（ASR）と Twin Peaks

- Chen・Ali Babar・Nuseibeh（IEEE Software 30(2), 2013）は、90 人の実務者への面接から、すべての要求が構造に等しく効くのではなく、一部の要求（ASR）が構造を決めると特徴づけた [二次] https://eprints.lancs.ac.uk/id/eprint/64499 （本文未読）
- Nuseibeh「Weaving Together Requirements and Architectures」（IEEE Computer 2001）: 要求と構造を並行して育て、交互に進める（Twin Peaks）[二次] https://oro.open.ac.uk/2213
- 含意 [推論]: 調査の段階で「この要求は構造を決めるか（ASR か）」を判定し、ASR なら品質シナリオまで書く。要求を凍結してから設計するのではなく、調査で見つけた構造上の制約を要求の側（PO）に返してよい

### Q3.4 トレードオフの既定値として明文があるもの

| 原則 | 本文 | 出典・印 |
|---|---|---|
| トレードオフは事業の文脈で決める。ただしセキュリティと運用は既定では譲らない | "When architecting workloads, you make trade-offs between pillars based on your business context. … Security and operational excellence are generally not traded-off against the other pillars." 開発環境では信頼性を落としてコストを下げる、ミッションクリティカルではコストを上げて信頼性を取る、EC では性能が売上に効く、という例を併記 | [一次] AWS Well-Architected Framework, Definitions https://docs.aws.amazon.com/wellarchitected/latest/framework/definitions.html |
| 信頼性は 100% を目標にしない。許容する不信頼性を予算として数値で持つ | "100% is probably never the right reliability target"。エラーバジェットは「サービスがどれだけ不信頼であってよいかを決める明確で客観的な指標」で、開発の速さと信頼性の間の緊張を共通の動機で解く | [一次] Google SRE book ch.3 Embracing Risk https://sre.google/sre-book/embracing-risk/ |
| 性能は先に予算として決める | "A performance budget is a set of limits imposed on metrics that affect site performance." 早く決めると後戻りを防げる。超えたら既存を改善する / 外す / 新しいものを足さない、のいずれかを選ぶ | [一次] web.dev https://web.dev/articles/performance-budgets-101 |

### Q3.5 セキュリティの脅威モデリングを調査段階で行う作法

- 脅威モデリングの 4 つの問い: "1. What are we working on? 2. What can go wrong? 3. What are we going to do about it? 4. Did we do a good enough job?" [一次] Threat Modeling Manifesto https://www.threatmodelingmanifesto.org/ 。出力（脅威）は、その後の設計・開発・テスト・運用の判断に使う [一次] 同上
- 時期: "Threat modeling is ideally performed early in the SDLC, such as during the design phase."、かつ一度きりでなく、システムとともに保守・更新する [一次] OWASP Threat Modeling Cheat Sheet https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html
- STRIDE: なりすまし（認証）/ 改ざん（完全性）/ 否認（記録）/ 情報漏えい（機密性）/ サービス拒否（可用性）/ 権限昇格（認可）[一次] 同上
- Microsoft SDL は脅威モデリングを設計段階の作業と位置づけ、関数呼び出しの粒度まで掘り下げるのは不要とする（Howard）[二次] 検索結果の要約
- **調査工程への当てはめ** [推論]: 4 つの問いのうち 1・2（何を作るか、何が起こりうるか）は調査で答えられる。3（どう対処するか）は設計。調査では、変更が認証・認可・個人データ・外部入力の境界に触れるかを判定し、触れるなら STRIDE の 6 区分で「起こりうること」を列挙して設計に渡す。触れないなら「対象外」と理由を書く

### Q3.6 がんばりクエストでの現状（読み取りのみ）

- 品質特性の優先を明文にしたものとして、ADR-0010 §2「Pre-PMF セキュリティ採用マトリクス」がある。層ごとに「採用 / 採用しない / PMF 後の再評価トリガ」を持ち、判断軸は「被害額 × 実装保守コスト × LP 掲載による新規不安誘発リスク」。同 §0 は「既存実装の品質を下げる根拠ではない」「security 是正には適用しない」と誤用を禁じている〔GQ〕`docs/decisions/0010-pre-pmf-scope-judgment.md`
- 性能（コスト）の側では ADR-0065 が、DSQL の課金を実測したうえで、クエリの規約を「正常時の節約ではなく事故（full scan / N+1 の常態化）の構造的防止」と目的づけている〔GQ〕`docs/decisions/0065-dsql-dpu-query-rules.md`
- これらは **ADR（横断の決定）**であり、Dev が個々の調査でトレードオフを洗い出す手順は、今回読んだ範囲（`dev-process/research-discipline.md`、impact-analysis、issue-triage 手順 C と方法論文書）には無い〔GQ〕。research-discipline の「顧客が離脱する failure class から逆算して問う」（§1-3）は、品質シナリオの「刺激と応答」を顧客の害から立てる作法に近い [推論]
- 含意 [推論]: 汎用ロールでは、ADR-0010 §2 のような**案件ごとの品質の優先表**を案件アダプタに持たせ、調査の計画段で読む。表が無い案件では、調査の成果物として暫定の順位を書き、PO / 技術判断者に確認する

### Q3.7 いつ・何を成果物にするか [推論、根拠は上の各節]

| 時期 | 成果物 | 根拠 |
|---|---|---|
| 調査の計画段 | 事業上の目的（なぜこの変更か）と、変更が効く品質特性の一覧（ISO 25010 で漏れを点検）。案件の品質の優先表があれば、その該当行 | ATAM Step 2・5、AWS（事業の文脈） |

## Q5. 「調査」工程の内部段階の案と、優先度付けの規則の候補

以下はすべて [推論]（出典の作法をエージェント向けに組み直したもの）。各行の出典は、その段・規則の根拠になった作法を示す。

### Q5.1 内部段階の案

| 段 | 目的 | 入る条件 | やること | 出る条件 | 成果物 | 出典 |
|---|---|---|---|---|---|---|
| R0 問いの設計 | 何が分かれば決められるかを、この製品の前提から言えるようにする | 11 §4.1 の入る条件 E1〜E3 | 依頼の言い直し（11 手順 1）。問いを分解する（Issue Tree の 1〜2 段）。製品の前提（実行基盤・顧客・体制・段階・制約）と、顧客に害が出る失敗の型から問いを立てる。仮説があれば対立仮説も出す | 完了に要る問いが列挙され、各問いが「何をしているか（事実）」「何をすべきか（意図）」「どれを選ぶか（判断）」のどれかに分類されている | 問いの一覧 | Kitchenham §5.3、Cartaxo（実務上の問題）、Double Diamond、ACH 手順 1〔GQ〕research-discipline §1 |
| R1 調査計画 | **集める前に**、何をどの基準で選び、どう重み付けし、いつ止めるかを決める | R0 の問いの一覧 | ①深さを宣言（11 手順 2）②読む範囲（11「調査の範囲」の該当区分）③証拠の扱い: 問いの種類ごとの正（既存 §2-2）、根拠の段（L1〜L6）、外部資料の格付け（Q2.3）④品質の優先: 事業上の目的と、変更が効く品質特性（ISO 25010 で点検）。案件の品質の優先表を読む ⑤止め方: 停止基準（飽和 / 労力上限 / 網羅）と時間枠 ⑥省く手順があれば明記 | 計画が調査メモの冒頭に書かれている。浅い調査なら 3〜5 行でよい | 調査計画（調査メモの第 1 節） | Kitchenham §5.4（プロトコル）、Anthropic（計画を先に保存）、KT（重みを先に）、ATAM Step 2・5、Garousi Guideline 8、Cartaxo（省略の明記） |
| R2 収集 | 計画に沿って、読んだ・動かした事実を集める | R1 の計画 | 11 手順 3〜8（土台 / 文書 / コード / 実行 / 影響範囲 / 既存の解）。計画外の重要な発見で計画を直すときは、直したことと理由を書く | 停止基準のどれかに達した | 読んだもの・実行結果の記録 | 11 §4.1、Kitchenham §6.1〜6.2、Garousi |
| R3 整理 | 集めたものを、問い・仮説ごとに比べられる形に並べる | R2 の記録 | 問い × 出所の表を作る（各セルに「何と言っているか・日付・状態」）。仮説があれば仮説 × 証拠の表。品質特性ごとに、関係する事実を寄せる。同じ出所の写しを 1 つにまとめる | すべての問いに、少なくとも「材料なし」と書いたセルがある | 突合表 | Kitchenham §6.4（抽出）、ACH 手順 2〜3、Runeson（出所の独立） |
| R4 評価 | 個々の材料の質と、判断に効くかを評価し、食い違いを裁く | R3 の突合表 | 材料ごとに根拠の段と弱点を付ける（Q2.5）。診断性のない材料を判断から外す。食い違いは 11「矛盾するとき」と `research-evidence-strength.md` §5.2 の手順で扱う。品質シナリオを (重要度, 難しさ) で順位付けし、トレードオフ点の候補を挙げる。触れるなら脅威を列挙 | 食い違いがすべて「裁いた / 上げた / 条件分岐だった」のどれかになっている。品質シナリオに順位がある（該当しなければ「対象外」と理由） | 評価済みの突合表、品質シナリオの順位表、脅威の一覧 | Kitchenham §6.3、Heuer（診断性）、Garousi Table 7、ATAM §5.3・§3、Threat Modeling Manifesto |
| R5 統合 | 問いに答え、どこまで確かかを言う | R4 の評価 | 各問いの結論を書く。仮説は反証を試みてから残す。三角測量の状況（何種類の独立した出所・方法で支えられているか）を書く。決め手になった証拠を名指しし、それが誤っていたら何が変わるかを書く。残った問いを「調べる / 仮定 / 聞く / 試す」に振り分ける（11 手順 9） | 完了に要る問いに結論か振り分けがある。トレードオフ点は解かずに設計への申し送りとして書かれている | 結論、確かさ、感度、残る問い | ACH 手順 5〜7、Runeson §2.2、ATAM（リスク・トレードオフ点を後の工程の焦点に） |
| R6 記録と受け渡し | 次の工程（設計）と、聞く相手が使える形で残す | R5 の結論 | 11 手順 10 の調査メモに、計画（R1）・省いた手順と限界・見直しの目印を足す。要約を 1 画面に収める | 11 §4.1 の出る条件に加え、計画と実際の差（止めた基準、省いた手順）が書かれている | 調査メモ（要約 + 詳細） | Kitchenham §7、Cartaxo（透明性・Evidence Briefing）、ACH 手順 8 |

**深さによる簡略化** [推論]: 浅い調査では R1 を 3〜5 行、R3・R4 を「問いごとに 1 行」に縮めてよい。ただし R1 の「止め方」と、R6 の「省いた手順」は省かない（Cartaxo の透明性）。深い調査では R1 を独立の確認点にし、計画を別のエージェントに点検させる（Kitchenham の「プロトコルの評価」に相当）。

### Q5.2 11 §4.1 との対応

| 11 §4.1 の手順 | 案の段 | 足りないもの |
|---|---|---|
| 1 依頼を言い直す | R0 | 問いの分解、対立仮説 |
| 2 深さを宣言する | R1 の一部 | 証拠の扱い・品質の優先・止め方を**集める前に**決める項目 |
| 3〜8 土台 / 文書 / コード / 実行 / 影響範囲 / 既存の解 | R2 | — （厚い） |
| （無い） | R3 | 問い × 出所の突合表 |
| 「矛盾するとき」の表 | R4 の一部 | 診断性、外部資料の格付け、品質シナリオの順位付け、脅威の列挙 |
| 9 問いを振り分ける | R5 の一部 | 確かさ・三角測量・感度、トレードオフ点の申し送り |
| 10 調査メモを書く | R6 | 計画と実際の差、省いた手順、見直しの目印 |

### Q5.3 優先度付けの規則の候補

| # | 規則（エージェント向けの言い換え [推論]） | 出典・印 |
|---|---|---|
| P1 | 証拠の採否・重み付けの基準と止め方は、材料を集める前に調査メモに書く。集めた後に基準を変えたら、変えたことと理由を書く | Kitchenham §5.4 [一次]、KT [二次]、MADR [一次] |
| P2 | 「いま何をしているか」と「何をすべきか」で正を分けてから比べる | `research-phase-practices.md` §2-2（既存、[推論]） |
| P3 | 値の正否は、文書の格ではなく、その値を支える根拠の段（L1〜L6）で比べる | `research-evidence-strength.md` §5.1（既存、[推論]） |
| P4 | どの仮説とも整合する証拠は判断に使わない。仮説を見分ける観測を探す | Heuer ch.4・ch.8 [一次] |
| P5 | 結論は、種類の違う 2 つ以上の出所・方法で支える（コードの読解と実行結果、文書と利用データ）。同じ出所の写しは 1 つと数える | Runeson & Höst §2.2・§4.1 [一次]、写しの扱いは [推論] |
| P6 | 外部資料は、発信者・方法・利害・日付・媒体の層で格付けする。製品の開発元による比較は利害ありとして一段割り引く | Garousi Table 7 [一次] |
| P7 | 古い文書は捨てずに、日付と状態を確かめ、実物と照合して使う | Lethbridge ら [二次]、Nygard（既存） |
| P8 | 品質特性の優先は、事業上の目的（なぜこの変更か）から導く。案件の品質の優先表があればそれに従う | ATAM Step 2・5 [一次]、AWS [一次]〔GQ〕ADR-0010 §2 |
| P9 | 品質シナリオは (重要度, 難しさ) を H/M/L で付け、(H,H) から深く調べる。細かい数値で順位を付けない | ATAM §5.3 [一次] |
| P10 | セキュリティと運用の健全性は、既定ではトレードオフの対象にしない。譲るなら決定記録と承認を要する | AWS Definitions [一次]。承認の要件は [推論]（11 の不可逆操作の扱いに合わせる） |
| P11 | 性能・信頼性の要求は「速く」「落ちない」でなく、数値の予算・目標で書く。100% を目標にしない | web.dev [一次]、Google SRE ch.3 [一次] |
| P12 | 品質要求は 6 要素（発生源 / 刺激 / 環境 / 対象 / 応答 / 測定値）のシナリオで書き、測れる形にする | SEI 品質特性シナリオ [二次] |
| P13 | 1 つのパラメータで品質が逆向きに動く点（トレードオフ点）を見つけたら、調査では解かずに候補として記録し、設計に渡す | ATAM §3 [一次]。調査と設計の分担は [推論] |
| P14 | 認証・認可・個人データ・外部入力の境界に触れる変更は、調査で「何が起こりうるか」を STRIDE で列挙する。触れないなら対象外と理由を書く | Threat Modeling Manifesto [一次]、OWASP [一次] |
| P15 | 結論の決め手になった証拠を名指しし、それが誤っていたら何が変わるか、何が見えたら見直すかを書く | Heuer 手順 6・8 [一次]、GRADE（既存） |
| P16 | 探索は、飽和 / 労力上限 / 網羅のどれで止めたかを書く | Garousi Guideline 8 [一次] |
| P17 | 調査を簡略化してよいが、省いた手順と、それによる限界を書く | Cartaxo §4.2 [一次] |
| P18 | 速さのために内部品質（保守性）を下げる選択を、調査の段階で前提にしない。下げるなら判断と返済を記録する | 和田 TW-qs [二次]、`research-dev-quality-bar.md` §2 の規則 [推論] |
