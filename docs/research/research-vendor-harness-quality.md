# ハーネスを公開する組織は、品質をどう保証し、何を公言しているか（ベンダー・大手公開者編）

調査日: 2026-11-15 / 問い（オーナー）: 「各社は自社の名前でハーネスを出している。全社が隠しているのでなければ、こちらの調査が足りないか、方法が違う」
前提として読んだ既存調査: `research-prior-art.md`（コミュニティの評価ツール）、`research-eval.md`（`claude plugin eval`・SkillsBench・統計）、`00-goal-charter.md` 1.1、AgentOps 技術レポートのリリースゲート節。重複する内容は再掲せず、差分だけを書く。

**凡例（根拠の水準）**
- **[一次]** = この調査で一次ソース（公式 docs・リポジトリのファイル・CI 定義・公式ブログ）を開いて本文を確認した。リポジトリは `gh api` で 2026-11-15 に取得
- **[一次・抜粋]** = 一次ソースだが、検索結果の抜粋または部分取得のみ（全文は未読）
- **[二次]** = 第三者の記事・要約経由
- **[未検証]** = 開けなかった、または確認していない
- **[推論]** = 証拠からの筆者の推論。「している」と「たぶんしている」を分けるために明記する
- **[計算]** = 筆者の計算値

## 要点

1. **公開者は品質を保証している。ただし保証している量は「ハーネスなしに対する効果」ではなく、「決めた振る舞いの契約が、固定したモデルで、決めた回数のうち決めた回数以上守られること」と「前の版から落ちていないこと」である。** gstack・superpowers・Anthropic・GitHub・Cursor のどれも、リリースを止める条件に「素の状態との差が統計的に有意」を置いていない [一次]。
2. **効果の比較（with/without）は、やっている所でも「報告」か「作者の自己点検」であり、ゲートではない。** Anthropic のディレクトリ審査は「検証とスキャンはプラグインの作りを見る。入れた人の役に立つかは見ない」と明記し、with/without の比較は提出前に作者がやることとして勧めるだけ [一次]。gstack は効果比較をブロッキング条件から外し、「合格は限界的な効果を立証しない」「検出力を設計した標本抽出は無い」と書いている [一次]。
3. **「公言しないこと」を明記するのが、質の高い公開者の共通点。** wshobson/agents は「静的層は lint。スキルが役に立つかは分からない」「judge 層は人のラベルで検証していない」、gstack は効果の状態語に `baseline_saturated`（素が満点、効果は示されていない）を持ち、superpowers は「この数字はすべてのハーネス・作業で成り立つわけではない」と添える [一次]。
4. **製品ベンダー（GitHub・Cursor）の最終ゲートはオフライン評価ではなく、本番の A/B とテレメトリ。** GitHub は「オフライン評価が見逃した回帰を最初のオンライン実験が見つけた」と書く [一次]。小さな公開者にはこの層が無い。代わりに使われているのは、利用者の transcript と Issue を回帰ケースに戻す運用（superpowers・gstack）[一次]。
5. **役割・プロセス型のハーネスが、モデル固定のベンチマーク（Terminal-Bench など）に載っている例は確認できなかった。** 載っているのはエージェントの実行基盤（scaffold）で、スキル群を処置にした比較は SkillsBench と個別のツール（skillarena など）に限られる [一次・一部未検証]。
6. **結論: 調査は足りていた（「統制比較を公表した例は無い」は今回も覆らなかった）。違っていたのは方法である。** 憲章 1.1 は「3 つの相手より上げる」を完了条件にしており、これは業界のどの公開者も自分に課していない種類の主張（平均効果の検出）。業界の「評価済み」は、ケース単位の契約と回帰の非劣化で定義されている。§6 に、小さなチームが満たせる定義の案を書く。

## 2. 品質の単位を並べる（誰が何を単位にしているか）

| 単位 | 使っている公開者 | リリースを止めるか |
|---|---|---|
| 静的な構造検査（lint・スキーマ・参照・版固定・秘密情報）| 全員。Anthropic ディレクトリ、wshobson、BMAD、spec-kit、gstack の無料層 | 止める |
| 契約ケース（必ず守る / 絶対しない）を固定モデルで N 回中 M 回 | gstack（rule・behavior）、superpowers-evals（受け入れ基準 + post-check）、`claude plugin eval`（`--threshold`）、OpenAI の指針（決定的な検査）| gstack は止める。superpowers は手動の受け入れ |
| 前の版からの非劣化（before/after）| gstack（履歴・flake 台帳）、superpowers（PR に before/after を要求）、GitHub（run 間のばらつき内）| 止める（GitHub・gstack）|
| 素（ハーネスなし）との差 | `claude plugin eval` の Δ、superpowers の stock arm、gstack の overlay ON/OFF、skillarena など | **止めない**。報告か作者の自己点検 |
| ベンチマークのスコア（モデル固定）| LangChain、Cursor（CursorBench）、GitHub（社内ベンチ）| 判断材料。しきい値は非公開 |
| 本番の A/B・テレメトリ | GitHub、Cursor | 止める（製品ベンダーのみ）|
| 人の審査・手動テスト | Anthropic ディレクトリ（新規掲載）、spec-kit（手動のコマンド試験）、superpowers（手動の受け入れ）| 止める |
| 利用者の報告を回帰ケースに戻す | superpowers（Issue の transcript）、gstack、OpenAI の指針 | — |

[推論] この表から読めること: **リリースを止める条件に使われるのは、合否が 1 回の実行でほぼ決まる量だけ**である。素との差は分散が大きく、少ない試行では決まらないので、どの公開者もゲートにしていない。gstack はそれを一度ゲートにして、外した。

## 5. 統合

### (a) 業界の実務で、公開ハーネスの「評価済み」が意味すること

[推論・§1〜§4 の証拠から] 次の 4 層の積み重ねであり、上ほど少数の公開者しかやっていない。

1. **構造が正しく、安全に読み込める**（静的検査。全員）
2. **決めた場面で、決めた振る舞いをする**（契約ケース。固定モデル・固定回数・事前に決めた合格規則。gstack、superpowers、`claude plugin eval`）
3. **前の版より悪くなっていない**（回帰。変更ごとの before/after、履歴）
4. **何を測っていないかを書いている**（限界の明記。gstack、wshobson、superpowers、Anthropic の免責）

「素より良い」は 5 番目の任意の報告で、出すときは件数とケース名で出す（superpowers: 「あるシナリオで 8 回中 8 回」）。平均効果・p 値・信頼区間を公開物の品質の根拠にしている公開者は、確認した範囲にいなかった。

### (b) 憲章 1.1 と現在の計画との違い

| 観点 | 業界の実務 | 憲章 1.1 / 現在の計画 |
|---|---|---|
| 主張の形 | 「場面 X で振る舞い Y を N 回中 M 回」（ケース単位・絶対）| 「3 つの相手（なし・GQ の写し・v1）より主な量を上げる」（比較・相対）|
| 決まり方 | 1 ケース 3〜12 試行で合否が出る | 約 300 試行でも「判定不能」になりうる。288-run の研究は 10 ポイントの差に 120〜200 タスクが要るとした（`research-prior-art.md` §2）|
| 素との比較の位置 | 報告。ゲートにしない | 完了の定義そのもの |
| 相手の数 | 0（契約）または 1（素）| 3 |
| 主な量 | 契約の遵守（工程・禁止事項）| 工程への準拠と根拠の裏付け — **ここは一致している** |
| 限界の扱い | 「測っていないこと」を公開文書に書く | 「上げられない工程を明記」— 一致 |

### (c) 厳しくて正しい部分と、道具が違う部分

**厳しいが理由がある（残す）**
- 事前登録と、結果を見たあとの変更の禁止。gstack も方針の定数の変更に再承認と再実行を要求している [一次]
- 採点器の妥当性の点検。wshobson は judge を「人のラベルで未検証」として実験扱いに落とした。gstack は「検出器は悪い対照で先に確かめる」。pit-crew の測り方の誤り（2026-11-12〜13）はこの層で起きた
- 主な量を工程への準拠に置くこと。superpowers-evals は自分を「汎用ベンチマークではなく、ワークフロー遵守の評価ラボ」と呼ぶ [一次]
- 素の arm を走らせて、天井（`baseline_saturated`）を結果に出すこと
- 課題に答えを入れない（leak の検査）。superpowers はテスト用の圧力シナリオがスキルと一緒に配布され、作業中のエージェントに見つかる問題を直している [一次]

**道具が違う（変える）**
- **平均効果の検出を完了条件にすること。** どの公開者も自分に課しておらず、gstack は課して外した。サブスクの計算枠では検出力が足りず、「判定不能」は情報にならない
- **相手を 3 つ並べること。** 試行を 3 倍にして、1 つの主張も強くしない
- **ロールごとに 1 つの大きな実験。** 業界の単位は小さなケースの集まりで、ケースごとに合否が出て、足せて、回帰に使える
- **「評価済み」を一度きりの判定とみなすこと。** 実務では、リリースごとに走るゲートを持っている状態を指す

### (d) 提案: 汎用の役割ハーネスの「評価済み」の定義

サブスクの枠で満たせて、第三者が再現できる形。各要素に根拠を付ける。

| # | 要素 | 中身 | 根拠 |
|---|---|---|---|
| E0 | 構造の検査 | 静的 lint・参照・マニフェスト。無料の CI で毎 PR | 全公開者。Anthropic ディレクトリの Blocks |
| E1 | **契約ケースの表** | ロールごとに 10〜20 件。実際の失敗（GQ の事故、会社の事例の抽象化）から作る。各ケースは「場面・必ずする / 絶対しない・決定的な検査」。種別（rule / behavior）と合格規則を実行前に固定 | gstack の 3 分類。OpenAI「1 スキルに 10〜20 プロンプト」「手で直したことは全部ケースにする」。Anthropic「素で失敗した所から評価を作る」|
| E2 | **採点器の検査を先に** | 各ケースに、通るはずの台本と落ちるはずの台本を置き、採点器が両方を正しく分けることを機械で確かめてから本番 | gstack「悪い対照で先に」。wshobson が未検証の judge を実験扱いにした判断。憲章の規律「検査は通る場合と落ちる場合の両方」|
| E3 | **リリースのゲート** | 固定したモデル・ハーネスの SHA で、rule ケースは 3 試行すべて合格、behavior は 3 中 2 以上かつ契約違反なし。再試行しない。基盤の失敗も失敗に数える。落ちたケースは単体で 10 試行し 9 以上で復帰 | gstack の panel と ship bar。`claude plugin eval` の既定 3 回 |
| E4 | **素の arm の報告**（ゲートではない）| 同じケースを素でも同数走らせ、ケースごとに `improved` / `baseline_saturated` / `no_measured_improvement` / `regressed` / `incomplete` を付けて公表 | gstack overlay 契約 v4 の状態語。Anthropic の提出前の勧め。`claude plugin eval` の Δ が exit code に効かない設計 |
| E5 | **看板ケースだけ厚く** | 「このハーネスが直す」と README に書くケース（最大 5 件）は各 arm 10 試行。主張は件数で書く（例: 素 2/10、ハーネス 10/10）| superpowers のリリースノートの書き方。[計算] 2/10 対 10/10 は Fisher の正確検定で両側 p < 0.001 — ケース単位なら 20 試行で決まる。10/10 の 95% 下限は 72%（gstack の記載と一致）なので「10 回中 10 回（下限 72%）」と書く |
| E6 | **版の間の非劣化** | v(n) で合格だったケースが v(n+1) で落ちたら出さない。GQ の写し・v1 は「比べる相手」ではなく、この履歴の最初の点として 1 回測って置く | gstack の履歴と freeze。Anthropic の回帰評価（ほぼ 100% を保つ）|
| E7 | **公言しないことの節** | README に固定の節: 測ったモデルと日付 / ケース数と試行数 / 天井だったケース / 通しの多ロール連鎖は測っていない / 他モデル・他の題材への一般化は主張しない / 平均効果は主張しない | NIST MEASURE 2.5・MS-2.5-001。gstack・wshobson・Anthropic の明記 |
| E8 | **再現の入口** | 1 コマンドで E0〜E4 が走る（Docker、または `claude plugin eval` の形式）。結果の JSON と transcript を同梱。第三者は自分のサブスクで同じ表を出せる | Terminal-Bench の「公開でアップロード、軌跡を審査」。`claude plugin eval` の `aggregate-result.json` |
| E9 | **利用からケースへ戻す道** | Issue テンプレートに transcript を付ける欄。再現した失敗は契約ケースに足す | superpowers（#2530 の transcript）、GitHub「テストされていない振る舞いは消える」|

**試行数の見積もり** [計算]: 15 ケース × 3 試行 × 2 arm = 90、看板 5 ケース × 追加 7 試行 × 2 arm = 70。**1 ロール 1 リリースあたり約 160 試行**で、結果は必ず「各ケースの合否と状態語」として出る（判定不能にならない）。5 ロールで約 800 試行だが、変更したロールだけ走らせれば済む。

**憲章 1.1 の書き換え案**（オーナーの判断事項）: 「…と比べ、事前に決めた規則で、主な量を上げるか、上げられない工程を明記している」→「ロールごとに契約ケースの表があり、固定したモデルで E3 のゲートを通り、素との比較をケースごとの状態語で公表し、測っていないことを明記している。GQ の写しと v1 は履歴の最初の点として測る」。主な量（工程への準拠と根拠）と、事前登録の規律は変えない。

### (e) 分かっていないこと

- **ベンダーの社内の受け入れ基準。** Anthropic の公式スキル・`openai/skills` の `.curated` に入る条件、GitHub・Cursor のオフラインのしきい値と試行数は公開されていない。「たぶん社内評価がある」は推論で、証拠は GitHub と Cursor の記事の記述だけ
- **契約ケースの合格が、実際の仕事での害の減少につながるか。** どの公開者も示していない。製品ベンダーは本番の A/B で埋め、小さな公開者は埋めていない
- **3 試行のゲートの見逃し。** gstack 自身の計算で、0.95 → 0.70 の劣化を 1 回で捉えるのは 21.6%。E3 は「壊れていない」ことの弱い証拠で、履歴（E6）と合わせて初めて意味を持つ
- **通しの多ロール連鎖の評価方法。** gstack は「有料の通し評価は無い」と明記。先行例なし（`research-prior-art.md` 差別化 3 と同じ結論）
- **モデルが変わったときの持ち越し。** LangChain は「ハーネスはモデルごとに調整が要る」とし、gstack はモデルごとに結果を分ける。固定モデルの結果は次のモデルに持ち越せない

## pit-crew への示唆

1. **オーナーの問いへの答え**: 隠しているのではなく、各社が保証しているのは別の量だった。公開の文書と CI にそのまま書いてある。調査の結論（統制比較の公表例は無い）は正しかったが、それを「だから自分たちがやる」と完了条件にしたのが方法の違い。
2. **次の分かれ道**: 憲章 1.1 の完了の定義を §5(d) の形に変えるか。変えるなら、計画 34 第 4 版の「契約・基準の段（重要失敗例の表・強制の生成器・場面・カード）」はそのまま E1〜E2 に当たり、追加の設計は E3 の合格規則と E4 の状態語、E7 の節だけで済む [推論]。
3. **統制実験は捨てない。位置を変える。** 約 300 試行の実験は「研究の証拠」として別に置き、公開の条件から外す（gstack の「比較は研究の証拠として別に報告」と同じ扱い）。看板ケース（E5）はケース単位なので 20 試行で決まる。
4. **差別化は残る**: 役割ハーネスで、契約ケースの表・素の arm の状態語・公言しないことの節・第三者が回せる 1 コマンドを全部そろえて公開している例は、今回の範囲にも無かった（gstack は最も近いが、評価は自分の CI 用で、利用者がフォークを同じスイートで測る形ではない）。
5. **半日で設計・半日でテスト（憲章の目安）との相性**: 契約ケースは 1 件ずつ足せ、採点器の検査（E2）を型にすれば、新しいロールは「失敗例 10 件 → ケース 10 件」で始められる。平均効果の実験はこの目安に入らない。
