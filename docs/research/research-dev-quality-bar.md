## 0. この文書の読み方

- 目的は、汎用 Dev ロールの品質基準を「二人の公開された立場」に根拠づけること。二人を真似ることや、二人の口調で話すことは目的にしない。
- 根拠の印:
  - **[一次]** 本人が書いた・話した文書を取得して確認した（本人のブログ、本人のスライドの読める部分、本人が書いた CPAN ドキュメントや連載記事、番組公式ページ）
  - **[二次]** 第三者による要約・報道、または文字化けしたスライドを取得ツールが復元したもの（原文の字面は未照合）
  - **[推論]** 二人の発言から本調査が導いたエージェント向けの規則。二人の主張そのものではない
  - **[未確認]** 存在は分かるが内容を確かめられなかったもの
- 引用の注意: t-wada の Speaker Deck のスライドは、多くが文字化けしていて取得できない。読めた文字列だけを引用し、復元されたものは [二次] とした。
- 宮川達彦氏の考えが最も多く表れているのは Rebuild.fm の音声だが、文字起こしは公開されていない。このため、番組ページで確認できるのは「何を話題にしたか（章題・リンク）」までで、**何を言ったかは [未確認]** とした。宮川氏の書いた文章として確認できたのは、CPAN ドキュメント、WEB+DB PRESS の記事、スライドである。

## 1. Dev の工程ごとの原則

各表の 4 列目「エージェント向け規則」は、二人の発言を本調査がエージェント向けに言い換えたもの。どれも **[推論]** である（二人がその形で述べたわけではない）。

### 1.1 調査・リサーチ

| 原則 | 本人の言葉（要旨／引用） | 出典・印 | エージェント向け規則 [推論] |
|---|---|---|---|
| 不具合修正の大半は既存コードの調査 | 「不具合修正は新機能の追加とは異なり、既存コードに対する調査の割合が大きくなります」 | TW-bug [一次] | 修正の依頼では、コードを書く前に、再現手順と最小の再現範囲を報告できるところまで調べる |
| 推測した原因はテストで確かめる | 再現テストが修正前に失敗することで、推測した原因が正しいかを確かめられる。修正前にテストが通るなら、テストの誤りか原因の理解不足を疑う | TW-bug [一次]（引用は要旨） | 「原因は X」と書く前に、X を突く失敗テストを示す。示せないときは「仮説」と明記する |

### 1.2 設計

| 原則 | 本人の言葉（要旨／引用） | 出典・印 | エージェント向け規則 [推論] |
|---|---|---|---|
| 誤りを検出するより、誤りにくく設計する | 「誤りを想定してチェックするのではなく、そもそも誤りにくい設計とはどのようなものか」 | TW-prev [一次: 講演概要の読める部分] | 実行時チェックを足す前に、型・列挙型・値オブジェクトで不正な値を作れなくできないかを先に検討する |
| 型・不変性・完全性・責務の配置 | 目次は「型宣言、列挙型、静的解析、型のモデリング、不変性、完全性、責務の配置」。更新しても元のオブジェクトは書き換えず、新しいオブジェクトを返す例がある | TW-prev [一次: 目次] / 各論は [二次]（本文の大半は文字化け） | 生成した時点で不変条件が成り立つ型にする。状態を変える API よりも、新しい値を返す API を選ぶ |
| fail fast | Claude Code に TDD を任せたログで、t-wada は不正な状態について Claude の推奨案ではなく「fail fast の原則に従い、実行時エラーにする案を採用する」と判断した。型で保証済みの値でも「実行時にノーガードなのは避けたい」 | TW-cc [一次] | 不正な入力は境界で早く失敗させる。型で保証していても、外部から入る値には実行時の検査を残す |
| テストしやすい設計は責務を整理する | 「テストのための設計が責務の再配置を促し、全体として責務がバランスしてシンプルになるのであれば、それはテストが良い設計へ導いてくれたということです」。複雑になるなら「やりすぎ」 | TW-dft [一次] | テストのために設計を変えたら、責務が単純になったかを確かめる。複雑になったら差し戻す |
| 非決定的な依存は外から制御できるようにする | テスト容易性とは「いつでも、何回繰り返しても、何時に実行しても同じように動作するテストを書けるようにするための設計」。そのため「時刻をテストから制御できなければなりません」 | TW-dft [一次] | 時刻・乱数・外部 I/O は引数か注入で受け取る。直接呼んでいたら設計上の欠陥として扱う |
| private をテストしたくなるのは設計の問題 | 「ホワイトボックステストを書きたくなるのは、テストの問題ではなく、設計の問題だ」（『テスト駆動開発』からの引用）。対処はクラスの抽出 | TW-priv [一次] | private を直接テストしたくなったら、クラスの抽出を提案する。リフレクションは最後の手段 |
| TDD は設計しないことではない | 「テスト駆動開発はテストコードを先にたくさん書くことではありませんし、設計せずいきなりテストコードを書き始めることでもありません」 | TW-canon 訳者コメント [一次] | コードを書く前に、設計方針とテストリストを示し、人の承認を得る（t-wada 自身も Claude Code に「まだコードは書かないでください」と指示している: TW-cc [一次]） |
| 仕様は最小に、実装の自由は残す | PSGI は "designed to be as simple as possible"。"minimize the requirements on backends so they can optimize things"。使いやすい API はフレームワーク側に任せる | MY-psgi [一次] | インターフェースを設計するときは、相手に求める義務を最小にする。便利機能は上の層に置く |
| 特定のモジュールへの依存は害 | "Backends depending on specific modules or having to reinvent lots of stuff is considered harmful." | MY-psgi [一次] | 公開インターフェースに特定のライブラリの型を漏らさない |
| 既存の仕組みとの互換性 | PSGI を CGI に似せたので "supporting PSGI in addition to CGI would be extremely easy"。Carmel は「Cartonと互換性があります」 | MY-psgi / MY-carmel [一次] | 置き換えは移行コストが小さくなる形にする。互換性を壊す変更は、明示して理由を書く |
| 一つのことをうまくやる | cpanm は取得・展開・ビルド・インストール以外は "does nothing else"。それ以外の機能は他の道具に任せる | MY-cpanm [一次] | 依頼の範囲外の機能を足さない。足したくなったら別の Issue として提案する |
| 要望に No と言う | 「そうした要望に「No」といえる勇気です」。中核でないもの、他と組み合わせて実現できるものには「明確に No といえることが」設計の単純さを保つ | MY-no（TW-oss の引用経由）[二次] | 機能を足す前に「中核か」「他と組み合わせて実現できるか」を確かめ、該当しないものは断る理由を書く |
| 意図は決めたその場で残す | 意図負債とは「明示的な根拠、目標、制約が存在しない、または侵食されていること」。AI エージェントは書かれた意図しか読めない | TW-debt26 [一次: 読める引用] | 設計判断をした時点で、根拠・目標・制約を ADR などに 1 段落で残す |

### 1.3 テスト設計

| 原則 | 本人の言葉（要旨／引用） | 出典・印 | エージェント向け規則 [推論] |
|---|---|---|---|
| TDD はテストリストから始まる | 「押さえておきたいテストシナリオを洗い出し、リスト（テストリスト）にまとめる」。TDD のステップは正確には「リスト、レッド、グリーン、リファクタ」 | TW-canon [一次] | 実装に入る前にテストリストを書いて見せる。t-wada も Claude Code に「テストリストは若干足りない」と差し戻している（TW-cc [一次]） |
| テストリストに実装の判断を混ぜない | ステップ 1 のよくある過ちは「実装の設計判断を混ぜ込んでしまうこと」 | TW-canon [一次] | テストリストには振る舞いだけを書く。実装方法は書かない |
| テストサイズで分類する | Small は単一プロセス、Medium は単一マシン、Large はリモートへのアクセスも許す。範囲や粒度による分類は「現場は混乱しがち」 | TW-size [一次] | テストごとにサイズを宣言する。Small を多く、Large を少なくする |
| 速さと忠実性のトレードオフ | Small は速く決定的だが本番との近さに欠け、Large はその逆 | TW-size [一次] | 新しい Large テストを足すときは、なぜ Small/Medium で足りないかを書く |
| SMURF の 5 軸 | 「S: 動作スピード M: 保守性 U: リソース使用率 R: 信頼性（決定性、安定性）」「F: 忠実性（本番環境との類似度）」 | TW-smurf [一次: 読めたスライド] | テスト戦略を提案するときは、この 5 軸で長所と短所を比べる |
| 実装から離れた安定した層を狙う | 「リクエスト/レスポンスあたりを狙えると実装から距離を取りつつ安定したテストを書ける」 | TW-legacy [一次: 読めた箇所] | テストは公開された振る舞いに対して書く。内部構造に結びつけない |
| 内部実装のテストはリファクタリングを妨げる | 内部実装に依存するテストは「構造的結合が強い」。「テスト「できる」ことと「すべきである」ことは異なります」 | TW-priv [一次] | 同上 |
| 良いユニットテストの条件 | F.I.R.S.T のうち「Fast 高速である」など。独立していないテストは実行速度の点でもデメリットが大きい | TW-clean [一次] | テストは互いに独立させる。順序に依存させない |

### 1.4 テスト実装

| 原則 | 本人の言葉（要旨／引用） | 出典・印 | エージェント向け規則 [推論] |
|---|---|---|---|
| 一度に一つだけ | 「テストリストの中から「ひとつだけ」選び出し、…テストが失敗することを確認する」。全部を先にテストコードにしてから一つずつ通そうとするのは過ち | TW-canon [一次] | 失敗するテストは一度に 1 本だけにする。複数のテストをまとめて生成しない |
| 失敗を見てから進む | 同上。不具合修正でも「テストを実行し、失敗することを確認」してから直す | TW-canon / TW-bug [一次] | 赤の実行結果（コマンドと出力）を記録してから実装に入る |
| アサーションのないテストを書かない | 「コードカバレッジを上げるためだけに、アサーションのないテストコードを書いてしまうこと」は過ち | TW-canon [一次] | カバレッジを上げるためだけのテストは禁止する。どのテストにも期待値を書く |
| 実際の出力を期待値に貼らない | 「テスト対象を実際に動かしたときの値をコピーして、テストコードの中の期待値にペーストしてしまうこと」は過ち | TW-canon [一次] | 期待値は仕様から導き、根拠（計算や仕様の該当箇所）を示す |
| 本番のロジックをテストで再実装しない | 本番コードの計算式をそのまま期待値に使う「自作自演」は、コードが誤っていても通る | TW 開発生産性の観点から考える自動テスト 2024-06 / YAPC::Hiroshima 2024 のコード例 [二次: スライドの復元] | 期待値は具体的な値で書く。本番と同じ式で計算しない |
| 失敗したときの情報を設計する | `assertTrue(x == 40)` は失敗しても情報が少ない。`assertEquals` なら実際の値が出る | TW 自動テスト実行結果の目的を整理する 2024-03 [二次: 読めたのはコード例と見出し] | 比較のアサーションを使い、失敗時に期待値と実際の値が出るようにする |
| AI が頻繁に回す時代こそ失敗時の情報量が大事 | power-assert の新フォーマットについて、「AIエージェントが自動テストを頻繁に実行して判断する時代こそ、テスト記述の容易性とテスト失敗時の情報量の両立が必要と思い」 | TW-2025 [一次] | 同上。エージェントが次の行動を決められるだけの失敗メッセージにする |
| 非決定性を固定する | 「自動テストの決定性を担保するため 値を決め打ちする」 | TW-legacy [一次: 読めた箇所] | 乱数・時刻・並行性に依存するテストは、値を固定するか注入してから書く |

### 1.5 実装

## 3. AI コーディングエージェントについての発言

### 3.1 和田卓人

- **協業の 2 つのモード** [一次: TW-ai-tdd の読める部分]: 伴走モード（対話しながら直列に進める）は「決定論的ではあるものの、人力であるためスケールしない」。委託モード（自走するエージェントに並列で任せる）は「非決定論的で結果が確率的ではあるものの、非常によくスケールする」。委託モードではレビューが課題になる。
- **ハルシネーションは機能** [一次: TW-ai-tdd]: 「ハルシネーションは「バグ」ではなく機能。模倣エンジンの必然的帰結」。だから、言うことを聞かせる方法には限界があり、聞かなくても問題が起きない仕組みにすべきだ、という論理である。
- **レビューが担っていた厳密さの移り先** [一次: TW-ai-tdd / TW-ase26]: 上流の仕様レビュー（EARS、デシジョンテーブル）、「第一級の成果物としてのテストスイート (TDD)」、型システムと制約によるガードレール、ビジネスへの影響度に基づくリスクマッピング、継続的な理解（ペアプロ・モブプロ）。
- **伴走ワークフロー** [二次: TW-ai-tdd のスライドの要約]: 対話で設計 → 設計書（Design Doc、ADR）をレビュー → タスクリスト → サブタスクを TDD の順に並べる → タスクごとのブランチ → マージ前に全体をレビュー → 学びを議論に戻す。
- **AI Slop** [二次: TW-ai-tdd]: 2025 年の課題として「AI Slop: もっともらしい出力による、他者へのレビュー負担押しつけ」を挙げている。
- **認知負債と意図負債** [一次: TW-debt26 の読める引用]: 生成 AI は「生産」と「理解」を切り離す。Ward Cunningham の比喩から 34 年経って「構図が逆転し、より手強くなった」。将来の中核スキルは「システムが何をするもので、なぜそうなっていて、どう進化できるかについての正しい理解を維持すること」かもしれない。
- **実践の記録** [一次: TW-cc、2026-10-28]: Skills も CLAUDE.md もない素の Claude Code で、古典的 TDD を回した。テストリストの差し戻し、fail fast の採用、TDD のステップごとのコミット、混ざったブランチの分割といった判断は、人（t-wada）が行っている。
- **普及と意味の薄まり** [一次: TW-2025 が引用する X 投稿 2025-12-31]: 「2025年は自動テストが最も普及した年になったと感じます」。理由は「学習コストと実装コストをAIエージェントが大幅に削減したから」。ただし「「意味の希薄化」も激しい」。
- **Vibe Coding** [二次: エンジニアtype の取材記事]: 「バイブコーディングはエンジニアのためのものではない」。
