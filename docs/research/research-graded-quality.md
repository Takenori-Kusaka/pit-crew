## 0. 要点

1. **「段階で測る」先例は 4 つの型に分かれる。** (a) 隠した実行検査の通過の割合を種類ごとに出す（SWE-bench の FAIL_TO_PASS / PASS_TO_PASS、SlopCodeBench の Core / Error / Functionality / Regression、OmniCode の書式の点）、(b) 終了状態のコードを計量する（SlopCodeBench の構造の劣化・冗長）、(c) 既知の正解項目に対する当たり外れ（レビューの recall / precision、エージェントが書いたテストが既知の悪いパッチを落とすか、範囲外の操作の罠）、(d) 人か LLM が全体を読んで評定する（METR の 5 軸、保守者のマージ判定、ルーブリック judge）。**人のラベル無しで計算でき、文面を読まずに済むのは (a)(b)(c)** [一次: §A の各原典。型の分け方は推論]
2. **(d) の型は、人が基準のときにだけ妥当性の証拠がある。** METR の 5 軸も保守者 4 人のマージ判定も、採点したのは人で、LLM の判定器との照合は載っていない [一次]。LLM の判定器は、**「正解項目に当たったか」を聞く形（κ 52.8〜62.0、人どうし 56.3〜62.6）のほうが、点数を付けさせる形（κ 31.0〜44.9）より人に近い** [一次: SWR-Bench]。品質の低下を仕込んだ答えを、評価用 LLM は平均で半分以上見逃した [一次・要旨: Doddapaneni ら]。別系統のモデルでも、両方が誤るとき 60% は同じ誤りをする [一次・要旨: Kim ら]
3. **既定スキルは、候補の軸のほぼ全部を「行為として」指示している。** 範囲を守る・期待値のあるテスト・差分に限ったミューテーション・lint と型検査・設計書の追随・同じ型を探す・弱化しない、はどれもスキルの本文にある（§B の表に行番号）。「スキルが明示しない軸」に厳しく絞ると、残るのは **隠した検査での挙動の正しさ（段階）、隠した回帰、構造の劣化と冗長（スキルは一部だけ触れる）、後続の変更のしやすさ、費用** だけになる [一次: スキルの行。絞り方は推論]
4. **したがって分けるべき線は「スキルが触れているか」ではなく「採点器が何を読むか」になる** [推論]。スキルが「書け」と言った物（対応表・判定記録の欄・`path:line` の書式・PR 本文の欄・状態ファイル）の有無や形を数える項目は汚染。スキルが行為を指示していても、**エージェントが見ていない検査を終了状態に対して実行した結果**は、書くだけでは上がらない。ただしこの場合の差は「言われたからやった」効果を含む（Overeager の著者が同じ問題を「宣言の文面への反応」と呼び、同意文あり / なしの対で測った [一次]）。どちらの読みを採るかはオーナーの決定事項（§F-1）
5. **段階にしても、余地は課題からしか来ない。** 手作りの小さなセルでは、段階の値も上に張り付く（fix のプロセス準拠は 0.95〜0.99 [一次: `runs/2026-11-12/exp45-analysis.json`]）。外部で強いモデルに余地が残っている設定は、積み増しの長い課題（SlopCodeBench: 最良でも区切りの 14.8%、Opus 4.5 の core 67.3%）、保守者の基準（自動採点より 24.2 ポイント低い）、PR 単位のレビュー（F1 約 20%、正解項目が 5 件以上の PR で recall 8.88%）、テストを書く課題（最良 20.9%）、範囲の推し量り（Claude Code × Sonnet 4.6 で 27.7%）[一次]。**Opus 5.5 級での値は、どの原典にも無い** [未確認]
6. **課題の出どころの見込み（公開リポジトリ Takenori-Kusaka/ganbari-quest、gh で数えた）:** マージ済み PR 2,322。fix 型の issue で PR と結び付いて閉じたもの 514、うち critical 67。題名に hotfix を含むマージ済み PR 53、revert 3、題名に「再発」の issue 64。レビュー後に手直しが入った形跡は、PR 500 本の標本で 47 本（人の作成 435 本中。うち 800 行・20 ファイル以下が 34 本）。**正式な「changes requested」は 500 本中 1 本**しか無く、差し戻しはラベルとコメントで行われている [一次: §C-1。数え方の限界つき]
7. **少数での検出力（§D、計算）:** 課題を対にして課題を誤差の単位にすると、検出できる最小の差は、**6 課題 × 3 試行で全体の標準偏差の 0.8〜1.2 倍、10 課題 × 3 試行で 0.5〜0.8 倍、20 課題 × 5 試行で 0.3〜0.5 倍**（課題内の相関 0.3〜0.7、課題 × arm の交互作用が残りの分散の 25% のとき。有意水準 5%・検出力 80%）。試行を増やしても、交互作用が作る床（10 課題で 0.4〜0.6 倍）より下には行かない [推論・計算。台本 `_scratch-graded-quality/mde.mjs`]。標準偏差そのものは、段階の品質の値がまだ無いので仮定（0〜1 の尺度で 0.15〜0.25）[未確認]
8. **「この測度は書式ではなく品質を映している」を偽とする観測を先に決めておける**（§E-2）。要は 3 つ: スキルが求める書き物を全部そろえ中身は何もしない台本が床より上に出たら偽 / 同じ中身を別の書き方にして値が動いたら偽 / 既知の悪い版が良い版より下に並ばなかったら偽 [推論]

## A. 品質の軸の目録（先例・計算・妥当性・失敗の形・文面の汚染）

「汚染」の列は、その軸の値が**エージェントの書いた文章の形**に依るかどうか。スキルの文面との照合は §B。

| 妥当性の証拠 | 査読者の人数、保守者かどうかは本文に無い。著者は時間の見積りを「very rough/high variance, subjective」と書く。標本は小さい | [一次] |
| 後続（2026-03-10） | SWE-bench Verified の 3 リポジトリで保守者 4 人（scikit-learn 2、Sphinx 1、pytest 1）が AI の PR 296 件と人の正解 47 件を判定。自動採点は保守者のマージ判定より平均 **24.2 ポイント（標準誤差 2.7）高い**（人の正解パッチのマージ率 約 68% で正規化。正規化なしは 34.9）。却下の区分は code quality / breaks other code / core functionality failure / other。「マージ可能までの進み具合」の % も付けている（正解パッチの平均は約 90%） | [一次] METR 2026-03-10 |

pit-crew から見た要点 [推論]: 5 軸は「何を見るか」の一覧として使える。ただし METR の値は人の判定で、機械だけで同じ値を出した先例ではない。5 軸のうち lint・型、テスト、中核機能は実行で測れる（A-2・A-4）。文書と「その他の品質」は、機械では A-3・A-7 の代理か judge になる。

### A-2 SWE-bench の系統: テストの先にあるもの

| 測度 | 何を測り、どう計算するか | 妥当性・失敗の形 | 水準 |
|---|---|---|---|
| FAIL_TO_PASS / PASS_TO_PASS | 直す前に落ち直した後に通るテストと、前後とも通るテスト。「all tests across FAIL_TO_PASS and PASS_TO_PASS pass」で解決。後者は「does not break or violate any existing expected behavior」のため。値は課題ごとに 2 値 | 通ったパッチの多くは保守者が受け取らない（A-1）。2 値のまま | [一次] Jimenez ら arXiv 2310.06770（付録 A.4・A.5） |
| 差分テスト（PatchDiff） | テストに通ったパッチと正解パッチの**挙動の差**を出すテストを自動で作る。通ったパッチの 29.6% に差が出た。手で見ると、差のあるパッチの 28.6% は確かに誤り。解決率は 6.2 ポイント水増し | 差 = 誤りではない（正解パッチが偶然入れた挙動、意図が不明な入力がある）。裁定に人を使っている | [一次・要旨] Wang ら arXiv 2503.15223。後段の読みは [二次]（arXiv 2611.10837 の検索抜粋） |
| SWE-Lancer | Upwork の実際の発注 1,400 件超・総額 100 万ドル。個人の課題は「end-to-end tests triple-verified by experienced software engineers」、管理の課題は実装案の選択を「the choices of the original hired engineering managers」と比べる。成績を金額に写す | 写し方は要旨に無い。金額は難しさの重みで、品質の段階ではない [推論] | [一次・要旨] arXiv 2502.12115 |
| 区切りごとのテスト（SlopCodeBench） | テストを Core（仕様に書かれた挙動）/ Error（失敗の扱い）/ Functionality（隠した網羅）/ Regression（前の区切りの全テスト）に分け、strict（全部通る）・ISO（回帰以外）・CORE の 3 段で報告 | 同じ課題で strict 14.8% / ISO 28.1% / core 67.3% と段が開く = 種類を分けると段階になる [推論] | [一次] arXiv 2603.24755 |
| 進化の重み付き（SWE-CI） | 100 課題、平均 233 日・71 commit の実際の履歴。各回の「通るテスト数の変化を正規化した値」を、後の回ほど重く平均する（EvoScore、γ ≥ 1） | 「保守しやすさは、機能の正しさが時間とともにどう変わるかに表れる」という前提に立つ。前提の検証は開いていない [未確認] | [二次] arXiv 2603.03823（検索の抜粋） |
| OmniCode | 4 種の課題（不具合修正 / テスト生成 / レビューへの対応 / 書式の修正）、1,794 課題。**レビューへの対応**は「誤ったパッチ + レビュー」を渡し、通常のテストで採点（SWE-Agent で 4.5〜52.2%）。**書式**は、テストが 1 つでも落ちれば 0、そうでなければ max((直した違反 − 新しい違反) / 元の違反, 0) | レビューは LLM（Gemini 2.5 Flash）が正解パッチを見て書いた合成。悪いパッチも LLM 製。人の点検は一部だけ | [一次] arXiv 2602.02262 |

pit-crew から見た要点 [推論]: 「通過率を検査の種類ごとに分けて報告する」は、人のラベル無しで段階を作る最も確かな道。ただし検査は隠しておく必要があり（エージェントが見た検査に合わせると近道になる。`research-ecological-validity.md:148` の ImpossibleBench）、検査の質そのものに点検が要る（SWE-bench Verified では 61.1% の検査が正しい解を不当に落とすと判定された。`research-practice-gap.md:572`）。

### A-3 構造の劣化と冗長（SlopCodeBench）— 定義の原文

- **構造の劣化（erosion）**: 「the fraction of the codebase's total complexity mass that resides in high-complexity functions」。各関数の質量 = 循環的複雑度 × √(行数)。循環的複雑度が 10 を超える関数の質量の合計 ÷ 全関数の質量の合計。閾値 10 は Radon の区分による [一次]
- **冗長（verbosity）**: 「the percent of lines that are either flagged by ast-grep patterns or are structural duplicates」。ast-grep の 137 規則に当たる行と、構造の重複（クローン）の行を、行数で割る。重なる行は 1 回だけ数える。0〜1 [一次]
- 規模: 36 問・196 区切り・15 モデル。劣化は 77%、冗長は 75.5% の軌跡で上がる。人のリポジトリ 473 本と比べ、劣化は 2.0 倍、冗長は 2.3 倍。人のリポジトリでも 53% は劣化が上がる [一次]
- 指示の効果: 「冗長と作り込みの型を避けよ」（anti-slop）と「先に計画を書け」（plan-first）は、初期の劣化と冗長を下げる（劣化は最大 57.6% 減）が、strict の解決率は平均 2.4 / 3.6 ポイント下がり、費用は約 12.1% 上がり、区切りを追うごとの悪化は続く [一次]
- **妥当性の証拠: 人の評定との照合は無い。** 閾値と 137 規則は経験則で、著者は 2 つの失敗の型を狙った測度だと位置づける。言語は Python だけ [一次]
- 失敗の形 [推論]: 必要な複雑さ（状態機械・解析器）を罰する。関数を機械的に割れば下がる。規則に当たらない冗長は見えない。pit-crew の題材（bash・JS）にそのまま使える道具があるかは [未確認]
- 汚染: 文章を読まない。コードだけを見る。ただし「短く書け」と言えば下がる種類の量で、指示への反応は上に示したとおり実測されている [一次]

| **CRScore**（Naik ら、NAACL 2025）| 参照なし。LLM（6.7B）が差分から「主張」を作り、静的解析が smell を出す。これを擬似参照にする | レビューの文と擬似参照の埋め込み類似度（閾値 0.7314）。conciseness = precision、comprehensiveness = recall、relevance = 調和平均 | 人の評定との Spearman **0.5431**。GPT-4o の judge は 0.605。システムの順位では 0.95。LLM の主張の約 17% は誤りか検証不能 | — | [一次] arXiv 2409.19801 |

| **c-CRAB**（2026）| 人のレビューコメントを LLM が実行できるテストに変える（直す前に落ち、後に通る。2 人が 50 件を見て一致 84%）。184 PR・234 コメント | **レビューの文章を採点しない。** レビューを決まったコーディングエージェント（Claude Code、Sonnet 4.6）に渡してパッチを直させ、テストが通れば「役に立った」 | 著者自身が「the outcomes may reflect not only the quality of the reviews but also the capability of the agent」と書く。偽陽性は測っていない | Claude Code 32.1%、4 道具の和集合で 41.5% | [一次] arXiv 2603.23448 |
| **CR-Bench**（2026）| SWE-bench の修正から git blame で不具合を入れた PR を特定。584 件（確認済み 174）| LLM（Claude Sonnet 4.5）が各コメントを BUG_HIT / VALID_SUGGESTION / NOISE に分ける。recall、precision、usefulness、SNR = (当たり + 妥当な提案) / 雑音 | **判定器と人の照合は載っていない** | recall 27〜33%、precision 3〜5% | [一次] arXiv 2603.11078 |
| 業者のベンチマーク（Macroscope、Martian ほか）| 実際の不具合を入れた commit + 欠陥の無い対照 | recall と precision | 業者ごとに別のデータで自社が勝つ、という指摘がある | — | [二次] 検索の抜粋のみ |

pit-crew から見た要点 [推論]:
- レビューの品質を段階にする先例は「正解項目への recall」と「欠陥の無い PR での偽陽性」の 2 本立てで一致している。指摘の無い PR を半分入れるのは SWR-Bench と同じ形で、pit-crew の「回す正解と直す正解を半々」（`subjects/fix-skill-default/skills/fix/SKILL.md` の「過剰な上げも誤り」）と同じ向き。
- **当たり判定は、レビューの文章を読む。** 位置を `path:line` で書く arm が有利に読まれる危険は、fix で起きた誤り（返信の文面を表の形で読む、`docs/claims.md` M-2）と同じ形。c-CRAB の「文章を読まず、後段に渡して実行で測る」は、この危険を避ける唯一の先例。代わりに後段のエージェントの力が混ざる。
- 正解項目が多い PR ほど recall が大きく下がる（38% → 9%）のは、**1 本の PR に欠陥を複数入れると余地が出る**ことを示す。

### A-5 エージェントが書いたテストの効き目（ミューテーション・テストの十分さ）

| 先例 | 計算 | 妥当性・失敗の形 | 水準 |
|---|---|---|---|
| ミューテーション点 | 落とした変異 ÷ 全変異。TestGenEval は実行の成功・網羅率・ミューテーション点で採点（例: GPT-4o の素の生成で網羅 34.8%・ミューテーション 18.4%）| 大規模な実証（CoreBench・Defects4J）で、**テスト群の大きさをそろえると、ミューテーション点と実際の欠陥の検出の相関は弱い**。ただし点の高い群は欠陥の検出が有意に良い | [二次] TestForge arXiv 2503.14713 の検索抜粋 / [二次] Papadakis ら ICSE 2018 の要旨の検索抜粋 |
| 既知の悪いパッチを落とすか（OmniCode）| テストは「passes for the gold test, but fails for all bad patches」のときだけ正解。悪いパッチは 1 課題あたり 3 つを目標（失敗したエージェントの試み + LLM による正解の改変）| 悪いパッチの質は 100 件の標本の分類だけ。最良 20.9%（Java）| [一次] arXiv 2602.02262 |
| SWT-Bench | 課題の再現率（issue reproduction rate）と網羅の変化。書いたテストで修正候補をふるうと SWE-Agent の precision が 2 倍 | 要旨だけ。計算の詳細は開いていない | [一次・要旨] arXiv 2406.12952 |

汚染: テストの**ファイル**を実行するので文章は読まない。ただし既定の Dev スキルは「差分に限ったミューテーション」を指示している（§B）。

### A-6 範囲（頼まれていない変更・操作）

- **Overeager**（Qu ら、arXiv 2605.18583）: 無害な依頼（「片付けて」）で、許可の範囲を超える操作をしたかを**決定的な罠の述語**（終了状態・ファイルの前後・イベント列）で判定する。LLM の判定器は使わない。500 場面・約 7,500 run・4 製品・6 モデル。完遂率（70〜75%）とは別に報告する [一次]
- 場面の受け入れ: 慎重 / 中庸 / 攻撃的の 3 つの**台本**に対して、罠が単調に反応することを作る時点で確かめる（behavioral-gradient validator）[一次]
- 人との照合: 50 件の再注釈で κ = 0.73、規則の precision 0.76・recall 1.00 [一次]
- 結果: Claude Code × Sonnet 4.6 で 27.7%。同じモデルが OpenHands では 1.1% — **差を作るのはモデルより足場** [一次]
- **測定上の指摘（この調査の問いに直結）**: 範囲を課題文に明示すると「the agent stops inferring boundaries and starts pattern-matching declaration text」。そのため同意文あり / なしの対で測る。同意文を消すと Claude Code × Sonnet 4.6 で 3.9% → 15.8%（76 場面）[一次]
- 限界: 罠は宣言できる述語に限る。シェルを通らない経路は範囲外。run を独立とみなし、まとまりの補正をしていない [一次]
- Anthropic の先例: 実際の Claude Code の記録を、破壊的な操作の直前で切って続きを引き直し、破壊的かを LLM が判定する（§C-2）。2 値の判定で、品質の段階ではない [一次]

### A-7 保守しやすさの計量（既存の指標）

- Sjøberg・Anda・Mockus（ESEM 2012）: 同じ機能を実装した 4 つのシステムに、Maintainability Index・構造の指標・code smell 2 種・規模を当て、開発者 6 人に保守課題 3 つをさせた実測と比べた。「The metrics were not mutually consistent. Only system size and low cohesion were strongly associated with increased maintenance effort.」「The choice of metrics, rather than actual maintainability, may determine the outcome of a study.」[一次: 著者の所属機関の PDF を抽出サービス経由で]
- 多くの指標は規模との相関で説明できる、という指摘がある [二次: Chowdhury ら arXiv 2205.01842 の検索抜粋]
- pit-crew から見た要点 [推論]: 複雑度・重複・MI を「品質」として主の量に置くと、指標の選び方が結論を決める危険がある。A-3 の 2 指標も同じ系統で、人の基準との照合は無い。**使うなら補助の量として、規模（変更行数）と並べて報告する。**

### A-9 費用と軌跡の効率（補助）

- 精度だけでなく費用を並べて報告せよ、という指摘（AI Agents That Matter、HAL）[二次: `research-practice-gap.md:575-578` が要旨を一次で引く]

### A-10 LLM の判定器（ルーブリック・点検表・参照つき・対の比較）

| 型 | 先例 | 分かっている妥当性 | 水準 |
|---|---|---|---|

判定器の既知の偏り（本リポジトリの調査が既に一次で引いているもの。繰り返さず行だけ指す）[二次]:
- 偽の参考文献を足すと判定が動く（Claude-3 で 0.70）、自己申告のコメントで正答判定が最大 34.3 ポイント動く（`research-process-evidence-evaluation.md:279`）
- 出所のラベルだけで判定が動き、盲検で消える。自己選好は「自分の文を見分ける」と「見慣れた文を好む」の両方から来る（同 `:284`・`:297`）。**ハーネスの arm が Claude の書いた型で書かせると、その文は Claude の判定器に見慣れた文になる**（同 `:297`、[推論] の印つき）
- ルーブリックを報酬にすると、網羅・存在の基準だけが伸び、正しさと全体の質が下がる（Mahmoud ら。同 `:68`）
- 判定器の多数決・一致率は検証にならない（条件付き独立が破れる。`research-machine-only-rationale-evaluation.md` 結論 3）

系統を越えた誤りの相関 [一次・要旨]: Kim ら（ICML 2025、arXiv 2506.07962）「on one leaderboard dataset, models agree 60% of the time when both models err」「larger and more accurate models have highly correlated errors, even with distinct architectures and providers」。判定器として使ったときの数値は要旨に無い。**別系統の判定器を足すと誤りがどれだけ減るかを直接測った値は、今回開いた範囲に無い** [未確認]。

- 「PR → 差し戻し → 手直し」の組（QM と fix の課題の素材）は、500 本あたり 30〜50 本、うち 1 セッションで扱える大きさは 30 本強。全 2,322 本に同じ率を当てると 150〜220 本だが、**標本は更新順で無作為ではなく、8 月より前の運用が同じとは限らない**。

- 正式なレビュー機能がほぼ使われていないので、差し戻しの中身（何を指摘したか）は PR のコメントの文章から取り出す必要がある。機械で取り出すと SWR-Bench と同じ工程（LLM で抽出 → 一致したものだけ → 確認）になり、**その確認を SWR-Bench は人でしている** [一次]。

- **数えられなかったもの**: 各候補が強いモデルで実際に落ちるか（モデルを回していない）。差し戻しのコメントの中身。hotfix と元の PR の対応。

### C-2 実際のセッションの記録を切って引き直す（Anthropic の先例を一次で確かめた）

- **Claude Opus 5.5 のシステムカード**（公式 PDF、抽出サービス経由）[一次]: 社内の Claude Code の記録のうち、利用者の許可なしに、または明示の制約に反して破壊的に振る舞ったもの（実行中のジョブを止める、他人の commit の上に force push する、唯一の写しを消す）を使う。「We truncated each transcript to just before the destructive action and tested how different models would behave when continuing from that point.」各モデルから「a trajectory of up to eight actions」を引く。道具の応答は Opus 5 が模擬し、破壊的かどうかも Opus 5 が判定する。差は「paired t-tests (paired with respect to the prefill)」、区間はブートストラップ。
- **著者が書く限界** [一次]: 「models are more likely to act destructively when continuing prefills generated by prior instances of themselves due to selection effects」。破壊的な振る舞いは絶対数では稀（「we flag fewer than 1% of recent model sessions」）。
- **Claude Opus 4.6 のカード** [一次: 公式 PDF の検索抜粋]: 問題のある記録の引き直しで「5 samples per example」、Wilson の 95% 区間。元の記録を出したモデル（Sonnet 4.5・Haiku 4.5）は、結果が偏るので比較から外した。
- **Mythos Preview のカード** [一次: 公式 PDF の検索抜粋]: 破壊的な操作の直前で切り、各モデルから 1 手を引き直し、LLM が判定。別のモデルの記録から続ける（方策外）影響を見る追加の分析がある。
- pit-crew への当てはめ [推論]:
  - 先例が測っているのは**次の数手が破壊的かどうかの 2 値**で、品質の段階ではない。品質の段階に使うなら、切った後を最後まで走らせて終了状態に隠した検査を当てる形（§B の D-a・F-a）になり、その形の先例は今回開いた範囲に無い [未確認]。
  - 対にする単位が「切り口（prefill）」である点と、試行が少ない（1〜8 手、5 標本）点は、§D の設計と同じ。
  - pit-crew には実セッションの記録を軌跡に変える変換器と、1 回の spike がある（`00-goal-charter.md:75`）。**使える記録が何本あるか、切り口にできる失敗が何件あるかは、この調査では数えていない**（記録は非公開の側にあり、読んでいない）[未確認]。
  - ハーネスの比較に使うときの固有の問題: 切った記録は、あるハーネス（GQ の v0）の下で作られた文脈。別のハーネスの arm をその続きから走らせると、スキルが途中から入る形になり、「最初からそのハーネスで働いた場合」を測らない [推論]。

### C-3 散らかりの要素を合成の課題に足す（METR の 16 項目）

## D. 強いモデル × 少ない課題 × 少ない試行: 段階の値で何が言えるか

### D-1 設計の先例

### D-2 検出できる最小の差（計算）[推論・計算]

模型: 値 = arm の平均 + 課題の効果 + 課題 × arm の交互作用 + 試行の雑音。全体の分散を 1 とし、
- ρ = 課題の効果の割合（同じ課題の、別の arm の 2 試行の相関。依頼の「課題内の相関」をこう読んだ）
- λ = 残り（1 − ρ）のうち、課題 × arm の交互作用の割合（課題によって arm の効き方が違う度合い）

課題ごとの arm の差の分散 = 2(1 − ρ)(λ + (1 − λ)/R)、R は 1 arm・1 課題あたりの試行。T 課題の差の平均を、対の t 検定（自由度 T − 1）で見る。有意水準 5%（両側）、検出力 80%。値は**全体の標準偏差の何倍か**。台本は `_scratch-graded-quality/mde.mjs`（模擬 2 万回で、計算した差での検出力が 0.79〜0.80 になることを 3 行で確かめた）。

### D-3 標準偏差に何を置いたか（保存された要約から取れなかった）

- 試行ごとの分布（標準偏差）は、どちらのファイルにも無い [一次]。監査の報告 2 本にも、試行ごとの標準偏差の記載は見当たらない（鍵語の grep）[一次]
- したがって §D-2 の「標準偏差 0.15〜0.25」は**仮定** [未確認]。目安: 0〜1 の値が 0.6〜1.0 に固まっていれば標準偏差は 0.12〜0.15 程度、5 段の順序尺度で全段に散れば 0.3 を超える [推論]。**余地のある課題ほど標準偏差は大きくなり、点で見た検出下限も大きくなる。** ρ と λ も、段階の値で試走してみないと分からない
- 最初の試走で、課題 × arm × 試行の値から 3 つの分散成分を推定し、この表を実測で引き直すのが先（試走の値で arm の優劣は言わない）[推論]

### D-4 少数を支える他の道具 [推論。出典のあるものは併記]

- **ベイズの階層模型**（課題を乱数効果に）: 「B が A より高い事後確率」と差の区間を出せる。6 課題では、課題間の分散の事前分布に結果が左右される。事前分布と、それを変えたときの幅を一緒に報告する。「有意でない」と「良さそう」を分けて書ける（`research-next-steps-small-n.md:101`）[二次]
- **2 段の止め方**: 例「10 課題 × 3 試行で一度見る。差の区間が事前に決めた下限を超えていれば止め、そうでなければ決めた数まで課題を足す」。足すのは試行でなく課題（読み 1）。途中で見るぶん、各段の有意水準を先に割り振る
- **追う差の下限を先に決める**: 段階の値なら「0.1 点未満は追わない」のように書ける。これは 11-01 に提案され、以後使われていない（`research-practice-gap.md:498`）[一次]
- **順序尺度のまま使う場合**: 課題ごとに「どちらの arm が上か」を取る符号の検定は、6 課題なら 6 対 0 でようやく両側 p = 0.031、10 課題なら 9 対 1 で 0.021。段階の大きさを捨てるので検出力は下がる [計算]

### D-5 この規模では言えないこと [推論]

- 6〜10 課題では、**標準偏差の半分より小さい差は「ある」とも「無い」とも言えない**。差が見えなかったことを「同等」と書けない（同等を言うには、同等の幅を先に決めた別の設計が要る）。
- 結論は**その課題の集まり**についてのもの。別の題材・別の難しさへ広げる根拠にはならない（課題を乱数効果として扱っても、6〜10 個は 1 つの出どころからの標本）。
- arm が 3〜4 で軸が 5〜8 あると、比べる組は数十になる。主の軸と主の比較を先に 1〜2 個に絞らない限り、どれかが偶然に出る。
- 課題ごとの効果の違い（どの種類の課題でハーネスが効くか）は、この規模では推定できない。
- 「上げられない工程を明記する」（憲章 1.1）を、差が見えなかった軸の一覧で代えることはできない。

## E. 最も強い反対論と、主張を偽とする観測

### E-1 反対論

1. **段階にしても天井は動かない。** 段階の値は 2 値の検査の割合で、課題が易しければ割合も上に張り付く（fix の B が 0.95〜0.99 [一次]）。余地を作るのは測度ではなく課題で、強いモデルで余地が確認された設定（§0-5）はどれも作るのが重い。段階への切り替えは、G3 が通らない問題を名前を変えて残すだけになりうる [推論]
2. **行為を指示された軸の差は、能力ではなく「知らされたか」の差。** 既定スキルは範囲・テスト・ミューテーション・lint・文書を全部指示している（§B）。ハーネスなしの arm は、案件が何を重んじるかを知らされていない。Overeager の著者が示したとおり、範囲を明示すれば率は 4 分の 1 になる（15.8% → 3.9%）[一次]。これは `research-process-evidence-evaluation.md:15` の構成概念の混同と同じ形で、採点が終了状態になっても消えない [推論]
3. **コードの計量には、人の基準との照合が無い。** SlopCodeBench の 2 指標は著者自身が人の評定と照合していない [一次]。保守の実測と合ったのは規模と凝集度だけ、という研究がある [一次]。計量を品質と呼ぶ根拠は「先例が使っている」だけになる [推論]
4. **人を基準にしない妥当性は、感度しか示さない。** 仕込み・劣化版は「既知の悪化に反応する」を示すが、「尺度の向きが保守者の判断と合う」は示さない。合うことを示した先例（METR、SWR-Bench、CRScore、Overeager の κ = 0.73）は、どれも一度は人を使っている [一次]。人を入れない方針のままだと、主張は「仕込んだ悪化に対して単調」までで止まる [推論]
5. **判定器を足しても、同じ向きの誤りは残る。** 別系統でも、両方が誤るとき 60% は同じ誤り [一次・要旨]。評価用 LLM は仕込んだ品質の低下の半分以上を見逃す [一次・要旨]。判定器の再現性の高さは正しさを意味しない [一次]。ハーネスの arm が Claude の書いた型で書けば、Claude の判定器に見慣れた文になる [二次]
6. **後段に渡して測る型は、後段の力を測る。** c-CRAB の著者自身が認める [一次]。後段を弱いモデルにすれば費用は下がるが、良いレビューを活かせずに差が潰れる方向の偏りが入る [推論]
7. **測る軸が公開されると、スキルはその軸に合わせて書かれる。** ルーブリックを報酬にすると存在・網羅の基準だけが伸びる（Mahmoud ら）[二次]。このプロジェクトではスキルの作者と評価の設計者が同じ系統で、隠した軸を持てるかが問題になる [推論]
8. **憲章の品質の定義と向きが違う。** 憲章 1.1 の主の量は「規定したプロセスへの準拠と根拠の裏付け」で、最終結果は補助（`00-goal-charter.md:18`）。QM のスキルも「判定の正しさは結果論」と書く（`qm-review/SKILL.md:86`）。§B で生き残る軸はほぼ全部が**結果の品質**で、11-03 に主の量から外した側に戻る。11-13 の決定がこの定義を置き換えるのか、足すのかは決まっていない [一次 + 推論]
9. **少数。** §D。6 課題で見える差は、これまで観測された差の 2〜5 倍 [推論]
10. **実失敗の素材は、当時のモデルとハーネスの失敗。** いまのモデルで再現する保証は無く（本物の直前の文脈でも再発は 50% 未満。`research-ecological-validity.md:109`）[二次]、そのモデルに不利な選び方の偏りを持つ [一次]
