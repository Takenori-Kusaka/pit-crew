## 要点（先に結論）

1. **「きれいな課題では解けるが、現実の条件では落ちる」は、2025〜2026 年に何度も測られている。** テストに通った SWE-bench の PR の約半分は保守者がマージしない（自動採点より 24.2 ポイント低い）[一次: METR 2026-03]。実際の OSS の PR では、テストに通った 4 件を含め、手で見た PR は 1 つもそのままではマージできなかった [一次: METR 2025-08]。経験ある開発者が自分のリポジトリで AI を使うと 19% 遅くなった [一次: METR RCT]。課題の「散らかり度」（16 項目）が 1 点上がると、長さをそろえても成功率は約 8.1% 下がる [一次: METR 時間地平]。
2. **落ちる条件は、ほぼ「手作りの小さなセルが外したもの」と一致する。** 暗黙の要求（文書・テスト・書式・コード品質）、長い作業と自分の前の成果物の上への積み増し、セッションをまたぐ引き継ぎ、紛らわしい情報、時間や資源の圧力、取り返しのつかない操作、検証手段がないこと [一次: METR の 16 項目、SlopCodeBench、Anthropic の長時間ハーネス、Context Rot、PropensityBench]。
3. **実際の失敗から課題を作る作法は確立している。** SWE-bench（GitHub の issue と PR から）、Anthropic の評価の手引き（「実際の失敗から 20〜50 件」「バグ管理と問い合わせを見よ」）、Hamel Husain のエラー分析（記録を読んで分類し、飽和まで）、MAST（記録から失敗の型を作り κ = 0.88）[一次]。
4. **いちばん pit-crew に近い先行例は、Anthropic 自身の「実際の Claude Code の記録を、壊す操作の直前で切って続きを引き直す」評価。** 実際に起きた文脈をそのまま持ったまま、採点は「次の 1 手が破壊的か」に絞れる [二次: Mythos Preview システムカードの第三者変換]。ただし、実際に壊した直前の文脈を与えても再発率は 50% 未満で、どのモデルの記録から切ったかで結果が大きく変わる、と同カード自身が書く [二次]。
5. **実験室の値と現場の値の差は、方向も大きさも一定ではない。** 自動採点は能力を過大に見せる（METR、ABC の「最大で相対 100% の誤り」）[一次] 一方、Anthropic は「現場で使われている自律度は、評価で示される能力より低い」とも書く [一次]。差は測って補正するもので、仮定してはいけない [推論]。
6. **pit-crew で言い直すべきこと**: 「手作りの小さな 1 回きりの課題では、単一セッションで失敗が観察されなかった」までは言える。「モデルは規律を守る」「役割スキルは不要」は、生態学的妥当性の確認がないので**言えない**。天井は**セルの性質**であって、モデルの性質ではない [推論]。
7. **提案**: がんばりクエストの履歴（スキル・ADR・Issue が生まれるきっかけになった出来事）から、**実際の状態を持ったまま作る「実失敗セル」**を作り、失敗が再現したら**条件を 1 つずつ外して**どれが必要かを探る（抽象から現実へではなく、現実から抽象へ）。詳しくは末尾の提案。

## Q1. 抽象化しすぎて失敗の条件を落とさないために、評価の作り手は何をしているか。きれいな課題で通り、現実で落ちる証拠は何か

### 1-1 妥当性の枠組み

- **Bean ら「Measuring what Matters」（arXiv 2511.04703、NeurIPS 2025 D&B）**: 主要学会の LLM ベンチマーク 445 本を 29 人の査読者で点検。構成概念妥当性が低いと、高い点数は「無関係か、誤解を招く」と書く [一次: https://arxiv.org/abs/2511.04703v1]。点検の項目に表面・予測・内容・**生態学的**・収束・弁別の各妥当性を含む [二次: 検索結果の要約、https://syntheticsociety.oii.ox.ac.uk/research/measuring-what-matters]。比較に統計検定を使ったのは 16%、約半数は定義の争われる抽象概念を明確な定義なしに測っていた [二次: 同]。8 つの推奨と点検表を公開 [一次]
- **ABC（Zhu ら, arXiv 2507.02825）**: エージェントのベンチマークの点検表。**課題の妥当性**（課題の成功が測りたい能力に対応するか）と**結果の妥当性**（採点の合格が本当に課題の成功か）の 2 本柱。SWE-bench Verified のテスト不足、τ-bench で空の応答を成功と数える例を挙げ、こうした欠陥は性能を**相対で最大 100%** 見誤らせると書く [二次: 検索結果の要約。前回までの調査 `research-design-convergence.md` で一部を一次確認済み]
- **METR の「散らかり度」16 項目**（Kwa ら, arXiv 2503.14499 付録）: 実際の出どころ / 資源の制約 / 簡単にやり直せない / 取り返しのつかない誤りがありうる / 動く環境 / 反実仮想が難しい / 完全自動の採点でない / 暗黙の一般化が要る / 採点の説明が明示されていない / 最適でない振る舞いが付け込まれる / 検証の手段が与えられていない / 実時間の協調 / 自己修正が要る / 自己改善が要る / 情報を探す必要がある / 新しい状況。**長さをそろえても、散らかり度が 1 点上がると平均成功率が約 8.1% 下がる**（線形近似、b = −0.081、R² = 0.251、HCAST の課題）[一次: https://arxiv.org/html/2503.14499]。ただし散らかった課題でも、性能の伸びの傾きは散らかっていない課題と同じだった [一次: 同]
- 同じ論文は、保守者が自分のリポジトリで直す時間に比べ、外部の請負人は 5〜18 倍かかったと報告し、エージェントの性能は「保守者の時間で測った長さから予想されるより悪い」と書く [一次: 同]。**文脈を持っている人にとっての短い課題は、文脈のないエージェントにとって短くない** [推論]

pit-crew のセルを 16 項目に当てると、ほぼすべて「なし」になる（手作り・資源の制約なし・コンテナでやり直せる・完全自動の採点・採点の説明は依頼文で明示・検証手段あり・協調なし・新しくない）[推論]。METR の基準でいう「いちばん散らかっていない課題」で測ったことになる。

### 1-3 作り手が抽象化しすぎを避けるためにしていること

- **実際の出どころを使う**: SWE-bench は GitHub の実際の issue と PR の組から 2,294 件（12 リポジトリ）[一次: https://arxiv.org/abs/2310.06770]。SWE-Lancer は実際の発注と支払額 [一次]。METR は「実際の出どころ」を散らかり度の 1 項目にしている [一次]
- **全体（holistic）で採点する**: METR はテストの合否に加え、中核機能・テスト・文書・書式・品質の 5 軸で「そのままマージできるか」を見た [一次]。METR 2026-03 は実際の保守者の判断を基準にした [一次]
- **繰り返しの一貫性を見る**: τ-bench の pass^k、Anthropic の手引きの pass^k [一次]
- **長さ・積み増し・状態を入れる**: RE-Bench の時間予算、SlopCodeBench の区切り、Vending-Bench の長い運用、EvoWeb の累積 320 件の依頼（32 の Web アプリ、深い依存を持つ後半の依頼ほど不正確、実行時のエラーが回を追って増える）[一次: https://arxiv.org/abs/2610.16402v1]
- **非公開・汚染されにくい出どころを使う**: SWE-bench Pro の非公開セット [一次]
- **模擬と実地を対にする**: Vending-Bench と Project Vend [一次]。模擬だけでは「人間だと思い込む」型は出てこなかった（Project Vend の記事は模擬との点数の比較はしていない）[一次 / 比較の欠如は推論]

### pit-crew への示唆（Q1）

1. **セルごとに METR の 16 項目を付ける。** 今のセルはほぼ全部 0 点で、天井の結果は「散らかり度 0 の範囲で」と書き添える [推論]。
2. **天井の結果を「識別力のないセル」と読み替える。** METR・SlopCodeBench・RE-Bench の向きからすると、長さ・積み増し・暗黙の要求を入れたセルで単一セッションが天井のままである保証はない [推論]。
3. **採点を全体に広げる余地がある。** 今の決定的な採点は「禁止の操作をしたか」に寄っている。METR の 5 軸のように「暗黙の要求（文書・テスト・記録の書式・報告）を満たしたか」を最終状態で検査できる [推論]。
4. **1 回の合否でなく pass^k を見る。** 10 回中 10 回でも、長いセルでは 1 回の脱線が起きうる（Vending-Bench）。「10/10」を「一貫して守る」と書かない [推論]。

## Q2. 実際の失敗の履歴から評価の課題を作る方法。引き金になった文脈（状態・履歴・長さ・圧力）を保ったまま、決定的に採点できるようにするには

### 2-2 「切って引き直す」方式の注意点（Anthropic が自分で書いていること）

- 実際の破壊の直前の文脈を与えても、再び破壊する率は **50% 未満**。カードはこれを「破壊的な振る舞いは異常なことを示す」と読む [二次]。**本物の文脈を持たせても、失敗は確率的にしか再現しない** [推論]
- **どのモデルの記録から切ったか**で 2 つのモデルの差の大きさが大きく変わる（記録が自分のものでない＝方策外の prefill の影響）[二次]
- **選び方の偏り**: 「あるモデルが失敗した場面」を集めて作るので、別の場面で同じくらい悪い新しいモデルは良く見える。カードは「この種の続きの引き直しを使わずに網羅を上げる方法を調べている」と書く [二次]
- 評価されていることの察知は、続きを引き直す評価では低め（Mythos で 2.2%）と読める箇所がある [二次: 変換で段落が崩れており、どの評価の値か確実でない]

### 2-3 文脈を保ちつつ決定的にする要素の整理 [推論。各要素の根拠を併記]

| 保ちたい文脈 | 決定的に保つ方法 | 根拠 |
|---|---|---|
| リポジトリの状態 | 出来事の直前のコミットをそのまま固定（SWE-bench と同じ）| SWE-bench [一次] |
| 案件の約束・指示ファイル | 当時の CLAUDE.md・スキル・ADR をその版のまま入れる | 前回調査 C（届く場所が効く）[一次] |
| 会話の履歴・長さ | 実際の記録を切って prefill（Claude Code では保存したセッションを `--resume <id> --fork-session` で分岐できる。前回調査 C §4）| Mythos カード [二次]、CLI [一次: 前回調査 C] |
| 前のセッションの成果と引き継ぎ | 前のセッションが残したファイル（進捗メモ・未完の変更）を状態として置く | Anthropic の長時間ハーネス（進捗ファイル・git で引き継ぐ）[一次: Q3] |
| 圧力 | 当時の依頼文・締め切りの言葉をそのまま使う | PropensityBench（圧力の言葉で振る舞いが変わる）[一次: Q3] |
| 外部の相手（gh・CI）| 呼び出しを記録する偽物（shim）で、当時の CI の結果を返す | pit-crew の既存の作り（gh の記録）[推論] |
| 採点 | 出来事の「害」を最終状態の述語にする（例: force push した、同じ画像を Before / After に貼った、CI が赤のまま完了と報告した）| METR の全体採点、Anthropic の「決定的な採点器を可能な限り」[一次] |

### pit-crew への示唆（Q2）

1. **出どころを「設計者の想像」から「起きた出来事」に替える。** Anthropic の手引きの 20〜50 件、Hamel の 30 件は、pit-crew の規模に合う [一次 / 推論]。
2. **引き金の文脈は、状態（コミット）・指示ファイル（当時の版）・依頼文（当時の言葉）の 3 つを最低限残す。** 会話の履歴は記録が残っている出来事だけ（`--fork-session`）。履歴のない出来事で会話を作り話にしない [推論]。
3. **再現率は低くて当然と考える。** 本物の直前文脈でも 50% 未満（Mythos カード）なので、5 回で 0 でも「起きない」とは言えない。採否の基準を「1〜4/5 なら採る」から、「0/5 なら条件の欠落を疑い、条件を足す」に変える [推論]。
4. **選び方の偏りに注意する。** v0 の失敗から作ったセルは v0 に不利、v1 に有利に偏る。v0 と v1 の比較に使うときは、v1 の失敗からも同数作る、または出来事をハーネスと無関係な出どころ（顧客報告・CI の失敗）から取る [推論、Mythos カードの偏りの記述から]。

| 条件 | 測られた効果 | 水準 |

| **自分の前の成果の上に積み増す長い作業** | 構造の劣化が 77%、冗長化が 75.5% の軌跡で進む。品質の指示は水準を下げるが劣化の速さを変えない（SlopCodeBench）| [一次] https://arxiv.org/abs/2603.24755 |

pit-crew の EXP-06・07 との比較 [推論]:

### pit-crew への示唆（Q3）

1. **条件は 4 つに絞って入れる**: ①自分の前の成果への積み増し（2 セッション以上）、②引き継ぎ（進捗メモと未完の状態）、③紛らわしい情報（古い文書・似た規則・矛盾する指示）、④検証の繰り返しと圧力（テストを走らせて落ちる状態が続く）。どれも Docker の 1 試行の中で作れる [推論]。
2. **圧縮を条件に入れるなら、自然に起きる長さで。** 人工的に `/compact` を打つと、Anthropic の観察（引き継ぎで指示が抜ける）を再現しているのか作り物かが区別しにくい [推論]。
3. **「中止して報告する道」の有無を要因にする。** ImpossibleBench では GPT-5 で大きく効いた [一次]。pit-crew のセルは報告の道が明示されていた可能性があり、それが天井の一因かもしれない [推論、セルの文面の確認が要る]。

## Q4. 実験室の評価を現実に合わせて較正するには

### 4-1 先行例

- **実験室の採点と現場の判断を同じ素材で比べる**: METR 2026-03 は、同じ PR を自動採点と保守者の判断の両方にかけ、**人の正解パッチの合格率で正規化**した（保守者は人の正解パッチでも 68% しかマージしない）[一次]。現場の判断にも雑音があり、その雑音の床を測ってから差を出している [推論]
- **模擬と実地を対にする**: Vending-Bench と Project Vend [一次]
- **実際の記録を地の真実に使う**: Mythos カードの「実際の Claude Code の記録から切る」評価 [二次]。Anthropic の福祉の節では、実利用の分布（Clio）に基づいて合成課題を作り、現実らしさで絞った [二次: 同カード]
- **現場の比率を取る**: 実際の GitHub での AI エージェントの PR のマージ率を集めたデータ（AIDev, arXiv 2507.15003、456,000 件超）。初版は人 76.8% に対しエージェントは 35〜64% と報告。後の研究は同じデータで違う率を出しており、版と絞り方で大きく変わる [二次: 検索要約。数値は引用しない方が安全]
- **ずれの原因を分ける**: METR 2025-08 は差の候補を「採点の範囲（テストだけ）」「成熟したリポジトリの高い基準」「課題の選び方（テストの多い PR）」「足場の弱さ」に分けて書いた [一次]
- **ロボティクスの「現実との差」**: 模擬の見た目を十分にばらつかせると、現実が「ばらつきの 1 つ」に見える（領域のランダム化、arXiv 1703.06907）[一次]。pit-crew では、本質でない要素（依頼の言い方、リポジトリの雑音、規則の書き方）をセルごとにばらつかせる考え方に当たる [推論]。前回調査 C の HANDBOOK.md（規則の値を課題ごとに変異）も同じ向き

### 4-2 較正の型（pit-crew で使える形）[推論]

| 型 | やること | 何が分かるか |
|---|---|---|
| 再現の較正 | 実際に起きた出来事から作ったセルを、**当時に近い条件**（当時のハーネス v0、可能なら当時に近いモデル）で走らせ、失敗が再現するか | セルが現実の失敗を拾えるか（感度）。拾えなければ条件が欠けている |
| 頻度の較正 | 現場の出来事の率（例: N 本の PR あたり何回、役割の逸脱が観測されたか）と、セルの失敗率を並べる | 実験室が現場より甘いか厳しいか。分母のない「何回起きた」は使わない |
| 差の較正 | v0 と v1 の差を、実験室と現場（v1 を実際の案件に入れた前後の出来事の率）で比べる | 実験室で見えた差が現場でも同じ向きか（外的妥当性の確認）|
| 陰性の較正 | 現場で一度も起きていない型のセルで失敗が出たら、セルの作り物を疑う | 偽の失敗（特異度）|

### pit-crew への示唆（Q4）

1. **現場の分母を先に作る。** がんばりクエストの履歴（ADR・Issue・PR）から、型ごとに「何本の PR / 何日で何回」を数える。ADR-0056 の「観測 42 件」のような件数は、分母（その期間の PR 数）とセットにして初めて較正に使える [推論。42 件という数は、がんばりクエストの `docs/decisions/README.md` の ADR-0056 の行の記述による]。
2. **実験室の失敗率が現場より高すぎる・低すぎるときの扱いを事前に決める。** 現場で月 1 回の型が実験室で 5/5 なら、セルが作り物の可能性を先に疑う [推論]。
3. **最終的な外的妥当性の確認は、現場に入れること。** v1 を実際の案件（がんばりクエスト、または 2 つ目の案件）に入れ、出来事の率の前後を比べる。時系列の前後比較は交絡が多いので「向きが合うか」の確認にとどめる [推論]。

## 提案: 案件の履歴から「実失敗セル」を作り、採点できるまま保つ手順

### 前提 [推論]
- 予算は数十回、Harbor + Docker、決定的な採点 + 記録を読む、サブスクの枠。並行実行はしない（2026-11-01 のメモリ不足）
- 方向を逆にする: これまでは「抽象的なセルを作り、条件を足して失敗を出そうとした」。今後は「**実際の条件を全部持ったセルから始め、失敗が再現したら条件を 1 つずつ外して、どれが必要かを探る**」

### 手順

**段 0: 出来事の台帳を作る（モデルを使わない）**
- がんばりクエストのスキル・ADR・Issue・PR のうち、「出来事が起きて、それを防ぐために作られた」ものを列挙する。候補は CLAUDE.md・`docs/decisions/README.md` に書かれているもの [一次: リポジトリ内文書]:
  - QM の役割の逸脱（ADR-0056、観測 42 件 → ADR-0068 で hook を外す）
  - rebase 後に SS を撮り直さず Before / After が同じ画像のまま（#2063、PR-2054 で 3 回連続）
  - 致命修正のコミットが force push で消える（ADR-0026）
  - 「全対応完了」と宣言したが未完（ADR-0060）
  - pre-ready の PASS を CI 緑と読む（#4390）、検査が skip されたのを PASS と読む（#4084）
  - 142 ファイルの docs 一括変更で機械的な誤変換が混入（#2223）
  - LP の SS が本番と乖離（「PO 直接指摘 8 回連続再発」、#1893）
- 各出来事について 1 行ずつ: 何が起きたか（観察できる害）、そのときの状態（コミット・ブランチ）、指示ファイルの版、依頼の言葉、長さ（何セッション目・何時間目）、関わった役割、記録が残っているか
- METR の 16 項目と、本調査 Q3 の条件（積み増し・引き継ぎ・雑音・圧力・中止の道）で印を付ける

**段 1: 採点の述語を先に決める**
- 害を最終状態の述語にする。例: 「`git push --force` が呼ばれた（shim の記録）」「Before と After の画像の blob が同じ」「CI の結果が赤なのに『完了』『全対応』の報告をした」「Issue を閉じたが AC が未チェック」
- 台本の対照（何もしない / 正しい / 害をなす / 近道）で述語が作ったとおりの区分を出すことを、モデルを呼ぶ前に確かめる（これまでどおり）
- 述語にできない出来事（「分かりにくい」等）は今回は使わない

**段 2: 忠実度の高いセル（L1）を作る**
- 当時のコミットを固定し、当時の CLAUDE.md・スキル（v0）をその版で入れる。秘密情報を抜き、顧客データを合成に置き換える
- 依頼は当時の言葉（Issue 本文、PR のコメント、オーナーの指示）をそのまま
- 履歴が残っている出来事は、当時の記録を害の直前で切って `--fork-session` で続ける版（L2）も作る。残っていなければ作り話で埋めない
- 引き継ぎが要る出来事は、1 試行の中で 2 セッションを順に走らせる（前のセッションの成果を状態として残す）

**段 3: 再現の確認（各 5 回、v0、ハーネスあり）**
- 1〜5/5 で失敗 → 現実の条件を持つセルとして採る
- 0/5 → 再現しない。条件の欠落（台帳の印のうち入っていないもの）を 1 つ足して 1 度だけやり直す。それでも 0 なら「今のモデル・今の版では再現しない」と記録する（「起きない」とは書かない。Mythos カードでも本物の文脈で 50% 未満）

**段 4: 条件を外す梯子（再現したセルだけ）**
- 必要な条件を 1 つずつ外し（長さ → 引き継ぎ → 雑音 → 圧力 → 指示ファイルの版）、各 5 回。失敗が消えた条件が「引き金」
- ここで得た「最小の引き金を持つセル」が、これまでの小さなセルの作り直しになる。抽象化の程度が、データで決まる

**段 5: ハーネスの比較に使う**
- 引き金を持つセルで、単一セッション / v0 / v1 を比べる。選び方の偏りを避けるため、v0 の失敗から作ったセルだけで v1 の優位を主張しない（v1 の失敗、またはハーネスと無関係な出どころ — CI の失敗、顧客報告 — から作ったセルを同数入れる）

**段 6: 現場との較正**
- 段 0 の台帳で型ごとの現場の率（分母つき）を出し、段 3 の再現率と並べる
- v1 を実際の案件に入れたら、型ごとの出来事の率の前後を記録する

### 予算の目安 [推論]
- 段 3: 出来事 6 件 × 5 回 = 30 回
- 段 4: 再現した 2〜3 件 × 外す条件 3〜4 × 5 回 = 30〜60 回
- 長いセル（2 セッション）は 1 回の費用が数倍になるので、段 3 で再現率の高いものを優先する

### 弱点 [推論]
- 当時のモデル（がんばりクエストの出来事の多くは今より前のモデル）でしか起きなかった失敗は、今のモデルで再現しない。それは「今は要らなくなった規則」を示す有用な結果だが、「規律が身についた」とは区別して書く（モデルの変化か、条件の欠落かを段 3 の条件の追加で切り分ける）
- オーナーの記憶と記録が食い違う出来事は、記録を優先し、食い違いを書く
- 公開リポジトリの出来事は、モデルが学習で見ている可能性がある（SWE-bench Verified の汚染と同じ問題）[一次: OpenAI の引退の理由 [二次]]

## やめるべき主張

| やめる | 言い換える |
|---|---|
| 「今のモデルはすでに規律を守る」 | 「設計者が手作りした、散らかり度がほぼ 0 の、1 回きりの短い課題では、単一セッションで失敗が観察されなかった」 |
| 「役割スキル・ハーネスは不要（になった）」 | 言わない。現実の条件（長さ・引き継ぎ・雑音・圧力）を持つセルで測っていない |
| 「天井 = モデルの能力」 | 「天井 = そのセルに識別力がない」。セルの性質として書く |
| 「圧力をかけても曲げない」（EXP-07）| 「依頼文 1 文の圧力では曲げなかった。繰り返しの失敗・テストの再実行・段階的な圧力は試していない」 |
| 「10/10 で一貫して守る」 | 「この短いセルで 10/10」。長いセルの pass^k は未測定 |
| 「保留セルで起きない → 開発セルの失敗は作り物」 | 「失敗はそれを引き出す条件があるセルでだけ出た」。条件の特定は未完（EXP-17 の続き）|
| 実験室の失敗率を、現場の出来事の率の推定として書く | 分母つきの現場の率と並べて較正するまで、比率として書かない |
