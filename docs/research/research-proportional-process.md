## 結論の要約

1. **「すべての変更を同じ手続きに通す」ことを、実務のデータと方法論の両方が退けている。** DORA は変更承認の落とし穴として「すべての変更を同じに扱う」を挙げ、「高リスクの変更を早く見つけて追加の精査に回す」ことを勧める。重い外部承認は変更の失敗率を下げる証拠がなく、むしろ遅らせて変更を大きくすると書く [一次・実証]。Google のコードレビューも、変更の種類（新規 / 挙動の変更 / 不具合修正 / リファクタと大規模変更）で見るところを変え、低リスクの機械的な変更は別経路で承認する [一次・方法論]。**批判 C-1 の方向（受け付けで軌道を決め、工程の重さを変える）は支持される。**
2. **「軌道を決める基準」に使える実測は少なく、雑音も大きい。** 変更単位のリスク予測（Kamei ら 2013）は「触るファイル数」と「不具合修正であること」を危険側の要因とし、全変更を点検する労力の 20% で欠陥を生む変更の 35% を拾えた。ただし精度（precision）は 34% [一次・実証]。**判定は外れる前提で、戻せない操作と影響の広さで上げる側に倒し、迷ったら上の軌道にする**のが妥当 [推論]。
3. **「計画を省いてよい場面」の Anthropic の原文は 2026-01 版にはあったが、2026-11 の現行版には無い。** 旧版: 「範囲が明確で修正が小さい（誤字・ログ 1 行・変数名の変更）ならそのまま頼む。計画が効くのは、進め方が不確かなとき・複数ファイルを変えるとき・コードに不慣れなとき。差分を 1 文で言えるなら計画を飛ばせ」[一次: Web Archive 2026-01-22]。現行版は代わりに「何が欲しいか決まっていないときは仕様をインタビューさせる」と、条件付きで計画を勧める形 [一次]。根拠として引くなら版と日付を付ける。
4. **t-wada の「リスクマッピング」は、Thoughtworks の Future of Software Development 報告（2026-02）が出所で、「コードを事業上の被害半径（blast radius）で階層に分け、人のレビューが要るところと自動の検証で足りるところを決める」こと。** 単位は変更ではなく**コードの領域**（社内ツール / 外向けのサービス / 安全に関わる系）で、「この変更が誤っていたら被害半径は何か、検証はそのリスクに比例しているか」と問う [一次]。t-wada のスライドはこの項目名を引用したもので、独自の定義は読める範囲に無い [一次]。
5. **t-wada は TDD を「全変更の標準」とは言っていない。** 「自動テスト」「テストファースト」「TDD」を 3 段に分け、「自動テストが最も重要」「テストファーストや TDD は個人が選択する開発スタイルと考えるのが穏当」と書く [一次]。AI 時代の TDD（2026-04）は、TDD の当て方を領域で変える図（伴走: 監督ループと流量制御 / 委託: 自律ループと監査 / 買ってくる・使わない）を示す [一次: 読める文字列]。一方で「TDD のステップごとに Conventional Commits でコミット」は研修の練習だけでなく**伴走モードの典型パターン**として示されている [一次]。批判 I-1 の「研修の作法を一般化した」は半分正しく、半分は言い過ぎ。
6. **コード調査の実証研究は、文献レビューや諜報分析の段とは別の形を示す。** 変更作業中の開発者の問いは「焦点を見つける → 焦点を広げる → 部分グラフを理解する → 複数の部分グラフをまたぐ」の 4 種に分かれ（Sillito ら、計 25 名の観察）[一次・実証]、うまくいった開発者は「構造をたどる検索」と「変更するメソッド名まで書いた計画を外に書く」を行い、場当たりの読み流しより短い時間で終えた（Robillard ら、5 名）[一次・実証]。デバッグでは、早く正しい仮説を持つことが成功を強く予測し、仮説の候補を渡すと成功が 6 倍になった（Alaboudi & LaToza、20 名）[一次・要旨・実証]。**調査の段は「焦点 → 展開 → 仮説と確認 → 変更計画」に組み直すのが実証に近い** [推論]。
7. **レビューの層を足す費用は、主に待ち時間と、層どうしの手抜きの誘因。** apenwarr の「1 層ごとに 10 倍遅くなる」は本人が「理論的な根拠は聞いたことがない」と書く経験則で、測った値ではない [一次・意見]。実測では、Google は 1 変更あたりレビュアー中央値 1 人・変更の中央値 24 行で、他社（2 人・承認まで 15〜24 時間）より速い [一次・実証]。Microsoft では欠陥を指すレビューのコメントは約 15% で、初めてその部分を見るレビュアーの有用なコメントは 33% [一次・実証]。一方、レビューの網羅と参加が低い部品は出荷後の欠陥が多い（McIntosh ら）[二次・実証]。**独立の確認は「やめる」ではなく「後段と重ねない・危険な変更に寄せる」が根拠に合う** [推論]。
8. **道具の雛形はそれぞれ前提を明記している。** superpowers writing-plans は「このコードベースも仕様も見ていない技術者」に渡す計画で、実行方式（タスクごとに新しいサブエージェントと新しいレビュアー / 自分で全部やって最後に 1 回レビュー）を「タスクの相互依存・数・出荷した誤りの費用」で選ばせる。現行版には「2〜5 分のタスク」の記述が無い [一次]。feature-dev は README で「1 行の不具合修正・自明な変更・明確で単純な作業・緊急の修正には使うな」と書く [一次]。superpowers の作者は「速いウォーターフォール」を「エージェントが走り出してから細かく監督しなくて済むよう、前で計画を最大にする」設計と説明し、「ずっとこれが正しいとは思わない」「小さな反復の変更の方法論はまだ無い」と言う [一次: 番組ページの書き起こし]。
9. **ATAM は「複雑なソフトウェア集約システム」のアーキテクチャ評価で、3 日（2 段階、段階の間に数週間）、評価者 2〜5 人・関係者 3〜50 人**の手法 [一次]。チケット単位で適用した例は見つからなかった [未確認]。品質シナリオの考え方（測れる形で書く）は借りられるが、効用木と順位付けは「構造・インターフェース・データの形を変える危険な変更」に限るのが原典の規模感に合う [推論]。
10. Q8 に、軌道の判定基準（3 軌道）、工程 × 軌道の「必須 / 省略可 / 不要」表、調査の段の組み直し（4 段＋危険時の追加段）、TDD を当てる範囲、独立の確認の条件、設計の成果物の 3 段と ADR の条件を、出典と根拠の水準つきで示した。

### 1-1 Anthropic Claude Code best practices の「計画を省いてよい場面」

| 版 | 本文 | 印 |
|---|---|---|
| 2026-01-22 時点（Web Archive） | "Plan Mode is useful, but also adds overhead. For tasks where the scope is clear and the fix is small (like fixing a typo, adding a log line, or renaming a variable) ask Claude to do it directly. ### 1-4 変更をリスクで振り分ける実務の例

| 実務 | 振り分け | 判定基準 | 種類・印 |
|---|---|---|---|
| Google のコードレビューの種類 | ①新規（greenfield）②挙動の変更・改善・最適化 ③不具合修正と差し戻し ④リファクタと大規模変更 | 新規は**コードレビューとは別に設計レビュー**を要する。不具合修正は「その不具合だけを直し、再発を捕まえるテストを足す」。自動生成の大規模変更は「**低リスクとみなされたものは全コードベースの承認権を持つ指定レビュアーが**」「リスクがありうる・領域の知識が要るものは各チームの技術者が」見る。生成の仕組み自体が先にレビュー済みなので、個別の変更で仕組みに拒否権を持たない | 方法論 [一次] Software Engineering at Google 第 9 章 https://abseil.io/resources/swe-book/html/ch09.html 、第 22 章 ch22.html |
| Google の承認の 3 つの側面 | 正しさと理解（LGTM）/ 所有者（OWNERS）/ 言語の可読性 | 1 人で兼ねられれば 1 人。分けるのは規模のため | 方法論 [一次] 第 9 章 |
| ITIL 4 の変更の種類 | 標準（低リスク・反復・事前承認済み）/ 通常（評価と承認が要る）/ 緊急 | 標準変更は初回に完全な評価を経て、以後はその手順で繰り返す限り個別の承認が要らない | 方法論 [二次] 解説ページ（https://wiki.en.it-processmaps.com/index.php/Change_Management ほか）。AXELOS の原典は読んでいない |
| Shape Up の appetite | 小バッチ（1〜2 週）/ 大バッチ（6 週）。「見積もりは設計から始まり数字で終わる。appetite は数字から始まり設計で終わる」「固定の時間・可変の範囲」 | 「この主題にどれだけの時間と注意を使う価値があるか」を先に決める | 方法論 [一次] https://basecamp.com/shapeup/1.2-chapter-03 |
| Kanban のサービスクラス | 至急 / 期日固定 / 標準 / 無形 | **遅延の費用**で分ける（リスクの大きさではない）。大半は標準であるべき | 方法論 [二次] 解説ページ。Anderson の原典は読んでいない |
| 変更単位のリスク予測（JIT 品質保証） | 欠陥を生みそうな変更を予測し、点検をそこに寄せる | 危険側の要因: **触るファイル数**、**不具合を直す変更であること**、相対的な変更量。前回の変更からの時間が長いことは OSS で危険を下げる側。全変更を点検する労力の 20% で欠陥を生む変更の 35% を拾える。正解率 68%・再現率 64%・**精度 34%** | 実証 [一次] Kamei ら, IEEE TSE 39(6), 2013, DOI 10.1109/TSE.2012.70, https://das.encs.concordia.ca/pdf/Kamei_TSE2013.pdf |

読み取り [推論]:

- 「自明 / 通常 / 危険」に近いのは ITIL の標準 / 通常（と緊急）と、Google の「低リスクの機械的変更は別経路」。どちらも**自明（標準）とみなせるのは、種類として事前に評価済みのものだけ**で、その場の印象で軽くするのではない
- Kanban のサービスクラスは急ぎの度合いの区分で、工程の重さの軌道とは軸が違う。採らない
- Kamei らの結果から: 「小さな不具合修正だから軽い」は成り立たない。**不具合修正は危険を上げる要因**として観測されている。また精度 34% は、機械的な判定でも 3 件に 2 件は空振りすることを示す。軌道の判定は外れる前提で設計し、上げる合図（§Q8-a）を置く
- Shape Up の appetite は「重さを先に決め、範囲をそれに合わせる」発想で、批判 C-1 の「投資はリスクに比例させる」と同じ向き

### 1-5 反する証拠（軽くしすぎることへの警告）

| 証拠 | 内容 | 種類・印 |
|---|---|---|
| 計画は時間を延ばさなかった | うまくいった開発者は詳しい変更計画を書いたが、計画した側の方が**約半分の時間**で終えた（5 名の観察） | 実証 [一次] Robillard ら 2004（§Q4） |
| 通るパッチの 4 割弱は誤り | 失敗するテストを通したパッチ（plausible）は 97%、コードレビューで正しいと判定されたのは 63%。誤りの 4 件に 3 件は退行か不完全な修正 | 実証 [一次] Böhme ら, ESEC/FSE 2017（§Q4） |
| レビューの網羅が低いと欠陥が増える | Qt・VTK・ITK で、レビューの網羅と参加が低い部品は出荷後の欠陥が最大 2 件・5 件多いと推定 | 実証 [二次] McIntosh ら, MSR 2014（要旨のみ） |
| Claude は控えめに作りがち | 現行の best practices（§1-1） | 雛形・公式 [一次] |

→ 軽い軌道でも「変更する箇所を名指しした数行の計画」と「完了の条件」と「実行した確認の証拠」は省かない方がよい [推論]。

### 2-2 出所での定義

出典 URL（Fowler の bliki）は Thoughtworks の合宿（2026-02 ユタ州 Deer Valley、2026-06 スイス Engelberg）の索引で、本文は Thoughtworks の報告にある。報告「1. Where does the rigor go?」の 4 番目 [一次] https://www.thoughtworks.com/content/dam/thoughtworks/documents/report/tw_future%20_of_software_development_retreat_%20key_takeaways.pdf :

> "Into risk mapping — Not all code carries the same risk. The retreat discussed tiering code by business blast radius, distinguishing between internal tools, external-facing services and safety-critical systems. This risk mapping determines where human review is essential and where automated verification is sufficient. One practitioner framed this as the new core engineering discipline: instead of asking "did someone review this code?" organizations need to ask "what is the blast radius if this code is wrong, and is our verification proportional to that risk?" This moves engineering from a craft model (every line is hand-reviewed) to a risk management model (verification investment matches exposure)."

読み取り:

- 単位は**コード（系・領域）**で、変更 1 件ではない。社内ツール / 外向けのサービス / 安全に関わる系の 3 段の例 [一次]
- 何を変えるか: **人のレビューが必須か、自動の検証で足りるか**。検証への投資を被害の大きさに比例させる [一次]
- 報告は Chatham House Rule の下の議論の要約で、発言者は特定されない。実証データは示されていない [一次]。種類は「実務家の意見の集約」
- 同じ節で TDD について「エージェントが壊れた挙動を確かめるテストを書く失敗を防ぐ。テストを先に置けばエージェントは自分の誤った実装を追認するテストで誤魔化せない」とも書く [一次]（§Q3）

**11 への当てはめ** [推論]: 「リスクマッピング」は軌道の判定の**入力**として使える。案件アダプタに「領域 × 被害半径（社内 / 外向け / 金・データ・法務・安全）」の表を持たせ、変更が触る領域から軌道の下限を決める。批判 C-2 の方向は支持される。ただし「t-wada の主張」ではなく「t-wada が引いた Thoughtworks 合宿の議論」と出典を書く。

### 3-1 「自動テストとテスト駆動開発、その全体像」（Software Design 2022-03、gihyo.jp 公開版）の該当箇所 [一次] https://gihyo.jp/article/2024/01/automated-test-and-tdd

執筆の紹介記事（2022-02-22）[一次] https://t-wada.hatenablog.jp/entry/automated-test-and-tdd-sd202203 : 「テスト駆動開発まで行かずとも、自動テストを行えば十分価値があると伝える」。テストファーストや TDD は「一部の個人が選択する開発スタイルのひとつに落ち着きました（これは妥当なところでしょう）」。参考文献に TDD に懐疑的な『A Philosophy of Software Design』『アジャイルイントロダクション』を意図して含めた。

| 出典 | 内容 | 種類・印 |
|---|---|---|
| Thoughtworks 合宿の報告 | 「TDD はエージェントから劇的に良い結果を生む」。仕組みは「エージェントが壊れた挙動を確かめるテストを書く失敗を防ぐ」こと。「TDD をプロンプトエンジニアリングの一種と捉え直す」 | 意見の集約 [一次] |

### 3-4 読み取り [推論]

- **t-wada の主張に忠実に書くなら**: 「自動テストは全変更に（挙動を変える変更には必ずテストを伴わせる）」「テストファースト・TDD は選択」が字面。11 の「全変更に Red → Green → Refactor とステップごとのコミット」は、t-wada の 2022 年の整理より強い
- **エージェントでは事情が一段違う**: 「テストを先に置き、失敗を見てから実装する」は、エージェント特有の失敗（自分の誤りを追認するテストを書く、不要なコードを書く）への対策として複数の実務家が勧める（Thoughtworks、Willison、Anthropic の SWE-bench 手順）。ここで効いているのは**テストファースト（失敗の確認）**の部分で、TDD の全周回（1 本ずつ・リファクタの段・ステップごとのコミット）が要るという証拠ではない
- **当てない場面**は t-wada 自身の材料から言える: 汎用の領域（買う・使わない）、実装よりずっと前にテストを書くこと（スコープクリープ）。11 の設定・文言・削除・依存更新に Red から始める意味が薄いという批判 I-1 は、この線引きと矛盾しない

## Q4. コードを読んで原因を探す実務の実証研究

### 4-1 プログラム理解・コード調査の観察研究

### 4-4 読み取りと段の提案 [推論]

- 実証研究が示すコード調査の形は「**焦点を見つける → 依存をたどって広げる → 仮説を立てて動かして確かめる → 変更する箇所を名指しした計画を外に書く**」。文献レビュー（Kitchenham）や競合仮説分析（Heuer）の「集める前に採否の基準を決める」「出所 × 主張の表を作る」に当たる段は、観察研究のどれにも現れない
- 「基準を先に決めないと期待で選択が歪む」（Kitchenham）の懸念は、コード調査では**仮説への固執**として現れる（Alaboudi & LaToza: 誤った仮説が進行を止める）。対策の形は「採否の基準」ではなく「**仮説の候補を 2 つ以上並べ、見分ける観測を取りに行く**」
- 「調べたことを外に書く」は、Ko ら（集めた情報を見失って探し直す、35%）と Robillard ら（計画を外に書いた者が成功）の両方から支持される。ただし書くのは**変更計画**（どのメソッドを変えるか）で、13 項目の調査メモではない
- Böhme らの「通るが誤り 37%」は、調査で再現テストを作るだけでは足りず、**退行と不完全な修正を探す段**（同じ型の箇所の検索、端の場合）が要ることを示す
- 段の具体案は §Q8-c

### 5-3 エージェントの独立の確認についての既存の知見（参照のみ）

`research-when-separation-helps.md`・`research-conventions-and-self-review.md` の要点: 新しい文脈のレビュアーは作った推論を見ていないことが効く（Claude Code docs）、自分の直前の行動として評価すると見逃しが増える（Self-Attribution Bias）、Opus 4.6 では「モデルが単独でこなせる範囲の課題では評価役は不要なオーバーヘッド」（Anthropic 長時間アプリ開発の記事）。

### 5-4 読み取り [推論]

- apenwarr の「10 倍」は**人の承認の待ち時間**についての経験則で、エージェントの新しい文脈のサブエージェントは待ち時間が分単位なので、費用の形が違う（トークンと時間、Claude Code docs）。**そのまま 11 に数字として持ち込まない**
- 一方で、apenwarr の**誘因の議論**（後段があると前段が手を抜く、後段は前段を厳しく見ない）は、Dev の独立の確認 → QM のレビュー（adversarial reviewer 付き）→ 統合 PR の監査という多層にそのまま当てはまる懸念。DORA の「問題に手続きを足すと悪循環」と同じ向き
- 実証研究は「レビューは欠陥より理解・保守性に効く」「初見のレビュアーの指摘は有用率が低い」を示す。文脈を持たない新しいサブエージェントは「初見のレビュアー」にあたり、**範囲を絞らないと有用でない指摘が多くなる**（Claude Code docs の「問題を探せと言われたレビュアーは必ず何かを見つける。スタイルは無視と指定せよ」とも一致）
- 反対側: McIntosh らと Böhme らは「レビューを減らすと欠陥が増える」「テストを通っても誤りがある」を示す。**独立の確認をやめるのではなく、層の重なりを避け、危険な変更に寄せる**が、両方の証拠に合う
- 置き場所の分担: Dev 側の確認は「実行できる証拠（コマンドと出力）」（自動・決定的）に寄せ、独立の目は「後段にレビューが無い」「危険軌道」「自分の成果物を同じ文脈で評価している」ときに置く。条件は §Q8-e

## Q7. ATAM・品質特性シナリオの適用単位と所要時間

原典 [一次] Kazman, Klein, Clements, "ATAM: Method for Architecture Evaluation", CMU/SEI-2000-TR-004（2000-08）。https://resources.sei.cmu.edu/asset_files/TechnicalReport/2000_005_001_13706.pdf から PDF を取得し全文を抽出した（前の調査の設計者照合メモでは取得できていなかった）。

| 論点 | 本文 |
|---|---|
| 対象 | 「ATAM はリスクを特定する方法で、**複雑なソフトウェア集約システム**のアーキテクチャの潜在的なリスク領域を見つける手段」「アーキテクチャの決定の帰結を品質特性の要求に照らして評価する」 |
| 時期 | 「開発の早い段階で行える」「設計の成果物を評価するので比較的安く速い」（比べる相手はシステムの実装・試験） |
| 所要時間 | 「**3 日連続**で行ったことがある。ただし最も効果的だったのは、最初の段階で評価チームと顧客がアーキテクチャの共通理解を作り、後でより大きな関係者を集めて正式な評価会議をするもの」。第 1 段階は評価チームの 1〜3 人と設計者・1〜2 人の主要関係者で、情報の収集に「**典型的に数週間**」。段階の間にも分析が続く |
| 人数 | 評価者 2〜3 人＋案件側 2〜3 人（第 1 段階）、評価者 4〜5 人＋案件側 5〜10 人（第 2 段階）。関係者は「**3〜5 人から 40〜50 人まで**」 |
| シナリオの量 | 投票は「シナリオ総数の 30% の票を各人に」。「**通常の 1 日の会議で扱えるのは 10〜15 本**」 |
| 効用木の順位 | 重要度と難しさを H/M/L で。「関係者は H/M/L より細かい区別を信頼性と再現性をもってできない」（逐語を照合した） |
| 線形ではない | 「手順に番号はあるが、厳密なウォーターフォールではない。必要に応じて前に戻り、先に進み、繰り返す」 |

派生の軽量版:

- Lightweight ATAM は「6 時間未満」で、ATAM・アーキテクチャ・目標に慣れた開発チームが、洗い出しと順位付けを省いて行う、と総説が紹介している [二次] https://pmc.ncbi.nlm.nih.gov/articles/PMC8838159 （原典は読んでいない）
- **チケット単位（1 つの変更）で ATAM や効用木を適用した例は見つからなかった** [未確認]。探した語: ATAM と user story / ticket / pull request / lightweight の組み合わせ

読み取り [推論]:

- ATAM の単位は「システムのアーキテクチャ」、時間は「日〜週」、人数は「数人〜数十人」。チケット 1 件の調査の必須手順にするのは、原典の規模から 2〜3 桁外れる（批判 R-3 を支持）
- それでも借りられる考え方はある: ①品質要求を「速く」「安全に」でなく測れる形のシナリオにする ②重要度 × 難しさで絞り、上位だけ深く見る ③細かい数値ではなく H/M/L で付ける。これらは**危険軌道**で、かつ**構造・インターフェース・データの形を変える**ときに、数本のシナリオに縮めて使うのが規模に合う
- 通常軌道では「この変更で悪くなりうる品質は何か」を 1 行で足りる（批判 R-3 の方向）

| T2 危険軌道 | 入れる | DORA（高リスクに追加の精査）、Thoughtworks（被害半径に比例した検証） | 実証 [一次]、意見の集約 [一次] |
| 後段に人・QM のレビューが無い（pit-crew を単独で使う案件） | 入れる | McIntosh（レビュー網羅が低いと欠陥増）、Böhme（通るが誤り 37%） | 実証 [二次] / [一次] |
| 自分が同じ文脈で作った成果物を、同じ文脈で「完了」と判定しようとしている、かつ「全部できた」と複数条件を主張する | 入れる | Self-Attribution Bias（既存）、11 事故 I-14 | 実証 [一次・要旨]（既存調査）、事故 |
| superpowers 型の「タスクごとに新しいレビュアー」 | タスクが互いのインターフェースに強く依存し、出荷した誤りの費用が大きいときだけ。それ以外は最後に 1 回 | writing-plans の実行方式の選び方 | 雛形 [一次] |
| T0 自明軌道 | 入れない | DORA（すべてを同じに扱う落とし穴）、Google（レビュアー中央値 1） | 実証 [一次] |
| T1 通常軌道で、後段に QM レビューがある | 原則入れない。Dev は実行の証拠と「確かめていないこと」を報告に書き、独立の目は QM に任せる | apenwarr（層の誘因）、Czerwonka（初見のレビュアーの有用率 33%）、DORA（手続きを足す悪循環） | 意見 [一次]、実証 [一次] |
| 層を足す前の確認 | 足す前に、後段のどの検査と重なるか、何を後段に任せるかを書く | apenwarr「代わりを置かずに減らすな」、DORA | 意見 [一次]、方法論 [一次] |

**反する証拠の扱い**: Anthropic の長時間アプリ開発の記事は「作る者と判定する者を分けるのは強い手立て」かつ「素の Claude は QA 役として甘い」とも書く（既存調査）。独立の確認は「やめる」ではなく「危険と単独運用に寄せる」に留める [推論]。

### (f) 設計の成果物の段階と ADR の条件

| 段 | 条件 | 中身 | 出典 | 水準 |
|---|---|---|---|---|
| 書かない（理由 1 行） | T0、または解が一つに決まりトレードオフが小さい | — | Google design docs（既存）、feature-dev README「単純な作業には使うな」 | 方法論・雛形 [一次] |
| 数行（PR 本文） | T1 で、妥当な案が複数ある | 推奨案、捨てた案 1 つと理由。3 方向の案は不要 | Ousterhout（主要な判断に Design it Twice、小さな単位なら 1〜2 時間以内）[二次]、feature-dev（3 案は新機能で構造の判断が要るとき） | 方法論 [二次]、雛形 [一次] |
| 設計書（1〜3 ページ） | T2、または新しい公開インターフェース・新規の機能（greenfield） | 背景と範囲 / ゴールと非ゴール / 設計 / 検討した代替案 / 横断的関心事。品質シナリオは数本 | Google 第 9 章（新規はコードレビューと別に設計レビュー）、Google design docs（既存）、ATAM を縮めて | 方法論 [一次] |
| タスク一覧（分単位） | **別のエージェント・人に渡すときだけ**。自分で続けて実装するならテストリストが計画を兼ねる | writing-plans（文脈ゼロの実行者が前提） | 雛形 [一次] |

**ADR を書く条件**（どれか 1 つ。どれでもなければ PR 本文の 1 段落か、検査・テンプレート・指示ファイルに置く）[推論、根拠: Nygard 方法論 [一次]、がんばりクエストの gate 運用規則 [一次]]:

1. 後から覆すときに背景の理解が要る、案件の残りの進み方に影響する決定（構造・非機能・依存・インターフェース・構築技法のうち**重要なもの**）
2. 既存の ADR と矛盾する新しい判断（古い ADR を superseded にする）
3. 機械で強制できない判断原則

「構造・品質特性・依存・インターフェース・作り方に関わる決定は全部 ADR」（11 手順 12）は採らない。

### (g) まとめて 11 に当てるときの注意 [推論]

- 上の (a)〜(f) は**規則を足す提案ではなく、既存の手順に「どの軌道で要るか」の列を足し、要らないところを外す提案**。11 の X5「足す前に減らす」と整合させるため、書き直しでは手順の総数を減らす（例: 調査の 23 手順を 4〜5 段に）
- 軌道の判定そのものも誤る（精度 34% の例）。評価計画（12）で「軌道の判定の正しさ」と「T0 で事故が起きないか」を測る価値がある
- 出典の多くは人の開発者の実務・研究で、エージェントでの検証は無い。エージェント向けの言い換えはすべて [推論]
