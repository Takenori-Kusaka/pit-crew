About the Radar
Thoughtworkers are passionate about technology. We build it, research it, test it, open source it,
write about it and constantly aim to improve it — for everyone. Our mission is to champion software
excellence and revolutionize IT. We create and share the Thoughtworks Technology Radar in support
of that mission. The Thoughtworks Technology Advisory Board, a group of senior technology leaders
at Thoughtworks, creates the Radar. They meet regularly to discuss the global technology strategy for
Thoughtworks and the technology trends that significantly impact our industry.
The Radar captures the output of the Technology Advisory Board’s discussions in a format that
provides value to a wide range of stakeholders, from developers to CTOs. The content is intended
as a concise summary.
We encourage you to explore these technologies. The Radar is graphical in nature, grouping items
into techniques, tools, platforms and languages and frameworks. When Radar items could appear
in multiple quadrants, we chose the one that seemed most appropriate. We further group these
items in four rings to reflect our current position on them.
For more background on the Radar, see thoughtworks.com/radar/faq.

Radar at a glance
The Radar is all about tracking interesting things, which we refer to as blips. We organize the blips in
the Radar using two categorizing elements: quadrants and rings. The quadrants represent different
kinds of blips. The rings indicate our recommendation for using that technology.
A blip is a technology or technique that plays a role in software development. Blips are “in motion”,
which is why their position in the Radar often changes. This usually indicates our increasing
confidence in recommending them as they move through the rings.

Themes
Harness engineering at scale
There was debate about whether to include harness engineering as an individual blip in the Radar, but
given it’s a theme that connects many techniques and technologies, we decided to highlight it as such
in this volume.
Although the term isn’t new, this edition highlights a growing ecosystem of practices and tools
that shows how harness engineering (everything we do to construct the environment around an AI
agent, from memory and context to feedback loops and guardrails) is maturing into a more cohesive
discipline. In particular, an emerging plugin ecosystem is taking shape, illustrated by Agent Plugins,
agent plugin marketplace and supporting tools such as Agent Package Manager.
Alongside these developments, it’s becoming clear that the harness is a living asset that requires
ongoing ownership and maintenance. We’ve discussed, for example, harness quality evaluation,
building a self-improving harness and using a feedback flywheel to ensure agents improve over time.
The broader challenge is scaling the harness to meet enterprise needs. In the coming months, we
may see the enterprise harness emerge as a product, not unlike what happened with platforms and
platform engineering a few years ago.
Beyond frontier models
We’re entering a new phase of AI model use, one where automatically reaching for a proprietary
frontier model is no longer the obvious choice. This edition highlights significant innovation in this
space, encouraging organizations to think more creatively about which models to use, how and when.
Open-weight models are particularly notable here. Twelve months ago, the gap with proprietary
frontier models was stark, but today it’s much smaller for many tasks. Cost is a major driver, but not
the only one: open-weight models can run in your public cloud environments, on neoclouds or on your
own hardware. That flexibility can help meet strict privacy requirements and reduce dependence on
a single vendor. This is especially visible in software engineering, where the GLM family has made
open-weight models credible alternatives to proprietary frontier models for some coding-agent
workloads. Self-hosting can also help organizations keep source code and prompts within their own
infrastructure. But the shift isn’t limited to open-weight models. Local coding models are rising in
popularity, while developments such as Foundation models for structured data and decision models
like Jev reflect growing recognition that frontier LLMs aren’t the only approach to AI.

With this growing range of options, choosing the right model for each task is becoming an important
responsibility for engineering teams. Model routing is emerging as a key consideration. We caution
against blanket frontier model usage and encourage teams to make deliberate model choices while
remaining open to alternatives.
Putting more agents to work
In our previous edition, coding agents drove most of our blips and themes. This time, many proposals
focused on putting more agents to work, mostly describing developers running several agent sessions
in parallel and steering each one. Others described handing agents larger pieces of work that run for
longer, such as unattended overnight agentic builds, where developers define the tasks and review
the results. This is a lighter-weight approach than the coordinated multi-agent approaches we’ve
covered in previous editions. A team of coding agents assigns agents roles in a predefined workflow.
Coding agent swarms go further, with orchestrating agents dividing and assigning work themselves.
In both approaches, developers delegate more decision-making. Thoughtworkers are mostly running
multiple sessions under more direct control, which we think is a sensible place for engineers to start.
Of the many tools we discussed for managing parallel sessions, including Claude Squad, T3 Code,
Orca and Paseo, Herdr attracted the most interest. Most include an attention inbox that organizes
sessions by status and prioritizes those waiting for an answer or approval. Omnigent has one, and
Paseo lets developers check sessions from their phone. Git worktrees give each of these sessions
its own working copy, although they can leave behind a tangle of partially merged branches.
Within a session, subagents take on narrow tasks and keep exploration and retries out of the main
context. AgentsView lets developers review past sessions, while Hunk helps them review agent-
generated changes.
As developers run more agents, their attention and review capacity become bottlenecks. When
review can’t keep up, oversight risks becoming human-in-the-loop theater. The pressure extends
downstream. When several developers each run multiple agents, changes can arrive faster than the
delivery pipeline can handle them. Path-to-production mapping helps identify where work queues up.
Before adding sessions, teams should consider how much their review and delivery processes can
handle. In the near term, we expect more practices and tools to emerge for orchestrating agentic work
across multiple engineers. Tools such as Entire CLI, which shares agent sessions across a team, are an
early sign of growing interest in making multi-engineer agentic work more effective.

Themes
Constructing the AI factory
While the demands of AI infrastructure have appeared in several recent Radar volumes, this edition
brings them into much sharper focus. As generative AI and agent use intensify, enterprises are
discovering that token economics ultimately comes down to infrastructure economics. The cost of
AI depends not only on model pricing but also on model selection, routing, batching, data movement
and the efficiency of the underlying platform. Much of the innovation needed to make AI economically
sustainable therefore sits deeper in the stack and often falls below many people’s radar.
In putting this edition together, we encountered a vibrant ecosystem emerging around AI
infrastructure. Kubernetes, in particular, is becoming a key foundation for what are sometimes
described as AI factories: industrialized platforms for running AI workloads at scale. Several blips
illustrate this shift. KServe and KAITO support model serving, deployment and accelerator-aware
workload management. Higher in the stack, llm-d tackles distributed inference and scheduling, while
LiteLLM provides routing and abstraction across models and inference providers. The AI factory stack
also extends beyond compute to storage and networking. Technologies such as VAST DataStore
address the high-throughput storage demands of accelerator-heavy workloads, while Netris brings
software-defined network automation to the underlying infrastructure, helping teams provision and
operate the high-bandwidth connectivity AI clusters depend on.
The bigger shift is that models, GPUs, inference engines, storage and networks are increasingly
managed as programmable resources coordinated through a common platform layer, making AI
infrastructure a central factor in enterprise AI economics.

Techniques
1. Agent sandboxing
Adopt
We’ve previously recommended sandboxed execution for coding agents. As AI agents become
increasingly autonomous and capable of acting not only in coding environments but also in business
systems, restricting their operational scope has become critical. We now consider agent sandboxing a
sensible default for all agents. Running agents in isolated environments with restricted privileges and
access to external systems reduces the risk and limits the impact of unexpected behavior, unintended
actions or malicious exploitation. We recommend teams apply a risk-based approach to sandboxing,
informed by threat modeling of their agents and systems. Although there is no one-size-fits-all
solution, recent security headlines reinforce the importance of applying established security practices,
such as the principle of least privilege, when building and running agents.
2. Mutation testing
Adopt
Mutation testing evaluates test suite quality by automatically introducing small, artificial bugs into
application code and verifying that at least one test fails. If tests pass despite the code change, the
mutation survives, revealing gaps in test coverage or assertion quality. As teams adopt AI coding
assistants, the volume of AI-generated code and tests increases rapidly, making traditional code
coverage metrics easier to inflate with superficial tests that lack meaningful validation. This technique
acts as a guardrail, helping ensure generated tests don’t simply pass without catching logic changes.
Beyond dedicated frameworks, AI agents can now perform mutation testing autonomously during
execution by directly modifying code, running tests and evaluating assertions in their loop. Because
automated mutation runs are time-consuming, developers should target specific internal packages or
rely on incremental checks to run tests only on recently changed code.
3. Path-to-production mapping
Adopt
Path-to-production mapping is a standard practice at Thoughtworks that has become newly relevant
with the advent of agentic coding. Increased code throughput can expose or amplify bottlenecks
elsewhere in the path-to-production, making it essential for teams to optimize the end-to-end flow
of software rather than coding speed alone. The activity is most often done in a workshop that
includes everyone involved in designing, developing, releasing and operating the software. First,
participants list the steps in the process on a whiteboard, from the developer workstation all the
way to production. In a second pass, they capture pain points. The activity is often eye-opening, as
participants identify delays, risks and inconsistencies they weren’t previously aware of. Tackling those
bottlenecks is key to improving overall delivery productivity.
4. Post-quantum cryptography
Adopt
Post-quantum cryptography (PQC) refers to cryptographic algorithms designed to protect digital
data against attacks by future quantum computers. As quantum computing advances, the threat
to conventional encryption becomes increasingly real: data encrypted today can be harvested
now and decrypted later, making key exchange the most urgent area to migrate. With NIST’s
standards now finalized (ML-KEM, ML-DSA and SLH-DSA), governments worldwide target migration
between 2030 and 2035.

5. Progressive context disclosure
Adopt
Progressive context disclosure is a context engineering technique for providing information to LLMs
on demand. The system bootstraps the LLM with essential context and allows the LLM’s responses
or user input to trigger the loading of additional data. We’re moving progressive context disclosure to
Adopt because the practice is nearly universal in serious applications, although it takes many forms.
In coding, one example is to keep your AGENTS.md lean and provide links to documentation that the
agent can look up when needed. Coding harnesses also use this approach to defer the full context
cost of MCP tools and agent skills until they’re used. Business applications might use vector RAG or
GraphRAG to retrieve additional information based on user input. In each case, progressive context
disclosure can reduce token consumption and costs and help counter context rot.
6. Threat modeling
Adopt
Threat modeling is an exercise for identifying potential threats to your systems. It’s a core security
practice for all software development, especially for generative AI applications, whose distinctive
security risks, such as prompt injection and autonomous action, may be missed by rule-based
checks and scans. Threat modeling should be a regular, human-led part of the software development
lifecycle, with support from agents. The discussion helps surface undocumented behaviors and build
stakeholder understanding.
We recommend starting with known threats and mapping them to your context. Useful resources
include the MITRE ATLAS catalog of AI threats, MAESTRO as a companion to frameworks such as
STRIDE and toxic flow analysis for reasoning about where prompt injection might enter. A session
should end with explicit decisions about where nondeterministic model behavior is acceptable, where
it isn’t and where deterministic guardrails are needed to limit risk and harm.
7. Agent plugin marketplace
Trial
An agent plugin marketplace is a means of distributing harness assets across an organization. The
need arises when multiple teams adopt coding agents and want to share skills, instructions, MCP
servers, subagent definitions and other assets. Copying these between repos provides no easy way to
publish, discover or update them. We’ve implemented an agent plugin marketplace using documented
Git repositories, with plugins in the Agent Plugins format that coding agents consume directly or that
are managed as dependencies with Agent Package Manager. Anthropic popularized the pattern with
its Claude Code plugin marketplace, and hosted registries such as Tessl’s and community collections
like wshobson/agents have adopted the idea. We see agent plugin marketplaces as a practical way to
make your enterprise harness available across the organization.

8. Agent-maintained knowledge bases
Trial
With agent-maintained knowledge bases, a team keeps its shared knowledge in linked plain-text
files, often in an Obsidian vault, and uses a coding agent to maintain them. Andrej Karpathy’s LLM
Wiki describes the pattern: raw sources the agent reads but never changes, a wiki it maintains and a
schema that guides how it does it. OpenWiki applies a narrower version of the idea to a single code
repository’s documentation. The technique is practical today because general-purpose coding agents
can already read and edit files effectively, while Git provides version control. Many people start with a
personal “second brain.” We recommend taking the next step and sharing one across a team, although
expanding it into an organization-wide knowledge base takes more than pointing a coding agent at a
folder of files. Generated knowledge can drift from reality, and without regular human effort to keep it
accurate, the knowledge base risks creating AI-driven documentation sprawl.
Several of our teams use variations of this approach, with product managers, designers, developers
and their agents all querying the same knowledge base. These teams find their information more
connected and accessible.
9. Anchoring coding agents to a reference application
Trial
Anchoring coding agents to a reference application addresses the challenge of application template
decay by separating lean, structural scaffolding templates from evolving platform configuration
rules. Previously, we focused on using live, compilable reference applications to keep generated
code in sync with current practices. We’re now seeing teams successfully extend this pattern to AI-
driven scaffolding.
Traditional code generators and scaffolding CLI tools quickly fall behind as platform guidelines,
dependencies and architectural best practices change. Instead of hardcoding these rules into static
templates, coding agents query centralized, up-to-date information sources, such as an OpenWiki
or structured agent-maintained knowledge bases, at runtime to retrieve current conventions and
settings. Consolidating evolving platform rules into unified, agent-accessible repositories helps agents
generate code that follows current standards without requiring continuous updates to the underlying
scaffolding tools.
10. Coding harness for general-purpose agents
Trial
Teams building agents for non-coding work, such as document processing, operations support or
migration planning, have typically started with an agent framework and assembled the agent loop
themselves. Increasingly, we see teams instead build on a coding harness for general-purpose agents,
reusing the runtime of a mature coding agent. Popular coding agents now expose their runtime
programmatically through the Claude Agent SDK, the Codex SDK and app-server, OpenCode’s server
and SDK or Pi’s SDK and RPC mode. These harnesses already handle complex aspects of the agent
loop, including compacting context on long-running tasks, persisting sessions and running headlessly
with the same agent skills, subagents and instructions used in interactive coding-agent sessions.
Compared with agent frameworks, the trade-off is less control in exchange for a runtime that’s
already been tested extensively. We’ve used this approach to build an internal accelerator for .NET
application migrations.

Techniques
However, these harnesses differ in their capabilities. Codex and the Claude Agent SDK provide
sandboxing and approval policies, while Pi deliberately leaves guardrails to extensions, making
it easier to adapt but requiring more work. Because these runtimes are designed for software
development, their system prompts and built-in tools tend to steer agents toward writing and running
code. Teams should review these defaults for their intended domain. They should also monitor costs,

11. Feedback flywheel
Trial
In the previous Radar, we described the feedback flywheel as a way to improve a coding agent’s
harness from earlier sessions. Most developers update AGENTS.md files and agent skills when an
agent gets something wrong, but what one developer learns may not be shared with the rest of the
team. The feedback flywheel adds a question at the end of each session, asking whether anything
should change in a shared artifact, along with a retrospective item where the team decides what to
update. Feedback sensors show which checks keep failing, an agent suggestion box collects problems
agents report and tools such as Backpass propose edits based on past sessions for a human to
accept or reject. We’re moving feedback flywheel to Trial because harness edits are now routine.
The flywheel needs to remove as well as add. Rules that only accumulate become agent instruction
bloat, and a sensor that produces only noise should go. We recommend continuously checking which
artifacts are still used and up to date. Context profiling shows whether edits are increasing what
each session loads. Where a self-improving harness has an agent run the loop, the feedback flywheel
makes it a team habit, with agents proposing changes and people choosing which changes to make.
12. Graph-grounded codebase reasoning
Trial
As context-heavy workflows become more common, sending full source files or unstructured text to
LLMs increases token costs. Graph-grounded codebase reasoning addresses this by representing
code, documentation and relationships as a structured graph, allowing agents to retrieve relevant
subgraphs as context. Tools such as Graphify capture structural dependencies, helping agents
identify relationships that text-based retrieval may miss.
However, graph grounding comes with trade-offs. Recent research suggests agents can sometimes
perform worse with graph-based context than with simpler tools such as find and grep. We’ve placed
the technique in Trial to encourage readers to explore when graph-based context improves efficiency
and accuracy, building on our previous blip on code intelligence as agentic tooling.
13. Grilling
Trial
Grilling is a technique in which a coding agent interviews you about a plan before acting to resolve
potential areas of ambiguity. The best-known example comes from mattpocock/skills, but other skills
libraries have their own versions. One benefit is that grilling discourages coding agents from guessing
where your intent is unclear. It surfaces assumptions the coding agent might otherwise make on its
own. Another advantage is that it helps counter codebase cognitive debt. The grilling process forces
you to examine your own assumptions, leaving you with a better understanding of the implementation
plan that can be captured in decision records. Our teams have found grilling a useful addition to their
agentic coding practice.

14. Interactive visual plans with agents
Trial
Interactive visual plans with agents are self-contained HTML or MDX plans with diagrams, user flows
and wireframes that teams can explore before implementation. Our teams find that stepping through
these artifacts makes it easier to verify intent and review complex changes than reading long text
plans. Our teams warn against using this technique for “big upfront designs” and favor a more iterative
approach, breaking work into smaller, verifiable steps to build understanding along the way. The
same approach can provide a visual recap of completed work, but our teams find recaps most useful
when the implementation deviates from the original plan. We recommend using interactive visual
plans with agents to build shared understanding and establish a human review point before agents
implement changes.
15. Managed agents runtime
Trial
Managed agents runtime is the practice of running software delivery agents on a platform that
manages their execution, infrastructure and operational needs rather than relying on a developer’s
workstation. The runtime hosts the agent loop and provides sandboxed compute, triggers, credential
handling, session state and observability, leaving teams to define the model, prompt, tools and skills.
Long-running, asynchronous work is well-suited to background agents that pick up tasks from issues,
pipelines or schedules and submit pull requests for review.
Coding tools are converging on this approach, with Cursor cloud agents, the GitHub Copilot coding
agent and OpenAI Codex cloud tasks all running in remote sandboxes. Claude Managed Agents offers
a general-purpose equivalent. Our internal security team runs a daily agent that triages endpoint
detection false positives and proposes rule changes. “Managed” doesn’t necessarily mean someone
else’s cloud. At one client, we run custom agents on a self-hosted runtime in a continuous loop across
multiple repositories, fixing code smells flagged by scanners and upgrading dependencies along with
any required code changes.
A hosted service is often the easiest place to start, but organizations with data residency, security or
integration constraints may need their own platform. Either way, we recommend treating the runtime
as production infrastructure, with agent sandboxing and version-controlled agent definitions.
16. Open-weight models
Trial
Open-weight models, where model weights, architectures and inference code are publicly released,
have reached a significant inflection point. Attracted by their lower total cost of ownership, we’ve been
evaluating the latest models from families such as DeepSeek, GLM and Kimi for production delivery
work requiring complex reasoning and high-quality code generation, and we’re seeing good results.
Beyond cost efficiency, open-weight models provide deployment flexibility, freedom from vendor
lock-in and stronger data sovereignty. Engineering teams can right-size their deployments, from
lightweight flash models to hundred-billion- or trillion-parameter mixture of experts (MoE) models,
and perform private fine-tuning using domain data. Although self-hosting requires greater operational
effort, major cloud providers now offer managed open-weight models that lower the barrier to
adoption. Rather than treating them merely as budget options, organizations should evaluate
open-weight models for a broad range of enterprise workloads, well beyond coding.

17. Risk-tiered human oversight
Trial
Risk-tiered human oversight aligns review depth with what a change could break. Reviewing
everything with the same intensity ends in human-in-the-loop theater. We suggest systematically
triaging changes. The riskiest or hardest-to-reverse changes are reserved for humans to apply.
Intermediate-risk changes go through human review. Low-risk changes can be auto-merged by coding
agents through a continuous integration pipeline.
Two strategies can help us decide which changes need more review. Zones in the codebase require
elevated review with particular files or directories, while LLM-based change classification analyzes
the impact of changes but is fallible. Meta’s published process combines these two approaches.
Our teams find risk-tiered human oversight an effective way to make the best use of scarce
human attention.
18. Self-improving harness
Trial
A self-improving harness uses agents to analyze execution traces and evaluation feedback, then
propose or implement improvements to the system surrounding the model, including prompts,
context strategies, workflows, skills, tools, memory and middleware. The idea isn’t new: techniques
such as the feedback flywheel use successes and failures from coding-agent sessions to improve
the harness but still rely on humans to interpret the feedback, decide what to change and update
the system. Recent research explores a more self-directed approach. Meta-Harness and VERSE use
execution traces and evaluation results to improve harness code; VERSE also evolves the optimizer’s
own tools and procedures. Lilian Weng’s overview traces this progression from prompt optimization to
harness evolution.
Observability and programmability are essential to this transition. Observability helps agents diagnose
failures from execution traces and connect changes to measurable outcomes, while programmability
gives agents access to components they can inspect, modify and test, expanding the scope for self-
improvement. Pi’s extensions, Claude Code Mods and DeepSeek Harness (DSH) illustrate this direction
through extensible context, workflows, tools and harness components.
Greater openness creates more opportunities for improvement, but gains still require validation.
We recommend bounded experiments with regression testing, while humans define objectives, set
modification boundaries and assess whether improvements generalize to new tasks.

computational resources of larger models. As organizations face rising costs from running LLMs,
teams are recognizing the value of choosing the right model for the task.
Compact models are also viable for edge computing, as Apple Core AI demonstrates by running
small foundation models directly on devices. Our teams have found SLMs effective for narrow, high-
frequency tasks that don’t require extensive knowledge or complex reasoning, such as summarization,

20. Stateful guardrails
Trial
Stateful guardrails extend LLM guardrails from single messages to whole conversations. Instead
of checking only the current user message or the final model response, they evaluate a compact
transcript of recent turns against policy-specific checks and maintain strike or ban state across
the session. This matters because unsafe intent can emerge gradually: each message may look
acceptable on its own, while the conversation as a whole reveals attempts at policy evasion,
jailbreaking or prompt extraction. In practice, stateful checks run as a runtime gate before the agent
acts, working alongside conventional single-turn input and output guardrails.
Evaluating conversation history on every turn adds latency and cost, and strike or ban thresholds
need tuning to prevent false positives from locking out legitimate users. Our teams have used this
technique in a production conversational assistant for sensitive workflows, tracing guardrail decisions
in Langfuse. We recommend that teams running multi-turn assistants in production try stateful
guardrails rather than relying on per-message checks alone.
21. Subagents for better context management
Trial
Subagents for better context management is the practice of delegating work to subagents to keep it
out of the orchestrating agent’s context. Exploration, tool output, retries and intermediate reasoning
stay in the subagent, and the main session receives a short summary. Most people first use subagents
to run tasks in parallel or form a role-based team of coding agents. Protecting the orchestrator’s
context is another reason to use them. Whatever remains in the orchestrator’s context competes for
its attention on subsequent turns. Pulling a subagent’s full transcript into the main thread to check its
progress undoes this benefit. Useful guidelines include running two to four subagents at a time and
keeping tasks that require the same understanding of the code within one agent, so multiple agents
don’t each have to rebuild that understanding.
Using subagents to protect the orchestrating agent’s context is a form of context engineering
that’s easy to try because most coding agents support subagents, and the change is largely in the
instructions. We’ve used cheaper models for subagents handling narrow tasks such as research,
potentially reducing costs compared with blanket frontier model usage. We’re placing the technique
in Trial because its benefit hasn’t been measured systematically. The evidence so far comes from
practitioners’ accounts of their own sessions, without detailed token accounting. We’ve also observed
that the same model with the same prompt uses subagents differently depending on the harness.
Teams trying this approach should use context profiling to check whether the orchestrator’s context
actually shrinks.
22. Toxic flow analysis for AI
Trial
As AI agent capabilities expand, teams are increasingly deploying systems that face a lethal trifecta of
security risks: access to private data, exposure to untrusted content and the ability to communicate
externally. This combination creates opportunities for attacks such as prompt injection and tool
poisoning. To address these risks, we’ve moved toxic flow analysis for AI to Trial.

Techniques
While general threat modeling provides a broad security foundation, toxic flow analysis focuses
on identifying unsafe data paths through agentic systems. These risks aren’t limited to standard
integrations. They can also arise from malicious agent skills that appear useful but contain hidden
instructions to exfiltrate sensitive data. We’ve successfully used tools such as Agent Scan to perform
this analysis, helping teams identify and mitigate unsafe data paths before they’re exploited.
23. Unattended overnight agentic builds
Trial
Unattended overnight agentic builds refers to the practice of giving a coding agent a feature-sized
piece of work when the team leaves for the evening and reviewing what it produced the next morning.
We’ve done this with epic-level features and infrastructure tasks that can take hours. One agent is
enough, without a coding agent swarm, although it may use subagents. One Thoughtworks team
spends the day collaborating on plans and specifications and leaves the coding to agents overnight.
“Overnight” is in the name because it’s hard to fake. A team that can do this will likely run similar jobs
during the day too. (A team that doesn’t leave an agent coding unwatched overnight probably isn’t
running fully autonomous work during the day either.)
Like microservice prerequisites, this practice has entry requirements, and pushing teams to meet them
is a big part of its value. Agents need sandboxed execution, work specified up front as in spec-driven
development and feedback sensors so they can correct their own mistakes. A night’s work can be too
large a batch to review effectively line by line, so teams need a harness they’ve tested to validate the
changes instead of relying on human code review. Complementary techniques include running the
agent in a managed agent runtime and letting agents keep the build green by fixing pipeline failures
themselves. We’ve placed this in Trial for teams that have those foundations; for other teams, it’s a
goal that justifies building them.
24. Agent pipeline responsibility
Assess
Agent pipeline responsibility incorporates coding agents into the team’s accountability for keeping the
build green. An agent that can’t see the build status can’t respect a team agreement not to push on
red, while a human relaying failure logs into a chat window becomes a meat proxy.
We recommend making the build state part of the agent’s context. Expose pipeline status and logs
through the agent’s tools so it can see what went wrong and help fix it. Enforce important rules
mechanically with pre-push and server-side gates to prevent agents from pushing broken changes.
The increased commit rate from coding agents is leading teams to rethink assumptions around build
discipline through techniques such as risk-tiered human oversight. Include the role of agents in your
build policy when conducting path-to-production mapping.
25. Agent suggestion box
Assess
An agent suggestion box gives a running agent somewhere to report the problems it encounters, such
as a bug in a tool or a dependency missing from its environment. When an agent’s only output is a
pull request or a structured verdict, it may work around the problem without anyone hearing about it.
The next session then hits the same problem again. The box can be a Slack channel, a memory store
or an issue tracker. Lovable calls its version a “vent tool,” and agents-feedback offers one for coding
agents. Memory can help an agent avoid a broken tool, but a suggestion box gets the tool fixed. The
technique works for business agents in production as well as for coding agents.

Techniques
We’ve used an agent suggestion box with an agent that starts a fresh session each day to draft
detection engineering rules. A second agent deduplicates the reports. The same report from several
sessions is a clear signal, although some reports are subjective or transient. With the box in place,
runs went more smoothly, and we had a list of improvements to make. The suggestions still need to be
reviewed and acted on, for example, through self-improving harness. We’re placing agent suggestion

from its vents but reports that roughly half the fixes its triage agent proposes are false positives.
26. Context profiling
Assess
As token costs have risen and the industry has left the tokenmaxxing fad behind, developers are
looking for ways to manage token usage. The old advice that you should always measure before
optimizing still applies. Context profiling means analyzing where your token spend is going (for
example, are tokens being spent on file reads or MCP tool calls?). Intuition is a poor guide to
identifying which optimizations are worthwhile, especially when you factor in caching, model tiers and
promotional pricing. Mature tooling hasn’t yet emerged, but you can make do by analyzing your agent
sessions or data from tools such as Entire CLI and AgentsView.
In our experience, the biggest savings often come from simple changes, such as clearing sessions at
the right time, tuning cache parameters or quietening chatty build scripts. Yet we often see developers
reaching for complex solutions such as compression proxies without measuring their impact.
27. Enterprise harness
Assess
An enterprise harness is the organization-wide layer of what coding agents consume managed
collectively. It includes skills, tools, connectors to internal context, approved technologies, architecture
decision records, path-to-production guidance, hooks and security policies. We observe that as
multiple teams in an organization adopt coding agents, they need common context to complement
each team’s curated shared instructions. It’s like a developer experience platform, but for agent
experience. We’ve seen organizations go as far as building a custom coding agent on top of

agent plugin marketplace. There’s no consensus yet on how to do this well, so keep the enterprise
harness thin and federated, leave room for experimentation and harvest what works.
28. Foundation models for structured data
Assess
Enterprise AI has focused heavily on text and vision, while much business data remains locked
in relational databases. Foundation models adapt transformers to structured data, pretraining
on an organization’s event sequences and transaction logs to learn reusable representations of
business behavior.
Unlike traditional gradient-boosted models that require extensive feature engineering and retraining,
these models can support multiple downstream tasks with lightweight fine-tuning. Tools such as
TabPFN and TabFM can improve risk assessment, predictive analytics and customer retention directly
from tabular or relational data. Given their potential to unlock business insights without complex

29. Harness quality evaluation
Assess
Nowadays, organizations and teams come up with custom harnesses tailored to their projects,
including agent skills, plugins, AGENTS.md and deterministic guardrails. Harness quality evaluation has
become an important technique. Guardrails and harnesses help a coding agent course-correct and
improve overall quality, but only if they actually work.
A harness usually includes both deterministic and non-deterministic components. For non-
deterministic harnesses, our teams use PluginEval to evaluate coding agent plugins or skills. For
deterministic harnesses, we introduce a test suite to enable TDD-style development of any guardrails,
ensuring each one actually works and providing evidence of its effectiveness. We recommend running

30. Local coding models
Assess
In previous editions of the Radar, we put local coding assistants in Caution because the available

to the concerns they were intended to address. With coding agents now being adopted much more

31. MITRE ATLAS
Assess

33. Programmatic tool calling
Assess
Programmatic tool calling is a tool-use pattern where the model writes code instead of issuing one
tool call at a time. Rather than making a round-trip through the model for each operation, it combines
tool calls into a program that runs in an execution environment, looping, filtering and shaping results.
Only the selected results or the final output are returned to the model’s context.
The concept appears in several implementations, although the naming is still unsettled. Cloudflare and
Pi call it Code Mode; Anthropic calls it programmatic tool calling; and an earlier Anthropic engineering
article describes code execution with MCP. DeepSeek Harness (DSH) also provides a closely
related PTC Mode.
Implementations differ mainly in where the execution environment runs: in a model provider’s
container, the agent harness or, more recently, through a Code Mode MCP server. The latter allows
MCP clients to use programmatic tool calling without implementing their own execution runtime.
However, it can reduce the granularity of client-side approvals, so authorization and approval for
individual operations must still be enforced by the server and its tool handlers.
34. Semantic review of AI-edited prose
Assess
Coding agents produce and revise prose artifacts such as specifications, ADRs and plans far faster
than humans can review them. Text diffs bury intent under rewording and formatting noise, making
it hard to see whether a plan has changed significantly. Semantic review of AI-edited prose adds a
layer on top of the text diff: an LLM analyzes changes in meaning, such as altered facts, conflicting
statements, redefined acceptance criteria and changes in scope. Much like automated PR review
but for prose, it can be implemented as an agent skill that runs whenever a coding agent edits a
document. We’ve seen Thoughtworks teams use this technique to reduce cognitive load and review
fatigue, helping reviewers better understand changes to planned work before implementation.
35. Tests as data over tests as code
Assess
Tests as data over tests as code means expressing test cases as structured data, typically YAML
or JSON, rather than as test code. A project-specific test harness reads that data and executes the
underlying code: the harness provides the building blocks, while the test cases define how they’re
assembled. The technique isn’t new; BDD with Gherkin is a prime example. What makes it relevant
again is that AI coding agents now write more code, including tests. We’ve found that a defined
schema better constrains what they produce, making tests easier to generate and review, with less
AI-generated test code.
A few of our teams have also seen a compelling use case in legacy modernization, where the same
test cases expressed as data can run against both legacy and modern code by swapping the harness
adapter. This helps teams verify that the modernized system behaves like the original, at least for the
cases covered by the tests. Using the technique with AI is still relatively new to us, and we haven’t
applied it broadly. However, the results so far are promising, and we think it’s worth assessing.

36. Agent instruction bloat
Caution
Instructions for coding agents, such as AGENTS.md guidance, process skills and workflows, tend to
grow longer over time. Although each new rule might be useful in isolation, this accumulation often
leads to agent instruction bloat. The instructions become long, contradictory and stale, especially if
teams engage in agent skill cognitive surrender and import external instruction sets wholesale. First,
convert any instructions you can into deterministic hooks or checks. Then, reevaluate instructions
against each new model and delete those it no longer needs; progression testing, rather than
regression testing. Anthropic removed over 80% of Claude Code’s system prompt for its latest models
with no measurable loss, as frontier models now follow instructions more reliably. Progressive context
disclosure keeps the remaining instructions out of the way until they’re needed.
37. Agent skill cognitive surrender
Caution
There is a growing trend of agent skill cognitive surrender, an antipattern in which teams adopt large,
community-curated skill libraries or heavyweight AI agent frameworks without fully understanding
what they do. Much like blindly importing large software dependencies, developers can treat
these skills as ready-made capabilities and lose sight of how the underlying system works. This
isn’t a new problem; similar examples include copy-pasting code without understanding it or
over-relying on generic design patterns. However, the proliferation of AI tools has made the issue
much more apparent.
Beyond the loss of system understanding, surrendering critical evaluation introduces security risks:
unreviewed prompt instructions can make their way into execution pipelines. Skills from different
sources may also conflict when they weren’t designed to work together. It’s important to inspect
and review skill instructions before adapting them rather than using general-purpose agent skills
indiscriminately. As underlying models become more capable, generic community skills can become
unnecessary or obsolete, making it more valuable to curate domain-specific skills tailored to a
project’s context.
38. AI-accelerated shadow IT
Caution
We observe many noncoders graduating from no-code platforms to coding agents such as Claude
Code and OpenAI Codex. We celebrate people solving their own problems, but AI-accelerated shadow
IT, whether built by noncoders or developers, comes with risks. First among these is security. Second,
software originating from outside traditional development usually lacks testing, deployment pipelines
and observability. This particularly matters if one person’s productivity tool is adopted by their team
or department. Organizations should prioritize governance with limits and guidelines on AI-generated
applications. In our experience, it’s better to provide colleagues with environments and enterprise
harnesses for safe experimentation than to extinguish their enthusiasm. Be firm on security, and give
useful tools a clear path to support.
39. AI-driven documentation sprawl
Caution
AI-driven documentation sprawl occurs when teams use AI agents and spec-driven development tools
such as Spec-kit or BMAD to generate large volumes of Markdown files and documentation. Because
AI can produce polished, professional-looking docs in seconds, the result can create an illusion of

Techniques
software quality and rapid progress. Unlike source code, however, documentation rarely passes
through automated quality gates or CI tests. As projects evolve, repositories rapidly accumulate
verbose, unmaintained and contradictory specs that developers lack the time to clean up, resulting in
a chaotic “big ball of documentation mud.”
This overabundance of obsolete documentation is particularly problematic in agentic workflows.
When coding agents read through a repository littered with outdated architectural decision records
or conflicting specification files, these redundant and contradictory documents consume valuable
context and provide unreliable information. Rather than aiding development, obsolete context can lead
AI tools astray and result in poor code generation. To maintain agent effectiveness, teams must treat
Markdown as a first-class artifact, spending deliberate human effort to prune, refine and consolidate
generated context files so the agent’s context remains crisp, relevant and authoritative.
40. Blanket frontier model usage
Caution
We’ve sometimes caught ourselves defaulting every task that requires an LLM to the most capable
model available, paying no attention to cost, latency or required capability. We call this blanket frontier
model usage. Frontier models can cost significantly more and run more slowly than their more nimble
counterparts; routine work such as exploration, simple edits or summarizing is often better served by
a smaller model or even open-weight models. You can switch tiers manually, per subagent or through
harness settings that switch automatically based on task complexity or stage. Each model has its own
prompt cache, so you can also switch at natural boundaries, like a new session, a subagent or the
handoff from planning to implementation, rather than per request. A warning on our warning, though:
more capable models sometimes finish tasks using fewer tokens, so use context profiling to check
whether your optimization is working.
41. Coding throughput as a measure of productivity
Caution
In a previous Radar, we warned against using coding throughput as a measure of productivity. As the
industry pushes for AI adoption and seeks tangible metrics, we increasingly see activity-based metrics
such as the percentage of code generated by AI or tokens consumed treated as badges of honor.
Although such metrics may indicate adoption levels, they’re poor proxies for real productivity gains.
To measure meaningful productivity, we continue to recommend established frameworks such as
DORA metrics and collaboration quality, along with tying improvements directly to business outcomes.
Treating activity metrics as targets rather than signals risks falling prey to Goodhart’s law. We’ve seen
developers generating AI busywork simply to hit these targets.
42. Human-in-the-loop theater
Caution
Human-in-the-loop theater is keeping a human in an agent’s loop as an empty approval step rather
than a real check. The human approves actions, prompts or diffs they can’t realistically evaluate.
The approval step functions as an accountability sink: no one truly owns the decision. Our advice is
instead to triage. Reserve human review for changes a human can genuinely judge, using risk-tiered
human oversight. For the rest, shift from reviewing individual changes to steering the system with
mutation testing, property-based testing, formal models such as TLA+ and Quint and agent-assisted
semantic review.

43. Meat proxy
Caution
A meat proxy is a person who unthinkingly passes on unverified LLM output to a colleague, forwarding
it without reading, validating or adding substantive judgment. It’s a violation of good AI etiquette
and, in our unfortunate experience, a growing problem. When you act as a meat proxy, you shift the
verification burden downstream onto the other person and shirk your own responsibility for assuring
quality work. This is similar to human-in-the-loop theater, except that it’s fake authorship instead of
fake approval. In neither case is the human adding value. KDE’s draft AI guidelines put it well: “Don’t
be a meat proxy.”
44. Naive context compression
Caution
As token costs rise, teams increasingly turn to tools like Headroom, RTK and Tamp to shrink their
prompts. However, we advise against naive context compression, which can introduce several
subtle problems. First, it often interferes with prompt caching; reducing token counts while missing
cache hits can lead to higher actual bills. Second, aggressive compression causes information loss,
degrading the performance and accuracy of agentic loops. Third, some tools rely on an LLM to
summarize context during compression, adding latency and costs that defeat the purpose.
Before adopting these tools, profile your context usage and rigorously evaluate both net cost and task
accuracy; token reduction means nothing if prompt caches break or agent performance degrades.
Opt for tools that compress tool outputs while preserving references to the raw data and that prune
history only in one shot at task boundaries, to protect cache prefixes.
45. Stacked pull requests
Caution
Stacked pull requests break a large change into an ordered chain of small, dependent pull requests
(PRs). Rather than targeting the main repository branch, each subsequent PR targets the branch
directly below it in the stack. We’ve seen a surge in interest in this technique recently due to the
rapid adoption of AI-assisted coding tools. Teams adopt this approach to reduce review latency and
developer idle time. By evaluating small, isolated layers, reviewers face lower cognitive overhead.
Tooling has also improved to support this workflow; GitHub recently introduced native support.
Despite better tooling, we’ve placed this technique in the Caution ring because it’s often a workaround
for poor upfront decomposition. Stacking doesn’t create decomposition problems; it exposes ones
that were already there. The risk isn’t the technique itself; it’s using it as a substitute for that planning.
Habitual, undifferentiated stacking can easily become an excuse to write one enormous change. We
maintain that the better habit is to specify, split, size and deliver work as small, independent units.

47. Kafka share groups
Trial
Kafka share groups (introduced in KIP-932, production-ready since Kafka v4.2) bring a new
cooperative event consumption model to Kafka, enabling queue-like behavior. Historically, Kafka’s
traditional consumer groups have imposed a concurrency bottleneck because the number of active
consumers can’t exceed the number of partitions. Share groups remove this constraint: individual
records are handed to any available consumer in the pool under a per-record acquisition lock,
which the consumer must explicitly acknowledge. On failure or timeout, the record is released and
redelivered to any consumer in the group, up to a configurable maximum number of delivery attempts.
This provides at-least-once delivery with the possibility of duplicate-processing. Records that exhaust
their delivery attempts are archived; dead-letter queue support (KIP-1191) is not yet available.
The tradeoff is that share groups don’t guarantee per-partition ordering because records are
dispatched and redelivered independently. However, for teams that previously had to run both
Kafka and an external queue system, share groups can simplify the architecture by consolidating
workloads onto Kafka.

Trial

Trial

57. Agent Client Protocol (ACP)
Assess
While CLI-based coding agents excel at repo-wide implementation and workflow execution,

62. Decision models
Assess
A new class of AI models called decision models has emerged since the last Radar. TypeSafe AI
released Jev, which it calls a “system one” model, built to make fast, structured decisions. Many other
models have followed, including Laya, Nimble and Kev. In contrast to deliberative reasoning models,
decision models output predefined structured values instead of generated text. Rather than using
reinforcement learning from human feedback (RLHF) to optimize for human preferences, Jev uses
reinforcement learning from calibrated decisions (RLCD) to optimize for well-calibrated decisions,
where predicted probabilities reflect how often an outcome actually occurs. Their smaller, structured
outputs enable faster and cheaper processing.
Decision models receive a state and a set of questions. Every question asked against the state must
map to one of three types: Noul for yes/no questions
that return the probability of a “yes” answer, Choice for categorized multiple-choice options or Score
for evaluations on an ordered list of levels or a numerical scale. Decision model use cases include
Jev-as-a-judge as an alternative to LLM-as-a-judge, model and tool routing, policy gates and bulk
labeling. We recommend teams avoid overenthusiastic LLM use and define evaluation criteria to
determine whether a decision model can replace an LLM for classification use cases.

64. llm-d
Assess
llm-d is an open-source distributed inference serving stack designed to operate model servers such
as vLLM and SGLang across multiple Kubernetes nodes. Traditional web applications often rely on
stateless routing and horizontal scaling, but LLM inference is highly stateful due to key value (KV)
caching. Rather than treating model-serving pods as interchangeable HTTP backends, llm-d uses
inference-aware routing to coordinate requests across multiple accelerators, extending optimization
beyond individual model servers.
Built around Kubernetes and the Gateway API Inference Extension, llm-d offers several capabilities
tailored to stateful AI traffic. It supports model-aware and KV-cache-aware routing, using factors
such as cache affinity, queue depth and predicted latency to guide scheduling decisions. A notable
feature is prefill and decode disaggregation, which allows operators to place compute-intensive prefill
workloads on one set of GPUs and memory-bandwidth-bound decoding tasks on another. This can
improve hardware utilization and reduce inference costs. Teams building large-scale GPU inference
platforms should assess llm-d as an emerging foundation for their inference layer, particularly when
looking to scale while meeting strict latency objectives.
65. Netris
Assess
Netris is an out-of-band network automation and multi-tenancy platform for physical data centers
and AI infrastructure. Using a declarative, infrastructure-as-code model accessible through a UI,
an API, Kubernetes CRDs and Terraform, it simplifies network management by abstracting switch
configurations into cloud-style virtual private clouds (VPCs), virtual networks, access control lists
(ACLs) and Layer 4 load balancers. A central controller manages policies while lightweight agents
execute changes on switches and data processing units (DPUs). The controller operates out-of-
band as an automation control plane, so packet forwarding can continue uninterrupted even if the
controller goes offline.
We’re highlighting Netris for its support of high-bandwidth AI workloads. It automates routed
Ethernet VPN (EVPN) fabrics, manages flow control for RDMA over Converged Ethernet (RoCE) and
orchestrates NVIDIA BlueField DPUs for hardware-enforced multi-tenancy. It also integrates with
NVIDIA UFM for InfiniBand partition keys (PKeys) and NMX-C for NVLink domains, helping manage
multi-tenant boundaries across different AI fabrics through a unified management layer. We’re placing
Netris in Assess for teams building automated private clouds or AI data centers, although teams
should evaluate compatibility with their switch operating systems, such as SONiC, Cumulus Linux and
Arista EOS, as well as the boundaries of bare-metal orchestration support.

66. Omnigent
Assess
Omnigent is an open-source meta-harness, released by Databricks, that sits above coding agents
such as Claude Code, OpenAI Codex and Pi, as well as agents defined in YAML. It provides a common

67. VAST DataStore
Assess
VAST DataStore is the storage layer of the VAST Data platform. It provides file (NFS and SMB),
object (S3) and block (NVMe/TCP) access through a unified namespace. Its disaggregated shared-

capacity and performance to scale independently. We’re assessing it because storage throughput

it’s expensive and ties you to VAST’s broader data platform, so it may be more than teams need unless
they’re training models or running large-scale inference. We think VAST DataStore is worth assessing
for teams designing large GPU clusters for AI and high-performance computing (HPC) workloads,
where data loading, checkpointing and metadata-heavy access to billions of files can leave expensive
GPUs waiting on storage.

68. mise
Adopt
Since our last assessment, mise has evolved from a high-performance alternative to asdf into a
default frontend for the development environment. We’re keeping it in Adopt because it consolidates
three fragmented concerns (tool and language versioning, environment variable management and task

73. ast-grep
Trial
ast-grep is a command-line tool for structural code search, linting and rewriting. Patterns are written

Trial

90. DeepSeek Harness (DSH)
Assess
DeepSeek Harness (DSH) is an open-source runtime from DeepSeek AI for building customized coding
and general-purpose agents. Rather than offering a monolithic assistant, DSH uses an “everything
is a plugin” architecture powered by the Cordis kernel. The model adapter, tool registry, session log
and agent loop are all plugins, organized into profiles: named plugin lists that you extend and override
in your own YAML.
Cordis is a meta-framework built around spatiotemporal composability: plugins contribute registrations
as reversible effects, so reloading and teardown unwind them predictably rather than leaving dangling
state. The combination of this plugin architecture and spatiotemporal composability could provide a
foundation for domain-specific enterprise harnesses and future self-improving harnesses.
DSH also treats observability as a first-class concern. Every model-visible interaction, including
prompts, context injections, tool calls and subagent collaborations, is captured in an append-only
session log. This allows runs to be inspected, resumed, forked, searched and replayed, providing a
record of what a recomposed system actually did.

Openness comes with a cost, however. Entire CLI keeps a permanent record of how each person
prompts, and anyone with access to the repository can read it. When we tried introducing it to other
teams, some developers pushed back. A coding agent can feel like a personal assistant, and they
weren’t comfortable sharing everything they asked it with the team. For those teams, AgentsView
offers a local alternative, letting developers review their own sessions without sharing them. We
suggest trying Entire CLI in highly collaborative teams with a strong culture of trust. It stays in Assess
because our experience comes from one internal team, and we don’t yet know how other teams can
adopt it comfortably.

92. FreeToken
Assess
FreeToken is an open-source inference engine designed to run large open-weight mixture-of-experts
(MoE) models on consumer hardware. As these models become more capable, their full weights can
exceed the memory limits of consumer GPUs. Unlike general-purpose local model runners, FreeToken
specializes in oversized MoE models by adaptively combining GPU memory, CPU execution, host
memory and PCIe bandwidth. It dynamically caches active experts on the GPU and swaps them based
on which experts are activated. By coordinating this process, FreeToken enables developers to run
much larger models on existing or older hardware. We’re starting to see MoE offloading techniques
incorporated into broader tools such as llama.cpp, which is used by Ollama, but FreeToken offers a
specialized approach worth assessing.
93. GLM
Assess
As the capability gap between open and closed AI models shrinks, the GLM model family by Z.ai
stands out for its performance on software engineering workloads. Using a roughly 700-billion-
parameter mixture-of-experts (MoE) architecture, models such as GLM-5.3 achieve strong benchmark
results in coding, reasoning and agentic tasks, driven largely by specialized post-training rather than
pretraining scale alone. This makes GLM-5.3 one of the best open-weight models currently available
for coding and software engineering.
We like GLM because it provides teams with an open-weight alternative that competes with
proprietary frontier models and complex reasoning tasks. However, in our experience, the model can
sometimes “think” too much, overanalyzing straightforward prompts. We advise teams to configure
the reasoning effort based on the complexity of the workload.
94. Habit Hooks
Assess
Habit Hooks is an open-source code-quality coaching tool for AI coding agents. It runs existing static-
analysis and linting tools such as Ruff, ESLint, Knip, PMD, deptry and jscpd. Instead of returning raw
linter errors, it translates tool-specific rule violations into actionable forward guidance and code
smell context. A bare linter violation tells an AI agent that a check has failed but might encourage a
superficial change that merely satisfies the rule. Habit Hooks maps the finding to the associated code
smell and deterministically injects explicit guidance into the model’s prompt. This context helps the
agent address the actual design problem and self-correct immediately without relying on an LLM to
generate the recommendation. The tool provides a practical implementation of feedback sensors for
coding agents, integrating deterministic checks into the implementation loop so agents can respond
to failures before human review.
95. Herdr
Assess
Herdr is an open-source terminal multiplexer and runtime designed to manage multiple coding agent
sessions. It provides familiar multiplexer capabilities such as panes, keyboard navigation, detaching
and reattaching, making it easier for developers to migrate from tools such as tmux. Herdr keeps
agents running in persistent terminal sessions while exposing agent-aware states such as working,
blocked, done and idle. Integrations via a CLI allow agents to create panes, exchange prompts and
coordinate work.

As developers increasingly run parallel coding agents across multiple workspaces, keeping track of
which sessions require attention and how to resume interrupted work has become a new workflow
challenge. Tools such as T3 Code, Orca and Paseo provide alternative experiences for developers who
prefer a GUI. Teams managing parallel agents should assess Herdr if they want persistent sessions

96. Hunk
Assess
Hunk is an open-source terminal diff viewer for reviewing changes made by coding agents. It displays
a GitHub pull request or a Git, Jujutsu or Sapling changeset as a multi-file review with a file sidebar
and split or unified layouts. A watch mode refreshes the view as an agent edits the working tree. An
agent can load Hunk’s agent skill to drive a live review session, jumping to a file or Hunk and adding
notes alongside the lines it changed. Reviewers can then read the agent’s reasoning next to the
relevant code. Those notes distinguish Hunk from syntax-aware diff tools such as Difftastic.
We aren’t sure line-by-line human review of agent output will remain the norm, but many teams
still need it today: skimping on it can lead to complacency with AI-generated code. The project
started in March 2026 and hasn’t yet reached version 1.0. Teams that review agent changes in the
terminal should try Hunk and assess whether the agent’s notes make reviews faster or simply give
reviewers more to read.
97. nono.sh
Assess
nono.sh is an open-source security shell and lightweight sandbox designed to run AI agents
without the overhead of traditional virtual machines or Docker containers. It addresses a common
gap: although sandboxing is widely recommended, setup overhead can discourage teams from
implementing it. nono.sh isolates agent processes directly at the OS level using native kernel features
such as Landlock on Linux and Seatbelt on macOS. It operates in-process as native host processes
without background daemons, blocking access to sensitive host assets, such as SSH keys, by default.
We think nono.sh is worth assessing because it lowers the barrier to process isolation. Its minimal
design makes it straightforward to configure, test and integrate into existing workflows across macOS,
Linux and Windows through WSL2. Security profiles can be tweaked, forked and shared across teams
or the broader community through the nono registry, providing a low-overhead layer of defense for
developers adopting autonomous tools such as Claude Code or OpenAI Codex.
98. OpenResearch CLI (orx)
Assess
OpenResearch CLI (orx) is an open-source harness that turns coding agents such as Claude Code into
research agents that run experiments in parallel. Each experiment is isolated in its own Git worktree,
so attempts don’t interfere with one another. All experiments use the same run command, which keeps
results comparable, and every run is pinned to an immutable snapshot of the code for reproducibility.
Because orx runs on compute you choose (local, Slurm, Kubernetes or Modal) teams can implement
a method from a paper, reproduce its experiments and then test whether its results hold in their
enterprise context. This can help identify the gap between academic results and enterprise practice.
We think orx is worth assessing as a promising domain-specific harness for narrowing that gap.

99. Safe Chain
Assess
Safe Chain is a free tool from Aikido that wraps the package managers for Node.js and Python,
such as npm, pnpm, Bun, pip and uv. It sends package downloads through a local proxy that blocks
versions published in the last 48 hours and any package Aikido’s open threat feed lists as malicious.
Worms such as Shai-Hulud have shown how quickly a compromised package can spread, and a short
delay gives scanners time to catch a bad release. Most package managers now have a minimum
release age setting, and teams should configure it in their projects. Safe Chain covers what those
settings miss, such as a one-off npx command outside any project, or malicious packages older
than the age limit.
Safe Chain covers only two ecosystems, but both have been targets of supply chain attacks. A version
blocked for its age produces only a generic notice that packages were suppressed. Teams pulling
through a private mirror with its own age limit gain little, and the malware blocking depends on a single
vendor’s feed. Safe Chain is licensed under the AGPL or a commercial license, so check the terms
before building it into anything you distribute.
100. Swamp
Assess
Swamp is an automation tool built to be used by AI coding agents. When an agent carries out an
operational task directly, it may do it differently each time and leave little record of what it did. With
Swamp, the agent writes the automation instead, as TypeScript models of external systems and
YAML workflows that chain the models’ methods together. The workflows follow the same defined
process every time, their definitions live in a Git repository and the output from each run is kept as
versioned data the agent can query later. Credentials are injected from a vault at runtime, so they stay
out of prompts. Models can also be packaged as extensions and shared through a registry. An agent
instructed to write and commit scripts without Swamp can produce something similar, but without
built-in typed interfaces, run history or reusable modules.
Swamp replaces System Initiative, which we featured in Assess in a previous volume. Swamp grew
out of infrastructure management but is aimed at operational workflows more broadly, from incident
response to data pipelines. The source is open under AGPLv3, although the official distribution uses
a commercial license that requires a subscription for use at work. The project is new and moves fast,
with a fresh release for every commit, so teams should try it on low-risk internal automation before
depending on it.
101. Vale
Assess
Vale is a linter for prose. It parses Markdown, AsciiDoc and reStructuredText, skips code blocks and
checks the text against style rules stored as YAML in the repository, so writing conventions can be
enforced in the editor and in CI, much like code style. Packaged styles cover the Google, Microsoft
and Red Hat documentation guides; others check for inclusive language or readability, and you can
write your own. Vale has been part of docs-as-code toolchains for years, but the volume of LLM-
drafted documentation, ADRs and PR descriptions makes it more relevant now. Packages such as
vail-ai-tells flag the phrasing typical of generated text, and Vale works well as one of the feedback
sensors for coding agents, allowing an agent to revise a draft before anyone reads it.

102. Varlock
Assess
Varlock is an open-source environment configuration and secrets-management layer designed to
avoid exposing secrets to coding agents via plaintext. Instead of relying on informal .env.example
conventions, Varlock introduces a committed .env.schema that describes variable names, types,
validation rules and documentation. It separates the configuration contract from the actual values.
Secrets are resolved and injected at runtime from external vaults such as 1Password, AWS Secrets
Manager or Azure Key Vault. For workloads where an agent must call an authenticated service, Varlock
also offers a credential proxy that provides a placeholder to the agent and substitutes the real value
only at the network boundary. We’ve found this to be a useful pattern that replaces ad hoc helper
scripts and extends secret injection across multiple environments without exposing credentials.
103. zizmor
Assess
zizmor is a static analysis tool for GitHub Actions workflows that also checks Dependabot and pre-
commit configurations. It flags misconfigurations attackers can exploit, including template injection,
overly broad permissions and actions pinned to mutable tags as well as the use of risky triggers such
as pull_request_target. It can also fix some findings automatically.
This year, attackers exploited a pull_request_target workflow in the Trivy repository, then rewrote the
tags of its GitHub Action so pipelines referencing those tags ran the attackers’ code. Our teams have
used zizmor on client work, running it from the command line and as a pre-commit hook while writing
workflows. Coding agents can run it too, providing quick feedback on the pipelines they write.
Amid the attention on AI-powered security scanning, we like having a deterministic tool for this job.
Snyk and Wiz cover some of the same ground commercially and general linters catch some of these
issues, but zizmor is free and open source. Its drawback is scope: it doesn’t cover any other CI
platforms beyond GitHub Actions. Teams using GitHub Actions should evaluate zizmor alongside zero
trust security for CI/CD.

104. Open Data Contract Standard (ODCS)
Adopt
The Open Data Contract Standard (ODCS) defines data contracts declaratively in YAML, covering
a data product’s schema, quality expectations and service levels. It’s developed by the Linux
Foundation’s Bitol project, which graduated in July 2026. Although several competing standards and
homegrown formats exist, ODCS has emerged as a leading standard, with the maintainers of Data
Contract CLI deprecating DCS in favor of ODCS.
Several of our clients building data meshes and data products are moving to ODCS, often alongside
the Open Data Product Standard (ODPS). Interest in data contracts is also growing, partly because
their declarative format makes them easier for both humans and AI agents to interpret, review and
validate. We’re placing ODCS in Adopt as a sensible default for teams building data products.
105. BoTorch
Trial
BoTorch is an open-source, PyTorch-based framework for Bayesian optimization. While Bayesian
optimization is often used for hyperparameter tuning, we’re seeing it increasingly applied to real-
world scientific and engineering problems. When standard tools for this challenge fall short, BoTorch
provides the modularity and low-level control needed to construct probabilistic models and custom
acquisition functions.
Paired with Ax for experiment orchestration, BoTorch excels in domains such as product formulation
and R&D optimization, where physical or experimental evaluations are costly and exhaustive search is
impractical. In these complex search spaces, BoTorch helps teams efficiently navigate trade-offs and
maximize a limited evaluation budget.
106. Deep Agents
Trial
Deep Agents is an open-source agent harness from LangChain, built for long-running tasks. Deep
Agents provides an opinionated architecture for breaking down problems, delegating work to
subagents and managing execution. It includes key harness features such as planning tools, agent
skills, memory, human-in-the-loop checkpoints and filesystem access.
Available as Python and TypeScript libraries, Deep Agents integrates well with LangChain and
LangGraph. It’s particularly useful when specific steps in a complex agentic graph require a capable,
long-running agent. In our experience, it complements multi-agent research and legacy modernization
use cases and integrates with the broader LangChain ecosystem, including observability
tools like Langfuse.

running and managing AI agents. Instead of requiring bespoke infrastructure, the framework turns
agents into standard Kubernetes custom resource definitions (CRDs) that teams can deploy, scale

108. OpenFGA
Trial
OpenFGA is an open-source, fine-grained authorization system inspired by Google’s Zanzibar. It

109. Presidio
Trial

112. CALM
Assess
The Common Architecture Language Model, or CALM, is an open-source specification from FINOS
for defining software architectures in a standardized, machine-readable format. Built on an extensible

In large enterprises, ensuring systems follow established design patterns can be challenging. CALM

113. Hindsight
Assess
Hindsight is Vectorize’s open-source memory system for AI agents. An LLM extracts facts, entities
and timestamps from conversations and stores them in Postgres. Recall combines semantic,
keyword, graph and time-based search and reranks the results. A reflect operation consolidates
stored memories into observations and “mental models” that evolve as new evidence arrives. This
consolidation sets it apart from Mem0, which extracts and stores the facts it judges most relevant.
Hindsight maintains a separate memory bank for each user or agent and can be self-hosted or
used through the managed Hindsight Cloud service. Agents connect to it through SDKs, framework
integrations or an MCP server.
Hindsight is particularly useful for custom-built agents that need memory across sessions. One of our
teams used it in a hackathon project to give agents per-user memory that improves over repeated
sessions. Hindsight also has plugins for coding agents such as Claude Code, although those agents
already have their own mechanism for retaining memory across sessions. The vendor reports leading

114. Quint
Assess
Quint is a formal specification language based on the underlying calculus of TLA+, the temporal
logic of actions. Like TLA+, it’s designed to help you find subtle bugs in complex systems involving
concurrency. Quint distinguishes itself from TLA+ through its readability and developer experience. It
has a TypeScript-like syntax that makes review easier, especially when agents write the specification.
It also has a type checker, REPL and simulator and can be installed with npm. The simulator exercises
the model inexpensively with randomized runs and can also generate traces from the spec to test
an implementation. Our teams have found the choice between Quint and TLA+ a close call, weighing
Quint’s tooling against TLA+’s maturity. We hope that its ongoing development signals growing
momentum behind polyglot verification.
115. SolidJS
Assess
SolidJS is a declarative JavaScript library for creating user interfaces that continues to stand out
for its high performance and fine-grained reactivity. Recent updates introduce significant built-
in capabilities for asynchronous client-to-server communication. By handling these concerns
natively, SolidJS eliminates the need for external libraries to manage API calls, caching and
request deduplication. These features improve the developer experience by addressing common
asynchronous challenges, such as race conditions and loading states, directly within the framework.
SolidJS also provides detailed control over suspense boundaries, allowing developers to sequence
how asynchronous components are revealed rather than leaving their order to network availability.
Coupled with an expanding toolset that includes the SolidStart framework, SolidJS is a compelling
alternative worth exploring for building high-performance web applications.
116. spartan/ui
Assess
spartan/ui applies the approach of shadcn to Angular. You install accessible, unstyled primitives
built on the Angular CDK from npm and combine them with styled components that live in your own
source code. This division is central to the design: accessibility, behavior and state are maintained by
upstream libraries, while you control the styling.
It’s a credible Angular Material alternative. One of our teams used it as the basis for a branded
component library across several applications, avoiding the need to build a design system from
scratch and reducing the effort required to build and maintain shared components. spartan/ui reached
version 1.0 in June 2026, but it’s still relatively young. We’ve encountered some rough edges when

117. TLA+
Assess
TLA+ is a formal specification language for identifying design flaws in distributed systems. When we
last blipped it in 2015, the investment was too high for all but critical systems. Since then, coding
agents have changed the calculus: the cost of using TLA+ has gone down, while its value has gone
up. TLA+’s awkward developer experience is no longer a blocker, although teams looking for friendly
syntax might prefer Quint. We’ve observed teams verify application traces against a TLA+ model
without prior experience.
Meanwhile, developers now have greater need for quality assurance techniques to manage agent-
generated code. Where TLA+ was once the preserve of organizations like AWS, which used it to
find subtle bugs in DynamoDB, it’s now part of a broader trend of polyglot verification, alongside
techniques like mutation testing and property-based unit testing.
