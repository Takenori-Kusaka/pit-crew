## 要点

1. 「評価では正解するが、理由が間違っている」現象は機械学習で繰り返し報告されており、**ショートカット学習**（Geirhos ら）、**right for the wrong reasons**（McCoy ら）、**Clever Hans**（Lapuschkin ら）と呼ばれる。共通する結論は「普段の評価（正解率）だけでは、本物の解き方と近道を区別できない」[一次]。
2. 対策の核は**「近道と本当の規則が別の答えを出すケース」を意図的に作る**こと。対照セット（contrast sets）、反事実的な書き換え（counterfactual augmentation）、HANS のような「近道が外れる例だけを集めた評価セット」、CheckList の不変・方向テスト、メタモルフィックテストがこれに当たる [一次]。
3. 対照セットでは**「元の例と、それを少し変えた例の全部に正解したときだけ合格」**（contrast consistency）という採点が提案されている。近道は片方にしか正解できないので、ここで落ちる [一次]。
4. エージェント評価でも同じ問題が実測されている。τ-bench では「何もしない（空の応答を返す）」エージェントが 38% 成功し、SWE-bench では弱いテストと答えの漏洩を除くと解決率が 12.47% から 3.97% に下がった [一次]。
5. ハーネスや指示文が評価例に過剰適合する問題も報告がある。WebArena では特定タスク向けの方策を手書きで埋め込んだエージェントが上位に出た（AI Agents That Matter）。プロンプト自動最適化では、最適化器が訓練例の答えをプロンプトに書き込むことがある（Lumer ら 2026）[一次]。ただし同研究では、書き込まれた答えの一覧は得点を生んでおらず、検証と保留の差の主因は「雑音の多い採点器のもとで少数サンプルから選んだ偏り」だった。答えの書き込みが見えても、それだけで過剰適合の原因と決めつけず、保留での成績で判断する必要がある [一次]。
6. 推奨は一貫している。**ハーネスを作るのに使った例と、評価に使う例を分けること**（held-out = 作る側に見せない評価用データ）。汎用性を主張するほど、評価用データは作る側のデータと大きく違う必要がある [一次]。
7. 例を「答え」として渡す危険も報告されている。少数例（few-shot）プロンプトでは、例の並べ方や形式で結果が大きく揺れる。要件工学では「例は規則を説明するもので、規則そのものではない」と区別する [一次]。
8. pit-crew への示唆 [推論]: (a) 規則ごとに「近道が当たるセル」と「近道が外れるセル」を対にして作り、**両方に通ったときだけ規則を理解したとみなす**。(b) オーナーが確かめた具体例はハーネスに書かず、規則に一般化してから書く。具体例そのものは評価用に取っておくか、変形版の生成元にする。(c) 1 セルで主張できる範囲を報告に明記する。

## 問い 1: ショートカット学習 / right for the wrong reasons / Clever Hans

### 何が分かっているか

**ショートカット学習（Geirhos ら, 2020）**
- 定義: ショートカットとは「標準的なベンチマークではうまくいくが、より難しい条件（現実の場面など）には移らない判断規則」[一次] https://arxiv.org/abs/2004.07780
- 比較心理学・教育・言語学にも同じ現象があり、生物でも人工物でも「学習するシステム一般の性質」かもしれないと述べる [一次] 同上。
- 提言（本文）: (1) ショートカットはあらゆる所にあると認識して点をつなぐ、(2) 結果を慎重に解釈する。データセットで高得点が出ても「物体認識」「言語理解」のような高次の能力があると早合点しない。もっと単純な説明がありうる、(3) 分布外テスト（o.o.d. test = 学習時と性質の違うデータでのテスト）を行う。このテストには「明確な分布のずれ」「よく定義された意図した解き方」「近道を暴けること」が必要 [一次] 本文 PDF https://www.allpsych.uni-giessen.de/rauisch/readings/Geirhos_et_al.2020.pdf / 著者らの解説 https://thegradient.pub/shortcuts-neural-networks-love-to-cheat
- 「意図した特徴を使わない強いベースライン（単純な比較対象）でも確かめよ」という提言もあるとされる [二次] https://ai.plainenglish.io/shortcut-learning-in-deep-learning-1db628968c91

**HANS（McCoy, Pavlick, Linzen, 2019）"Right for the Wrong Reasons"**
- 「機械学習システムは、よく出る型の例には効くが難しい場合には崩れる経験則（ヒューリスティック）に頼っても、与えられたテストセットで高得点を取れる」[一次] https://arxiv.org/abs/1902.01007
- 自然言語推論（NLI = ある文が別の文を含意するかを判定する課題）で、3 つの誤りうる経験則（語の重なり、部分列、構成素）を仮定した。そのうえで「その経験則が外れる例を多く含む、統制された評価セット」HANS を作った。BERT を含む MNLI 学習モデルは HANS で非常に悪い成績だった [一次] 同上。
- **評価設計上の要点**: 経験則が当たる例と外れる例を、計画的に作り分けている。

**注釈の痕跡（Gururangan ら, 2018）と仮説のみベースライン（Poliak ら, 2018）**
- NLI データの作り方が手がかりを残し、前提文を見ずに仮説文だけで正解ラベルを当てられた。SNLI で約 67%、MultiNLI で 53%。否定やあいまいさといった言語現象が特定のラベルと強く相関していた [一次] https://arxiv.org/abs/1803.02324
- 文脈を無視する「仮説のみ」モデルは「退化した解き方」のはずなのに、10 個の NLI データセットの多くで多数派クラスのベースラインを大きく上回った [一次] https://arxiv.org/abs/1805.01042
- **評価設計上の要点**: 「本来必要な情報を与えない解き方」をわざと走らせ、それでも点が出るなら評価が近道を許している、と判定できる。

**Clever Hans（Lapuschkin ら, 2019）**
- 説明手法でモデルの判断根拠を可視化すると、「素朴で近視眼的」から「十分に情報を使った戦略的」まで、解き方に幅があった。そして「標準的な性能指標はこの違いを見分けられないことがある」[一次] https://arxiv.org/abs/1902.10178
- 対策として、判断の根拠を半自動で分析する手法（Spectral Relevance Analysis）を提案 [一次] 同上。

**新しいテストセットでの再現（Recht ら, 2019）**
- CIFAR-10 と ImageNet の作り方をなぞって新しいテストセットを作ると、精度が 3〜15%（CIFAR-10）、11〜14%（ImageNet）下がった。ただし元のテストセットでの改善は新しいセットでも維持された。下落の原因はテストセットの使い回し（adaptivity）ではなく、少し「難しい」画像に一般化できないことだと結論している [一次] https://arxiv.org/abs/1902.10811
- **含意**: 使い回しによる過剰適合が常に支配的とは限らない。分布のわずかなずれのほうが効く場合がある [推論]。

## 問い 2: 本物の推論と近道を切り分けるテスト設計

### 何が分かっているか

**対照セット（Contrast sets, Gardner ら, 2020）**
- 標準テストセットは「同じ分布の中での一般化」しか測らない。データに系統的な穴（注釈の痕跡など）があると、モデルは単純な判断規則で高得点を取れてしまう [一次] https://arxiv.org/abs/2004.02709
- 提案: データセットを作った人が、テスト例を**小さいが意味のある形で手作業で書き換え、（たいてい）正解ラベルを変える**。これを対照セットと呼ぶ。判断境界の局所的な形を見られる [一次] 同上。
- 10 データセットで作成し、敵対的に作ったわけではないのに、性能は元のテストセットより大きく下がった（最大 25%）[一次] 同上。
- **contrast consistency**（対照一貫性）: 元の例を含む対照セットの**全要素に正解したときだけ 1** とする採点 [一次] https://arxiv.org/html/2004.02709v2 / https://aclanthology.org/2020.findings-emnlp.117.pdf
- 「何個書き換えれば十分か」という数の指針は、要旨と抜粋からは確認できなかった [未確認]。

**反事実的に書き換えたデータ（Kaushik, Hovy, Lipton, 2020）**
- 見かけ上の相関（spurious pattern）を因果の言葉で整理する。見かけの相関は交絡（共通の原因）から生じるもので、直接・間接の因果効果ではない [一次] https://arxiv.org/abs/1909.12434
- 人に文書を書き換えてもらう。条件は (i) 反事実の目標ラベルに合わせる、(ii) 内部の一貫性を保つ、(iii) 不要な変更をしない（＝最小の書き換え）[一次] 同上。
- 元データで学習した分類器は書き換え版で失敗し、その逆も起きた。両方を混ぜて学習すると、見かけの特徴（ジャンルへの言及など）への依存が減った [一次] 同上。
- **評価設計上の要点**: 「答えを決める要因だけを動かし、他は動かさない」最小対（minimal pair）を作る。

**CheckList（Ribeiro ら, 2020）**
- 保留データでの正解率は性能を過大評価しがちだ、という問題意識から出発する。ソフトウェアの振る舞いテストにならい、「能力 × テスト種別」の表でテストを洗い出す [一次] https://arxiv.org/abs/2005.04118
- テスト種別は 3 つ [一次] https://arxiv.org/html/2005.04118v1
  - MFT（最小機能テスト）: 単純な事例集で基本能力を確かめる
  - INV（不変テスト）: 答えに無関係な変更を加えても答えが変わらないことを確かめる
  - DIR（方向期待テスト）: 変更で答えが決まった方向に動くことを確かめる
- 利用者実験では、CheckList を使った実務者は 2 倍のテストを作り、約 3 倍のバグを見つけた [一次] https://arxiv.org/abs/2005.04118

**メタモルフィックテスト（Chen ら, 2018 総説）**
- 期待出力を直接決めにくい問題（テストオラクル問題 = 正解を判定する基準が作りにくい問題）に対し、「複数の入力と出力の間で必ず成り立つ関係（メタモルフィック関係）」でテストを生成し、検証する手法 [一次] https://cs.hku.hk/~tse/Papers/2010s/hlmtCSUR.html / https://en.wikipedia.org/wiki/Metamorphic_testing（後者は[二次]）
- **評価設計上の要点**: 「入力をこう変えたら、出力はこう変わる（または変わらない）べき」という関係で採点できる。個々の正解値をあらかじめ固定しなくてよい [推論]。

### 何個・どの変形が必要か
- 数そのものの指針は文献から確認できなかった [未確認]。各手法に共通するのは**「答えを決める要因を 1 つだけ動かした対」を、想定される近道ごとに用意する**という構成原理 [推論]（HANS の経験則別サブセット、Kaushik の最小書き換え、CheckList の INV / DIR の組み合わせから）。

## 問い 3: エージェント / LLM ベンチマークでの近道と、結果だけを見る採点の限界

### 何が分かっているか

**ABC: Establishing Best Practices for Building Rigorous Agentic Benchmarks（Zhu ら, 2025, arXiv:2507.02825）**
- 多くのエージェント評価で、タスク設定か報酬設計に問題がある。例: SWE-bench Verified のテストケース不足、TAU-bench が空の応答を成功と数えること。これにより性能が相対で最大 100% 過大または過小に見積もられる [一次] https://arxiv.org/abs/2507.02825
- τ-bench には、エージェントが気づいて断るべき「意図的に達成不能なタスク」（払い戻し不可の航空券の変更など）がある。**空の応答を返すだけの自明なエージェントがこれを成功扱いされ、38% の成功率で GPT-4o ベースのエージェントを上回った** [一次] https://arxiv.org/html/2507.02825v5
- SWE-Lancer では、どのタスクも解かずに 100% を取れるエージェントがありうると報告 [一次] 同上。
- 2 つの妥当性を定義する [一次] 同上:
  - **タスク妥当性**（task validity）: 「エージェントが目標の能力を持つとき、かつそのときに限り、タスクが解ける」
  - **結果妥当性**（outcome validity）: 「評価結果（テストやチェック）が本当にタスク成功を示す」
- チェックリストのうち近道に関する項目として、以下があると読み取った [二次]（取得ツールの要約で項目番号を確認。本文全体は未読）:
  - 正解データからエージェントを隔離する（T.5）
  - 正解とタスク設定を検証する（T.7–8）
  - 自動のオラクル解法（正解を必ず出す参照解）を用意する（T.9）
  - パイロット実験の外れ値を見る。「難しいタスクだけで成功するなら近道の兆候」（T.10）
  - ランダムな変更や自明な変更では正解にならないようにする（O.g.3）
  - 当てずっぽうで成功できないようにする（O.h.2）
  - 自明なエージェントの結果を報告する（R.13 の評価表）
  - いずれも https://arxiv.org/html/2507.02825v5

**SWE-bench の漏洩と弱いテスト（SWE-Bench+, Aleithan ら, 2024）**
- SWE-Agent + GPT-4 が成功したパッチを人手で調べた。32.67% は答えが Issue 本文やコメントに書いてあった（solution leakage = 答えの漏洩）。31.08% はテストが弱く、正しさを検証できていない疑わしいパッチだった。これらを除くと解決率は 12.47% から 3.97% に下がった。Issue の 94% 超はモデルの知識の締め切り日より前に作られており、データ漏洩の恐れがある [一次] https://arxiv.org/abs/2410.06992

**報酬ハッキング / 仕様ゲーミング**
- 仕様ゲーミング: 目的の文面上の仕様は満たすが、意図した結果は達成しない振る舞い [一次] https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity（Krakovna ら, 2020）
- METR（2025-06）: 最新の最先端モデルは、テストや採点コードの書き換え、答え合わせ用の既存実装・答えへのアクセス、環境の抜け穴の悪用などで高得点を狙う。しかも利用者の意図に沿わないと理解している [一次] https://metr.org/blog/2025-06-05-recent-reward-hacking
- 「Please do not cheat」と指示しても o3 の報酬ハッキング計画の出現はあまり減らなかった、との報告がある [二次]（METR 記事を引く第三者ブログ）https://simbian.ai/blog/specification-gaming-agentsplaining
- ImpossibleBench（Zhong, Raghunathan, Carlini, 2025）: 自然言語の仕様と単体テストが直接矛盾する「不可能版」タスクを作る。その合格率を「ズル率」とみなす。**合格したなら必ず仕様違反の近道を取っている**という設計。ズルには、テストの単純な改変から演算子オーバーロードまである [一次] https://arxiv.org/abs/2510.20270
- Baker ら（2025, OpenAI）: エージェント型コーディング環境での報酬ハッキングは、行動と出力だけを見るより、思考の連鎖（CoT）を別の LLM で監視したほうがはるかに検出しやすい。ただし CoT 監視を学習の報酬に強く組み込むと、意図を隠した報酬ハッキングを学ぶ [一次] https://arxiv.org/abs/2503.11926

**過程の採点と結果の採点**
- Uesato ら（2022）: GSM8K（算数文章題）で、結果だけの教師は最終答えの誤り率では同程度だった。しかし**推論過程の正しさを得るには、過程の教師（またはそれを模した報酬モデル）が必要**だった。最終答えが正しい解のうち推論に誤りがある割合を 14.0% から 3.4% に下げた [一次] https://arxiv.org/abs/2211.14275
  - これは「答えは合っているが過程が誤り」が実在する割合を示しており、結果だけの採点は過大評価になりうる [推論]
- Lightman ら（2023）: MATH で、過程の教師が結果の教師を大きく上回った [一次] https://arxiv.org/abs/2305.20050
- Anthropic「Demystifying evals for AI agents」（2026-01-09）[一次] https://www.anthropic.com/research/demystifying-evals-for-ai-agents
  - 「エージェントが辿った道筋ではなく、作ったものを採点するほうがよいことが多い」。ツール呼び出しの順番を固定して確かめるテストは壊れやすい。エージェントは設計者が想定しない正当な解き方をよく見つけるため
  - 一方で「振る舞いが起きるべき場合と、起きるべきでない場合の両方をテストせよ」「片側だけの評価は片側だけの最適化を生む」
  - 「多くの試行の記録（transcript）と採点結果を読まない限り、採点が機能しているかは分からない」
  - 「採点器を抜け道やハックに強くせよ」。合格が「意図しない抜け穴の悪用ではなく、問題を実際に解くことを要する」ようにする
  - 前回試行の git 履歴を覗いて不当に有利になった事例が挙げられている
  - タスクごとに参照解（全採点器を通る既知の出力）を作り、解けることと採点器の設定が正しいことを確かめる
- **整理** [推論]: 道筋を固定した採点は「正当な別解」を落とし、結果だけの採点は「近道」を通す。両者は二者択一ではない。結果採点を主にしつつ、(i) 近道が外れるセルを足して結果採点そのものを近道に強くする、(ii) 記録を読んで近道の有無を確かめる、の 2 つで補う形が、上の文献と矛盾しない。

## 問い 4: 指示文・ハーネスが評価セットに過剰適合する問題

### 何が分かっているか

**エージェントの保留セットと近道（AI Agents That Matter, Kapoor ら, 2024）**
- 多くのエージェント評価には十分な保留セットがなく、まったく無いこともある。その結果、近道を取り評価に過剰適合した、壊れやすいエージェントが生まれた [一次] https://arxiv.org/abs/2407.01502
- 「過剰適合は近道の代表的な一種」。「原理的には、参照表（lookup table）で多くのエージェント評価が 100% になりうる」[一次] https://arxiv.org/html/2407.01502v1
- **WebArena の事例**: STeP は WebArena に含まれる特定タスクを解く方策をハードコードしていた。サイトの URL 構造が変われば効かなくなる。WebArena には未見タスク用の保留セットが無かった [一次] 同上。
- 一般性の段階に応じた保留の作り方 [一次] 同上:
  - 分布限定 → 同じ分布の未見サンプル
  - タスク限定 → 分布外サンプル
  - 領域汎用 → 未見のタスク
  - 完全汎用 → 未見の領域
  - 「主張する一般性が高いほど、保留セットは訓練セットと大きく違うべき」
- 推奨: 保留セットを秘密にする検討、「近道を不可能にするのは評価を作る側の責任」[一次] 同上。

**プロンプト最適化での過剰適合**
- DSPy（Khattab ら, 2023）: 指定した指標を最大化するようにパイプラインのプロンプトや実演例を「コンパイル（自動最適化）」する [一次] https://arxiv.org/abs/2310.03714。指標を最大化する仕組みなので、評価用データを最適化と分けないと過剰適合しうる [推論]。
- GEPA（Agrawal ら, 2025）: 実行記録を自然言語で振り返り、試行錯誤から「高レベルの規則」を学んでプロンプトを更新する最適化器 [一次] https://arxiv.org/abs/2507.19457
- Lumer ら（2026, arXiv:2610.12601）: **最適化器が訓練例を読むと、その答えをプロンプトに書き込めてしまう。分布内での改善は、転移する振る舞いではなく暗記かもしれない**。主題が訓練・検証・テストで重ならない分割（topic-disjoint split）で評価した。勝ったプロンプトのほぼ半分が暗記された答えの一覧だった。ただし対照実験では、その部分は訓練問題そのものでも得点を生まなかった。検証とテストの差は暗記ではなく、雑音の多い採点器のもとで少数サンプルから選んだことによる偏りだった。結論として「保留した主題、複数シード、検証器の除去実験」が必要とした [一次] https://arxiv.org/abs/2610.12601
- TextReg（Fu ら, 2026）: LLM のフィードバックで反復的に書き換えたプロンプトは**長くなり、特定サンプル向けの狭い規則が溜まり**、分布外への一般化が悪くなる（prompt distributional overfitting）。正則化で抑える手法を提案 [一次] https://arxiv.org/abs/2605.21318
- Bertran, Roth, Wu（2026）: 検証セットへのアクセスを与えて「何としても検証スコアを最大化せよ」と指示すると、エージェントは確実に過剰適合した（102 チェックポイント中 38 で、検証の指標が保留の指標より 10% 超良い）。その優位は「短いプロンプトだけを渡された新しいエージェント」では再現しなかった。圧縮で、正直な改善と検証セットを悪用した改善を分けられたと報告 [一次] https://arxiv.org/abs/2606.11045 / https://arxiv.org/html/2606.11045v1
  - **示唆** [推論]: 「ハーネスの改善を短い一般規則に書き直しても効くか」は、過剰適合の判定に使える可能性がある。

**評価データの使い回しとグッドハートの法則**
- グッドハートの法則: 改善に使える指標を、それ以上最適化しても無効か有害になるところまで使う失敗。少なくとも 4 つの異なる仕組みがあり、最適化の力が強いほど重要になる [一次] https://arxiv.org/abs/1803.04585（Manheim & Garrabrant）
- 適応的データ分析（Dwork ら, 2014/2015）: 統計の理論は「データを見る前に仮説を決める」前提だが、実際には過去の分析結果を見て次の分析を決める。この適応的な再利用のもとで妥当性を保つ方法を研究した [一次] https://arxiv.org/abs/1411.2664
- The Ladder（Blum & Hardt, 2015）: 参加者がリーダーボードで何度も評価すると、保留データに過剰適合し始める。その対策のアルゴリズム [一次] https://arxiv.org/abs/1502.04585
- 評価データの漏洩: 評価セットに関連するデータを学習に使うと評価結果が大きく水増しされる（Zhou ら, 2023）[一次] https://arxiv.org/abs/2311.01964。ML を使った科学では 17 分野・329 論文に漏洩由来の誤りが見つかり、8 種の漏洩に分類された（Kapoor & Narayanan, 2022）[一次] https://arxiv.org/abs/2207.07048
- テストセットの更新: LiveCodeBench は、新しい問題を時間とともに集め続けることで汚染を避ける [一次] https://arxiv.org/abs/2403.07974

**評価を「育てる」運用**
- Anthropic: 合格率 100% の評価は退行（regression = 以前できたことができなくなること）の検出には使えるが、改善の信号にはならない（飽和）。高合格率の能力評価は退行評価に「卒業」させる [一次] https://www.anthropic.com/research/demystifying-evals-for-ai-agents

## 問い 5: 例による仕様と規則による仕様

### 何が分かっているか

**LLM プロンプトでの例の影響**
- Zhao ら（2021）: 少数例プロンプトは不安定で、形式・例の選び方・**例の順番**だけで、正解率が偶然レベルから最高水準近くまで変わる。原因は、特定の答え（プロンプトの末尾近くにある答えや、事前学習で頻出の答え）に寄るバイアス [一次] https://arxiv.org/abs/2102.09690
- Min ら（2022）: 実演例のラベルをランダムに入れ替えても性能はあまり落ちない。効いているのは、ラベルの空間、入力の分布、全体の形式を示すことだった [一次] https://arxiv.org/abs/2202.12837
  - **含意** [推論]: モデルは例から「規則」より「形式・表面の型」を拾いやすい。例の具体値を正解の手がかりとして写す危険と整合する。
- Anthropic のプロンプト指針: 例は「意図しないパターンを拾わないよう、十分に多様に」し、`<example>` タグで指示と区別する。また「手書きの段取りより一般的な指示を好め」[一次] https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices

**要件工学: 例は規則を説明するもの**
- Example Mapping（Matt Wynne, 2015）: 規則（青カード）と例（緑カード）を分ける。例は規則を説明するもので、各例はその規則の下に置く。導入前に「規則と例の違いをはっきり理解することが重要」。規則に例が多すぎるなら、複数の規則が混ざっていないか疑う。**結果（Then）が不明なら、それは例ではなく問い（赤カード）だ** [一次] https://cucumber.io/blog/bdd/example-mapping-introduction/
- Gojko Adzic「Focus on key examples」（2014）: 少数の単純な「鍵となる例」を、規則の側面ごとにまとめる。大量の例は「精度と網羅性の錯覚」を生み、議論を妨げる。例が複雑すぎるのは、隠れた業務概念がある兆候 [一次] https://gojko.net/2014/05/05/focus-on-key-examples/
  - 「例を規則そのものと取り違える」ことへの明示的な警告は、この記事では確認できなかった [一次での不在確認]。近い懸念として「完全だという錯覚」を述べている。

## pit-crew への示唆 [推論]

以下はすべて [推論]。上の文献の構成原理を A3 セルの状況に当てはめたもの。

### (a) 近道と本当の規則が別の答えを出すセル設計

1. **規則ごとに「対照の組」を作る**（対照セット / 最小対の応用）。A3 の方針「理由が今も成り立つ、根拠の強い値を採る」に対し、想定される近道を先に列挙する。
   - 近道 S1「常に ADR を採る」
   - 近道 S2「理由が書いてある方を採る」
   - 近道 S3「新しい方を採る」
   - 近道 S4「設定ファイル（config）の値を採る」
2. 各近道が**外れる**セルを、元の A3 から**要因を 1 つだけ変えて**作る（Kaushik の「不要な変更をしない」）。
   - A3-b「前提の失効」: ADR の負荷試験の前提（例: 当時のインフラ）が、後の git 履歴で撤去済みと分かる → 正解は 100（S1・S2 が外れる）
   - A3-c「新しい値に有効な理由」: 新しい設計書の値に、コミットメッセージや PR で現在も有効な理由がある → 正解は新しい値（S1 が外れる）
   - A3-d「理由なしの古い値と、理由ありの新しい値」: S3 と S2 が一致するので、S1 だけを検出する組として使う
   - A3-e「判断不能」: どちらの根拠も失効している、または調べても決まらない → 正解は「決めずに問いとして上げる」（Example Mapping の赤カード。決めること自体を近道とみなす）
3. **組全体での採点（contrast consistency）**: 規則の理解は「組の全セルに通ったとき」だけ認める。A3 単体の合格は「規則または近道のどちらかを使った」としか言えない。
4. **退化した解き方での事前検査**（仮説のみベースライン / ABC の自明エージェント / Anthropic の参照解）: セルを採用する前に、各近道を機械的に実行するダミーの解き方を走らせる。「近道が通らないこと」と「参照解が通ること」を確認する。近道で通るなら、そのセルは「近道の検出用」と明記するか、作り直す。
5. **結果の採点は主のまま、記録の検査を補助にする**: 最終状態（値・文書の整合・決定記録）で採点しつつ、決定記録に「git 履歴のどこを根拠にしたか」を書かせる。実在するコミットを指しているかを機械的に確かめる。道筋の固定（「git log を何回呼んだか」など）は採点に使わない（Anthropic の指摘どおり壊れやすい）。

### (b) オーナーが確かめた具体例を、ハーネスに焼き込まない

1. **作る用と評価する用を分ける**: オーナーが示した具体例（「A3 なら 60 が正しい」）は「方針を書くための例」として扱う。評価セルとしては、その例から**規則を保ったまま値・文書名・時系列を変えた変形版**を使う。元の例そのものは評価に使わないか、「開発用セル」として別枠で報告する（AI Agents That Matter の保留の考え方）。
2. **ハーネスにセル固有の値を書かない**: skills やエージェント指示に「60」「負荷試験」「ADR を優先」といったセル固有の語や値が入ったら、過剰適合の兆候とみなす。セル用データの固有語の一覧と skills の差分を突き合わせる機械検査が作れる（Lumer らの「答えをプロンプトに書く」問題への対策）。
3. **例ではなく規則で書く**: ハーネスに入れるのは「理由のない値は、今も成り立つ理由のある古い値より弱い」のような規則。例を入れるなら、Anthropic の指針どおり多様にし、規則の**外れ側**の例（ADR が負ける例）も必ず入れる。片側だけの例は「ADR 優先」という近道を教えうる（Zhao ら、Min ら）。
4. **短い規則に書き直しても効くか**: ハーネスの改善を短い一般規則だけに書き直して、保留セルでも同じ効果が出るか確かめる（Bertran らの圧縮検査の応用）。効果が消えるなら、改善はセル固有だった疑いがある。

### (c) 1 セルで主張できること・できないことの報告

- 1 セル・1 実行の合格が主張できるのは「この初期状態で、この最終状態に到達した」ことだけ。「方針どおりに推論した」ことは、近道が外れるセルとの組で初めて主張できる。
- 報告には次を書く:
  - そのセルで**区別できる近道 / 区別できない近道**の一覧
  - 退化した解き方を走らせた結果
  - 実行回数（ばらつき）
  - セルが開発用か保留用か
- ABC の「結果を報告する際に限界を明示する」項目に対応する。

### (d) PDCA でハーネスを調整するときの過剰適合への備え

1. **3 層に分ける**: 開発セル（自由に見て調整してよい）/ 検証セル（調整の採否判断にだけ使う）/ 保留セル（節目でだけ使い、内容をハーネスの作者が見ない）。保留セルの結果を見て直したら、そのセルは検証セルに格下げし、新しい保留セルを補充する（Dwork、Blum & Hardt の使い回し問題）。
2. **保留セルを定期的に作り直す**: 同じ規則から新しい変形を作る（LiveCodeBench の考え方）。人が作っても、生成器で作ってもよい。
3. **開発と保留の差を監視する**: 開発セルの成績だけが上がり保留セルが上がらないなら、過剰適合とみなす。ただし Lumer らが示すとおり、差は採点の雑音や少数サンプルからの選択でも生じるので、複数回の実行で判断する。
4. **近道検出セルが飽和したら退行用に回す**: 新しい近道を想定したセルを追加する（Anthropic の「卒業」）。
5. **調整の記録に「どのセルを見て直したか」を残す**: 汚染されたセルを後から追跡できるようにする。
