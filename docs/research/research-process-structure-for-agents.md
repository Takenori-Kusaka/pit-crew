## 結論の要約

1. **案 A（20 前後の工程を一列）も案 B（大工程の判定 → 詳細を読む）も、そのままでは弱点がはっきりある。** 案 A は「全部が常に文脈にある」ので工程の読み飛ばしは起きにくいが、1 ファイルに入らない（調査工程だけで 143 行・約 1 万字。9 工程なら 1,000 行超）。入れれば圧縮後に先頭 5,000 トークン以外が落ちる [一次: Claude Code docs] [推論: 量の見積り]。案 B は文脈を節約できるが、**判定の誤り**（入れ子の分岐は最も守られない: GPT-4 で 14.9% [一次: ComplexBench]）と**詳細を読まない**（本文を読むかを任せると改訂の効果が約半分 [既出]、要約があると本文を読まずに要約に従う [一次: superpowers]）の 2 つの穴が増える。
2. **最も支持が厚いのは混合案**: 大工程は少なく（9 前後）、**大工程の一覧と各工程の入る・出る条件・止める点（関門）だけを常に文脈に置き**、工程の中身は工程に入るときに 1 階層だけ読む、中身はフラットな番号付きのチェックリストにする。根拠: Anthropic の公式の「条件分岐ワークフロー」パターン [一次]、1 階層の段階的開示は規模が大きいと効き、2 階層目は効かず壊すこともある [一次: 2607.17598]、常時読み込む索引が呼び出し型を上回った [一次: Vercel]、航空チェックリストは飛行段階ごとの短いリスト＋重要項目を先頭に [一次: Degani & Wiener]。
3. **工程の判定はエージェントの推測に任せず、外に置いた状態（ファイル・成果物の有無）で決める**のが公開ハーネスの主流だった。BMAD は計画ファイルの `status` で次の工程ファイルへ分岐、GSD は `STATE.md` を読んで次の工程を決める、Spec Kit は人がコマンドを選び、前提の成果物をスクリプトで確かめる [一次: 各 raw ファイル]。研究でも、状態を外で追う SOP-Agent は 5,000 回中の失敗 9 回のうち 6 回が「分岐の選び間違い」で、判定こそが残る誤りだった [一次]。
4. **工程ごとにスキルを分けて自動発火に頼る形は、根拠が弱い。** スキルが増えると選び間違いが増え、性能低下の主因は文脈の大きさではなく選び間違いだった（202 スキルで最大 21% 低下）[一次]。superpowers では claude-opus-5-5 で TDD スキルが 3 回中 0 回しか呼ばれなかった報告がある [一次: issue #2386]。工程別に分けるなら「核のスキルが明示的に読ませる」形にする [推論]。
5. **大きな指示の害は実在するが、主因は「長さそのもの」より「関係のない内容」と「作業の長さ」**。関係のない道具を 20 個足すと成功率が 37% → 20.8% [一次: SOP-Bench]、網羅的な長いスキルはほぼ効かない（+0.7pt。ただし 5 課題）[一次: SkillsBench]。一方で**詳しい外部チェックリストは 10/10、一般的な自己点検は 5/10** [一次: 2607.17937]、粒度の違いは小さく不確か [一次: 2605.31408] という反証もある。「短く」ではなく「**今の工程に関係するものだけを、具体的に**」が当てはまる [推論]。
6. **確度は中**。コーディングエージェントで案 A と案 B を直接比べた研究は見つからなかった [未確認]。証拠は顧客対応・文書読解・汎用 SOP の研究と公開ハーネスの設計判断からの類推で、pit-crew で小さく比べる価値がある（§Q6-4 に実験案）。

## Q1. 指示の数・長さ・入れ子・書式と遵守

### 1-1 既存調査で答えが出ている点（参照のみ）

`research-conventions-and-self-review.md` §1-1〜1-4。今回の判断に使う要点:

- 規則の数: 100 個程度までは高い（claude-sonnet-4 で 10 個 100% → 100 個 94.4% → 250 個 77.2%）。失敗の多くは丸ごとの抜け
- CLAUDE.md の大きさ・位置・分割には効果が検出されず、作業が長くなるほど落ちる（関数 1 つごとにオッズ約 5.6% 減）
- 工程・順序の規則は、出力の形の規則より落ちやすい
- 多ターンで平均 39% 落ち、主因は不安定さ

→ **工程の数を 20 前後にすること自体は、規則数の点では危険域ではない** [推論]。問題は数ではなく、各工程の中身の量と、作業の長さの中で「どの工程のどの規則が今効いているか」が見失われる点にある。

### 1-2 入れ子・分岐の構造（新規）

| 研究 | 条件 | 結果 | 水準 |
|---|---|---|---|
| ComplexBench（Wen ら, arXiv 2407.03978）| 制約の組み合わせ方を And / Chain（順に）/ Selection（条件で分岐）/ 入れ子に分類、1,150 指示 | 「組み合わせの複雑さが増すと全モデルで大きく落ち、とくに Selection と Chain で落ちる」。**多層に入れ子になった Selection は GPT-4 でも一貫性テストの正答 14.9%**。付録: 「Selection を何重にも入れ子にするのは、他の入れ子より明らかに難しい。And を足しても複雑さへの影響は小さい」 | [一次] https://arxiv.org/html/2407.03978v3 |
| FollowBench（arXiv 2310.20410）| 制約を 1 つずつ足して段階を上げる | 段階が上がるほど遵守が下がる（具体値は要旨に無し）| [一次・要旨] |
| KCIF（arXiv 2410.12972）| 知識課題に単純な指示を組み合わせる | 大型・最先端モデルでも 40〜50% 低下 | [一次・要旨] |

**読み取り [推論]**: 案 B の「いまどの大工程にいるか」の判定は Selection そのもの。工程の中にさらに分岐（不具合なら / 挙動を変えるなら …）があれば入れ子の Selection になる。**分岐を 1 か所の文章の中で入れ子にすると最も守られにくい**。ただし ComplexBench は「全分岐が 1 つの指示文に同時に書かれている」条件で、案 B のように**選んだ分岐の中身だけを後から読む**形（他の分岐が文脈に無い）は測っていない。この差が案 B の利点になりうる（§1-4 の WARPP、§Q2 の SOP-Agent）。

### 1-3 書式（箇条書き・番号・見出し・表・XML）（新規）

| 資料 | 内容 | 水準 |
|---|---|---|
| He ら "Does Prompt Formatting Have Any Impact on LLM Performance?"（arXiv 2411.10541）| 同じ内容を平文 / Markdown / JSON / YAML で与える。GPT-3.5 はコード翻訳で最大 40% 変動、GPT-4 はより頑健 | [一次・要旨] |
| FlowBench（Xiao ら, arXiv 2406.14884）| 同じワークフロー知識を文章 / Python 風の擬似コード / Mermaid のフローチャートで与える。51 場面・6 領域 | 知識を与えると大きく改善。**擬似コードは弱いモデルで効きにくい、文章はどのモデルでも安定、フローチャートが総合で最良**（ターン単位の道具呼び出し F1 で +5.6〜6.5pt、セッション単位の完了では他と同程度）。著者の推測: 「整理されていて、モデルが**いまの状態を特定しやすい**ため」。3 形式を同時に与えると更に上がる | [一次] https://arxiv.org/html/2406.14884v1 |
| OpenAI GPT-4.1 Prompting Guide | 推奨の手順: まず高い水準の規則の節 → 特定の振る舞いは詳細の節を足す → **手順を踏ませたいなら番号付きリストにして従えと指示**。区切りは Markdown の見出し（H4 以上の深い階層も可）から始め、XML も良い、長い文脈では XML が良く JSON は特に悪かった。長い文脈では指示を前後両方に置くと良い。矛盾があると後ろの指示に従いやすい | [一次] https://github.com/openai/openai-cookbook/blob/main/examples/gpt4-1_prompting_guide.ipynb |
| Google Gemini API "Prompt design strategies" | 「多くの指示を 1 つのプロンプトに入れず、指示ごとにプロンプトを作り、入力に応じてどれを処理するか選べ」「多段の作業は各段を 1 プロンプトにして連鎖させよ」。区切りは XML 風タグか Markdown 見出し、1 つに決めて一貫させる | [一次] https://ai.google.dev/gemini-api/docs/prompting-strategies |
| superpowers writing-skills の flowcharts.md | 図（graphviz）は「自明でない判断点 / 早く止めすぎるループ / A と B の使い分け」だけに使い、**直線の手順は番号付きリスト**、参照情報は表 | [一次] https://github.com/obra/superpowers/blob/main/skills/writing-skills/references/flowcharts.md |

**読み取り [推論]**: 書式の効果は弱いモデルほど大きく、現行の強いモデルでは小さい。工程の書き方としては「**分岐（工程の判定）は図か条件の表、工程の中の直線の手順は番号付きリスト**」が、資料どうしで一致している。どの書式でも、判定を「状態として特定しやすく」することが効く。

### 1-4 無関係な指示が混ざることの害（新規、Q7 と共通）

| 研究 | 結果 | 水準 |
|---|---|---|
| Shi ら GSM-IC（arXiv 2302.00093）| 問題文に無関係な情報を入れると性能が大きく落ちる。「無関係な情報は無視せよ」と書くと一部回復 | [一次・要旨] |
| SOP-Bench（Nandi ら, arXiv 2506.08119）| Claude Sonnet 4.5 の ReAct 型で、関係する道具 6 個だけ → 成功率 37%、似た無関係の道具 20 個を足す → 20.8%（1.7 倍の差） | [一次] https://arxiv.org/html/2506.08119v2 |
| WARPP（arXiv 2507.19543）| 条件つきの長いワークフローで、利用者の属性から**該当しない分岐を実行時に刈り込む**と、ReAct より遵守が上がり、意図が複雑なほど差が広がり、トークンも減る | [一次・要旨] |

→ 案 B の「選んだ工程の中身だけを読む」は、他の工程の規則という「似ているが今は無関係な指示」を文脈から外す効果を持ちうる [推論]。

### 2-2 読み取り

- **構造化（状態・グラフ・段の固定）は、平らな自由文より一貫して良い結果が報告されている** [一次: 上表]。ただし、良い結果の多くは**状態の追跡をコード（ナビゲータ・固定パイプライン）が担っている**。LLM 自身が「いまどの状態か」を文章から推定する条件の比較は少ない [推論]。
- **残る誤りは分岐の選択に集中する**: SOP-Agent の失敗の 2/3、ComplexBench の入れ子 Selection、Anthropic の「分類が正確にできるとき」という条件 [一次]。案 B の弱点はここに出る [推論]。
- **平らなチェックリストを支持する証拠**: Anthropic 公式は「複雑な手順はチェックリストを応答にコピーさせて消し込ませる」を推す（既出）。後述の 2607.17937 で詳しい外部チェックリストが 10/10。feature-dev も最初に「全フェーズの todo を作れ」。いずれも**一覧を外（todo・応答）に出して追跡させる**点で、状態の外部化の一種と読める [推論]。
- **工程の誤判定・取りこぼしの報告**: Laban らの「早いターンで仮定を置いて早すぎる最終解に飛び、戻れない」[一次・要旨, arXiv 2505.06120] は、工程を飛ばして実装に入る型と同形 [推論]。superpowers の issue でも「承認の関門が飛ばされた」（#2372）、「計画スキルを呼ばずに直接実行」（#2638）、「検証行が満たされないのに工程完了を宣言」（#2510）が報告されている [一次: issue 本文または題名、§Q8-3]。

**エージェントへの当てはめ [推論]**:

- 航空と手術はどちらも「**段階（大工程）ごとに短いリストを分け、段階の切り替わりで確認する**」= 混合案の形。全部を 1 枚に並べる案 A は「76 項目の始動前リスト」に近く、飛ばしの温床になる。
- 「いまどの段階か」は人間の場合、外の状況（機体の状態・手術の進行）が明らかなので判定の誤りは起きにくい。エージェントにはその手がかりが無いので、**状態をファイル・成果物で外に出す**ことが航空の「外の状況」の代わりになる。
- 重要項目は先頭に、致命的な項目（例: 戻せない操作は承認を記録するまで進まない、報告は実物で）だけは**工程をまたいで重複させる**。それ以外は重複させない。
- メニュー研究の「深さより幅」は案 A 寄りの証拠。ただし人間の探索の速さの研究で、規則の遵守の研究ではない。エージェント側の対応する証拠（2607.17598 の「2 段目は効かない」）も同じ向きで、**階層は 1 段まで**という結論に収束する。

## Q7. 大きな指示がもたらす害と、詳しく書いた方が良かった証拠

### 7-1 量の見積り（pit-crew の設計書から）[一次: ファイルを数えた / 推論: トークン換算]

- 設計書 §4.1 調査だけで 143 行・10,238 字（表が中心）。9 工程を同じ密度で書くと 1,200〜1,300 行・約 9 万字になる
- 日本語は 1 字あたりのトークンが英語より多く、1 工程で数千〜1 万トークン程度、全工程で数万トークンと見込む（実測していない）[推論]
- 公式の上限・挙動と照らすと: SKILL.md 500 行未満の推奨を 2 倍以上超える / 圧縮後の再添付は 1 スキルあたり先頭 5,000 トークンまで / CLAUDE.md は 200 行未満の目安 [一次: 既存調査・Claude Code docs]
- → **全工程を 1 ファイルの常時文脈に置く案は、物理的に成り立たない**。案 A を採るとしても、工程の一覧は短く、詳細は別に置くことになる（＝実質は混合案）

### 7-2 害の証拠

**(a) 文脈の圧迫**

### 7-4 Q7 のまとめ [推論]

- 害の主因は「長さ」そのものより、**①いまの作業に関係しない内容（似ているものほど悪い）②作業が長くなること ③網羅的で行動につながらない文章**。一方、**いまの工程に関係する具体的な規則・チェックリストは、詳しいほど効く**側の証拠が複数ある。
- したがって設計の方向は「スキルを小さくする」ではなく、「**常に文脈にあるものは小さく（索引・判定・関門）、いまの工程の詳細は具体的に詳しく、ほかの工程の詳細は文脈に入れない**」。
- 「考え方」「典型的な失敗」のような散文は、SkillsBench の「網羅的な散文はほぼ効かない」に当たりやすい。各工程で行動に直結する「やること・出る条件」と、判断に迷ったときにだけ読む「考え方・失敗例」を分け、後者は参照に回す余地がある。

### 6-2 推奨と確度

**混合案を推す。確度: 中**（コーディングエージェントで A・B を直接比べた研究が無く、証拠は類推。ただし研究・公式指針・公開ハーネス・人間のチェックリスト研究が同じ方向を指している）。

具体形 [推論、各要素の根拠を併記]:

1. **常時の層（核のスキル本文、または `--agent` の定義）**: 9 前後の大工程の表、各工程の「入る条件・出る条件・成果物の置き場所」、工程をまたぐ原則、**致命的な項目（戻せない操作の承認・報告は実物で・未解決の印が残れば進まない 等）だけを重複して**置く。説明文には工程の要約を書かない（superpowers）。重要なことを先頭に（Degani & Wiener 指針 10、Claude Code の再添付は先頭から）
2. **判定**: 「いまどの工程か」は、状態ファイル（例: 作業の計画ファイルの `phase:`、または成果物の有無: 調査メモがあるか・失敗するテストがあるか）から決める。推測で決めた場合はそう書かせる（BMAD・GSD・Spec Kit、SOP-Agent）
3. **工程の詳細**: 工程ごとに 1 ファイル、核から 1 階層。中身は**番号付きのフラットなチェックリスト**で、工程内の分岐（不具合なら / 挙動を変えるなら）は入れ子にせず「場合の表」にする（ComplexBench、Anthropic の条件分岐パターン）。100 行を超えるなら先頭に目次（公式）
4. **工程に入るときと圧縮の後に、その工程のファイルを読み直す**規則と、読んだことを状態ファイルに記録させる（§3-1 の未確認点への備え）
5. **チェックリストを todo / 応答にコピーさせて消し込ませる**（Anthropic 公式、feature-dev、2607.17937 の外部チェックリスト 10/10）
6. 「考え方」「典型的な失敗」の散文は、行動の手順と分け、迷ったときに読む参照にする（SkillsBench の網羅的散文 +0.7pt、SkillReducer）。ただしこれは効果の不確かな最適化で、まず実験で確かめる
7. 2 階層目（参照ファイルからさらに参照）は作らない（公式、2607.17598）
8. 例外を許さない関門（例: 承認なしに戻せない操作）は文で書くだけでなく hook で強制する（公式、既存調査）

案 A が勝つ条件: 工程の中身を各 10〜20 行に収められる場合（feature-dev 規模）。そのときは 1 ファイルの 2 層構造（大工程の見出し＋番号リスト）で十分で、開示の仕組みは不要 [推論]。pit-crew の設計書の密度ではこの条件を満たさない。

| 工程別サブエージェント | 部分的に採用 | 探索と独立評価にだけ。逐次の工程の受け渡しには使わない |

### 6-4 pit-crew で比べる小さな実験の設計案

**目的**: 同じ内容の Dev 工程定義を、構造だけ変えて、工程の取りこぼし・誤った工程の詳細の読み込み・工程内の手順の遵守・長い作業での劣化を比べる。

**arm（内容は同一、構造だけ違う）**

| arm | 構造 |
|---|---|
| A | 1 ファイル。大工程の見出しを外し、約 20 の工程を番号で 1 列に（収まらない詳細は省かず、500 行超を許す。圧縮の害も含めて測る）|
| B | 核（大工程の表と判定の規則だけ）＋工程別ファイル。判定はエージェント自身 |
| M | 混合案（§6-2 の 1〜5）。判定は状態ファイル |
| M-skill | M の工程ファイルを `user-invocable: false` の工程スキルにし、核から名指しで呼ぶ |
| （任意）S | 工程別スキルの自動発火（不発率の基準として。費用が許せば）|

**課題**: 既存の事故由来の課題（`research-ganbari-incidents.md`、`research-ecological-validity.md` の作法）から、複数工程をまたぐもの 3〜4 本。各課題に 2 つの入り方を用意する:
- 頭から（チケットだけ）
- **途中から**（調査メモと失敗するテストが既にあり、本来は実装から始めるべき状態）＝工程の判定を試す
- さらに 1 条件で、作業の途中で `/compact` を強制する（劣化を試す）。依頼文に「すぐ実装して」を入れる条件も作る（BMAD が警戒している飛ばし）

**測るもの（transcript と成果物から決定的に）**

| 指標 | 定義 |
|---|---|
| 工程の取りこぼし | 各工程の出る条件の成果物（調査メモの必須項目、失敗したテストの実行ログ、検証ログ）が無いまま次の工程の行動（実装ファイルの編集など）が始まった回数 |
| 誤った工程の詳細を読む | その時点の正しい工程（状態・成果物から決まる）と違う工程ファイルを Read した回数。読むべきファイルを読まなかった回数（Missed connections）|
| 工程内の手順の遵守 | 各工程のチェックリスト項目のうち、成果物で確かめられるものの充足率 |
| 圧縮後の劣化 | 圧縮の前後での充足率の差。圧縮後に工程ファイルを読み直したか |
| 費用 | 入出力トークン、所要時間（既存調査の方針どおり、必ず記録）|
| 説明文の近道 | 核の要約文だけに従い詳細を読まなかったか（M と B で、核に要約を書く / 書かない の差を見る余地）|

**規模と判定**: pit-crew の既存の方針（`research-next-steps-small-n.md`、`research-experimental-method.md`）に合わせ、arm ごとに課題あたり 10〜12 回。主要な比較は M 対 A と M 対 B の 2 つに絞り、事前に「取りこぼし回数」を主指標として登録する。差の判定は Fisher の正確確率か、課題を単位にした対の比較。まず 1 課題 × 3 arm × 3 回の試走で、指標が transcript から機械的に取れるかだけを確かめる（walking skeleton）。

**反証になる結果**: A の取りこぼしが M と同等以下で費用も同等 → 構造の差は小さく、内容の具体性が効いている（2605.31408 と同じ向き）と読む。B が M と同等 → 状態ファイルの手間は不要。

## 確かめられなかったこと

- コーディングエージェントで、同じ内容をフラット / 階層で書き分けて遵守を比べた研究（見つからなかった）
- Read ツールで読んだ参照ファイルが自動圧縮でどう扱われるか（公式に明記なし）
- superpowers の「説明文の要約が本文の読み飛ばしを生む」実験の条件（回数・モデル）。Vercel の評価の課題数・試行回数
- SkillsBench の長さ別・スキル数別の結果は観察で、課題の難しさと交絡している可能性（網羅的は 5 課題のみ）
- MTAC-IFBench の分類別の値（既存調査と同じく図のみ）、FollowBench・KCIF・StateFlow・PADME・RAG-MCP は要旨のみで本文の条件を読んでいない
- WHO チェックリストの 3 段階の名称、Gawande の項目数の推奨、メニューの深さ・幅の研究（Miller 1981、Larson & Czerwinski 1998）、post-completion error は本文を取得していない
- feature-dev の利用者が報告した構造上の問題（探していない）、Spec Kit・BMAD・GSD の利用者の不具合報告（探していない）
- superpowers #2510・#2551・#237 は題名だけを読んだ
- 日本語の工程定義のトークン数（字数から推測しただけ）
- Claude Code のスキル数の上限（説明文の予算以外の明記は見つからなかった）
