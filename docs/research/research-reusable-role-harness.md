# 使い回せる役割分離ハーネスの作り方と測り方 — 文献・一次資料調査

作成: 2026-11-01 / 目的: 「役割ごとのスキルをゼロから作り直すと時間がかかった」という動機から、**汎用の核 + 案件ごとの小さな差分（アダプタ）**でできた役割分離ハーネスを作り、pit-crew で版ごとに改善・改悪を判定するための材料を集める。特定の問題を解くスキルを作るのが目的ではない（具体的な問題はテストの題材にすぎない）。

前提として読んだもの: `docs/planning/06-where-we-are.md`、`docs/log/2026-11-01.md` の末尾（基準点 v0 の結果: 役割スキルは読み込まれていたが 6 回とも 1 度も呼ばれなかった）。既出の調査（`research-prior-art.md` / `research-eval.md` / `research-next-steps-small-n.md`）で扱った SkillsBench、AGENTS.md の効果研究、caliper / skill-eval-harness、skill-creator の説明文最適化、MAST の概要は、ここでは繰り返さず、新しい論点だけを足す。

## 要点（先に結論）

1. **v0 のスキルが呼ばれなかったのは、仕組みどおりの結果である。** スキルの説明文（description）だけが常に文脈にあり、本文は「関係がある」とモデルが判断したときにしか読まれない [一次: Claude Code docs / agentskills.io]。v0 の説明文は 5 本とも「〜のタスクを poll するときに使う」と書かれており、文書の矛盾を直す依頼とは一致しない。さらに公式資料は「単純な 1 段の依頼では、説明文が合っていてもスキルは呼ばれないことがある」と明記している [一次: agentskills.io]。
2. **役割を「自動で呼ばれること」に頼らない設計が、各フレームワークの主流である。** MetaGPT / ChatDev は役割を工程（SOP / ChatChain）に固定して順に呼ぶ [一次]。Claude Code も、セッションそのものを役割として起動する `--agent <name>` や設定の `agent`、`/skill-name` の明示呼び出し、サブエージェントへの `skills` の事前読み込みを持つ [一次]。自動の発火は「入口の補助」と見るのが妥当 [推論]。
3. **自動発火に頼る場合の効果は、明示的に読ませた場合の約半分になる、という実測がある。** スキルの改訂を調べた研究で、本文を読むかどうかをエージェントに任せると、改訂による行動の改善は平均で約 51%（オープンモデルでは約 38%）しか残らなかった [一次: arXiv 2610.04832 要旨]。
4. **「汎用の核 + 案件ごとの差分」は既存の道具がそれぞれ持っている。** ChatDev の CompanyConfig（欠けたファイルは Default で補う）、Spec Kit の 4 層の解決順（案件ローカルの上書き → preset → extension → 核）、BMAD の 3 層の上書き（同梱の既定 → チームの上書き → 個人の上書き）、Claude Code プラグインの `userConfig`（`${user_config.KEY}` をスキル本文に差し込める）、Codex / Claude Code の階層化した指示ファイル [一次]。共通する作法は「**核のファイルは編集しない。差分は別ファイルに、薄く置く**」 [一次: BMAD は「上書きを薄く保て。丸ごと写すと上流の既定が黙って隠れる」と明記]。
5. **役割分離そのものの効果は、条件しだいで正にも負にもなる。** ChatDev では役割をシステムプロンプトから消すと品質が 0.3953 → 0.2212 に落ちた [一次]。一方、計算量（トークン）をそろえると単一エージェントが多エージェントと同等以上になる研究 [一次: arXiv 2604.02460]、逐次的な課題では多エージェントが最大 −70% になる研究 [一次: arXiv 2512.08296] がある。**比較するときはトークン・所要時間を必ず記録し、単一セッションの基準を置く**必要がある [推論]。
6. **再利用の手間を測る確立した指標は、エージェント構成についてはまだない。** 近いのは、公開スキルを fork した人が何を書き換えたかの実証研究（1,126 件、最多は説明文の書き換え）[一次: arXiv 2607.03238] と、ソフトウェア再利用の費用モデル（COCOMO II の設計・コード・統合の改変率）[二次]。pit-crew では「**核の編集行数（0 が目標）・アダプタの行数・未解決の参照数・新しい案件での合格率の比**」を組で測るのが現実的 [推論]。

## Q1. 役割ベース / 多エージェントのハーネスは、案件をまたいで使い回すためにどう設計・配布されているか

### 1-1 研究系フレームワーク（役割を工程に固定する型）

- **MetaGPT**（Hong ら, arXiv 2308.00352）[一次・本文]
  - 役割は「名前・プロファイル・目標・制約」と役割固有の道具で定義する。SOP（標準作業手順）を「プロンプトの列」に符号化し、PM → アーキテクト → プロジェクトマネージャ → エンジニア → QA の順に動く
  - 受け渡しは**会話ではなく文書・図（構造化出力）**で行う（PRD、システム設計、シーケンス図）。共有のメッセージ置き場に出し、各役割は自分の関心（購読）で必要なものだけ拾い、前提の入力がそろってから動く
  - 役割の ablation（SoftwareDev、表 3）: エンジニアのみ（実行可能性 1.0、修正 10 回、$0.915）→ 4 役割すべて（4.0、2.5 回、$1.385）。役割を足すと費用は増える。ただし途中の組み合わせは単調ではない（PM + プロジェクトマネージャは 2.0 で、PM + アーキテクトの 2.5 より低い）[一次]。課題数は小さい [未確認: 正確な課題数]
  - 核と案件差分の分け方: 役割と SOP はコード（Role / Action クラス）で持ち、案件ごとに変わるのは入力の要求文 [一次・要旨程度、詳細はリポジトリ未確認]
- **ChatDev**（Qian ら, arXiv 2307.07924）[一次・本文]
  - 設定は **CompanyConfig**（仮想ソフトウェア会社）として 3 つの JSON に分かれる: `ChatChainConfig.json`（工程の順番・繰り返し回数・振り返りの有無）、`PhaseConfig.json`（工程ごとのプロンプトと参加者）、`RoleConfig.json`（各役割の背景プロンプト、プレースホルダ入り）。**独自の CompanyConfig に欠けたファイルは Default で補われる**。振り返りを動かすには CEO と Counselor の役割を残す必要がある [一次: chatdev1.0 ブランチの wiki]
  - 評価: SRDD（1,200 件の要求文）で完全性・実行可能性・一貫性・品質（3 つの積）。ChatDev 品質 0.3953、MetaGPT 0.1523、GPT-Engineer 0.1419。**役割をシステムプロンプトから消すと品質 0.2212（実行可能性 0.88 → 0.58）で、ablation 中で最大の低下** [一次]。表の品質の値が積と合わない行が 2 つある（ablation の「役割なし」で 0.231 と 0.2212）[一次・転記の確認]
  - 現在の main は ChatDev 2.0（DevAll）で、YAML のワークフローとノーコードの画面に移った。旧版は `chatdev1.0` ブランチで保守 [一次]
- **AgentVerse**（Chen ら, arXiv 2308.10848）: 人間の集団の動きにならい、**課題に応じて構成員を動的に組み替える**。集団は単一エージェントより良かったと要旨にある [一次・要旨]。段階（専門家の募集など）の詳細は本文未読 [未確認]
- **AutoGen**: 0.2.2 で全エージェントに `description` を追加し、GroupChat が次の話者を選ぶときに `system_message` ではなく `description` を使うよう変えた。理由は、長いシステムプロンプトでは「どこまでが誰の役割説明か分からない」「`You` が 3 人の別エージェントを指す」「トークンを食う」ため。「description は GroupChatManager のためのもので、エージェント自身への指示ではない」[一次: AutoGen ブログ 2023-12-29]
  - → **「その役割に何をさせるか（本文）」と「いつその役割を使うか（説明文）」を分けて書く**、という教訓は v0 にそのまま当てはまる [推論]
- **CrewAI**: 役割は role / goal / backstory の 3 項目（必須）。`{topic}` のようなプレースホルダを role・goal・backstory・課題文に書き、実行時の入力で埋める。新規プロジェクトは JSONC、従来の YAML（`config/agents.yaml`）も引き続き使える [一次: CrewAI docs]

### 1-2 コーディングエージェントの設定ファイル系（指示を層に重ねる型）

- **Claude Code** [一次: 公式 docs]
  - CLAUDE.md は管理者 → ユーザー → プロジェクト → ローカルの順に読み込まれ、後のものが文脈の後ろに来る。`@path` で取り込める（最大 4 段）。**1 ファイル 200 行未満を目安。長いほど文脈を食い、守られにくくなる**。取り込みは整理には役立つが文脈の費用は減らさない
  - 「2 つの指示が矛盾するとモデルはどちらかを恣意的に選ぶことがある」「ユーザーの rules とプロジェクトの rules は互いに上書きしない」
  - `.claude/rules/` は `paths` で対象ファイルを絞れる。共有の rules をシンボリックリンクで複数プロジェクトに配れる
  - 「CLAUDE.md は文脈であって強制される設定ではない。どんな判断でも止めたいなら PreToolUse フックを使え」
  - **スキル**: 置き場所は管理者 / 個人 / プロジェクト / ネスト / `--add-dir` / プラグイン。プラグインのスキルは名前空間（`/plugin:skill`）付きで衝突しない
  - **サブエージェント**: 管理者 > `--agents` > プロジェクト > 個人 > プラグインの優先順。`skills` 欄で**スキル本文をサブエージェントの起動時に注入**できる。`--agent <name>` や設定の `agent` で**メインのセッションそのものをその役割で起動**できる。ただし「カスタムサブエージェントのプロンプトは既定の Claude Code のシステムプロンプトを丸ごと置き換える」
  - **プラグイン**: skills / agents / hooks / MCP / commands などを 1 つの単位で配る。`userConfig` で導入時に値を尋ね、`${user_config.KEY}` を**スキルとエージェントの本文**、MCP 設定、フックの引数に差し込める。`${CLAUDE_PROJECT_DIR}` も使える。プラグイン直下の CLAUDE.md は読み込まれない（指示はスキルに入れる）。`version` で版を固定でき、`dependencies` で他のプラグインに依存できる
  - **エージェントチーム**（実験的）: リード 1 人 + 仲間、共有のタスク一覧、受信箱（`~/.claude/teams/{team}/inboxes/{agent}.json`）。役割の定義はサブエージェント定義を再利用する。**`-p`（非対話）では仲間を作らない**。仲間から届いたメッセージは「ユーザーの同意」として扱われない。「逐次的な課題、同じファイルの編集、依存の多い作業は単一セッションかサブエージェントのほうが有効」
- **Codex（AGENTS.md）**: ルート（git root）から作業ディレクトリへ下りながら AGENTS.md を連結し、**作業ディレクトリに近いものが後ろに来るので優先**される。`AGENTS.override.md` で一時的に上書き。合計が `project_doc_max_bytes`（既定 32 KiB）に達すると以降は足さない [一次]
- **Cursor rules**: 4 種類（常に適用 / 説明文でエージェントが関係ありと判断したとき / glob に合うファイルがあるとき / 手で @ したとき）。プロジェクト・ユーザー・チーム（チームが優先）。「1 ルール 500 行未満」「大きいルールは小さく分ける」「同じ間違いを繰り返すのを見てからルールを足す」[一次]
- **OpenHands**: AGENTS.md（常時、システムプロンプトに全文）、Agent Skills（`.agents/skills/<name>/SKILL.md`、説明文だけ先に読み込み）、**キーワードで発火する skills（`triggers` の語がユーザー発言に出たら注入）**、`paths` で発火する規則。CLAUDE.md / GEMINI.md も認識する。公開の登録所は `github.com/OpenHands/extensions` [一次]
- **Agent Skills 標準**（agentskills.io）: 必須は `name`（64 文字以内）と `description`（1,024 文字以内、「何をするか」と「いつ使うか」）。任意で `license` / `compatibility` / `metadata` / `allowed-tools`（実験的）。段階的開示: メタデータ約 100 トークン（起動時に全スキル分）→ 本文 5,000 トークン未満推奨（発火時）→ 参照ファイル（必要時）。**案件ごとのパラメータの仕組みは標準にはない** [一次]

### 1-3 仕様駆動の開発キット（工程と雛形を配る型）

- **GitHub Spec Kit** [一次: リポジトリ README / presets リファレンス]
  - 核: 工程ごとのスキル（constitution / specify / plan / tasks / implement など）と雛形・スクリプト。案件側: constitution（案件ごとに 1 回）、`.specify/` 以下の成果物
  - **解決順（上が優先）: 案件ローカルの上書き `.specify/templates/overrides/` → インストールした preset（優先度順）→ extension → 核 `.specify/templates/`**。既定は「最初に見つかったものを丸ごと使う（replace）」で、前置・後置・包む（prepend / append / wrap）の合成も選べる
  - preset は「雛形・コマンド・用語・方法論を合わせる」「組織や規制の基準を強制する」ため、bundle は「役割やチームのための構成を 1 つにまとめる」ため、と README にある
  - 既知の穴: Copilot 用に生成された指示が核の雛形のパスを直書きしており、preset の上書きが効かなかったという Issue（#2761）がある [二次: 検索結果の要約、修正状況は未確認]
- **BMAD Method**（v6）[一次: 公式 docs]
  - 各スキルに `customize.toml`（同梱の既定 = スキーマ）。上書きは `_bmad/custom/<skill>.toml`（チーム、コミットする）と `.user.toml`（個人、gitignore）。上ほど優先
  - 合成の規則は値の形で決まる: スカラーは上書き、表は再帰的に深い合成、`code` / `id` を持つ表の配列は一致したものを置き換えて新しいものを追加、それ以外の配列は既定 → チーム → 個人の順に連結。**上書きで既定の項目は消せない**
  - `persistent_facts`（セッション中ずっと保持する事実。文か `file:` 参照）、`activation_steps_prepend / append`（起動時の手順の前後に足す）
  - 「同梱のファイルは編集するな。更新で上書きされる」「`customize.toml` を丸ごと写すな。写した項目は下の層から継承しなくなり、上流の新しい既定が黙って隠れる。上書きは薄く保て」

### 1-4 まとめ: 核と案件差分の境界（各方式の比較）

| 方式 | 核（使い回す） | 案件ごとの差分 | 差分の当て方 |
|---|---|---|---|
| ChatDev 1.0 | 役割・工程のコード、Default の 3 JSON | CompanyConfig の 3 JSON のうち必要なものだけ | 欠けたファイルは Default（ファイル単位の置き換え）[一次] |
| CrewAI | role / goal / backstory の書き方 | `{placeholder}` の値 | 実行時の入力で置換 [一次] |
| Spec Kit | 工程スキル・雛形 | constitution、overrides、preset | 4 層の解決順。既定は置き換え、合成も可 [一次] |
| BMAD | スキル + `customize.toml` | チーム / 個人の toml | 値の形による深い合成。既定は消せない [一次] |
| Claude Code プラグイン | skills / agents / hooks | `userConfig` の値、プロジェクトの CLAUDE.md・rules | `${user_config.KEY}` の差し込み、指示ファイルの層 [一次] |
| Codex / Cursor / Claude Code の指示ファイル | 上位（ユーザー・組織）の指示 | プロジェクト・サブディレクトリの指示 | 連結。近いものが後ろ（Codex は近いものが優先と明記）[一次] |

- 新しい案件への適応について、各方式が言っていること [一次]: Spec Kit は「既存のコードから始める」ガイドを別に持つ。BMAD は「同梱ファイルを編集しない」ことで更新に耐えるとする。Cursor は「同じ間違いを見てから規則を足す」。Claude Code は「CLAUDE.md には毎回必要な事実だけ。手順や一部にしか関係しないものはスキルか path 付きの rules へ」
- **どの方式も「役割の振る舞い（判断の規則）」と「案件の事実（パス・ラベル名・コマンド）」を別の場所に置く**。差分の当て方は「置換（プレースホルダ）」「層の重ね合わせ（後ろが優先）」「ファイル単位の差し替え」の 3 通り [推論]

### pit-crew への示唆（Q1）

1. **v1 は 3 層に分ける** [推論、Q1 の各方式に基づく]
   - 層 1「役割カード」（核）: 責任の範囲、決めること・決めないこと、受け渡しの約束（何を渡し、何を受け取ったら動くか）、どの依頼にも効く判断の規則。案件の固有名詞・パス・ラベル名を含まない
   - 層 2「手順」（核）: 受信箱の見回り、レビューの手順など。役割カードから呼ぶ別スキルにする（v0 は役割と見回り手順が 1 ファイルに混在し、説明文が手順側に寄っていた）
   - 層 3「アダプタ」（案件ごと）: ラベル名、文書の場所、ビルド・テストのコマンド、SSOT の場所。1 ファイル（または `userConfig` の値）に集め、核からは名前で参照する
2. **差分は「置換」より「層」を基本にし、核のファイルは編集しない** [推論、BMAD・Spec Kit に基づく]。v1 → v2 の改良が案件側に自動で届くかが、使い回しの肝になる。
3. **測るべきこと**: 核とアダプタの境界が守られているか（核にアダプタの値が漏れていないか）を、セルの外の静的検査で毎版確かめる（後述の Q4 の指標）。

## Q2. スキル・指示の発火: エージェントはどう決めるのか、どう設計し、どう評価するか

### 2-1 仕組み（公式資料）

- 起動時に読み込まれるのは**全スキルの名前と説明文だけ**。本文は発火したときに 1 つのメッセージとして入り、その後の各ターンに残る（読み直しはしない）。圧縮（compaction）後は最新の呼び出しの先頭 5,000 トークンだけが再添付される（合計 25,000 トークン）[一次: Claude Code docs]
- 説明文 + `when_to_use` は 1 件あたり 1,536 文字で切られる。スキルが多いと一覧全体の予算（文脈窓の 1%）を超え、**使われていないスキルから説明文が落とされる**。名前は残る [一次: 同]
- `disable-model-invocation: true` にすると自動では呼ばれず、説明文も文脈に入らない。`user-invocable: false` にすると人は呼べずモデルだけが呼べる。`paths` を付けると一致するファイルを扱うときだけ自動で読み込む [一次: 同]
- 「単純な 1 段の依頼では、説明文が完全に合っていてもスキルが呼ばれないことがある。エージェントは自力でできない知識や能力が要る課題でスキルを参照する」[一次: agentskills.io "Optimizing skill descriptions"]
- サブエージェントへの委譲も同じく説明文で決まる。「use proactively」のような語を入れると自発的な委譲が増えると公式にある。サブエージェントの説明文の合計が 15,000 トークンを超えると警告 [一次: Claude Code docs]

### 2-2 説明文の書き方（公式の指針）

- 三人称で書く（説明文はシステムプロンプトに入るため、視点がぶれると発見に支障が出る）。「何をするか」と「いつ使うか」の両方、具体的な語を入れる。「Helps with documents」のような曖昧なものは避ける [一次: Anthropic "Skill authoring best practices"]
- agentskills.io はさらに: **命令形（「Use this skill when ...」）**、**実装ではなく利用者の意図を書く**、**押し気味に**（利用者が領域名を口にしない場合も挙げる）、短く（数文〜短い段落）[一次]
  - 注: 三人称（Anthropic）と命令形（agentskills.io）は文の形としては食い違って見えるが、「エージェントに視点の混乱を起こさせない」「いつ使うかを明示する」点では同じ方向 [推論]
- 文言の作り方の実例: 改善前「Process CSV files.」→ 改善後は「何をするか（統計・列の追加・グラフ・整形）を具体的に」「いつ使うかを広く（CSV / TSV / Excel、利用者が CSV と言わなくても）」[一次: agentskills.io]

### 2-3 発火の評価方法（公式・研究）

- **発火テストの設計** [一次: agentskills.io]
  - 約 20 件の依頼文: 発火すべき 8〜10 件、すべきでない 8〜10 件。発火すべき側は言い回し・明示度・詳しさ・複雑さを変える。**最も役に立つのは「スキルが役立つが依頼文からはつながりが見えないもの」**
  - すべきでない側は**ニアミス**（語や概念は重なるが別のことが要る依頼）を使う。無関係な依頼は何も試さない
  - 各依頼を 3 回ずつ走らせ発火率を出す。発火すべき依頼は発火率 0.5 超で合格、すべきでない依頼は 0.5 未満で合格。判定は `claude -p ... --output-format json` の出力から `tool_use` の `name == "Skill"` かつ `input.skill` を数える例が載っている
  - **訓練 6 割・検証 4 割に分け、検証の合格率で最良の説明文を選ぶ**（最後の版が最良とは限らない）。失敗した依頼の語をそのまま説明文に足すのは過学習。5 回の反復で足りることが多い
- Claude Code のプラグインなら `claude plugin eval` に `tool_used: Skill` の採点器があり、説明文を変えるたびに発火率を測れる。`/skill-doctor` は「一覧にあるが一度も呼ばれていないスキル」を報告する [一次: Claude Code docs]
- **研究での実測**
  - Agent Skill Evolution（Wang ら, arXiv 2610.04832, 2026-10）: 3,159 スキルの 2,608 組の改訂を分析。改訂の 55% は規則か手順の変更。サンドボックスの 4 エージェントで、規則を足すと求められた行動をとる率が平均 +0.23（+0.16〜+0.36）、最終的な正しさが平均 +0.10。**改善の大半は「旧版が触れていなかったコマンドやパスを名指しする規則」から来る**。**本文を読むかをエージェントに任せる実際の設定では、行動の改善は 4 エージェント平均で約 51%、オープンモデル 3 つで約 38% しか残らない**。本文を読むと 1 回あたりのトークンは約 50% 増える [一次・要旨]
  - SkillsBench の発火率（46〜99%、構成で大きく違う）は既出（`research-eval.md`）。検索結果の要約では Codex の構成の 1 つで 99.2%、別の構成で 54.0% [二次]
  - ACES（Kevin ら, arXiv 2608.20614）: スキルあり・なしの対の試行で「Skill Lift」を出す。64 の本番スキルのうち 58 で 947 の対、合成の Lift 平均 0.2134（95% 区間 0.1967〜0.2301）、対の 72.8% で正。**構造の検査と LLM 採点の相関は Spearman ρ = 0.14** で、静的な検査ではスキルの効き目は分からない [一次・要旨]。明示呼び出しと暗黙の発火を分けて扱うと検索結果の要約にある [二次]
  - コミュニティの実験: 説明文だけでは発火が約 50% だったところ、`UserPromptSubmit` フックで毎回「各スキルが関係あるか YES/NO で判定してから進め」と強制すると 84%（50 回、Haiku、API 経由）。ただし実際の Claude Code バイナリでの再測定では差が出なかった（55% 対 55%）と同じ著者が報告 [二次: scottspence.com、小標本・結果が一致しない]
- **調べたが見つからなかったもの**: 役割スキル（PO / Dev / QM のような「立場」のスキル）の発火率を測った公開研究 [未確認]

### 2-4 何が「確実に呼ばれる」を決めるか（整理）

| 手段 | 確実さ | 文脈の費用 | 出典 |
|---|---|---|---|
| セッションをその役割で起動（`--agent` / 設定の `agent`） | 決定的（ただし既定のシステムプロンプトが置き換わる） | 役割の本文が常時 | [一次] |
| 依頼文で明示（`/skill-name`） | 決定的 | 呼んだ時だけ | [一次] |
| サブエージェントの `skills` で事前注入 | そのサブエージェントには決定的 | 起動時に全文 | [一次] |
| キーワードで発火（OpenHands の `triggers`） | 語が出れば決定的 | 発火時 | [一次] |
| `paths` で発火（Claude Code / Cursor / OpenHands） | 該当ファイルを扱えば決定的 | 発火時 | [一次] |
| 常時の指示（CLAUDE.md / AGENTS.md） | 常に文脈にある（守られるかは別） | 常時。長いほど守られにくい | [一次] |
| 説明文による自動発火 | 確率的。単純な依頼では呼ばれにくい | 説明文だけ常時 | [一次] |
| フック（PreToolUse など） | 決定的に実行される（判断ではなく強制） | ほぼなし | [一次] |

- 公式の Claude Code docs は「毎回必ず守るべき規則はフックに移せ」「判断で適用する指針は『毎回の編集の後にテストを走らせよ』のように課題全体に効く言い方で書け（スキルの本文は読み直されないため）」と書く [一次]

### pit-crew への示唆（Q2）

1. **v0 の 0/6 は「スキルが悪い」ではなく「入口の設計がない」と読むべき** [推論]。v0 は (a) 説明文が見回り手順を述べており依頼と一致しない、(b) 依頼が 1 回きりで受信箱の文脈がない、(c) 依頼が単純で「自力でできる」と判断されやすい、の 3 つが重なっている。
2. **v1 では役割の入口を 2 本用意し、別々に測る** [推論]
   - 決定的な入口: 役割セッションは役割として起動する（`--agent <role>` か、最初の依頼で `/<role>`）。オーナーの実運用（ロールごとに別セッション）と一致する。ハーネスの「中身」の効果はこの入口で測る
   - 確率的な入口: 汎用セッションから、依頼に応じて役割（サブエージェントかスキル）へ振り分けられるか。説明文を「いつ使うか」で書き直し、発火率を別の指標として測る
   - 2 本を混ぜると「発火しなかった」と「発火したが効かなかった」が区別できない（caliper が発火と効果を分けて採点するのと同じ理由、既出）
3. **発火のセルは安い**。依頼文 20 件 × 3 回 = 60 回だが、発火したか（Skill の `tool_use` があるか）が分かった時点で打ち切れるので 1 回は短い。採点は transcript からの決定的な抽出で済む。訓練 / 検証の分割を最初から固定する [推論、agentskills.io に基づく]。
4. **`--agent` の副作用は要確認**: 役割の本文が既定のシステムプロンプトを置き換えるなら、役割セッションのコーディング力が落ちる可能性がある [推論、要測定]。v1 で「`--agent` で起動」と「既定のプロンプト + 最初に `/role` を呼ぶ」を比べる価値がある。

## Q3. 役割分離 / 多エージェント構成を評価する: 役割分離は効くのか、受け渡しの失敗をどう作り、どう測るか

### 3-1 役割分離の効果: 正の結果と負の結果

- 正: ChatDev の「役割なし」ablation（品質 0.3953 → 0.2212）、MetaGPT の役割の追加（実行可能性 1.0 → 4.0、修正 10 → 2.5 回）[一次]。いずれも 2023 年の GPT-3.5 / GPT-4 世代、評価は少数の課題か独自の指標
- 負・条件つき:
  - Towards a Science of Scaling Agent Systems（Kim ら, arXiv 2512.08296）: 最新版の要旨で 260 構成・6 ベンチマーク・5 構成方式・3 モデル系統。分解できる金融の推論で +80.8%、**逐次的な計画で −70.0%**。「中央での検証がない構成は誤りを広げやすい」「単一エージェントの基準がある水準を超えると協調の効果は逓減する」「構成と課題の相性が成否を決める」[一次・要旨]。v1 の要旨にあった「39〜70% の低下」「180 構成」「45% で飽和」は最新版の要旨には見当たらない [二次・版の違い]
  - Single-Agent LLMs Outperform Multi-Agent Systems ...（Tran & Kiela, arXiv 2604.02460）: 推論トークンの予算をそろえると単一エージェントが多エージェントと同等以上。**多エージェントの利得として報告されてきたものの多くは、数えていない計算量と文脈の効果で説明できる**。API の予算制御（特に Gemini 2.5）やベンチマークの癖が多エージェントの利得を水増しする [一次・要旨]
  - Single-agent or Multi-agent Systems? Why Not Both?（Gao ら, arXiv 2505.18286）: モデルが強くなるほど多エージェントの優位は縮む。両者の振り分け（cascading）で精度 +1.1〜12%、費用最大 −20% [一次・要旨]
  - Engineering Sustainable Agents（Astekin ら, arXiv 2610.03010）: 5 つの SE 課題。多エージェントは非エージェントの基準の平均 6.36 倍のエネルギー、6.07 倍の時間。精度の利得は限定的で課題依存（脆弱性検出だけが例外）。Pareto 最適 66 構成のうち 59 が非エージェントか単一エージェント [一次・要旨]
  - Anthropic の多エージェント研究システム: 性能の分散の 80% はトークン使用量だけで説明できる。多エージェントは通常の会話の約 15 倍のトークン。「共有の文脈や依存の多い課題は今の多エージェントに向かない」「ほとんどのコーディング課題は研究ほど並列化できない」[一次: Anthropic engineering blog]
- **pit-crew のハーネスへの含意** [推論]: オーナーの役割分離は、並列化のためではなく「作成者 ≠ 承認者」「決めてよい範囲の分離」「文脈の分離」のためにある。上の研究が測っているのは主に「課題の正解率」で、**権限の分離が守られるか（作成者が自分で承認しない、決めてはいけないことを決めない）は測っていない**。役割分離の価値は、正解率ではなく「境界の遵守」と「受け渡しの成果物の質」で測るほうが目的に合う。

### 3-2 失敗の分類と、受け渡しの失敗

- MAST（Cemri ら, arXiv 2503.13657）: 7 フレームワーク、1,600 超の注釈つき trace、14 の失敗モード × 3 分類、κ = 0.88 [一次・要旨]。出現率（本文）: 課題仕様への不服従 11.8%、**役割仕様への不服従 1.5%**、手順の繰り返し 15.7%、終了条件の不認識 12.4%、推論と行動の不一致 13.2%、確認を求めない 6.8%、情報の出し惜しみ 0.85%、他エージェントの入力の無視 1.9%、検証なし・不完全 8.2%、誤った検証 9.1%、早すぎる終了 6.2% など [一次・本文]
  - 介入の事例: 同じ依頼・同じモデル（GPT-4o）で **ChatDev の役割仕様を改善（CEO が最終決定権を持つ）すると成功率 +9.4%**、上位の目的の検証の段を足すと ProgramDev で +15.6% [一次・本文の見出し程度、表は未読]
  - 「役割仕様への不服従」は出現率としては小さいが、オーナーのハーネスで最も問題になる種類（QM が自分で実装する等）[推論]。trace に出にくい = 課題で誘発しないと観測できない
- Who&When（Zhang ら, arXiv 2505.00212）: 127 の多エージェント系の失敗ログに「どのエージェントのどの段が原因か」を注釈。最良の手法でもエージェント単位 53.5%、段単位 14.2% [一次・要旨]
  - → **失敗の原因の役割を後から trace で当てるのは難しい**。最終状態に「どの役割が何をしたか」の痕跡（ラベルの遷移、署名、成果物の置き場所）を残す設計にすれば、決定的に採点できる [推論]
- MultiAgentBench（Zhu ら, arXiv 2503.01935）: 課題の完了に加えて協調の質を「マイルストーン型の指標」で測る。星・鎖・木・グラフの構成を比較 [一次・要旨]。マイルストーンの定義は本文未読 [未確認]

### 3-3 受け渡しを使う課題の作り方（先行例から）

- ChatDev / MetaGPT: 工程（要件 → 設計 → 実装 → テスト）を固定し、各工程の成果物（PRD・設計書・コード・テスト）を次の役割の入力にする。評価は最終成果物（実行できるか、要求を満たすか）[一次]
- τ-bench（既出）: 方針の遵守 + 最終状態（DB）の決定的比較。受け渡し相手（利用者）をシミュレートする [既出・一次]
- エージェントチームの公式資料が勧める題材: 「境界がはっきりしていてコードを書かない課題（PR のレビュー、ライブラリの調査、バグの調査）から始めよ」「同じファイルを 2 人で編集させない」「タスクの状態更新が遅れて依存タスクが止まることがある」[一次: Claude Code docs]
- 調べたが見つからなかったもの: 「ラベルや受信箱を介した非同期の受け渡し」を課題にした公開ベンチマーク [未確認]

### pit-crew への示唆（Q3）

1. **比較の基準に「単一セッション（役割なし）」を必ず置き、トークンと所要時間を記録する** [推論、Tran & Kiela / Anthropic に基づく]。役割分離の版が合格率で並んでもトークンが数倍なら、それは改善ではない可能性がある。サブスクの枠という制約上もこの記録は必須。
2. **受け渡しのセルは「2 段の試走」で作れる** [推論]
   - 段 1: 役割 A のセッション（例: Dev）が fixture の受信箱から依頼を拾い、成果物を作り、受け渡しの印（ラベル相当）を付ける
   - 段 2: 段 1 の最終状態をそのまま入力に、役割 B のセッション（例: QM）を起動する
   - 採点は各段の最終状態で決定的に: 印の遷移が正しいか、成果物が約束の場所・形式にあるか、B が A の成果物を読んでから判断したか（tool の呼び出し順）、**境界を越えていないか**（QM がコードを書き換えていない、Dev が自分で承認の印を付けていない）
   - 受信箱は GitHub を使わず、コンテナ内のファイル（JSON か小さな偽の `gh`）で再現すれば Docker 内で決定的に回せる。エージェントチームの受信箱が JSON ファイルである点も参考になる [一次: Claude Code docs]
3. **境界のセルは誘発型にする** [推論、MAST の出現率に基づく]。「役割仕様への不服従」は自然には少ない（1.5%）ので、「直したほうが早い軽微な不具合をレビュー役に見せる」「承認の権限がない役割に承認を頼む依頼文」など、越境したくなる状況を作る。正解は「越境しない + 正しい相手に回す」で、最終状態で採点できる。
4. **段 1 の失敗が段 2 の採点を汚さないようにする** [推論]: 段 2 は段 1 の実際の出力ではなく、**台本で作った正しい段 1 の状態**から始める版も用意する（工程ごとの単体テストと、通しのテストを分ける）。前者は差の判定に、後者は回帰の見張りに使う。

## Q4. 再利用・移植・適応の手間をどう測るか

### 4-1 エージェント構成についての実証

- An Empirical Study of Downstream Adaptation for Agent Skills（Wu, Gong, Jahangirova, Chen, Zhang, arXiv 2607.03238）[一次・本文]
  - 6 つの公開スキルリポジトリ（anthropics/skills、vercel-labs/agent-skills など）の fork から 1,126 件の適応事例を集め、13 系統 46 パターンに分類
  - 系統の出現率（ブランチ単位）: ライフサイクル 40.9%、手順 40.8%、判断 25.3%、方針 23.9%、資源 16.8%、**対象の付け替え（retarget）16.3%**、スクリプト 16.2%
  - パターン: **メタデータの変更 18.2%（その 85.4% が説明文の変更）**、手順の追加 17.8%、判断規則の追加 15.1%、強い制約の追加 14.6%、外部システムとの統合 12.1%、**使う道具の付け替え 11.5%**
  - 書き換えた場所: SKILL.md 79.8%、追加ファイル 40.9%、スクリプト 23.3%。18.6% がセキュリティ上注意すべき内容（機密ファイルへのアクセス 13.2% など）を足していた。コミットメッセージは変更の記録として不完全
  - 著者の提言: RADAR（Route = 発火のメタデータを確かめる / Adapt = 手順・判断・方針を見直す / Declare = 資源とスクリプトの依存を宣言する / Audit = 危険な指示と実行面を監査する / Record = 変更を記録する）。「**道具・言語・発見用のメタデータを、核の指示を書き直さずに合わせられる、はっきりした拡張点とモジュール化**」を求めている
  - → **人が他人のスキルを自分の案件に合わせるとき、最も多く書き換えるのは説明文（発火の条件）と、使う道具・手順**である。これは v1 のアダプタに入れるべき項目の実証的な候補になる [推論]
- Agent READMEs（Chatlatanagulchai ら, arXiv 2511.12884）: 1,925 リポジトリの 2,303 の指示ファイル。**指示ファイルは静的な文書ではなく「設定コードのように、小さな追加を頻繁に重ねて育つ」**。読みにくく複雑。内容はテスト手順 75.9%、実装の詳細 70.8%、アーキテクチャ 68.1%。セキュリティ 14.8%、性能 14.5% はまれ [一次・要旨]
- Evaluating AGENTS.md（Gloaguen ら、既出）: LLM が生成した指示ファイルは成功率を下げ、開発者が書いたものでも効果は小さい。非標準の慣行を指定するには役立つ [既出・一次]。→ アダプタを LLM に自動生成させる案は、そのままでは効果が保証されない [推論]
- 調べたが見つからなかったもの: エージェントの構成（指示・スキル一式）を新しいリポジトリへ移すのに要した時間や編集量を測った研究 [未確認]。スキルのモデル間・役割間・課題間の転移の研究はある（役割をまたぐと転移しにくい、課題をまたぐと害になることもある、という要約）[二次: 検索結果の要約、本文未読]

### 4-2 ソフトウェア再利用の文献から借りられる考え方

- **COCOMO II の再利用モデル** [二次: 講義資料と参照マニュアルの抜粋。公式のモデル定義マニュアルの該当節は PDF を読めず未確認]
  - 改変の割合を 3 つに分ける: 設計の改変率 DM、コードの改変率 CM、統合のやり直しの割合 IM。適応の調整係数 AAF = 0.4·DM + 0.3·CM + 0.3·IM
  - さらに理解のしやすさ SU（自己説明的なら 10、分かりにくければ 50）、なじみのなさ UNFM（0〜1）、評価と取り込みの手間 AA を足す。DM と CM がともに 0 なら SU は 0
  - 考え方として使えるのは「**再利用の費用は、変えた量だけでなく、理解の手間と統合の手間に依存する**」「少し変えるだけでも理解の費用がかかる」こと [推論]
- **設定と核の厳密な分離（The Twelve-Factor App）** [一次]: 「設定とは、配備ごとに変わりうるものすべて」「設定とコードの厳密な分離を求める」。試金石は「**資格情報を損なわずに、コードベースをいつでも公開できるか**」
  - → ハーネスに当てはめると「核をいつでも公開できるか（案件の固有の事実が漏れていないか）」がそのまま試金石になる。オーナーの合格条件「公開できる汎用ハーネス」と一致する [推論]
- **製品ライン工学（共通性と可変性の分析）**: 製品群の共通部分を核とし、違いを「可変点」として明示的に管理する考え方 [二次・一般知識、一次未確認]。可変点の数が増えるほど設定の手間と組み合わせの検証が増える [推論]

### pit-crew への示唆（Q4）

1. **「適応の手間」は 1 つの数ではなく、次の組で測る** [推論]
   - (a) **核の編集量**: 新しい案件に合わせるために核のファイルを書き換えた行数。目標は 0。0 でなければ、それは核の設計の欠陥（拡張点の不足）として記録する
   - (b) **アダプタの大きさ**: 埋めた項目の数と行数。少ないほど良いが、(c) とあわせて見る
   - (c) **移植後の合格率の比**: 新しい案件の fixture での合格率 ÷ 元の案件での合格率（同じ種類のセル）。核とアダプタの分離がうまくいっていれば 1 に近い
   - (d) **未解決の参照の数**: 核が指しているが、案件側に存在しないファイル・ラベル・コマンドの数。静的に数えられる（v0 の PO スキルは `docs/sessions/po-session.md` などを指しているが pit-crew のコンテナにはない）
   - (e) **漏れの数**: 核に含まれる案件の固有名詞・パス・ラベル名の数（Twelve-Factor の試金石を機械化したもの）。既存の重なり検査（`leak`）は字面の重なりで雑音が多かった（log 2026-11-01）ので、**アダプタに書いた値の一覧と核の照合**にすれば雑音が減る
2. **人の時間は測りにくいので、エージェントに適応させる手間で代える** [推論]: 「アダプタの雛形 + 新しい案件のリポジトリ」を渡し、別のエージェントにアダプタを埋めさせ、固定の確認用セル（小さな受け渡しのセル 1 つ）が通るまでの往復回数・トークンを記録する。これは「新しい案件で立ち上げるのに時間がかかった」というオーナーの動機に最も近い代理になる。ただし LLM が埋めたアダプタは効果が保証されない（Gloaguen）ので、合格率 (c) と組で見る。
3. **適応の実証データ（説明文と道具の付け替えが最多）から、v1 のアダプタの必須項目を決める** [推論]: 役割ごとの「いつ使うか」の追記欄、ビルド・テスト・課題管理のコマンド、文書の置き場所、受け渡しの印の名前。

## Q5. 汎用の核と案件アダプタに分ける実践的な型と、避けるべき型

### 5-1 型（パターン）

- **層の重ね合わせ**: 組織 / 個人 / プロジェクト / サブディレクトリの指示を連結し、近いものを後ろに置く（Codex、Claude Code、Cursor）[一次]。Codex は「近いものが後ろなので優先」と明記。Claude Code は「ユーザーとプロジェクトの rules は互いに上書きしない。矛盾すればどちらかを選ぶことがある」と書く [一次]。→ 層は「優先順位」ではなく「両方が見える」ものとして扱い、**矛盾させない**のが前提 [推論]
- **置換（パラメータ）**: CrewAI の `{placeholder}`、Claude Code プラグインの `${user_config.KEY}`（スキル・エージェントの本文に差し込める）[一次]
- **既定 + 薄い上書き**: ChatDev の CompanyConfig（欠けたファイルは Default）、BMAD の 3 層（値の形で合成、既定は消せない）、Spec Kit の overrides / presets（既定は丸ごと置換、合成も選べる）[一次]
- **段階的開示**: 説明文だけを常時、本文は発火時、参照ファイルは必要時。本文 500 行未満、参照は SKILL.md から 1 段まで、100 行を超える参照ファイルには目次 [一次: Anthropic / agentskills.io]
- **path で絞る**: その種類のファイルを扱うときだけ読ませる（Claude Code の rules / skills の `paths`、Cursor の glob、OpenHands）[一次]
- **強制はフックへ**: 「判断に関係なく止めたいものは PreToolUse フック」「毎回守るべき規則はフックに」[一次: Claude Code docs]
- **自由度を壊れやすさに合わせる**: 正解が複数ある課題は文で方向だけ、手順が 1 つしかない操作は決まったスクリプトで [一次: Anthropic best practices]
- **受け渡しは構造化した成果物で**: MetaGPT の文書・図による受け渡し [一次]。サブエージェントへの依頼には「目的・出力の形式・使う道具と情報源・課題の境界」を書く（曖昧な依頼で重複作業が起きた例）[一次: Anthropic 多エージェント研究システム]

### 5-2 避けるべき型（アンチパターン）

- **規則の肥大化**: CLAUDE.md は 200 行未満が目安で「長いほど守られにくい」[一次: Claude Code]。スキルは 4 本以上だと効果が落ち、網羅的な文書はほぼ効かない（SkillsBench、既出）。指示ファイルは「小さな追加を重ねて育つ」[一次: Agent READMEs]。サブエージェントの説明文の合計が大きすぎると警告 [一次]
- **高さの誤り**: 「壊れやすい複雑な論理をプロンプトに直書きする」と「具体的な手がかりのない曖昧な指針」の両極 [一次: Anthropic "Effective context engineering"]。例外の羅列より、典型例を少数 [一次: 同]
- **案件の事実が核に漏れる**: Twelve-Factor の試金石に反する [一次の概念 + 推論]。v0 の役割スキルは、ラベル名（`state:needs-po` など）、cron の分（PO = 37 など）、案件の文書へのパス、案件のコマンドを本文に直書きしている（下の 5-3）
- **核を丸ごと写して上書きする**: 上流の新しい既定が黙って隠れる [一次: BMAD]
- **説明文に手順を書く**: 説明文は「いつ使うか」のためのもの。AutoGen は役割の説明（他者向け）とシステムメッセージ（本人向け）を分けた [一次]。v0 は説明文に見回りの手順を書いている
- **時期に依存する記述**: 「何月以前はこう」と書かない。古いやり方は別の節へ [一次: Anthropic best practices]
- **用語の揺れ**: 同じものを複数の語で呼ばない [一次: 同]
- **矛盾した指示**: 2 つの指示が矛盾するとモデルは恣意的に選ぶ [一次: Claude Code]
- **深い参照の連鎖**: 参照の参照は一部しか読まれないことがある [一次: Anthropic best practices]
- **見てから足す、の逆**: 起きていない問題のための規則を先に書く（Anthropic は「評価を先に作り、最小の指示で埋めよ」、Cursor は「同じ間違いを繰り返すのを見てから足せ」）[一次]

### (2) 次に作る評価課題（セル）

| 順 | セル | 何を測るか | 採点 | 1 実験の回数の目安 |
|---|---|---|---|---|
| 1 | **入口のセル（発火）**: 役割ごとに依頼文 約 20 件（発火すべき / ニアミス）。訓練 6 割・検証 4 割で固定 | 汎用セッションから正しい役割に入るか | transcript の Skill / Agent の `tool_use` を数える（決定的）。発火が分かった時点で打ち切り | 20 件 × 3 回。打ち切りで 1 回は短い |

### (3) 「再利用・適応の手間」の指標

主指標（版ごとに出す）[推論、Q4 に基づく]:

1. **核の編集行数**（新しい案件に合わせるために核を書き換えた行数。目標 0）
2. **移植後の合格率の比**（新案件の合格率 ÷ 元案件の合格率、同種のセル）
3. **アダプタの大きさ**（項目数と行数）

補助指標:

4. **未解決の参照の数**（核が指すが案件側にないファイル・印・コマンド。静的に数える）
5. **漏れの数**（アダプタに書いた値の一覧と核の照合。字面の重なり検査より雑音が少ない）
6. **エージェントによる立ち上げの手間**（雛形と新案件を渡し、別のエージェントがアダプタを埋めて確認用セルが通るまでの往復回数・トークン）。人の作業時間の代理
