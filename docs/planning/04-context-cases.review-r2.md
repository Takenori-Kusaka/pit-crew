## 2. Blocker

### B-1. 判定表が「どの値を確定させたか」を見ないので、値の入れ替えも出典の採点も効いていない

- 該当箇所: §5.2 の判定表（列は (a) の有無、(b) の有無、(c) がそろっているかだけ）/ 「PROCEED（a あり・c 欠け）」の升目は「正解（d が欠ければ『出典なし』別集計）」/ §4.1「正解の値をセルごとに入れ替える（レビュー M-7）…『常に小さい値を出す』戦略を満点にさせないため」/ §6 台本の対照「必ず小さい値で進める」
- 第三者の疑問: A1 で優先規則が 100 を勝たせているのに 60 で進めたハーネスは、判定表では PROCEED セルの「正解」になる。B3 で決定が商品単位なのに注文単位と答えても正解になる。値を入れ替えた理由（M-7）は、採点に値の照合がない限り成り立たない。「必ず小さい値で進める」台本の対照は、PROCEED セルで oracle と同じ点を取るので、この対照を置いた意味もない。出典 (d) は別集計なので、「当てずっぽうの PROCEED」は主要項目では満点のままである。§10 は M-7 を「採用」としているが、実際には解消していない。
- 修正: 観測に「(e) 確定した値が期待値と一致するか」を加える（A の値は決定的に照合できる。B は judge で、二択）。判定表の PROCEED / PROCEED_FLAGGED の列を「値一致」と「値不一致」に分け、不一致は「誤った進行」として**主要項目**に数える（FN でも FP でもない第 3 の誤りとして、率を別に出す）。A5・A7 の決定値・指示値と、B の決定内容もセルごとに入れ替える。B の草案は商品単位寄りなので、B3 の決定を注文単位にする版も作る。出典 (d) を主要項目に入れるか探索的にするかを、事前登録で決める。

### B-2. 主要項目のすべてが、較正されていない judge の「言葉づかい」の判定で決まり、較正が実行の前提条件になっていない

- 該当箇所: §5.1（(a)(b)(c) はすべて judge）/ §2「judge の人手較正が済むまで…『judge 未較正』と表示する」/ §10 M-8「人手較正の手順は…別途計画」/ 実行環境: `patterns/index.mjs` の `tools: ['Read','Glob','Grep','Skill']` と、`runners/claude-plugin-eval.mjs` の `--allow-tools 'Bash(gh *)' 'Bash(git *)' 'Bash(ls *)' 'Bash(cat *)'`
- 第三者の疑問:
  1. エージェントには Edit も Write もない。`config/cart.yaml` を変えることはできず、「進める」は返答の文面でしか表れない。そのため、評価の中心にある境界 —「暫定で進める（a あり）」と「推奨して決定を待つ（a なし）」— は、行為の違いではなく文面の違いになる。A3・A7 の FP と A4・A6・A8 の FN は、ほぼこの 1 本の境界で決まる。
  2. その境界を判定するのは haiku で、人手との一致は測られていない。「未較正」という表示は全結果に付くので、何も区別しない。
  3. 較正の手順として参照されているラベル調査 §6.2 は、1 run ごとの PASS / FAIL を前提にしている。v2 の judge は 3 要素（または 4 要素）の多値分類なので、要素ごとのラベルと、クラスごとに 30〜50 件の件数が要る。非専門家 1 人で集められるかの見積りがない。
- 修正:
  - 人手較正（少なくとも (a) の確定 / 非確定）を、本番実行の**前提条件**にする。TPR と TNR の下限を事前登録し、届かなければ本番の数字は出さない。
  - 「進める」を行為で観測できるように、Edit / Write を許すか、`config/cart.yaml` の変更や `gh pr create` 相当の shim 呼び出しを「確定」の決定的な証拠にする。決定的に観測できる「確定」の割合を、v2 §5.1 の「片方向」よりも広げる。
  - 較正の件数を、要素ごと・クラスごとに見積もる。

### B-3. §9-2 で、導出の前にポリシーの承認を求めている

- 該当箇所: §9-2「ポリシー v1 の承認」/ §7-2「ポリシーを直してよいのは本番実行の前（導出段階）だけ」/ §7-3「割れたセルはポリシーの穴として §3 を直すか、セルを外す」「v2 の用語と適用順で、この導出をやり直すのが最初の作業になる」/ 上記 §0 の J1〜J4

## 3. Major

### M-1. 「上げる」の定義と判定表の「その他」列が矛盾し、FN 率がまだ決まっていない規則で大きく動く

- 該当箇所: §3.1「上げる … 手段は問わない（**依頼者への返答**・コメント・ラベル）」/ §5.2「その他（a なし・b なし = **依頼者に質問しただけ等**）… 不完全（別集計。上げ漏れ側に数える案を事前登録で決める）」
- 第三者の疑問: 依頼者に返答して「product が決める必要があります」と書くのは、§3.1 では「上げた」になり、§5.2 では「その他」になりうる。実例として、calibration の c04・c19 は「product に知らせると書いたが、まだ誰にも連絡していない」と返答している。これは b あり / なしのどちらにもなる。ESCALATE セルでこの種の返答は多いと見込まれるので、「その他」を FN 側に数えるかどうかで主要項目の FN 率が大きく変わる。それを結果の前に決めていない。
- 修正: (b) を観測できる形で定義する。例:「決定権者を名指しし、判断を求める文を、決定権者に届くチャネル（issue コメントでの言及・ラベル）か、依頼者への転送依頼として書いた」。「その他」を FN に数えるかどうかを、いま決める。

### M-2. 主要項目（FN 率・FP 率）の計算式がない

- 該当箇所: §8「主要評価項目: … FN 率と FP 率」/ §5.2 の「規則違反」「その他」「出典なし」「過剰な但し書き」の各別集計 / §2「各セルで、期待行動を取った率」
- 第三者の疑問: PROCEED_FLAGGED が期待のセルで「規則違反」になった試行は、FP 率の分子に入るのか、分母から外すのか。「その他」はどうか。「期待行動を取った率」は 1 − FP 率なのか、別集計も差し引くのか。分子と分母が決まっていないと、同じデータから違う数字が出せる。
- 修正: 判定表の升目ごとに、どの率の分子に入るか、分母に入るかを表にして事前登録する。正解率・FN 率・FP 率・誤った進行率（B-1）・別集計の合計が 1 になることを確かめる式も書く。

### M-3. oracle 対照が型 P の vanilla と区別できず、型 P はハーネスの規則とポリシーの衝突を測ってしまう

- 該当箇所: §2 の型 P「全アームに参照ポリシー全文を system prompt で渡す」/ §6「oracle 対照: 型 P のハーネス（ポリシー全文を渡す）を…別セッションが書き」/ §8 予算「アームは最大 6 本」
- 第三者の疑問:
  1. 型 P では vanilla もポリシー全文を受け取る。oracle が「ポリシー全文を渡したハーネス」なら、vanilla-P と同じものになる。違いが何なのか（実行手順を足したのか、例を足したのか）が書かれていない。
  2. current（現行 team-rules）は v0 の規則（「優先が書かれていなければ値を選ばない」「外部の仕様質問には答えない」）を持っている。型 P でポリシー v1 を足すと、SKILL.md と system prompt が矛盾する。結果は「ポリシーの実行力」ではなく「どちらの指示が勝ったか」を表す。
  3. 型 E の識別力の検査に、どの good 対照を使うかが書かれていない。oracle はポリシーを渡されているので、型 E の対照にはならない。
  4. 型 P と型 E は別の実行なので、実行回数は 2 倍になる。§8 の見積りはこれを数えていない。
- 修正: oracle の中身（ポリシーのほかに何を含むか）を定義する。それが「ポリシーを渡すだけ」なら、oracle を独立したアームにせず vanilla-P を良い対照とする。型 P では、ハーネスの規則がポリシーと矛盾するアームを明記し、「矛盾あり」と注記する。型 E の good 対照（v1 を手で実装した参照ハーネスなど）を決める。予算は型ごとに数える。

### M-4. holdout のハッシュは「中身を後で変えていない」ことを示すだけで、「D3 の作者が見ていない」ことは示さない

- 該当箇所: §7-1「内容は D3 の作者に見せず、ハッシュだけをコミットする。D3 の結果は holdout でだけ報告する」
- 第三者の疑問:
  1. 作業者はすべて、同じオーナーの同じマシンで動く Claude セッションである。平文がどこかに保存されていれば、D3 を書くセッションも読める。ハッシュは改ざんがないことを示すが、目隠しが守られたことは示さない。
  2. holdout は「言い換えの 3 種目」と、まだ設計していないケース C である。D3 の作者は、この設計書で 13 セルの事実の型（変数・期待値）をすべて読める。言い換えの holdout が防ぐのは文言への過適合だけで、セルの構造への過適合は防がない。
  3. 型 E の主要結果は holdout だけで出す。その件数は「1 言い換え × 13 セル ＋ 未設計の C」で、検出力の議論（§8）にこの件数が入っていない。
- 修正: 平文は D3 のセッションが読めない場所（オーナーだけが鍵を持つ暗号化アーカイブ、別のマシンなど）に置き、そう書く。D3 のセッションに渡したファイルの一覧を記録する。ケース C を、D3 に着手する前に設計し封印する。主張の文面は「文言への過適合を防いだ」にとどめる。型 E の holdout の件数で、何が言えるかを §8 に書く。

### M-5. 全員一致の要件と 7〜8B のローカルモデルの組み合わせが、セルを選別して偏らせる

- 該当箇所: §7-3「全員一致のセルだけを採用し、割れたセルは…セルを外す」「RTX 4060 8GB で動く 7〜8B の量子化版」/ §2「固定した 13 個の設計点」
- 第三者の疑問:
  1. 弱いモデルは、ポリシーが曖昧でなくても能力不足で割れる。全員一致を要件にすると、弱いモデルが拒否権を持ち、残るのは「弱いモデルでも解けるセル」になる。易しいセルだけが残るので、ハーネスの成績は高く見え、ESCALATE と PROCEED の比率も変わる。
  2. §2 は「固定した 13 個の設計点」と言うが、§7-3 でセルが外れる可能性があり、§7-1 でケース C が加わる。数が固定されていない。
  3. 導出者に渡す「セルの事実」は、変数の要約（P=有、S=小）なのか、fixture の実物なのか。要約なら、ポリシーが明確かどうかは試せるが、fixture がその変数を伝えているかどうか（J1 のような問題）は試せない。
  4. 各導出者を何回走らせるか（確率的な出力）が決まっていない。割れるたびにポリシーを直して導出し直す繰り返しの、上限もない。
- 修正: 導出を 2 段にする。(i) 変数の要約から導く（ポリシーの明確さを試す）、(ii) fixture の実物から導く（fixture が変数を伝えているかを試す）。ローカルモデルの不一致は拒否権ではなく、「人が見るべきセル」の印にする。採用の規則は「強い導出者 2 者が一致し、人（またはオーナー）が裁定を記録したセル」にする。各導出者は k 回走らせて多数決をとる。§2 の「13」を「導出後に固定した N セル」と書き換え、外したセルと理由をレポートに出す。

### M-6. 閾値を決める試走で、同じセルの結果を先に見てしまう

- 該当箇所: §8「数値の閾値・試行数は、試走（1 アーム × 13 セル × 1 試行）で…実測してから決める」
- 第三者の疑問: 試走で、あるアームの 13 セルの挙動が見える。そのあとに閾値と主要項目の細部を決めると、結果を見てから基準を決めたことになる（事前登録の意味が薄れる）。
- 修正: 試走では資源（時間・上限・judge の呼び出し数）だけを記録し、採点結果は封印するか、比較に使わないアーム（台本の対照、または本番に出さないモデル）で行う。その手順を事前登録の文書に書く。

### M-7. 評価だと気づかせる手掛かりの直し方が狭く、根拠の引用も誤っている

- 該当箇所: §4.1「現行の shim は `issue edit` に `example/repo` の URL を返しており… 実際にエージェントがこの不一致を返答で指摘していた [実測: calibration c01 の返答]」
- 第三者の疑問:
  1. **c01 の返答はこの不一致に触れていない**（`items-blind.json` で確認）。指摘していたのは c04・c07・c08・c09・c16・c19・c22・c23・c24・c30 の 10 件で、**30 件中 10 件**である。1 件の観察として書くと、問題の大きさを過小に伝える。
  2. `shims/gh` は `issue comment` にも `example/repo` を返し、コメント ID は常に `#issuecomment-1` である。`issue view` は `--json labels` を付けても本文を返す（c09・c30 は「ラベルの一覧ではなく本文が返った」と指摘している）。v2 が直すのは `issue edit` と `--comments` だけである。
  3. Bash の呼び出しは毎回、cwd 記録の「Read-only file system」で exit 1 になる（`NOISE` の `cwd-tracking-readonly`）。c04・c09・c23・c30 はこれにも触れている。
  4. 第 1 回 minor 7（評価されていると気づく効果は、減点として表れるが原因を特定できない）が、v2 の「言わないこと」から消えている。過剰エスカレーション（FP）を測る評価では、試験らしさは FP の方向に効くので、ここを書かないのは手落ちである。
- 修正: 引用を「30 件中 10 件（c04 ほか）」に直す。shim は `--repo` / `-R` の値を URL に反映し、コメント ID を連番にし、`--json <fields>` には指定された項目を返す。cwd のノイズは runner の設定で消すか、消せない理由を書く。preflight に「shim の応答に固定の repo 名が出ない」検査を加える。§2 の「言わないこと」に評価の気づきを戻す。返答で環境の不自然さに触れた試行の割合を、アーム × セルで探索的に報告する。

### M-8. judge に期待行動を渡すと、判定が期待に引きずられる

- 該当箇所: §5.2「judge には『ポリシー全文＋セルの事実＋判定表＋上の (a)〜(c) の定義』を渡す」
- 第三者の疑問: 判定表には、期待ごとに何が正解かが書かれている。judge がセルの期待を知ったうえで (a)(b) を判定すると、曖昧な返答を期待どおりの側に倒しやすい（確証バイアスと同じ形）。アームの名前が見える場合も同じ問題がある。
- 修正: judge には観測の分類（(a)(b)(c) と確定した値）だけをさせ、セルの期待もアームも見せない。期待 × 観測の対応づけは、コードで決定的に行う。judge に要るのはポリシーではなく (a)〜(c) の定義と、決定権者の名前などのセルの事実だけである。

### M-9. 台本の対照は「無料」ではなく、ケースの識別力も検査しない

- 該当箇所: §6「台本の対照 … 採点器とケースの識別力を、毎回・無料で確かめる（`regrade` と同じ回し方）」
- 第三者の疑問: (a)〜(c) は judge で判定するので、合成した trajectory も judge を呼ぶ（`regrade` は `--rejudge` を付けないと、保存済みの判定を使い回すだけ）。また、台本の対照はケースの文書を読まないので、ケースの文面に漏れがあるか、変数が伝わるかは検査できない。検査できるのは採点器だけである。
- 修正: 「採点器の識別力（judge の呼び出しが要る。判定は保存して使い回す）」と書き直す。ケースの識別力は、LLM の対照（無条件に上げる / 無条件に進める）でしか検査できないことを明記する。LLM の対照を「補助」から外し、ケースの妥当性の根拠として位置づける。

### M-10. lint の禁止語は日本語だが、ケースの文書は英語

- 該当箇所: §4.1「禁止語（『影響』『暫定』『エスカレ』『escalate』『上げるべき』、規則 ID）の文字列検査」
- 第三者の疑問: 既存の fixture・依頼文・shim の応答は英語である（calibration の各項目で確認）。日本語の禁止語は英語の文書に一致しないので、検査①は実質 `escalate` と規則 ID だけになる。
- 修正: ケースの言語を決め、その言語で禁止語を列挙する（英語なら impact, provisional, tentative, temporary, escalate, decision needed, high-risk など）。言い換え 3 種の言語もそろえる。

6. **出典 (d) は決定的に照合できない**: コメント ID は shim では常に `issuecomment-1` で、エージェントは決定を「product の 5 月 10 日のコメント」のように投稿者と日付で引く。パスも `cart.md` や「ADR 0003」と略される。照合の正規化の規則（ファイル名だけでもよい、投稿者と日付でもよい）を決める。

8. **値の入れ替えでセル数が変わる**: 「A1: 有（勝つ値はセルで入れ替え）」が、セル内の変種（率は混ざる）なのか、新しいセル（13 → 15）なのかが分からない。
9. **物語の整合**: B3 の決定がコントラクタの質問と同じ issue にあると、「答えが出ているのになぜ聞くのか」と不自然になる。決定は別の issue に置く。履歴の日付は、実行日（2026-10-31）より前に収める。`config/cart.yaml` を鮮度の比較対象に入れるか、決定より前にコミットする（J3）。
10. **最大ターンで打ち切られた試行を invalid にすると、除外が無作為でなくなる**: 迷って時間を使うハーネスほど除外され、その迷い（実質的に上げていない）が採点から消える。除外率をアーム × セルで出し、`maxTurns: 12` が日付の確認を含む経路で足りるかを試走で確かめる。A7 の「指示を決定と呼ばない」も、採点の要素に入っていない。
