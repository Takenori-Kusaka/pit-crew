# 00 目的と完了の定義（プロジェクトの憲章）

作成: 2026-11-03（オーナーの goal 設定。下書きは Claude、オーナーが採用）。改訂: 2026-11-03 夜 成果物 1.0 を追加、1.1 の主な量をプロセス準拠と根拠に変更（いずれもオーナー承認）/ 状態: **有効**
この文書は pit-crew の目的・成果物・完了の定義・規律の正本。実験カードと現状サマリーは、冒頭にここの目的と、効く成果物の番号を 1 行書く

## 目的

汎用的なハーネスを評価済みの形で public リポジトリで公開する。

## 背景

がんばりクエストで作ってきたロール別のハーネスを汎用化し、仕事や新しいプロジェクトで取り入れられるようにしたい（会社では PO / Dev / QM / review / maintenance をゼロから作り直すことになり、時間がかかった）。汎用部分はそのまま使え、現場の導入時に案件固有の値と規則を足せる形で公開する。導入を容易にし、プロジェクトの効率と品質を上げることに寄与する。

## 成果物と完了の定義

1. **ロール別ハーネス**（PO・Dev・QM・review・maintenance など、ピットイン開発プロセスに要るロール）
   - 1.0 ロールごとに求められる仕事の難易度（受け取る入力の粒度と、判断の重さ）が定義されている。完了 = ピットイン開発プロセスと現場の実例（GQ の Issue、会社で起きた事例の抽象化）から、ロールごとの難易度の段階と、それぞれの実例を書いている（例: Dev は「AI エージェントの実行基盤をフルサーバレスで」程度の粗い依頼で呼ばれる。QM・review はその粒度でレビューする。PO は費用・技術の制約が顧客に与える影響を決裁する）
   - 1.1 構造化されていて、生成 AI がルールや役割の漏れを起こしにくいことが評価済み。完了 = ロールごとに、課題で「ハーネスなし・GQ を丸ごと写したもの・最初の汎用版 v1」と比べ、事前に決めた規則で、**主な量 = 規定したプロセスへの準拠と根拠の裏付け**（工程の成果物が順に残るか・挙げた出典を実際に開いたか・判断ごとの理由と代替案）を上げるか、上げられない工程を明記している。最終結果の害は補助の量（事故の型から作った課題で、害を減らすか）。品質の定義はピットイン開発プロセス（品質保証 = 根拠を証拠と論証で示す）と各ロールの設計書から取る（オーナー 2026-11-03）。課題は 1.0 で定義した難易度で作る（易しい課題だけで得た結論は、その難易度の範囲の主張にとどめる）
   - 1.2 ロールの仕事が体系的に整理され、利用者の状況からどの仕事をするかを判断できる。完了 = 仕事の一覧と、状況から仕事を選ぶ判断の規則があり、選び間違いを課題で測っている
   - 1.3 各仕事のプロセスが明確で、利用者の入力・世の中の動向・業界標準・社内ルールを体系的に整理してから進めることが基本動作として組み込まれている。完了 = 設計書の規定に出典（実証・方法論・事故・推論の別）があり、調査の工程が呼ばれ規定が届くことを測っている
   - 1.4 汎用部分と案件固有部分が分かれ、導入時に案件の値を足せる（アダプタ）。完了 = GQ 以外の 2 つ以上の題材で動くことを確かめている
2. **ハーネス評価基盤**（pit-wall）
   - 2.1 各ハーネスの評価基準を定義し、評価結果を記録する仕組み（実験カード・runs・判定の規則）
   - 2.2 評価結果からハーネスの改善点を抽出し、改善策を提案する仕組み
   - 2.3 テストデータ・教師データ（課題・台本の対照・保留セル）の作り方、偽判定の検出、AIOps の運用方法など、評価のノウハウを整理した文書
3. **新規ハーネスの開発を支援するフレームワーク / ハーネス**
   - 3.1 テンプレートとサンプル（設計書から arm とスキルを機械的に作る道具を含む）
   - 3.2 文書とガイドライン
   - 3.3 テストデータ・教師データの作り方
   - 3.4 AIOps の運用方法と評価方法
4. **公開**: public リポジトリ、第三者が自分の環境で評価を再現できる手順と CI

## 進め方

- 科学的なアプローチを重視し、目的への到達を急がず、確実な実現を目指す。論文・技術記事・業界標準を調べてロジックを組み立て、仮説を立て、検証の方法と条件を整理し、結果を考察して次へ進む基本動作を繰り返す。まだ誰も到達していないハーネスの評価手法の確立と実現を目指す
- 評価基盤は WSL の Docker 上に作り、評価を自動化して再現性と効率を上げる。第三者でも評価できるよう、個人環境に依存しない評価環境を作り、GitHub Actions などの CI/CD で自動化する
- 順序: Dev を評価まで仕上げる（1.0 の難易度の定義と、その難易度の課題での評価を含む） → 分かったこと（構造・届け方・測り方）を PO・QM・review・maintenance に当てはめ、ロールごとに評価する → 評価の文書とフレームワークを整える → 第三者の環境で再現できることを確かめて公開する。順序を変えるときはオーナーに聞く

## 規律

- **目的に戻る**: 各実験カードと現状サマリーの冒頭に、目的（汎用ハーネスを評価済みで公開）と成果物のどれに効くかを 1 行書く。比べる相手・課題・判断の問いを立てるときは、目的に照らして立てる。迷ったら目的に戻り、オーナーに聞く
- 方向を変える判断と、推奨を採るかはダイアログで聞く。それ以外は聞かずに進め、背景の作業を待つあいだも手を止めない
- 実験は、カードと集計の台本を実行前にコミットし、途中で結果を見ない。結果を見てから回数を足さない。集計の前に測り方と害の述語を確かめる。結果を見た後に直したら、直す前と並べて書く。事後の分析は判定に使わない。天井・床を一般化しない
- 出典のない規定や主張を書かない（[推論] と明記）。既存の調査を先に読み、調査を頼むときは読むべき既存の調査を指示に含める。課題や規定に答えを入れない（leak で確かめる）。書いたものは自分で批判的に読み直し、主張は全試行で数えて確かめる。検査は通る場合と落ちる場合の両方を確かめる
- 会社の情報・秘密・顧客データをリポジトリに入れない。公開（public 化・push）はオーナーの指示があってから行い、公開の前に全履歴の秘密情報の検査とライセンスの確認を行う
- 追加の支払いはしない（ホストの計算資源・サブスクの枠・GitHub Actions）。サブスクの認証を CI で使えるかは、規約と仕組みを確かめてから決め、オーナーに聞く
- WSL のコマンドはスクリプトファイルで `bash -l <file>`。JS・正規表現を含む台本は Write、書き換えは Edit。Harbor は並行させない。空きメモリ 6GB 未満で始めない。runs は commit 前に秘密情報を検査する
- 7 日枠の使用率が 0.99 に達したら止まり、ここまでの結果と残りの計画を書く

## 完了条件

成果物 1〜4 のすべてが「完了の定義」を満たし、public リポジトリで公開され、第三者の環境（GitHub Actions を含む）で評価を再現できることを確かめ、オーナーが公開を承認している。途中の各段階（Dev の評価完了・各ロールの評価完了・文書とフレームワーク・公開の準備）の終わりに現状サマリーを書き、次の段階に進むかをダイアログでオーナーに聞く
