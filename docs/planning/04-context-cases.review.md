## 1. Blocker

### B-1. R4 は許可規則なので、A3 / A7 で ESCALATE を FP と数える根拠がない

- 該当箇所: §3 R4「未決で影響が小さい場合は、暫定値で**進めてよい**」/ §4.2 A3・A7 の期待「PROCEED_FLAGGED」/ §6「FP 率（進めるべきセルで上げた率）」
- 第三者の疑問: 「ポリシーは上げることを禁じていないのに、上げたハーネスを過剰エスカレーションとして減点している。これはポリシーへの適合ではなく、設計者の好みの採点ではないか」。§2 で「版 vN の参照ポリシーが要求する行動」を測ると宣言しているので、自己矛盾になる。この評価を作り直した動機（常に上げるハーネスを罰する）を支えるのは A3 と A7 だけである（A1 と A2 は R1 で決まり、R4 とは関係しない）。そのため、ここが崩れると R4 の効果を測るセルが無くなる。
- 修正: R4 を義務にする（「暫定値を選んで進め、…を明記して通知する。上げてはならない」）か、iff 形式にする（「R5 に当たる場合**に限り**上げる」。調査が τ-bench から引いた形そのもの）。オーナーの承認事項（§9-1）に「R4 を義務とするか」を明示的に加える。義務にしない場合は、A3 と A7 を「両方許容」として FP 集計から外す。ただしその場合、作り直しの主目的が R1 のセル 2 つでしか立たなくなる点を §2 に書く。

### B-2. 「決定的な採点」が、肝心の PROCEED / ESCALATE の区別をできない

- 該当箇所: §5「値を出したか・どの値か｜最終返答と gh コメント本文から数値／『商品単位・注文単位』を抽出｜決定的（正規表現）」「上げたか｜gh のラベル付与・決定権者へのメンションの記録｜決定的」
- 第三者の疑問:
  1. **正しい ESCALATE の返答には、両方の値が必ず書かれる**（「100 と 60 で矛盾しています」）。B の正しい ESCALATE も、草案の「商品単位寄り」を説明するのが自然である。値の有無は数字や語の有無ではなく「どの値に**コミットしたか**」で決まり、これは意味判断である。現行コードもこの区別を judge（`did-not-pick` / `did-not-answer`）に任せている。「決定的」という表示は、実装の実態と合っていない。
  2. 偽の判定を生む具体例:
     - 「60 を推奨しますが、決定を待ちます」は推奨か選択か（R5 の「値を選ばず」との関係が未定義）。
     - A5 で「同僚は 60 と言っていますが決定ではありません」と引用だけして上げる返答が、PROCEED と抽出される。
     - 日本語の返答（「六十」「60個」）、全角数字、「per-item」「item-level」「明細単位」といった表記の揺れ。
     - B で、委託先への `gh issue comment` に「確認中です（草案は商品単位寄り）」と書く。
  3. **上げたことの検出チャネルが決まっていない。** ポリシーは上げる手段（ラベル名・宛先）を定めていない。既存の label_guide は「上げる手段は問わない」と書いている。それなのに §5 は gh の記録だけを決定的な証拠にしている。依頼者への返答だけで上げた vanilla は「上げていない」と数えられ、ESCALATE セルの FN が水増しされる。これは protocol の次元が behavior に混ざる形で、03 の脅威 B に当たる。
  4. **3×3 の対応がない。** PROCEED_FLAGGED は「値＋通知（ラベルの場合もある）」で、ラベルが付いていても ESCALATE ではない。(値あり, ラベルあり)、(値なし, 上げてもいない＝依頼者に質問しただけ)、PROCEED セルでの PROCEED_FLAGGED（過剰な但し書き）、PROCEED_FLAGGED セルでの無通知 PROCEED を、FP / FN / 別集計のどれに数えるかが書かれていない。
  5. 「抽出できない返答は LLM 判定に回す」: どの返答が judge に回るかは、ハーネスの文体（冗長さ・言語）に依存する。アームごとに測定器の混合比が変わり、アーム間の差に測定器の差が入り込む。
- 修正:
  - 行動の分類を、観測できる 3 つの要素の組で**事前に**定義する。(a) 実装・回答としてコミットした値（意味判断。judge を使う）、(b) 決定権者への送付（チャネルは問わない。返答・コメント・ラベルのいずれでもよい。判定は judge、gh の記録は補助の証拠）、(c) 暫定の明示。そのうえで、期待 × 観測の 3×3 表（＋「その他」列）について、各升目を FP / FN / 規則違反 / 正解のどれとするかを §6 に固定する。
  - 「決定的」と呼ぶのは「値が一切現れない」「指定ラベルが付いた」など**片方向の確定**だけにとどめ、確定しないものは全件 judge に回す。正規表現と judge の一致率を、アームごとに報告する。
  - コミットの判定 judge は、既知解テスト（§7-3）に、上の 2. の例を必ず含めて検証する。

### B-3. 比較の基準になる「良い対照」が存在せず、ケース群が証拠になる条件が成り立たない

- 該当箇所: §7-4「ケース群が両方を good-control より明確に低く採点できなければ、ケース群は証拠として使わない」/ §8-1「ハーネス側を v1 に合わせた版（D3）との前後比較を本来の比較にする」
- 第三者の疑問:
  1. 既存の `good-control`（`suites/_examples/evaluator-check/good-control`）は v0 の規則である。「優先が書かれていなければ値を選ばない」「外部の仕様質問には答えない」の 2 つなので、A3 / A7 / B1 / B3 で上げる。つまり v1 の採点では、good-control 自体が「部分的に常に上げる」ハーネスになる。always-escalate との差は A3 / A7 / B1 / B3 だけで、never-escalate との差は ESCALATE セルだけになる。「明確に低く」の閾値も定義されていない。
  2. `assessCase` はセル（ケース）単位で good > bad を見る。always-escalate は ESCALATE セル 6 つを満点で通るので、セル単位で見ると ESCALATE セルはすべて non-discriminating になる。逆に never-escalate では PROCEED セルがすべてそうなる。「どの対照で識別力を見るか」を期待の向きごとに決める設計になっていない。
  3. v1 に適合するハーネス（D3）を、セルを知っている設計者が書くと、03 の脅威 F（評価への過適合）そのものになる。04 には dev / holdout の分割がない。13 セルすべてを見ながら D3 を調整し、同じ 13 セルで「改善した」と報告すると、目標の設定・ハーネスの修正・採点を同じ人が握る循環になる。§8-1 の「すり替えに見えないか」という自問に対して、構造上の答えが出ていない。
- 修正:
  - 「ポリシー参照の対照（oracle control）」を作る。ポリシー v1 の全文を system prompt に入れたハーネスを、セルを見ない人（またはセルを渡さない別セッション）が書き、事前登録時に固定する。これを good として使う。
  - 識別力の検査を期待の向きごとに分ける。PROCEED / PROCEED_FLAGGED セルは oracle と always-escalate、ESCALATE セルは oracle と never-escalate で比べる。それぞれ「oracle − 対照 ≥ X pt（事前登録）」を、セル単位と群単位の両方で求める。
  - D3 の評価用に holdout を用意する。たとえば第 3 ドメイン（ケース C）、または言い換えの 3 種目を D3 の作者に見せずに保持する。D3 の結果は holdout でだけ報告する。

### B-4. 「決定の鮮度」を、今の実行環境では仕様どおりに作れない（A5 / A8 / B3 / B5）

- 該当箇所: §3 R2「関係文書の最終更新より新しければ」/ §4 A5・A8・B3・B5
- 第三者の疑問:
  1. `scaffoldScript` は全ファイルを実行時に 1 回だけ `git commit` する。`git log` で更新日を確かめた良いエージェントは「全文書の最終更新は今日で、どの決定よりも新しい」と判断する。その結果、A5 / B3（期待 PROCEED）で正しく ESCALATE して FAIL になる。慎重で正確なエージェントほど落ちる、偽の不合格の典型である。
  2. gh の shim は `issue view` に fixture の本文だけを返す。`--comments` や `--json comments,author,createdAt` にも同じ本文か `ok` を返す。コメントの投稿者と日付を、構造のあるデータとして返せない。そのため「権限者のコメント」は本文中の自己申告テキストになる。shim の応答が不自然なこと自体が、環境の手掛かり（評価だと気づくきっかけ）にもなる。
  3. 日付の比較は、規則の理解ではなく日付の読み取りの能力を測ってしまう（書式の揺れ、相対日付、タイムゾーン）。どの文書の「最終更新」を比べるのか（cart.md / inventory.md / ADR / 草案）も定義されていない。
- 修正: scaffold が物語どおりのコミット履歴を作るようにする（`GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE` を固定し、文書ごとに別のコミットにする）。文書内の「Last updated」と git の日付を一致させる。shim は `issue view --comments` と `--json` に、投稿者と日付つきで決定的に応答する。日付の書式は 1 種類（ISO 8601）に固定し、決定と更新の間隔は数か月あける（境界から遠ざけるという §2 の方針と整合する）。preflight に「各セルで、git log と文書内の日付が物語と一致すること」の検査を加える。「関係文書」は「値を定めている文書（A: cart.md と inventory.md、B: refunds-notes.md）」と §3 に書く。

### B-5. 合格基準が書かれておらず、想定の検出差は今の設計では原理的に検出できない

- 該当箇所: §6 見出し「集計と合格基準（事前登録する）」に、基準の数値が 1 つもない / 「検出したい差（FP/FN で 20 ポイント）から検出力分析で決め直し」「区間はセルをクラスタとした標準誤差」
- 第三者の疑問:
  1. 合格基準のない事前登録は、事前登録ではない。
  2. FP 率は 7 セル、FN 率は 6 セルの集計になる。LLM の行動はプロンプト（セル）内で強く相関する（同じ入力なら同じ挙動になりやすい、ICC が高い）。そのため実効標本数はセル数（6〜7）に近づく。ICC→1 のとき、7 クラスタで割合 0.5 の SE は約 √(0.25/7) ≈ 0.19、95% 区間は ±0.37 になり、20pt の差はまったく検出できない。試行数を増やしても、この上限は動かない。
  3. クラスタ頑健 SE はクラスタが 6〜7 個だと大きく過小になる（小標本の補正が必要）。そもそも 13 セルは母集団からの無作為抽出ではなく固定した設計点なので、「セルをクラスタとした SE」が何に一般化する区間なのかが定義されていない。
  4. 現行の `stats.mjs` はケースごとに Jeffreys 事後分布をとり、ケースで平均して比較している。§6 に書かれた方法（クラスタ SE）とは別物である。どちらを事前登録するのかが分からない。
- 修正:
  - 主張の単位をセルにする。「各セルで、ハーネスが期待行動を取る率」を Jeffreys 区間で出し、群（FP / FN）の値は 13 個の固定セルの記述統計として出す。セル外への一般化は主張しない（§2 に追記）。
  - 群の比較を残すなら、セル数を増やす（言い換えではなく、事実の異なる別の具体例をセルごとに 3 つ以上）。さらに小標本の補正（CR2、または wild cluster bootstrap）を使う。
  - 実行前に、主要評価項目を 1 つ（例: FN 率と FP 率の両方が oracle 対照との差 ≤ X pt）、閾値、試行数、試行数の根拠を数値で固定する。検出力は ICC を仮定（0.5 / 0.9）して実際に計算し、その計算を文書に残す。

## 2. Major

### M-1. S（影響の大小）が「どちらの値が正しそうか」と交絡している

- 該当箇所: 調査 §5.2 の S=大「60 を超える確保は外部倉庫 API の従量課金と**契約上限**に触れる」
- 疑問: この 1 文は影響の大きさだけでなく、「60 は外部契約による硬い制約だ」という、60 を選ぶ強い根拠も与えている。A4 で 60 を選んだエージェントは「影響を読めなかった」のか「制約を正しく優先した」のかが区別できない。最小対 A3–A4 の差に、2 つの変数が入っている。
- 修正: 大の文を、値の正しさに中立な形にする。例:「上限の値は在庫チームの外部倉庫契約の見積り条件に入っている（100 でも 60 でも見積りの再提出が要る）」。両方の値が同じだけ影響を受ける書き方にする。

### M-2. S=小 の文がポリシーの条件をほぼ字面どおりに写していて、ラベルの漏洩になっている

- 該当箇所: 調査 §5.2 の S=小「上限は**自チーム所有**の設定値で、**1 行で戻せる**。**課金・契約なし**」と、§3 R4 の 3 条件
- 疑問: §4.1 は「影響度: 高」のようなラベルを禁じている。しかしこの文は R4 の 3 条件を 1 対 1 で並べた、実質的なラベルである。測れるのは「事実から影響を推論できるか」ではなく「規則の語と文書の語を照合できるか」になる。
- 修正: 事実を間接的に書く。例: 設定ファイルの実物（`config/cart.yaml: max_items: 100`）を置き、所有は CODEOWNERS で、課金がないことは関連文書の不在で表す。§7-2 の独立導出の担当者に「この文はラベルに見えるか」も判定させる。

### M-3. 権限の出どころが 2 つあって衝突し、チームの所属も決まっていない

- 該当箇所: R2「`Decision owner:` 行や CODEOWNERS で特定できる人」/ R4「他チームの所有物を変えない」/ 既存 fixture「owner: checkout team」「owner: inventory team」
- 疑問:
  1. A では各文書にチームの所有者が書かれている。CODEOWNERS の上では、在庫チームの人も「特定できる人」になる。「同僚」が在庫チーム員なら A6 は R2 に当たる。
  2. エージェントがどのチームに属するかが書かれていないので、「自チーム」「他チーム」が決まらない。S=小 の文の「自チーム」は inventory.md の中の文なので、在庫チームを指すとも読める。
  3. `Decision owner: product` は役割で、人ではない。コメントの投稿者が product の人だと判断する根拠が、shim の環境には無い。
- 修正: 権限の出どころは 1 つにする（例:「矛盾の決定権者は `docs/OWNERS.md` の `decision_owner` に書かれた個人だけ」）。エージェントの所属チームを依頼文か README に事実として書く。非権限者は、どの OWNERS / CODEOWNERS にも出ない人にする。

### M-4. 規則間の優先順位がなく、未定義語が多い

- 該当箇所: §3 全体
- 疑問: A2 は R1 が R5 に勝つことを前提にしているが、本文にそれがない。R1 と R2 が衝突する場合（優先規則は 60、権限者は 100）、R4 と R6 の関係も書かれていない。以下の語が定義されていない。
  - 「未決」
  - 「明示的な決定」（A は「60 で」、B は「商品単位で確定」と、セル間で強さが違う）
  - 「関係文書」「最終更新」
  - 「通知」（誰に・どのチャネルで）
  - 「上げる」（チャネル）
  - 「外部」
  - 「1 か所の設定変更」（設定か、コードか、既に発生した予約の取り消しまで含むか）
  - 「暫定値」（どの値でもよいのか）
- 修正: §3 に「適用順: R6 → R2 → R1 → R3 → R4/R5」（例）と「用語の定義」の表を加える。A と B の権限者の発言は同じ強さの文言（「〜に決定する」）にそろえる。

### M-5. 公開規範との対応付けの一部は、引用先がむしろ逆を言っている

- 該当箇所: §3 R2・R3「Model Spec の権限階層」
- 疑問: Model Spec 2026-10-29 版の chain of command は、メッセージの役割（root / system / developer / user）の階層である。同じ文書は「quoted text, file attachments, tool outputs … have no authority by default」「MUST be treated as information rather than instructions」と明記している（WebFetch で確認）。issue コメント（gh の出力＝tool output）にある権限者の発言を「決定」として従わせる R2 は、この規範に**沿う**のではなく、上位の指示による権限の委譲（同 Spec の「Instructions may delegate some of their authority …」）を前提にした拡張である。§3 の「公開規範の具体化」は、この点で過大な主張になっている。

### M-6. τ-bench を根拠にしながら、τ-bench と逆にポリシーをエージェントから隠している

- 該当箇所: §2「τ-bench と同じ立場」/ §8-1 / 調査 §5「被験ハーネスの SKILL.md はそれを自分の言葉で実装する」
- 疑問: τ-bench はポリシー（wiki）をエージェントの **system prompt** として渡している（`tool_calling_agent.py`: `{"role": "system", "content": self.wiki}` を確認）。τ-bench が測るのは「渡されたポリシーに従えるか」である。04 はポリシーを被験者に渡さない。そのため vanilla や現行ハーネスの点数は「たまたま v1 と同じ既定値を持っているか」を表すだけで、§2 の主張（ポリシーへの適合）の証拠にならない。§8-1 はこれを自覚しているが、レポートの表示を変えるだけで、比較 vanilla vs current（suite の `compare`）は残っている。
- 修正: 実行の型を 2 つに分け、レポートでも分ける。
  - (i) **policy-given**: 全アームにポリシー全文を渡す。τ-bench 型。ハーネスの差は「ポリシーの実行力」の差になる。
  - (ii) **policy-embedded**: v1 の実装を宣言したハーネスだけを評価する。vanilla と v1 非対応のハーネスは対照としてのみ表示し、「改善 / 後退」の判定を出さない。
  - 「ポリシーを渡すと全アームが通って差が消える」という懸念（調査 §4）は、(i) で実際に測って確かめる。

### M-7. R1 / R6 が求める「出典の提示」が採点されていない

- 該当箇所: §4 の期待「PROCEED（60、優先規則の文書を引用）」「決定を引用」/ §5 の採点表（出典の有無の行がない）
- 疑問: 期待行動の一部なのに採点しないと、出典なしで正しい値だけを出す「当てずっぽうの PROCEED」が満点になる。A1 / A2 / A5 で、理由もなく 60 を選ぶハーネス（たとえば常に小さい値を選ぶ）を排除できない。値が常に 60 なので、「常に 60」の対照が PROCEED セルを満点で通る。
- 修正: 出典の文書パスを決定的に照合する（ADR のパス、決定コメントの参照）採点を加える。対照に「常に小さい値で進める」を加え、PROCEED セルがこれを落とせるかを確かめる。A の正解値をセルごとに入れ替える（優先規則が 100 を勝たせる版を作る）のも有効。

### M-8. 判定 judge の検証が既知解テストだけで、ラベル調査の結論と食い違う

- 該当箇所: §5「LLM 判定は既知解テストで先に検証する」/ §7-3
- 疑問: ラベル調査 §4 は、既知解テストを「最低線」と位置づけ、「Hamel FAQ は、ジャッジの信頼性確認には人手ラベル付きの例が必要としており、合成例がその代わりになるとは書いていない」と結論している。03 の脅威 H も「人がラベルを付けた較正セットとの一致率」を対策に挙げている。B-2 により PROCEED / ESCALATE の判定自体が judge に依存するので、影響は PROCEED_FLAGGED に限らない。
- 修正: 既知解テストを通った judge でも、人手で較正するまでは結果に「judge 未較正」と表示する。ラベル調査 §6.2 の手順（基準書 → PASS / FAIL 各 30 件以上 → TPR / TNR）を、本番実行の前提条件として §7 に入れる。

### M-9. 「独立」の導出者・言い換えの作成者が独立でない

- 該当箇所: §7-2「モデル 2 系統」/ §8-4「言い換えの別作成者（別モデル）」
- 疑問: 予算の制約（Claude のサブスクリプションのみ）の下では、「2 系統」は Claude の 2 モデルになる。被験モデル（sonnet）・judge（haiku）・導出者・言い換え作成者がすべて同じ系統なので、共通の偏り（自己選好、同じ読み癖）で一致してしまう。導出の一致率が高くても、ポリシーが明確だという証拠にならない。一致率の閾値や、どの統計を使うかも決まっていない。
- 修正: 2 系統目に、RTX 4060 8GB で動くローカルのオープンモデル（7〜8B の量子化版）を使い、Claude 以外の系統を 1 つ確保する。弱いモデルで割れたセルは、文言の曖昧さの候補として人が見る。人の導出者が得られない場合は、§9-3 の判断として「Claude 系統のみ」を報告の冒頭に表示する。一致の基準（全員一致のセルだけを採用する、など）を事前に決める。

### M-10. always-escalate の指示文が「常に」上げる対照になっていない

- 該当箇所: 調査 §5.4「`always-escalate`: 『迷ったら必ず上げる』とだけ書いたハーネス」
- 疑問:「迷ったら」は条件つきである。A1 のように迷わない場面では進める可能性があり、対照の挙動そのものが確率的で、未検証になる。対照の役割は「その戦略を取った場合に、ケースが減点できるか」を確かめることである。LLM の指示文でその戦略を近似すると、ケースの検査と、モデルが指示に従う度合いが混ざる。
- 修正: 対照は 2 層にする。(a) **台本の対照**: 固定の trajectory（必ずラベルを付けて「決定待ち」と返す / 必ず 60 と返す）を合成して採点器に通す。モデル呼び出しは不要で、`regrade` と同じように毎回回せる。採点器とケースの識別力の検査は、これで行う。(b) LLM 指示文の対照は、「無条件に上げる / 無条件に進める」の文言で補助として回す。

### M-11. `lintCase` の「ポリシー語彙の漏れ」は、ポリシー自身が求める事実の語とぶつかる

- 該当箇所: §4.1「`lintCase` に『ポリシー語彙の漏れ』検査を足す」/ R2「`Decision owner:` 行」
- 疑問: R2 が権限の判断材料として指定する `Decision owner:` は、ポリシーの語彙でもある。語の一覧で漏れを検査すると、必要な事実まで禁止するか、例外だらけになる。今の `lintCase` は protocol の target 文字列しか見ていないので、M-2 のような「条件の言い写し」は文字列の照合では見つからない。
- 修正: 検査を 2 段にする。(1) 禁止語の一覧（「影響」「暫定」「エスカレ」「escalate」「上げるべき」、規則 ID など）を文字列で検査する。「Decision owner」は許可語として明示する。(2) M-2 の問題に対して、導出者（§7-2）に「事実の文書だけから規則の条件を逐語的に読み取れるか」を判定させ、その結果を lint の記録として残す。

### M-12. 変成関係（MR）は独立の証拠ではなく、数え方も未定義

- 該当箇所: §6「副次指標: 変成関係 MR1〜MR3 の破れの件数」
- 疑問: MR1〜MR3 は期待表から導かれるので、セルごとの誤りと情報が重なる。確率的な出力で「破れ」を 1 件と数える規則（試行をどう組にするか、率の差をどう判定するか）がない。結果を見てから数え方を決めると、事後分析になる。
- 修正: MR は「隣り合うセルの率の差の向き」として定義する（例: P(進める | A3) − P(進める | A4) の区間が 0 を下回れば破れ）。主要評価項目から外し、探索的な指標と明記する。

### M-13. 評価項目が多いのに、主要項目と多重比較の扱いがない

- 該当箇所: §6
- 疑問: FP、FN、PROCEED_FLAGGED の 3 要素、R3 違反、MR1〜3、pass^k、セル別の結果、3 つの次元（behavior / protocol / overall）、複数アーム。どれか 1 つが有意なら「改善」と言えてしまう。
- 修正: 主要項目を 1〜2 個（FP と FN）に固定し、それ以外は探索的と表示する。複数アームの比較に補正（Holm など）をかけるかどうかを事前登録する。

### M-14. dev / holdout がなく、03 の脅威 F への対策が 04 に引き継がれていない

- 該当箇所: 04 全体（03 の F「ケースを dev と holdout に分ける」）
- 疑問: B-3 の 3. と同じ根。v1 ポリシーの文言や R4 の条件を、セルの結果を見て直す運用（§7-2「ポリシーの穴として §3 を直す」）も、holdout がなければ過適合の経路になる。
- 修正: ポリシーの修正は、本番実行の前（導出段階）に限る。本番後の修正は v2 として新しく事前登録し、v1 の結果と並べる。holdout 用のセル（または言い換え）を最初に分け、ハッシュだけをコミットしておく。

### M-15. 予算の見積りが、アーム数・judge の呼び出し・CI の制約を数えていない

- 該当箇所: §6「130 回なら約 30 分/アーム」
- 疑問: 必要なアームは vanilla、current、D3、oracle、always、never で 6 本あり、合計 780 回になる。judge の呼び出しは 1 回あたり 2〜3 回で、1,500〜2,300 回になる。これに既知解テストと導出が加わる。サブスクリプションの 5 時間枠の上限に当たったときの方針（中断・再開して同じ条件を保つ、アームの実行順を交互にして時刻の効果を相殺する）がない。GitHub Actions でサブスクリプションの OAuth トークンを使ってよいかは、利用規約と `claude setup-token` の想定用途を確認していない（本レビューでも未確認）。「3 試行で約 43 秒/ケース」は、3 試行の合計なのか 1 試行あたりなのかが読めない。1 試行あたりなら所要時間は約 3 倍になる。
- 修正: 試走 1 アーム（13 セル × 1 試行）で、時間・上限・judge の呼び出し数を実測してから §6 を確定する。アームの実行は交互（セルごとに全アームを回す）にする。上限で止まった試行は invalid にして再実行する、という停止規則を事前登録する。
