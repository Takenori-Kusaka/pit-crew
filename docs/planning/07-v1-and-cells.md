# 07 汎用ハーネス v1 の方針と、それを測る課題（提案）

作成: 2026-11-01 / 状態: **承認済み（2026-11-01、§7）**
根拠: `docs/planning/00-owner-statements.md`（オーナーの発言の棚卸し）、`docs/research/research-reusable-role-harness.md`（調査、照合済み）、`runs/2026-11-01/stage1-v0-1`（基準点 v0 の試走）

## 1. 目的の置き直し

- 作るのは、**役割分離のハーネスを新しい案件で使い始めるまでの手間を小さくする、汎用の核**。会社での 3 つの課題を解くことは目的ではない（オーナー 2026-11-01）
- オーナーが示した形: 汎用の部分はテンプレートに埋めず第三者が単独で手に取れる。案件ごとの部分と分ける。スキルの本文は英語、人とのやり取りは日本語（00 §3）
- したがって評価の主役は 2 つ:
  1. **移植の手間**（新しい案件に合わせるのに、どれだけ書き換えが要るか）
  2. **移植しても役割の振る舞いが保たれるか**（入口・受け渡し・境界）

## 2. 基準点 v0 で分かったこと

- v0（がんばりクエストのロール本体）は、スキルが読み込まれても 6 回とも呼ばれなかった。説明文が「受信箱を見回るときに使う」で、1 回きりの依頼と一致しないため。仕組みどおりの結果（調査 Q2）
- v0 は、役割の判断・見回りの手順・案件の事実（ラベル名・パス・コマンド）が 1 ファイルに混ざっている（調査 5-3 の実測: 受け渡しラベルが 1 本あたり 7〜12 行、案件のコマンドが 3〜11 行）

## 3. v1 の中身（1 版 1 変更の原則で、まず構造だけを変える）

| 層 | 中身 | 置き場所 |
|---|---|---|
| 役割カード（核） | 5 役割それぞれの責任、決めること / 決めないこと、受け取る入力と渡す成果物、どの案件でも効く判断の規則。案件の固有名詞・パス・ラベル名を含まない。1 役割 100 行未満が目安。英語 | 汎用の配布物 |
| 入口の約束（核） | 役割セッションは役割として起動する（例: `--agent <role>`、または最初に `/<role>`）。説明文は「いつ使うか」を利用者の意図で書く | 同上 |
| 手順スキル（核） | 受信箱の見回りなど、役割カードから呼ぶ手順 | 同上 |
| 案件アダプタ | 受け渡しの印の名前、文書と SSOT の置き場所、ビルド・テスト・課題管理のコマンド。核は名前で参照し、核のファイルは編集しない | 案件ごとに 1 ファイル |

- v1 で**やらないこと**: 役割の数を増やす、作業手順のスキル一式を足す、フックで強制する（別の版で比べる）
- v1 の中身は v0 から作る（v0 の規則を、核とアダプタに振り分ける）。新しい規則は足さない。足すと「構造の効果」と「規則の効果」が混ざる

## 4. 測る課題（セル）

| 順 | セル | 何を測るか | 採点 |
|---|---|---|---|
| 1 | **入口**: 役割ごとに依頼文 約 20 件（使うべき / 似ているが違う）。訓練 6 割・検証 4 割で固定 | 正しい役割に入るか | 記録のスキル / エージェントの呼び出し（決定的） |
| 2 | **受け渡し（2 段）**: 例 Dev → QM。受信箱はコンテナ内で再現 | 約束どおりの成果物と印、受け手が成果物を読んでから判断したか | 最終状態 + 呼び出しの順序 |
| 3 | **境界**: 越境したくなる状況（レビュー役に「直したほうが早い」不具合、承認権のない役割への承認依頼など） | 越境せず、正しい相手に回すか | 最終状態 |
| 4 | **移植**: 2 と 3 を、言語・印の名前・文書の配置が違う 2 つ目の架空の案件で。核は同じ、アダプタだけ差し替え | 移植後の合格率の比 | 2・3 と同じ |
| 5 | **単一セッションの基準**: 役割なしの 1 セッションで同じセルを解かせる | 役割分離の効果と、トークン・時間の上乗せ | 同じ + コスト |
| — | A3 / A4 / A9 | 回帰の見張り（版を変えるたびに各 1 回） | 既存 |

- 題材（どんな不具合・依頼か）は例にすぎず、会社での課題に寄せない。セルの題材は役割の振る舞いを引き出すための道具
- 判定の作法は既出（`research-next-steps-small-n.md`）: 識別力のあるセルだけ採る、止め方を先に決める、セル別の区間で報告する

## 5. 移植の手間の指標

- 主指標（並べて表示し、1 つの数に合成しない）: ① 新しい案件に合わせるために核を書き換えた行数（目標 0）、② 移植後の合格率の比、③ アダプタの大きさ
- 補助: 核が指すのに案件側にない参照の数、核に漏れた案件の値の数、別のエージェントがアダプタを埋めて確認用セルが通るまでの往復回数（人の作業時間の代理）
- 人の作業時間を直接測った研究は見つからなかった（調査 Q4）。往復回数は代理であり、主張はそこまでにとどめる

## 6. オーナーに決めていただきたいこと

1. 目的の置き直し（§1: 主役は移植の手間と、移植後も役割の振る舞いが保たれること）でよいか
2. v1 の構造（§3: 役割カード・入口の約束・手順スキル・案件アダプタ）でよいか。v1 は構造だけ変え、規則は足さない
3. 2 つ目の架空の案件（移植先）は、設計者が作ってよいか（言語・印の名前・文書の配置を変えた小さなリポジトリ）
4. 作る順: 入口のセル → v1 の作成 → 受け渡し・境界のセル → 移植のセル、でよいか

### 7.1 追加: 導入の手引きを v1 の配布物に含める

- 汎用の核と一緒に、**案件アダプタの作り方の手引き**（何を埋めるか、どの順で、確かめ方）と、**既存のプロダクトへ導入する手順**（既にある CLAUDE.md・ラベル・文書の配置をどうアダプタに写すか）を配る
- これは §5 の補助指標「別のエージェントがアダプタを埋めて確認用セルが通るまでの往復回数」で、そのまま測れる。手引きの良し悪しが、移植の手間の数字に出る
- 手引きもハーネスの一部として版を付け、変えたら同じ物差しで測る
