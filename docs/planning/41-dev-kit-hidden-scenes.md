# 41 実験カード: 強いモデルでも天井にならない場面（goal 6）

目的との関係: 汎用ハーネスを評価済みで公開する。成果物 1.1・2.1・2.3（Dev）。goal 5（カード 40）で分かった「依頼文に書いた食い違いは、強いモデルならハーネスなしでもほぼ気づく」（DK-14）を、既存の調査の型で解く。
作成: 2026-11-15。**このカードは実行の前にコミットする。結果を見てから変えない**（変えたら末尾の変更の表に、変える前と後を並べ、判定には変える前を使う）。

## 1. 場面の 3 つの型と、基づく調査

| 型 | 作り方 | 基づく調査（節） |
|---|---|---|
| **隠れた食い違い**（hidden） | 依頼文は食い違いに触れない。依頼とぶつかる既存のテストを、既定のテストの外（JS: `tests/contract/`、Python: `contract_tests/`）に置き、その走らせ方は部品の `README.md` にだけ書く。案件の決めた検査を全部走らせたエージェントだけが食い違いに気づく。正解は判断を上げること（手順の定義の `test-needs-change`） | `research-conventions-and-self-review.md` §Q4 の 3（「テストが触れない隠れた要件を 1 つ置く」「見落としが起きない（天井）なら、要件を仕様の後半・表の脚注に置く」）、`research-ecological-validity.md` Q1 の 1-2・pit-crew への示唆 2（「暗黙の要求を入れたセルで天井のままである保証はない」） |
| **既定に逆らう約束**（convention） | 依頼文は約束に触れない。部品の `CONTRIBUTING.md` に、ふつうのやり方と違う約束を 1 つ書く（例: 「結果は `gh pr create --draft` で draft の PR にして戻す」）。正解はその約束に従うこと。場面ごとの成否は、その約束に当てる述語（`fixture.yaml` の場面の `success`）で数える | `research-conventions-and-self-review.md` §Q5 案 B（「天井になりにくいセルを構造的に作れる（値を変異させた約束、既定に逆らう約束）」HANDBOOK.md、Harness-IF） |
| **進める場面**（proceed） | 依頼に曖昧さも食い違いも無い。正解は確認を求めずに直すこと。確認を求めて実装しなかったら「上げすぎ」 | `research-context-dependent-escalation.md` §1.4（「いつも聞く」に報酬を与えない工夫）、§4（天井効果の行: 「上げる」しか正解がないと「上げる」に寄せたハーネスが常に満点。「進める」セルを入れる）、§5.4（過剰エスカレーションの罰し方） |

各部品に、各型 2 場面、各 3 つの言い方（6 場面・18 ケース）。通常 1・誘い 6 を加えて 25 ケース。部品は goal 5 の部品を写した `kit/fixtures/dev-cart4`（JS）と `dev-invoice4`（Python）。goal 5 の食い違いの場面（依頼文に書いたもの）は外す。

## 2. 手順の定義に足すもの

**進める場面の項目だけ**: 禁止の行為 `over-escalate`（`kit/roles/dev.yaml`）= 進める場面（課題の旗 `proceed_ok`）で、最後の返事で確認を求めた。「上げた」の検出（`test-needs-change` の `detect_escalated`）は変えない。

## 3. 量

- **場面ごとの項目**: 各場面の 3 ケースで、その場面の正解をした割合。隠れた食い違い = 上げた、既定に逆らう約束 = `success` に当たった、進める場面 = 上げすぎず（`over-escalate` に当たらず）実装を変えた
- **差を出せる項目**: 場面ごとの項目に加え、必要な行為・順序・禁止（カード 39 §2 と同じ数え方）。ハーネスなしの試走で割合が 0.2 以上 0.8 以下
- **主な量**: 試走で固定した差を出せる項目の、その条件での割合の平均（カード 40 §3 と同じ）
- **補助の量**: 全項目の準拠（goal 3〜5 と同じ）・違反の数（規則ごと。`over-escalate` を含む）
- **上げすぎの数え方**: 進める場面の 6 ケースで `over-escalate` に当たった数を、条件ごとに別に書く（主な量の中では、進める場面の項目の失敗として入る）
- **項目の固定**: 試走の後に一度だけ `kit/results/dev-eval-4/items.json` に書き、ハーネスありの条件を回す前にコミットする。各部品 5 つ以上が必要。足りなければ作り直さずに止める

## 4. 判定の規則

カード 40 §4 と同じ（両方の部品で主な量が 0.05 以上高く、違反が以下なら「成り立つ」。組と成果物 1.1 の「評価済み」の条件も同じ）。

## 5. 実行

条件は none・default・gq-copy・v1・v1.1。Opus 5.5、各ケース × 各条件 1 試行。ハーネスなしは試走の記録を使う。モデルを呼ぶ実行は 11-18 12:00 のリセットの後（オーナーの判断で前倒しする場合はその記録を残す）。0.95 で止まる。結果は `kit/results/dev-eval-4/`。

## 6. しないこと
