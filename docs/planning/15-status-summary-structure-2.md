## 3. 分かっていないこと

- 「構造」のどの要素が効いたか。Mall と F の違いは 4 つ（状態ファイルで工程を決める案内 / 入る・出る条件を先頭にまとめる / 工程の中身を工程ごとにまとめる / F の「工程 1 から順に、どの工程も飛ばさない」の 1 文）で、分けていない
- 順序の取りこぼしが実害（修正漏れ・誤った修正）に結びつくか。この 2 課題では、どの arm も最終的に直した
- M 対 H、M 対 M-skill の差の有無（各 20 回では、H が M より +0.35 悪い程度までしか区別できず、M-skill と M の差は ±0.2 の幅で分からない）
- 別のモデル・別の課題（長い課題、複数の引き継ぎ）・圧縮の後で同じことが言えるか。圧縮の条件（窓 10 万・50%）は F に強すぎて空回りを起こし、まだ読めない
- Haiku で構造の差が大きくなるか（H5）。手数の上限 12 が結果を縛っている
- S（自動発火）との比較

## 4. 言えること・言えないこと

- 言えること: 「同じ Dev 工程定義（設計書 11）を渡すとき、状態ファイルと入る / 出る条件で工程を決め、工程ごとにまとめた構造（M・Mall・M-skill）は、全工程を 1 列に並べた構造（F）より、変更計画を実装の前に書く順序が守られた（2 課題・Sonnet・2 回の実験で再現）。その差は、常時読む量をそろえても残った」「工程の中身を工程ごとのファイル・スキルにすると、取りこぼしを増やさずに（差は示せないが増えた兆しも無い）文脈の最大が約 4 割小さかった」
- 言えないこと: 「M 型の方が品質が高い」（最終状態に差は無い）、「量は関係ない」（b は差を示せないだけで、同等は示していない）、「M-skill と参照ファイルは同じ」「H は M より悪い」（いずれも事前の規則で差を示せていない）、「どの課題・モデルでも」（2 課題・主に Sonnet）
- 規定について: 状態ファイルを作業ツリーに置く案内は、git の操作と衝突しうる（観察 2/40）

## 5. 次の一手

1. **構造の要素を分ける**: F に要素を 1 つずつ足す（F + 「入る / 出る条件を先頭に」、F + 状態ファイルの案内、F の 1 文を外す）か、Mall から 1 つずつ外す。どれが順序を守らせているかが分かれば、SKILL.md に必要な最小の構造が決まる
2. **状態ファイルの置き場所**: 作業ツリーの外（例: `.git` の外の作業用ディレクトリ）か、`.gitignore` 前提の案内にして、副作用が消えるかを見る [推論: 副作用の原因が置き場所であるという見立て]
3. **実害のある課題**（評価計画 12 の段 3、事故の再現）: 順序の取りこぼしが修正漏れにつながる課題（計画を書かないと 3 か所目を見落とす等）で、構造の差が成果物の差になるかを見る
4. M 対 H を回数を増やして確かめる（各 40 回で +0.3 の差を検出できる見込み [推論: 二項の検出力の概算]）
5. Haiku は手数の上限を上げて（例: 24）M 対 M-skill をやり直す
6. 圧縮は、条件を弱めて（窓を大きく、または課題を長く）やり直す

## 6. 設計書 11 の渡し方（SKILL.md にするときの既定の構造）の推奨

**推奨: 混合型の核 + 工程ごとの中身を「核から名指しで呼ぶスキル」（M-skill）にする。参照ファイル（M）は、Claude Code 以外にも配るときの代替**

```
skills/dev/SKILL.md                 工程をまたぐ原則（§2b・§3）、工程の一覧、各工程の入る / 出る条件、
                                    「いまの工程は状態ファイルと成果物で決め、工程に入るときと圧縮の後に
                                     その工程のスキルを呼んで読み直す」案内
skills/dev-phase-0-intake/SKILL.md  … dev-phase-8-report   各工程の手順（user-invocable: false、
                                    説明文は「dev スキルの指示で呼ぶ」）
```

| 判断 | 根拠 | 確度 |
|---|---|---|
| 1 列のフラット（F）にしない | F 対 Mall・M・M-skill で取りこぼしの差が大きく、常時読む量をそろえても残った（EXP-20・21、2 課題、Sonnet、再現あり） | **中**（2 課題・1 モデル。差は順序で、実害は未確認） |
| 工程の判定はエージェント任せ（H）でなく、状態ファイルと成果物で決める | H は取りこぼし +0.35、途中から入ると前の工程の手順を読み直した（5/5）。ただし事前の規則では差を示せていない | **低〜中** |
| 工程の中身は核に全部入れず、工程ごとに分ける | 取りこぼしは Mall と差を示せない一方、文脈の最大が約 4 割小さい。EXP-20 副（圧縮）で M は F より圧縮が少なかった（2/5 対 5/5） | **中**（取りこぼしについては「差を示せない」まで） |
| 分けた中身を、参照ファイルでなく名指しで呼ぶスキルにする | ① 実験の向き: Sonnet で M-skill 0/20 対 M 3/20、Haiku で 0/10 対 2/10（測り方の検査後）、Haiku が手数の上限に当たった回数 4/10 対 8/10（いずれも差は示せない）② 公式資料: 圧縮の後に再添付されるのは「呼んだスキル」の先頭 5,000 トークン（合計 25,000、新しい順）（Claude Code docs "Skills" [一次]、`docs/research/research-process-structure-for-agents.md` §Q6）。Read で読んだ参照ファイルは再添付の対象として書かれていない（公式の明記なし [推論]）。したがって長い作業で工程の詳細が消えにくいと見込む [推論: 圧縮の後の実測はまだ無い]| **低**（実験では差を示せていない。圧縮の後の差（計画 13 の H3）は未検証） |
| 参照ファイル（M）を代替に残す | 1 つのスキルのディレクトリで配れ、スキルの一覧に工程ごとの説明文が並ばない（遮蔽のおそれが少ない。同 §Q8 [推論]）。Claude Code 以外のエージェントで「名指しで呼ぶ」が使えない場合に要る | **低** |
| 状態ファイルの置き場所 | 作業ツリーに置くと git と衝突した（2/40）。案内に「commit しない。外すなら .gitignore に書き、`.git/` の中には書かない」を足す案 | **低**（次の一手 2 で確かめるまで） |

この推奨を採るかは、オーナーにダイアログで確かめる。採らない場合は、§5 の 1・3 を先に行い、構造の要素と実害を確かめてから決める
