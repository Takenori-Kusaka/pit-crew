## 1. 原則

- **P1 測定の受け入れが先、数は後。** 採点器・述語・課題・代役は、実走の記録で受け入れ検査を通るまで「未検証の計器」。未検証の計器の数で arm の優劣を言わず、セルも選ばない
- **P2 計画は調査から作り、前の計画から写さない。**
- **P3 点検は書いた本人と別の役が行い、点検そのものの精度を測って報告する。**
- **P4 主張は台帳で管理し、訂正を消さない。**
- **P5 門は機械が強制する。** 申告と信用で済ませない。門の合否は設計者以外が書いたファイルで、実行の台本はそれが無ければ始まらない
- **P6 「測れない」は結果である。** 範囲をつけて報告し、止まる。測れるように見せるための実験を回さない

## 2. 門と順番

**順: G5 → G4 → G2 → 試走 → G4（再）→ G1 → G3 → 本実験 → G1 → G6**（査読の指摘 1。セル選び G3 は、G1 を通った計器の値だけで行う。EXP-44 は逆の順で床 4 → 1 と誤った）

| 門 | 誰が | 何を確かめるか | 止める条件 |
|---|---|---|---|
| **G5 計画の査読** | 査読役（設計者と別）→ オーナー | §3 の点検表。査読役には、既知の悪い計画を黙って混ぜて検出を確かめる | 空欄、落とす理由なし、前の計画の写し |
| **G4 代役と実行環境** | 機械（エージェントが走る image の中の test） | 代役（偽 gh など）が実物の記録済みの出力と同じ応答を返す。**記録に無い形には答えを作らず、明示の失敗を返して数える**。裏のファイルが作業木から見えない。**各 arm のスキルの指示が実行環境で通る（拒否 0 の煙試験）**。試走の後にも回し、試走で出た呼び出しの形を足す | 不一致、拒否、記録に無い形への応答 |

| **G3 識別力** | 機械（事前に書いた規則。G1 を通った計器の値だけを使う） | **主の量の項目ごと**に、実運用と同じ級のモデルで、ハーネスなしの率が天井でも床でもない「項目 × セル」だけを主の量に入れる。全 arm で常に真の項目と、スキルなしの arm で原理的に 0 になる項目（スキルの語彙）は arm の比較から外す。選んだ後に、ハーネスなしを別に回して確かめる | 入る「項目 × セル」が事前に決めた数に満たない → 本実験を回さず、課題の出どころを変える。作り直し 3 回で満たせなければ、**範囲つきの「測れない」として報告して止まる** |
| **G6 主張の登録** | 設計者 → 台帳（§4）。公開の文は台帳から機械で作る | 主張の文、範囲、根拠の水準、各門の合否ファイルへの参照、未監査の部分、同系統の但し書き（§7） | 門の合否ファイルが無い主張は「未監査」としてしか書けない |

**数字は先に、設計者以外が決める**（査読の指摘 3）: G1 の標本数・誤読率と判定不能率の上限・検出率と一致率の下限、G3 の「項目 × セル」の数と率の範囲、追う差の下限、誤差の単位（セル）。最初の適用の前に査読役が案を出し、オーナーが決め、commit する。

**独立を物で守る**（指摘 7）: 作成役・導き直し役・監査役は、読んではいけないファイルが**存在しない作業木**で走らせ、道具の呼び出しの記録を残す。申告で済ませない（今日、導き直し役が 3 分で終えて裏が取れなかった）。

弱いモデルの実行は G4・G2・G1 のための「環境の確認」に使う。arm の優劣の主張には使わない（先例なし。`research-practice-gap.md` §3.3）。

## 6. 進捗の数え方

「実験を回した」「門を通った」を進捗に数えない（門の数を数えると、空で通す誘因になる。査読の指摘）。報告するのは: いまどの門の前にいるか、**門が止めたもの**（見つけた誤り・測れないと分かった範囲）、台帳で状態が変わった主張。止まって報告することを、進んだことと同じに扱う。憲章の規律に「測れないと分かったら、範囲をつけて報告して止まる」を足す（オーナーの決定事項 §8）。

## 7. 同じ系統の問題（解けていない。オーナーの決定が要る）

監査役・査読役・導き直し役・設計者は、被験体と同じ系統のモデルで、同じ見落としを共有しうる。外部の先例（ABC・HCAST・SWE-bench Verified）は、採点と課題の点検に人を使っている。機械だけで同じ強さの保証を出した先例は、開いた範囲に無い [一次 + 推論: `research-practice-gap.md` §4.6]。門自身の検査（植え込みの検出率、2 人の一致率）は「読み落とし」は測れるが、「正解の登録が妥当か」「何を答えと数えるか」のような**物差しそのもの**は測れない。選択肢:

- **(A) 計器ごとに 1 回、オーナーが 20〜30 件を校正読みする。** 物差しを人が一度だけ確かめ、以後は機械で回す。評価の輪に人が常駐するのではない。先例と同じ意味で「検証済み」と言える最小
- **(B) 人を入れず、主張を終了状態の項目に限る。** 正しさが機械的に決まるもの（検査が通る、ファイルが変わっていない）だけを主張し、過程の準拠（理由・根拠・代替案）は「記述」に留める。憲章 1.1 の主な量を狭めることになる
- **(C) 人を入れず、全主張に固定の但し書きを付け、「評価済み」と書かない。**「同じ系統のモデルによる点検のみ。人による校正なし」を全主張に付ける

どれかを選ぶまで、この手順を「信用できる手順」として公開しない。

## 7b. オーナーの決定（2026-11-13）と、それによる変更

1. **同じ系統の問題 → 別系統のモデルを点検役に入れる**（§7 の (A)(B)(C) のどれでもない 4 つ目）。反映: G1 の監査役 2 人のうち 1 人を別系統にする（追加の支払いなしの範囲: 判断用モデル Jev に型付きの問い、またはローカルの別系統）。植え込んだ誤りの検出率と 2 者の一致率を**系統ごと**に出す。調査は「モデルの誤りは系統を越えて相関する」と書くので（`research-next-steps-small-n.md` 要点 5）、別系統の一致を真偽の確認とは呼ばず、機械的な検査（終了状態）を併せる。台帳の全主張に「人による校正なし。同系統 + 別系統のモデルと機械的な検査による点検」と書き、「評価済み」の語は、この点検を通った主張にだけ、その但し書きつきで使う
2. **1.1 は成否ではなく能力の評価。「どれくらいの品質で出力できたか」を段階で測る**。反映: 主の量を、合否の割合ではなく品質の段階（連続量）にする。G3 は「天井・床でない」ではなく「**実運用の級のモデルで、ハーネスなしの品質の値にセルの中・セルの間でばらつきがあり、上に余地がある**」ことを確かめる門に書き換える。**品質の軸は、スキルの文面に依らないものに限る**（`research-process-evidence-evaluation.md:15`。スキルが「書け」と指示した物の有無を品質に数えない。Dev の E share の比較が成り立たなかった形）。軸の候補と先例（METR の 5 軸: 中核機能・テスト・文書・書式・品質 / SlopCodeBench の構造の劣化と冗長化 / レビュアーがそのまま受け取れるか）は、次の計画で調査の行を引いて決め、G5 を通す
3. これにより §8 の 1・2 は決定済み。残りは門の数字（査読役の案が出てから）
