# 18 現状サマリー: 順序を守らせる構造は、別の事故の型で成果物の差を生むか（2026-11-02 の goal、その 5）

## 1. 何をしたか

- 事故の調査（`research-ganbari-incidents.md`）と評価計画 12 から、「調べてから動く」順序を飛ばすと最終状態に害が残ると見込める型を 2 つ選んだ: **I-12 古い base**（設計書 11 の入る条件 E2・「土台を確かめる」）、**I-21・I-28 実物と違う報告**（「報告は実物ではない」・H1）。I-13・I-23 は QM 寄りで外した。見込みの根拠と外れたときの読み方は、実行前にカードに書いた
- 課題を生成器で作った: t5（昨日切った作業ブランチで直して main に merge。今日の main に同じ不具合のファイルがあり、土台を確かめないと残る）、t6（前のセッションのメモが「invoice は直した」と誤って書き、確かめないと残る）。pit-wall の fixture に `checkout`（過去の commit から作業ブランチを切って始める）を足した
- 台本の対照の関門が、イメージの既定ブランチ名（main でない）による t5 の欠陥を、本実行の前に止めた。直して取り直した
- F・Fa・既定のスキルを各課題 10 回、途中から入る条件で Fa・Fa1・Fa2 を各 10 回走らせた（EXP-24）。集計の前の測り方の検査は全 run で通り、害の述語は最終状態のファイルと突き合わせて取り違えが無かった

## 2. 分かったこと

- **2 つの型とも害はほぼ 0 で、天井だった**（t5 1/30、t6 0/30）。構造による害の差は示せない
- **構造が無い F でも、10 回とも実装の前に main を見た（t5）／ invoice を実物で確かめた（t6）**。依頼文が「昨日、担当者が切ったもの」「前のセッションのメモ」と手がかりを与えていたため、と見る（カードで事前に書いた「外れたときの読み方」どおり）[推論]
- 取りこぼし（変更計画・テストを実装の後に書く）は、ここでも F に多かった（t5 7/10、t6 10/10）が、害にはつながらなかった
- 害が出た 1 回（既定のスキル、t5）は、`git diff main --stat`（two-dot）で main と比べ、rebase せずに進めて merge し、statement が残った。I-12・I-23 と同じ形で、設計書 11 の「three-dot で見る」が守られなかった（1 回）
- 途中から入る条件では、Fa・Fa1・Fa2 の差は見えなかった（3 arm とも書き直し 0・全部守った 10/10）
- **これまでの 6 つの課題（I-14 系 4 つ、I-12、I-21・I-28）を通して、構造は順序を守らせたが、最終的な成果物の差は一度も出なかった**。成果物の差（修正漏れ）が出たのは大きい課題 t4 だけで、それは調査の広さで分かれた（17）

## 3. 分かっていないこと

- 手がかりを弱めた課題（例: 「fix/PRC-501 で直して merge」だけ、メモの存在を依頼で言わない）で、構造が害を減らすか。今回は手がかりで天井になった
- two-dot で土台を読み違える型（今回 1 回）が、どれくらいの頻度で起きるか。三点比較の規定の守られ方は、構造ではなく中身の問い
- 別のモデル、長いセッション、圧縮の後、Haiku（手数の上限を上げて）

## 4. 言えること・言えないこと

- 言えること: 「Sonnet で、6 つの課題・3 つの事故の型を通して、状態ファイルの案内を含む構造（Fa・M-skill 型）は、変更計画やテストを実装の前に書く順序を一貫して守らせた（F に対し毎回大きな差）。しかし最終的な成果物（修正漏れ・古い土台の害・誤った報告の鵜呑み）に差が出たことは一度もなかった。成果物の差が出た唯一の課題では、調査の広さが成果物を分けた」
- 言えないこと: 「構造は成果物に効かない」（手がかりの強い課題で天井だった。1 モデル。設計者が作った課題）、「三点比較の規定は守られない」（1 回）、「途中から入るとき a1 は不要」（天井）

## 5. 次の一手（推奨を採る場合）

1. **規定の中身の実験に移る**: 成果物の差が実際に出たのは、調査の広さ（t4: 同じ型を広く探すか）だった。「1 つ見つけたら同じ型を探す」に具体の手順（同じ意味の計算を共通の関数・呼び出し元・履歴で探す。式の grep だけで終えない）を足した版と今の版を、t4 で比べる。主の量は修正漏れ
2. two-dot の読み違い（I-12・I-23）を、手がかりを弱めた t5 で起こしやすくし、規定（three-dot）の守られ方を測る（中身の実験の 2 本目）
3. 構造の結論（既定のスキル・状態ファイルの案内）は、14〜17 の決定のまま保つ

## 6. 推奨: 構造の研究をここで区切る

| 判断 | 根拠 | 確度 |
|---|---|---|
| 構造（状態ファイルの案内・M-skill 型）は順序を守らせる | EXP-20〜24 で毎回再現（6 課題） | **高**（Sonnet・設計者の課題という範囲で） |
| 構造は、試した型では成果物の差を生まなかった | 6 課題・3 つの型で成果物の差なし（t1/t2 は最終状態が同じ、t3・t5・t6 は天井、t4 は差なしで関係もなし） | **中**（天井が 3 つあり、手がかりの強さが残る。1 モデル） |
| 構造の研究を区切り、規定の中身（調査の広さ・土台の比べ方）の実験に移る | 成果物の差が実際に出たのは中身の側だった（t4: 広い grep 12/12 対 7/17、t5 の害は two-dot）。構造でさらに差を探すには、手がかりを弱めた課題を作る費用がかかり、これまでの 6 課題で一度も成果物の差が出ていない | **中**（区切っても、手がかりを弱めた t5・t6 は中身の実験の課題として作るので、構造の再確認に使える） |
| 既定のスキルは今のまま（M-skill 型・状態ファイルの案内） | 順序と途中から入る条件の工程の判定（EXP-21）に効く。成果物を悪くした証拠は無い（t4 の向きは差を示せない） | **中** |

この推奨を採るかは、オーナーにダイアログで確かめる。採らない場合は、手がかりを弱めた t5・t6 で構造の比較をもう一度行う。
