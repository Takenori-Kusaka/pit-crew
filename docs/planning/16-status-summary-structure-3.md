## 2. 分かったこと

- **順序の取りこぼしを減らしたのは、状態ファイルの案内（要素 a）だった**。全工程を 1 列に並べたフラット（F）のまま、「いまの工程は `.dev-state.md` と成果物で決め、工程に入るときと圧縮の後に手順を読み直し、状態ファイルに書く」の 1 段落を足すだけで、取りこぼしが 15/20 → 1/20（−0.70、Newcombe −0.84〜−0.41、Holm で有意）。常時読む量は F と同じ約 7 万トークンのまま
- 入る / 出る条件を先頭にまとめる（b）、工程ごとにまとめる（c）、「工程 1 から順に…」の 1 文を外す（d）は、単独では取りこぼしを減らすことを示せなかった（12/20・15/20・16/20）
- これで、EXP-20・21 で見えた「M・Mall・M-skill は F より順序を守る」の差の大半は、要素 a で説明できる（Fa 1/20 と Mall 0/20 はほぼ同じ）[推論: 組み合わせは比べていない]
- **オーナーの最初の見立て（フラットの方が AI に解釈しやすい）と矛盾しない**: フラットそのものは悪くなく、F に欠けていたのは「いまどの工程にいるかを記録する仕組み」だった
- 実害の課題では、F は 8/10 で計画を後回しにしたが、**修正漏れは F・既定のスキルとも 0/10**。F も最初の 1〜2 手でリポジトリ全体（`cat lib/*`・`git log -p`・README）を読んでおり、計画を書く順序は遅れても調査そのものは省いていなかった
- 既定のスキルの状態ファイルの一文のあと、`.git/` への書き込みの試み・権限の拒否・commit 無しは 0/20（EXP-21 の M・Mall は t2 で 2/20）
- 測り方の検査は、集計前に見落としを止める働きをした（今回の EXP-22 は全 run で通った）

## 3. 分かっていないこと

- 順序の取りこぼしが実害になるか。今回の課題は小さく、一度に全体を読めるので、天井だった。全体を一度に読めない大きさの課題、または調査を省く圧力のある課題が要る
- 要素 a の機序（状態ファイルに書く動作が区切りになるのか、「工程は推測で決めない」の文が効くのか）。a を 2 つに分ければ分かる
- a と他の要素の組み合わせが a 単独より良いか（差の余地はほとんど無い）
- 別のモデル・長い課題・圧縮の後でも a が効くか
- 状態ファイルの一文が副作用を減らしたか（向きは減ったが、2/20 対 0/10 で差は言えない）

## 4. 言えること・言えないこと

- 言えること: 「同じ Dev 工程定義を渡すとき、『いまの工程を状態ファイルと成果物で決め、工程に入るときに手順を読み直して状態ファイルに書く』という 1 段落の案内があれば、全工程を 1 ファイルに並べた形でも、変更計画を実装の前に書く順序が守られた（2 課題・Sonnet・各 20 回）。入る / 出る条件の置き場所、工程ごとのまとめ方、順に進めよという 1 文は、単独では効かなかった」
- 言えないこと: 「状態ファイルの案内で成果物の質が上がる」（最終状態は全 arm で同じ。実害の課題でも差が出なかった）、「順序の取りこぼしは無害」（天井で、差が出る余地が無かった）、「他のモデル・課題でも」、「b・c・d は不要」（単独で効かないことと、組み合わせで要らないことは別）

## 5. 次の一手

1. **実害の課題を大きくする**: ファイル数と履歴を増やし、一度に全体を読めない課題（例: 利用箇所が 20 ファイルに散り、README は一部しか書かない。4 か所目は呼び出し関係をたどらないと見つからない）で、F・Fa・既定のスキルの修正漏れを比べる。順序の差が成果物の差になるかは、ここで初めて答えられる
2. **要素 a を分ける**: 「工程は推測で決めない」の文だけ / 状態ファイルに書く動作だけ、を F に足す。SKILL.md の最小の書き方が決まる
3. 圧縮の後と長い課題（計画 13 の H3）: 圧縮の条件を弱めて（窓を大きく、課題を長く）、a の効果が残るかを見る
4. Haiku（手数の上限を 24 に上げて）で Fa・既定のスキルを走らせる
5. 評価計画 12 の段 3 の他のセル（報告と実物の食い違いなど）を、既定のスキルで再現する
