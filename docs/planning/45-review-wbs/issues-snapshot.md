# #1 pit-wall の較正の出力を、標準 3.12.13 の記録の作法(上乗せ分と無作為分の分離・腕ごとの一致)に揃えるか
labels: 

## 背景

process-compass の #427(ADR-0105)で、AI の採点者(LLM-as-a-judge)の較正を、標準の第3章 3.12.13 として定めました。pit-wall(`packages/pit-wall/`)の較正の実装と照らすと、次の 3 点が標準の記録の作法と食い違う、または確かめが要ります。使用可否の規則(TPR/TNR 0.8 以上)は、組織が定める値の一例として標準と矛盾しません。値を変える提案ではありません。

## 提起すること

1. **抜き取りの値の合算**: `calibrate` の抜き取りは、判定が割れた事例を優先して選びます。標準 3.12.13 の要求事項3 は、意図して上乗せした事例の一致を分けて記録し、無作為に選んだ事例の一致と合算しないことを求めます。上乗せ分と無作為分の κ(と分割表)を分けて出す変更を提案します。
2. **比べる双方に分けた一致**: 要求事項6 (f) は、比べる双方のモデル(現行と候補、または腕ごと)の出力ごとに分けた一致を求めます。腕ごとの分割表と κ を出力に含められるかを確かめたいです。
3. **系統の違いを根拠に書かない**: 陪審の 3 系統について、説明文や出力で、系統・提供者・版の違いを採点の正しさの根拠として書いていないかを確かめたいです(ADR-0075 決定12、ADR-0105 決定7)。

## 扱い

pit-crew は別のセッションで開発が続いているため、この Issue での提起にとどめます。変更する場合は PR で行い、process-compass の submodule の参照は PR が main へ入った後に進めます。

関連: process-compass #427、ADR-0105、標準 第3章 3.12.13

# #2 評価系における Harbor と Langfuse の併用・連携の検討（実行基盤と観測・評価管理の分離）
labels: on-hold

## 背景

pit-crew（および `packages/pit-wall`）では、コーディングエージェントのハーネス評価基盤として **Harbor**（Docker コンテナ実行器）を採用し、ATIF 形式での軌跡収集、決定論的グレーダー（git 差分、`/tmp/pitwall-gh-state.tsv` 等の副作用）、および独自の LLM-as-a-judge（陪審・Jev 測度・伏せ字マスク）による評価・較正を行っています。

現在、評価の運用と分析において以下の課題や発展の余地が認識されています：
1. **実行と観測・分析の結合**: Harbor はコンテナ実行器（Runner）として優れている一方、思考過程や tool_calls の詳細な可視化、実験間（runs/、腕/arms 間）のスコア・振る舞いの横断比較は、ローカルの JSON や Markdown レポート、集計スクリプトに依存している。
2. **実行コストと柔軟性**: 各試行でコンテナを起動・初期化する Harbor は重く（メモリ消費・並行制限・WSL2 側の page cache 圧迫）、役割の入口振り分けや短尺のプロンプト/スキル単体テスト、軽量な事前検証（preflight）などで手軽に回しにくい。
3. **データセットとプロンプト・較正データの管理**: LLM-as-a-judge の較正データ（人手アノテーション）やプロンプト/スキルの版管理、スイートのケース管理がローカルファイルに閉じており、再現性や分析結果の共有基盤が求められている。

LLM 観測・評価プラットフォームである **Langfuse**（OSS / セルフホスト可能）を組み合わせることで、「実行基盤（Harbor 等）」と「観測・評価・実験管理基盤（Langfuse）」の責務を分離し、よりスケーラブルかつ分析性の高い評価系を組めないかを検討したいです。

## 提起すること（検討項目）

1. **Harbor（Runner）と Langfuse（Observability / Eval）の役割分担と連携パイプライン**
   - Harbor がコンテナ内で実行したエージェントの生軌跡（ATIF）や副作用（`gh-state`、git 終了状態）を、pit-wall の adapter を通じて Langfuse の Trace / Span / Scores に事後インポートする仕組み。
   - または、コンテナ内から OTel (OpenTelemetry) GenAI semconv 等を経由して Langfuse へ送信する経路の実現性と、ネットワーク制限（network_mode / 外部通信遮断）との整合性。

2. **決定論的グレーダーおよび LLM-as-a-judge と Langfuse Scores / Datasets の統合**
   - pit-wall の決定論的判定結果（害の述語、タスク成否、手順適合 B-1〜B-17）および LLM 陪審・Jev 測度の判定結果を、Langfuse のカスタムスコア（Scores）として記録・ダッシュボード上で可視化できるか。
   - テストスイート（`suite.yaml` の各ケース）を Langfuse Datasets として管理し、実験ごとの回帰テストやアーム比較（with / without harness）を UI 上で横断分析できるようにするか。
   - 人手アノテーション（較正 calibrate）のワークフローとして Langfuse の Annotation / Review 機能を活用できるか。

3. **軽量評価（Non-Harbor / API 実行）の受け皿としての Langfuse**
   - リポジトリの完全な環境（Docker コンテナ）を必要としない評価ケース（役割の入口振り分け、チケット読解、純粋な LLM 判断など）において、Harbor を介さず直接 LLM / 軽量 runner を呼び出し、Langfuse で直接 Trace & Eval を管理する軽量パイプラインの有効性。

4. **技術的・運用の制約とトレードオフ**
   - **機密性とホスト資源（セルフホスト vs クラウド）**: 評価対象のコードやプロンプト、判断記録に機密情報・未公開情報が含まれるため、セルフホスト（Docker Compose / PostgreSQL / ClickHouse 等）が必要になるか。その際、WSL2 / Windows のメモリ資源競合（すでに Harbor や Ollama でメモリ逼迫が発生している）に耐えうるか。
   - **データモデルの対応度（ATIF / ACP ↔ OTel / Langfuse）**: 先行調査（`docs/research/research-runners.md` §3）で指摘された「OTel GenAI semconv の情報粒度の粗さ」に対し、ATIF の steps / tool_calls / observation や ACP のファイル I/O 差分情報を Langfuse の metadata や span にどこまで損失なくマッピングできるか。

## 扱い

現行の評価実験（Dev / QM / Fix 等の進行）を妨げないよう、本 Issue での技術的実現性の検討・要件整理にとどめます。
必要に応じて、小さなスイートで ATIF → Langfuse 変換または OTel 送信を試す検証用スパイクの実施要否や優先度を議論したいです。

関連:
- `docs/research/research-runners.md`（OSS ランナーと軌跡フォーマットの先行調査）
- `docs/planning/02-design.md`（pit-wall の設計方針）
- `packages/pit-wall/src/runners/harbor.mjs`
- `packages/pit-wall/src/normalize/atif.mjs`

# #3 失敗トレースからテスト・ハーネス修正を導く仕組みの検討（NVIDIA NeMo / NemoClaw アプローチの調査と適用可能性）
labels: on-hold

## 背景

NVIDIA の技術記事 [Use NVIDIA NeMo to Turn Agent Failures into Tests and Harness Fixes](https://developer.nvidia.com/blog/use-nvidia-nemo-to-turn-agent-failures-into-tests-and-harness-fixes/) では、本番・現場のエージェント実行トレースから不具合・逸脱を検出し、テストケース（Verifier 付き）を自動生成してエージェントハーネスを修正するフレームワーク（NemoClaw blueprint）が紹介されています。

NVIDIA 系ツールは高性能 GPU が前提と捉えられがちですが、本手法は **ローカル GPU を必要とせず、Docker が動作する標準的な環境（Ubuntu 等）とクラウド API（build.nvidia.com や Claude Code / Codex 等のモデル）** で動作します。
さらに重要な点として、本手法は **テストケースの定義・実行基盤として Harbor（0.22.0+）を中核に採用** しており、pit-crew / pit-wall の既存基盤および「実事故からセルを作成し、ハーネスを改善して Held-out で検証する」という設計思想と極めて高い親和性を持っています。

## 調査内容の要約

### 1. NemoClaw の構成要素と入出力
- **NeMo Compass（トレースアナライザー）**:
  - 大量のエージェント実行トレース（JSONL）と、期待行動指針（`ETHOS.md`）を突き合わせ、ポリシー逸脱（無断送信、不正引数、手順不適合など）を検出。裏付けとなる Trace ID とともに優先度付きの課題バックログを出力。
- **NeMo Eval Author（テスト自動生成スキル）**:
  - コーディングエージェント（Claude Code や Codex）に注入するスキル群。Compass の分析結果や生トレースから、**Harbor 形式の評価タスクと合否判定ロジック（Verifier）** を自動生成する。
- **NeMo Relay（トレーシング層）**:
  - エージェントの実行時挙動（ツール呼び出し、プロンプト、引数）をインターセプトし、構造化ログとして記録。

### 2. 「Failure → Test → Harness Fix」ループと pit-crew の比較

| 観点 | NVIDIA NeMo のアプローチ | pit-crew の設計思想 | 親和性・考察 |
| :--- | :--- | :--- | :--- |
| **改善の起点** | 現場の実行トレース（失敗ログ） | 実事故・現場インシデント（GQ 失敗事例等） | **完全一致**。汎用ベンチマークではなく実環境での失敗を起点にする。 |
| **失敗の資産化** | 失敗トレースから直ちに再現テスト＋判定器（Verifier）を作成 | 事故から「セル（ユニット）」を作成し、テストとして固定化 | **完全一致**。最小再現テストケース化してリグレッションを防ぐ。 |
| **最適化の対象** | モデルの再学習ではなく**エージェントハーネス**（プロンプト、ツールバリデーション、ミドルウェア） | プロンプト、ツール定義、工程スキル、状態ファイル等のハーネス | **完全一致**。モデル本体ではなく制御層（Harness）を改修。 |
| **過学習・デグレ防止** | 修正役に見せない **Held-out（ホールドアウト）タスク** による汎化検証 | 修正用セルと Heldout セルを分離し、汎化性と他ケースの破壊を防止 | **完全一致**。局所的なこじつけ修正による副作用を防ぐ。 |
| **実行基盤** | **Harbor**（0.22.0+） | **Harbor**（0.25.0）+ Docker Engine | **完全一致**。評価タスクと判定コードの互換性が高い。 |

## 提起すること（検討項目）

1. **テストセル作成の型化・自動化（NeMo Eval Author のエッセンスの取り込み）**
   - 現在手動で行っている「インシデントやトレースからのテストセル（`suite.yaml`、fixture、checks）作成」を、コーディングエージェント用のサブエージェント／スキルとして型化・自動化できないか。
   - 失敗した ATIF 軌跡と期待される振る舞い（規約・標準）を入力として、Harbor 評価タスクをスキャフォールドするスキルの構築。

2. **行動指針（規範）とトレースの突合による自動アノテーション・逸脱検知（NeMo Compass 的アプローチ）**
   - プロセスの規範（例: `ETHOS.md` 的な運用ポリシー、手順適合 B-1〜B-17）と実際の ATIF 軌跡 / `gh-state` を照合し、人間の見落としやすい「微妙な手順飛ばし」や「不要な外部操作」を機械的にスコアリング・トリアージする仕組みの検討。

3. **Langfuse（Issue #2）や既存の pit-wall との統合アーキテクチャ**
   - 実行時トレースの収集・管理に Langfuse を用い、低スコアまたは失敗したトレースを抽出。
   - 抽出された失敗から Harbor 形式のテストセルを生成（Eval Author スキル）。
   - ハーネス修正後に Harbor 上で開発セット＋Held-out セットを実行し、結果を再び Langfuse や pit-wall レポートで検証する「閉ループ改善パイプライン」の実現可能性。

4. **ライブラリ直接導入 vs 設計思想の自前実装（軽量化）**
   - NeMo の関連ライブラリ（Python 製）をそのまま組み込むか、あるいはそのアーキテクチャ・プロンプト設計（Skill）を参考にしつつ、現行の pit-wall（Node.js / シェル）に合わせた軽量なスキルとして実装するか。

## 扱い

現行の評価実験（Dev / QM / Fix 等）の進捗を優先し、本 Issue では技術的フィージビリティの確認とアーキテクチャ検討にとどめます。
将来的にセル作成コストの削減や、失敗事例の網羅的収集・テスト化を自動化するフェーズで具体的なプロトタイプ（スパイク）の検討を進めます。

# #4 「ハーネスはプロダクトである（Harness is a product）」原則および「Enterprise harness」の要点整理と ADR 化の検討
labels: on-hold

## 背景

Thoughtworks の技術記事 [The harness is a product](https://www.thoughtworks.com/insights/blog/generative-ai/harness-is-a-product)（Cecilia Geraldo 著）および [Technology Radar Vol. 35（2026年11月発行）](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/11/tr_technology_radar_vol_35_en.pdf) では、エージェント型エンジニアリング（Agentic Engineering）時代における最重要潮流として **「ハーネスのプロダクト化」** および **「エンタープライズハーネス（Enterprise harness / Harness engineering at scale）」** が提起されています。

> **「ハーネスとは、モデルと仕事の間に存在するすべて（everything between the model and the work）であり、エンジニアリングの判断が表現される場所である。ハーネスは単なる実装の詳細やスクリプトの寄せ集めではなく、独立したプロダクトとして定義・管理・保守・進化させなければならない。」**

pit-crew（および評価基盤 pit-wall）が取り組んでいる「コーディングエージェントのハーネス設計」「実事故に基づく評価セルの作成」「ハーネス改修と Held-out 検証」「ロールごとの境界定義」は、まさにこの「ハーネスをプロダクトとして成立・進化させるための基盤」そのものです。
これらの文献の考え方・原則・和訳要点を整理し、本プロジェクトの存在意義・アーキテクチャ方針・運用ポリシーの強力な準拠先となる **設計決定記録（ADR）として明文化・採択するための Issue** とします。

---

## 調査内容と要点整理

### 1. 「The harness is a product」ブログ記事の要点
- **定義**: モデルと仕事の間に介在し、両者の協調を決定づけるレイヤー。エージェント時代にエンジニアリング判断が具現化する中心アーティファクト。
- **8つの構成要素**:
  1. 指示・スキル（Instructions & Skills）
  2. ツール群（Tools）
  3. 権限・サンドボックス（Permissions & Sandboxes）
  4. コンテキスト方針（Context Policy）
  5. 状態管理（State）
  6. オーケストレーション（Orchestration）
  7. 評価系（Evaluation）
  8. テレメトリ・観測可能性（Telemetry）
- **アンチパターン**: プロンプト付き設定負債（Configuration debt with a system prompt）、属人化、責任者の不在。
- **原則**:
  - **「評価（Eval）なき変更は禁止」**: 測定できないハーネスを安全に改善することは不可能。
  - **活動量指標と品質指標の分離**: トークン数や提案受入率（Busy の証明）を本質的改善と混同しない。
  - **ゴールデンテストセット（実業務タスク）のバージョン管理**: 実務の失敗・課題から抽出したテストセットをハーネスと共に版管理する。
  - **自己改善のエントロピー防止**: 提案は自動化しても、測定可能な評価ハーネス、来歴追跡（Provenance）、迅速なロールバック経路を備え、承認は人間が握る。
  - **権限と影響範囲（Blast radius）の仕様化**: 「何に触れてよいか」はプロダクト定義の一部。
- **ハーネスをプロダクトとして捉える3つの問い**:
  1. 誰がそれを所有（Own）し、品質とロードマップに説明責任（Accountable）を持っているか？
  2. 直前の変更で「良くなった」とどうやって確認したか（客観的エビデンス）？
  3. それ（エージェント）は何に触れることが許されているか（権限と影響範囲）？

---

### 2. Technology Radar Vol. 35「Enterprise harness」の核心と和訳要約

Technology Radar Vol. 35 では、ハーネスエンジニアリングが単一の Blip を超えた**マクロテーマ「Harness engineering at scale（大規模なハーネスエンジニアリング）」**として特集され、複数の関連 Blip が掲載されています。

#### (1) マクロテーマ：Harness engineering at scale（p. 8）
> **【和訳要約】**  
> ハーネスエンジニアリング（AIエージェントを取り巻く環境を構築するために行うすべて：メモリやコンテキストからフィードバックループ、ガードレールまで）は、より体系的で結束力のある専門規律（discipline）へと成熟しつつある。  
> **ハーネスは継続的なオーナーシップと保守を必要とする「生きた資産（living asset）」である**。  
> より大きな課題は、エンタープライズの要件を満たすようハーネスをスケールさせることにある。数年前にプラットフォームやプラットフォームエンジニアリング（IDP）に起きたことと同様に、**今後「エンタープライズハーネス（enterprise harness）」が1つのプロダクトとして登場してくる**。

#### (2) 関連 Blip の洞察
- **#7 Agent plugin marketplace（Trial, p. 16）**:
  - ハーネス資産（スキル、指示書、MCPサーバー、サブエージェント定義）をリポジトリ間でコピペするのではなく、依存関係（Agent Package Manager 等）として管理し、組織全体に流通・配布する仕組み。**エンタープライズハーネスを全社展開するための極めて実践的な方法**。
- **#10 Coding harness for general-purpose agents（Trial, p. 17–18）**:
  - ドキュメント処理や運用サポート等の非コーディング業務も含め、成熟したコーディングエージェントのランタイム（コンテキスト圧縮、セッション永続化、ヘッドレス実行）を汎用基盤として再利用するアプローチ。
- **#18 Self-improving harness（Trial, p. 20） & #11 Feedback flywheel（Trial, p. 18）**:
  - 実行トレースと評価フィードバックから、プロンプト、コンテキスト戦略、スキル、ツール等のハーネス環境をエージェントに自律改善させる。
  - **原則**: オブザーバビリティ（トレースから失敗を特定）とプログラマビリティ（検査・改変可能な設計）が前提。人間が目的と変更境界を定め、**リグレッションテストによる検証（Held-out 検証）** を行う。提案はエージェントが自動化し、承認は人間が握る。

---

## ADR 化に向けた検討項目（骨子案）

本プロジェクトの設計決定記録（ADR）として、以下の骨子を策定・採択することを提案します：

1. **基本方針: ハーネスのプロダクト化とオーナーシップ**
   - ハーネス（役割スキル、ツール定義、状態ファイル、実行環境）を第一級のソフトウェアプロダクトとして位置づけ、バージョン・来歴・オーナーシップを明確にする。
   - プロンプトの継ぎ足し（設定負債）を拒否し、リファクタリングと削除主義を徹底する。

2. **品質保証原則: 評価駆動型ハーネス改修（Eval-Driven Modification）**
   - 「客観的評価のないハーネス変更はマージしない」規律の確立。
   - 変更の妥当性は、実インシデントに基づく評価セル（pit-wall / Harbor / 決定論的グレーダー）および Held-out セットでの検証を根拠とする。
   - 活動量指標（ステップ数・受入率）と本質的品質指標（害の述語、手順適合 B-1〜B-17）を厳格に分離する。

3. **境界と権限の設計: サンドボックスと影響範囲（Blast Radius）**
   - ツール権限（ファイル書き込み範囲、Git サブコマンド制限、外部通信制限など）を実装詳細ではなく、ハーネスの仕様（Contract）として固定・検証する。

4. **改善ループのガバナンス: 自動提案と人間承認の分離**
   - 失敗トレースからのテスト生成やハーネス改修提案（NeMo 手法等）の自動化を取り入れる場合でも、適用判定は人間および決定論的グレーダー・陪審の承認を必須とする（Automate the proposal, keep the approval）。

5. **全社展開を見据えたモジュール設計（Enterprise Harness への接続）**
   - 汎用の核（Core）と案件アダプタの分離。
   - Agent Plugins や SKILL.md 等の標準形式に準拠し、将来的な全社配布・依存関係管理に耐えうるモジュール構造を保つ。

# #6 スキルの Shift-Left 静的リントと多層評価手法の検討（wshobson/agents の plugin-eval に学ぶ事前検証とハーネス移植性チェック）
labels: 

## 背景

[wshobson/agents の docs/plugin-eval.md](https://github.com/wshobson/agents/blob/main/docs/plugin-eval.md) では、Claude Code 形式（`SKILL.md`, `agents/*.md`, `plugin.json`）で書かれたエージェント用プラグイン・スキルの品質と適合性をスコアリング・認証する多層評価フレームワーク（`plugin-eval`）が提示されています。

現在、pit-crew / pit-wall では、Harbor コンテナ環境内でエージェントを実際に動かし、ATIF 軌跡や副作用（`gh-state` 等）を判定する **「動的実行評価（Dynamic Evaluation）」** が中心となっています。
動的評価は行動の事実を検証する上で不可欠である一方、コンテナ起動コストやメモリ消費、実行時間が重いという課題があります。
`plugin-eval` のアプローチ（モデル呼び出しゼロの静的リント、発火予測、ハーネス移植性チェック、アンチパターン検出）を取り入れることで、**「動的テストの前に低コストで品質を担保する Shift-Left 評価パイプライン」** を構築できないかを検討したいです。

---

## wshobson/agents「plugin-eval」の主な特徴と仕組み

### 1. 3層の評価アーキテクチャ
- **Layer 1: 決定論的静的解析（Deterministic Static Lint）** [モデル呼出: 0回, 所要時間: <2秒]
  - 前処理・構文チェック（フロントマター、説明文長、トリガー句 `Use when...`）
  - 行数・段階的開示（適正行数 200〜600行、`references/` への詳細分離）
  - 指示密度（過度な `MUST/ALWAYS/NEVER` の検知）
  - アンチパターン検知（リンク切れ、肥大化、孤立参照など）
  - **ハーネス移植性（Portability）**: 特定ツール名（\`Read\`, \`Bash\`）の直書きやサイズ制限（Codex 8KB cap）の検査
- **Layer 2: LLM-as-a-judge（意味論的評価）** [モデル呼出: 4回]
  - 発火精度（説明文からテストプロンプトを自己生成し F1 予測）
  - オーケストレーション適合性、出力品質、スコープ適切性のルーブリック評価
- **Layer 3: モンテカルロシミュレーション（統計的頑健性）** [50〜100 runs]
  - 応答率（Wilson score）、出力文字数変動（Bootstrap CI）、APIエラー率、トークン消費効率

### 2. 複合スコアリングとバッジ化
- 10 の品質次元（発火精度 25%, 適合性 20%, 品質 15%, 段階的開示 10% 等）のブレンド
- アンチパターン減点: `max(0.5, 1.0 - 0.05 * count)`
- 認証バッジ: Platinum (≥90), Gold (≥80), Silver (≥70), Bronze (≥60)

---

## 提起すること（pit-crew / pit-wall への導入検討項目）

1. **スキルの「Shift-Left（事前静的リント）」ゲートの導入**
   - Harbor の重いコンテナ実行を回す前に、`pit-wall lint` を拡張（または独立した `skill-lint` を構築）し、`SKILL.md` の静的チェックを CI やコミット前フックで即時実行する仕組み。
   - 対象: 行数制限、段階的開示（`references/` の有無）、トリガー句の明瞭さ、`MUST/NEVER` の過密、デッドリンク。

2. **ベンダー中立・ハーネス移植性チェック（Harness Portability）のルール化**
   - pit-crew は Claude Code だけでなく、Codex、Gemini CLI、Copilot CLI 等の異種エージェントへのハーネス提供を視野に入れている。
   - 特定の Claude 専用ツール構文（\`Read\` や \`Bash\` 等）のハードコードや、Codex のサイズ制限超過などを静的に弾く移植性ルールの策定。

3. **2段階評価モデル（2-Stage Eval Model）の確立**
   - **Stage 1 (Shift-Left / 静的・プロンプト評価)**:
     - PR 時に GitHub Actions 上で瞬時に実行。静的リント、アンチパターン検出、軽量な発火性テストを行い、品質バッジや警告を PR コメントに通知。
   - **Stage 2 (Deep Eval / Harbor 動的評価)**:
     - Stage 1 を通過したハーネスのみを Harbor コンテナに配備し、実事故セル（`suites/`）を用いた副作用判定・決定論的グレーダー・LLM 陪審を実行。
   - これにより、無駄なコンテナ起動や API トークン消費を大幅に削減し、評価サイクルを高速化できる。

4. **比較・回帰分析ツール（`compare` コマンド）の活用**
   - ハーネス改修時における旧版と新版（Baseline vs Candidate）の品質次元ごとの差分（Diff）や、スコア変化の可視化。

---
