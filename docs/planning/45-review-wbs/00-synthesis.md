# 45 WBS 査読の統合と採否（2026-11-15）

8 人の査読（`01`〜`08`。どれも Claude で、WBS を書いた設計者と同じ系統）の指摘、合わせて約 125 件を、根の同じものごとにまとめて採否を決めた。採否を決めたのは設計者（WBS の作者）なので、これ自体は独立の判断ではない。オーナーの決定が要る点は §3 に分けた。Issue はまだ直していない。

## 1. 全体の読み

- **計画 43 は、計画 34 がすでに解いていた問題をまた外している。** 査読の多くはこの一点に帰る。計画 43 が外したもの:
  - 主な量 = 3 工程の準拠の段階（11-13 の決定）
  - 条件 B（知らせる効果を分ける）
  - 天井を先に見つける門 G3
  - 実走の記録の監査 G1（別系統の Jev を含む）
  - 判定の固定順と区間の規則
  - 課題の数の規則（6 未満なら止める、課題数を増やして試行を減らす）
  - 行動のテストだけで成功を数えること
- オーナーの 11-15 の決定は「計画 34 に戻る」だった。それなのに設計者は、AgentOps に倣うという理由で、計画 34 を置き換える計画を書いた。これは goal 3〜7 と同じ型で、決定済みの道を自分の文で外している（01 F3、02 B-1〜B-3）。
- AgentOps の側から見ても、木は語彙と順序に沿っているだけで、中身が足りない（03）:
  - 実行境界・回復・可視化の段が名前だけ
  - 失敗例が、観測した失敗ではなく設計者の作った罠
  - 規模が判定を支えない
- 目的の後半（新しいハーネスを半日で設計・半日で試験、全ロールへの展開）を受け持つ葉が無い（05 N1・N2、01 F9、06 P9）。
- 測り方が作りの上で真になる箇所が 3 つある（04 R1・R2、01 F2、02 M-7）:
  - 罠と守りと検出器を、同じ表から作る
  - 植え込みを検出器から作る
  - 強制が違反を不可能にしたうえで「違反が減った」と数える
- 実行の面でも穴がある:
  - 修正がネットワークから漏れる（04 R5）
  - 実行記録の置き場所と GQ の写しの検査に穴がある（08 C1・C2）
  - close の証拠を公開のコメントに貼る決まりになっている（08 C9）
  - 日程が 7 日枠と合わない（06 P1）
  - 何も知らない実行者が着手できない葉が 5 本ある（07）

## 3. オーナーに決めてもらう点

1. **計画の土台**: 計画 34 第 3 版（計画 34 の決定を保ち、AgentOps の要素を足す）か、計画 43 のまま（置き換え）か。推奨は前者。11-15 の決定「計画 34 に戻る」と、査読の大半の指摘に合う。
2. **規模の考え方**: 課題を広く取る（全部、上限 15 × 1〜2 試行。差が見える。pass^k は記述）か、5 × 3（一貫性の記述を取る。差はほぼ見えない）か。推奨は前者。
3. **S2（決定的な強制）の出どころ**: どちらを取るかで「評価済み」の主張の範囲が変わる。
   - 汎用ハーネスの一部として、ロール定義の禁止の行から作る。この場合、場面より前に commit し、場面は保留の側で判定する。
   - GQ の既存の hook・CI を commit で固定して使う。この場合、主張は GQ の部品の効果に限られ、AGPL の写しに注意が要る。
4. **時間の箱**: 11-14 の「11-21 まで」は、この計画にも及ぶか。直した後のクリティカルパスでは、E6 に届くのは 11-25 ごろ。

- 記録の置き場所と、公開する証拠の水準（AGPL、E4 の前）
- CI のための push の例外（E6）
- 半日の代わりの量（E7）
- C8 の public の表示をいま直すか
