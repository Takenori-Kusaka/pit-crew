# 査読 07: 何も知らない実行者の視点

読んだもの: `issues-snapshot.md` と `tree.txt` の 2 つだけ。ほかのファイルは開いていない。下の指摘はすべて「Issue の本文だけでは分からないこと」として書く。

## 1. 判定（3 行）

- 本文だけで着手できない葉が 5 本（#19 #23 #27 #30 #31）ある。完了を自分で証明できる葉は、オーナーの決定を記録するだけの #29 #38 と、組み立てるだけの #22 #34 にほぼ限られる。
- 原因の大半は**入力の置き場所が書かれていない**こと（GQ の ADR、EXP-48 の課題、Dev の役割の手順、実行の命令、弱いモデルの名前）と、**内部の呼び名が説明なしで使われている**こと（GQ・EXP-48・G4・S0/S1/S2・pass^3・上げすぎ・計画 34 の A/B/C/D・goal 3〜7・e3-scale）。
- EPIC #7 は目的（評価済みの汎用ハーネスを public で出す、ハーネスに依存しない採点器）を一文で示しているので、方向は分かる。ただし予定外の事態で正しく判断するのに要る 3 点が無い。期限の具体値、目的と期限がぶつかったときにどちらを優先するか、オーナーへの聞き方（コメントか、ラベルか、待つのか）である。

## 4. 矛盾・食い違い

1. **段の順序と依存が合わない**: #10（E2）は「#9 の後」だが、その子の #26 の依存は #16 だけなので、E1 の途中で着手できる。どちらが正しいのか分からない。
2. **GQ の中身は `local/` にあり、CI は植え込み検査を回す**: #23 は GQ の中身を git が無視する `local/` に置けと言う。#25 は重要失敗例の行ごとに植え込み検査を CI で回せと言う。CI からは `local/` を読めないので、両方を同時には満たせない。
3. **#21 の受け入れ条件 3 は close の時点で証明できない**: 「commit が E4 の最初の試行より前」は、E4 が起きる前の close では確かめようがない。確かめられるのは #34 の時点。
4. **ゲートの数字（#21）が規模の決定（#29）より前に来る**: 試行数が決まらないうちに閾値を固定することになる。規模に依存しない書き方を指定しないかぎり、#34 で「E1 の数字を変えない」と衝突する可能性が高い。
5. **#1 の位置**: 本文は「提起にとどめる、変更は別のセッションの PR」と言う。木では E5 の子で、#33 の受け入れ条件がその「検討結果」に従えと言う。誰がいつ検討するのかが無い。さらに、κ を使う LLM 採点の作法を、決定的な採点器（#24）にどう当てはめるのかも不明。
6. **#6 の位置**: E1 の子なのに受け入れ条件が無く、#22（E1 のまとめ）の依存にも入っていない。#9 を閉じるのに #6 の close が要るのか分からない。
7. **#17 と #7・#8**: #8 はすでに「進捗の確かめは Issue の状態で行う」と書いている。#7 にもすでに LATE の規則がある。#17 の受け入れ条件 2 は着手前から満たされているように見える。また #17 は計画 43 を書き換えるのに、計画 43 を採るかどうかを決める #16 に依存していない。
8. **pass^3 の定義の重複**: #33 は定義を前提にしている（「3 回とも成功」）。#21 はこれから定義を書くことを求めている。正本がどちらか分からない。
9. **「秘密の検査 0 件」（#27 #30）と「隠した検査」（#24）**: 似た言葉が別の意味（秘密の漏れの検出か、課題の hidden test か）で使われているように読める。
10. **#32 の依存**: S2 の中身は #20 で決まるのに、#32 の依存には #31 しか無い（#20 が E1 で閉じている前提が暗黙）。
11. **#35 の「限界（確かめ役が同じ系統のモデル）」と #1 の 3 点目「系統の違いを根拠に書かない」**: 矛盾ではないが、台帳に系統をどう書くか（限界としてのみ書く、正しさの根拠としては書かない）を明記しないと、書き手が迷う。

## 5. EPIC #7 は予定外の事態に耐えるか

- 足りている点: 目的が一文で書かれている。止まる条件（LATE、needs-owner、範囲を狭めるならコメント）も明示されている。
- 足りない点:
  - (a) 期限の具体値が #7 に無い（計画 43 §5 を読まないと LATE を適用できない）。
  - (b) 「評価済み」の最小の意味（台帳の 1 行、Dev だけ、範囲の文つき）が #13 #35 に分散していて、#7 には無い。
  - (c) 目的と期限、目的と公開の安全がぶつかったときの優先順位が無い。
  - (d) オーナーに聞く手段（Issue にコメントして needs-owner を付け、待つのか）が無い。
  - (e) GQ と Dev が何かが無い。何も知らない実行者には、「GQ の実際の失敗を課題に通す」が何の作業なのか分からない。
