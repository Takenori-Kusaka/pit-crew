## 1. 判定（3 行）

- 木の骨格（失敗例 → 契約 → 版固定 Dataset → 決定的採点器 → 層を足す → 事前に固定したゲート）は AgentOps の流れの**語彙と順序**には沿っているが、ロードマップの段を「評価の手順」に読み替えており、「実行境界」「回復・一貫性」「可視化」の段は**名前だけ**で中身（強制が誤提案を止めることの決定的な確認・回復・トレースの記録）が無い。
- 最も重いのは規模: 5 課題 × 3 試行 × 3 層で出る pass^3 と違反 0 件では、リリースゲートの判定も「評価済み」の主張も統計的に支えられない（blocker）。失敗例も観測した失敗の軌跡ではなく ADR の経緯からの再構成で、S1 のスキル自体がその ADR を出典にしているため、保留のない開発セットで判定する形になっている。
- 「Dev だけ・GQ だけ・主張 1 本」という最初の切り方は AgentOps として正しい形（1 業務の縦切り、実際の失敗から少数で始める）だが、最初の成果物は「1 本の判定」ではなく「次のハーネス変更にそのまま再実行できる回帰ゲート（Dataset + 採点器 + 台本の対照）」とし、モデルを回した結果は範囲を限った記述にとどめるべき。

## 4. 木がよくやっていること（3 つ）

1. 指示（S1）と、モデルの外で動く強制（S2）を別の層にし、強制に「どの重要失敗例に効くか・どこで動くか」を書かせている（#20）。資料の中心の主張に沿う（R:13）。
2. ゲートの数字を最初の試行より前に commit させ、判定は試行を回していない役が集計ファイルだけで行う（#21・#34）。結果に合わせて基準が動くことを構造で防いでいる。
3. 上げすぎ（実行できたのに断った）を定義させ（#18）、採点器を植え込みで両方向に確かめ CI で走らせる（#25）。弱いモデルの煙試験を優劣の主張に使わないと明記している（#27、OS:219-221 と一致）。

## 5. オーナーへの問い（資料では決められないもの）

1. このゲートで「リリース」するのは何か — 既定の Dev スキル（S1）を「評価済み」として公開することか、強制の一式（S2）を公開することか、その両方か。候補が決まらないと、比較ごとの期待の向き（A6）と主張の文が決まらない。
2. 消費の測定（#28）の結果、ゲートを判定に使える規模（A1 の検出力の計算）が 7 日枠に収まらない場合、1.1 の主張を「記述（判定なし）」に下げて第 1 弾を締めてよいか、それとも規模が取れるまで判定を待つか。
