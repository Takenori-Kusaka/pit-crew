# pit-crew 企画書（ドラフト v0.1）

- 作成日: 2026-10-31
- ステータス: 承認済み（2026-10-31、D0）
- 根拠資料: 本書末尾の「根拠資料」を参照

## 1. 一言で

**役割分担した AI 開発チーム（PO / Dev / QM / Review / Platform）のハーネスを配布し、そのハーネスが本当に効いているかを数値で測り、改善の PDCA を回せるようにする repo。**

ハーネスは銀の弾丸ではない。それでも多くの人がハーネスに期待している。だから pit-crew では、配布物と評価系を同じ repo に置き、「効く・効かない・判定できない」を正直に出す。

## 2. 解く問題

### 2.1 オーナー自身の問題（一次の動機）

がんばりクエストでは、役割ごとにセッションを分けた運用が回っていた。ところが同じ型を会社に持ち込もうとしたとき、ノウハウが汎用化されておらず、ゼロから作り直すことになった。中でも時間を食ったのは次の 3 点である。

| # | 起きた失敗 | 本質 |
|---|---|---|
| F1 | Dev に「十分に調べてから、規模を小さく、独自実装を減らし、テストを単体・結合・API まで広げる（TDD と DDD）」という流れを教え込むのに時間がかかった | 工程の順序と、各工程の完了条件が型になっていない |
| F2 | QM が設計書や指針書を読まないままレビューした。外部委託先の質問に誤って答え、現場を混乱させた | レビュー前に何を読むかの義務がなく、ロールの権限の境界もない |
| F3 | 設計書の誤りや文書間の矛盾があり、Dev と QM のどちらが正しいか決まらないまま、やり取りが無限ループした | 文書の優先順位と、誰が裁定するかの経路がない |

がんばりクエストにも F1〜F3 は完全な解決策がない（research-inventory.md §会社で詰まった 3 点）。具体的には次のとおり。

- 新機能ではテストファーストを強制していない
- レビュー前に文書を読むことは強制していない
- 技術的な裁定をする人（`needs-tech`）がいない
- 文書どうしが実際に矛盾している（pr-review の Step 0 と憲章 §0 ルール 3 など）

### 2.2 世の中の問題

- 公開されているハーネス（Superpowers、BMAD、gstack など）は多いが、効果を素の Claude Code と比べて公表した例はほとんどない
- 小さく明確なタスクでは、既存のスキルはどれも差が出ない（+0pt）。それでいてコストは最大 +186% かかる（skillarena）
- ロールをセッションごとに分ける構成、作る人と承認する人の分離、label による受け渡し。この 3 つの効果を測った公開例は、調査した範囲では見つからなかった

## 3. 誰のためか

| 優先 | 対象 | 欲しいもの |
|---|---|---|
| 1 | オーナー自身（次の個人開発、会社） | ゼロから作り直さずに、3 つの現場へ持ち込めるハーネス |
| 2 | Claude Code で複数ロールを回している個人やチーム | 自分の現場向けに調整した fork が改善か改悪かを、同じスイートで確かめる手段 |
| 3 | ハーネスやスキルの作者 | SDLC の規律（越権、推測での実装、読まずにレビュー）を測るシナリオ集 |

## 4. 何を作るか

1. **ハーネスのコア（英語）**: 次のものを Claude Code plugin として配布する。人とのやり取りは利用者の言語（`language` 設定）で行う。
   - ロール定義の骨格
   - label mailbox
   - 作る人と承認する人の分離
   - SSOT の優先順位と裁定の経路
   - レビュー前に文書を読む工程
   - 汎用スキル
2. **評価スイート**: SDLC の規律を測る行動シナリオと、版どうしの回帰を判定する仕組み。利用者が自分の fork にも使える。
3. **adapter の仕組み**: `pit-crew.config.json` で、プロジェクト固有のもの（アカウント、ラベル、ブランチ、SSOT 一覧、cron）を差し替える。pit-in-template（process-compass）はこの repo を依存として読み込む。

## 5. 成功の定義

| 時期 | 成功 | 測り方 |
|---|---|---|
| M1（最初の 1 本） | F3 対策（裁定の経路）と F2 対策（レビュー前の読み込み）を測り、vanilla より違反率が下がったかを「改善・改悪・判定不能」のいずれかで言える。**判定不能でも、それを正直に出せれば成功とする** | 事前に commit した基準で判定する |
| M2 | 次の個人開発に pit-crew を導入し、ゼロから作り直さずに立ち上がる | 立ち上げにかかった時間と、手で直した箇所の数 |
| M3 | ハーネスを 1 回改訂し、評価で改善か改悪かを判定して、採用または却下を決める（PDCA が 1 周する） | 改訂前後の比較レポート |
| M4 | 会社の運用に抽象パターンとして持ち帰る（会社の固有情報は repo に入れない） | オーナーの判断 |

## 6. やらないこと

- 有料販売（エージェントのスキルのマーケットプレイスなど）。理由: 配布の方式が repo に置く一式と合わない。また競合はすべて無料
- 追加の費用がかかる評価（API の従量課金、有料の SaaS、有料のランナー）。使う計算資源は、ホストマシン、GitHub Actions の runner（公開 repo の無料枠）、既存のサブスクの枠だけ
- 「効く」と言うための評価。結果が null でも出す
- がんばりクエスト固有のスキル（年齢モード、ブランド、Stripe など）の移植
- 会社の固有情報を含めること

## 7. リスク

| リスク | 対策 |
|---|---|
| 評価がサブスクの枠を食い、開発作業を圧迫する | 評価の大半を機械判定にする。最初の試行で 1 ケースあたりの消費を実測し、その結果から上限を決める（設計書 §7） |
| 天井効果で差が出ない | 合格率ではなく、行動指標の違反率で測る。vanilla でも常に正解するケースは除外する（calibration） |
| 件数が足りず、何も言えない | MDE（検出できる最小の差）を事前に計算して開示する。ベースラインの違反率が高い規律から測る |
| 自分で作り、自分で採点する偏り | 事前に commit した基準を使う。審判には別のモデルを使い、人の採点で較正する。目隠しで欠陥を注入する |
| ハーネスを過剰に作り込む | ルールを 1 条ずつ外して測り（ablation）、効いていない条項を削る |
