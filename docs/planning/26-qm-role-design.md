## 0. この文書の位置づけと品質基準

- QM ロールは **2 つの仕事**を持つ: **(a) 1 つの変更の独立レビュー**（process-compass G-6。スキル `qm-review`）と **(b) 出荷の範囲の判定**（G-7。スキル `qm-ship`）。入力の単位・止める理由の範囲・独立の要件が違うので工程表は 2 つ（§1）、原則は 1 つ（§3）〔オーナー〕2026-11-04 Q1「2 つのスキル + 共通の原則」〔作法〕compass `gate-criteria.md` G-6 L876-885・G-7 L1032-1046、`human-ai-boundary.md` L508-509
- **QM は修正を書かない**（Y15、B-17 で測る）。修正は作成者（Dev）か、修正役 **fix**（QM の差し戻し・バグ報告・軽微な修正を低コストのモデルで高い回転率でこなすロール。会社の rereview に当たる）へ渡す〔オーナー〕2026-11-04 Q4。GQ の「QM が小さい修正は自分で直して merge する」（ADR-0022 Amendment 6、憲章 §0 ルール 2）は一人体制のアダプタの逸脱として記録する（§6）。fix ロールは本書の範囲外
- **AI の判定を「判定」に数えるか「検出の層」に数えるかは核で決めない**。案件アダプタの値 `verdict`（§6）で選ぶ〔オーナー〕2026-11-04 Q3「事業フェーズに合わせて選べるようにする。最初の MVP / PoC のフェーズで一個一個の approve を人がやる価値は小さい」。**既定の境目は設計者の案〔推論〕**: PoC / MVP = `final`（AI の判定が最終）、顧客のデータ・金・法務に触れる段階 = `detection`（判定の案 + 人の席の記名）。どちらでも**判定記録の欄（§3 Y13）は同じ**で、核が要求するのはその欄だけ（調査 結論 4・8）。`final` のとき核が保証する独立は「作成の文脈と編集権限からの分離」までで、人の記名は無い。判定記録に `verdict: final` と書き、出荷判定の保証の開示（S3）の「独立性の成立状況」に載せる〔作法〕compass 保証の開示 項目 1〔推論〕当て方。process-compass 自身は AI を判定者の席に置かない（HAB L508）ので、`final` は compass からの**逸脱**である
- 品質基準: QM の定義は、**その職種のプロが当たり前に行う標準動作を工程ごとに細かく規定したもの**（設計書 11 §0 と同じ水準、オーナー 2026-11-02）。出典の種類は設計書 11 §0 と同じ 7 種（〔作法〕〔GQ〕〔事故〕〔実証〕〔実測〕〔オーナー〕〔推論〕）。確度は角括弧（[一次] [二次] [未確認]）。〔両氏〕は本書では直接引かない。〔実証〕の数値と確度は調査 付録 A にだけ置く。**pit-crew の文書（設計書 11・23）は〔GQ〕でなく出典名で引く**
- 会社で詰まった 2 点（設計書を読まずにレビューした / 権限外の問いに答えた）は GQ の規定にも穴として残っていた [一次: `research-inventory.md` §(2)]。オーナーはのちに「3 つの例は題材としては良いが拘るものではない」と訂正している（`00-owner-statements.md` 11-01 14:25）。本書はこの 2 点を**題材**として使い、V2（文脈を読む）と Y3（宛先の表）を核に置く。測り方: V2 は決定的（B-2）、Y3 は label の付与まで決定的（B-9a）で「答えたか」は文の照合と judge の併用（B-9b）

## 1. 工程の一覧

### 1.1 `qm-review`（1 つの変更）

| # | 工程 | ひとことで |
|---|---|---|
| V0 | 受け付け | 受信箱から拾い、レーンと深さ（R1〜R4）を決め、自分の決定権の中か（付表 3a）を判定する。PR を伴わない問い合わせは VQ へ |
| V1 | 土台を固定する | 読む HEAD と base を固定し、three-dot の差分と Draft / 未起動を確かめる |
| V2 | 文脈を読む | チケット・受入基準・変更パスから引いた設計書・決定記録・入口の文書を**開いて**読み、開いた一覧を残す |
| V3 | 差分を読む | 変更した全ファイルを開き、R3 以上で差分の外へ広げる。作者の主張を 1 つずつ実物で照合する |
| V4 | 検証の証拠を読む | 検査が走って通ったかを context 単位で確かめ、作者の検証記録・画面の記録を開く。要るなら自分で再実行する |
| V5 | 判定する | 所見を書き、止める理由の範囲で合否を決める。権限外の問いは回す。未確認を書く。挙動を自分の言葉で要約する |
| V6 | 返す | 判定記録を残る場所に定型で書き、`verdict` に従って判定または判定の案とし、状態を次の受信箱へ付け替える |
| VQ | 問い合わせ | PR を伴わない問い（`needs-qm` 相当）: 事実の確認だけ答え、決定の問いは付表 3a で回し、元の状態へ戻す（V5 手順 3 + V6 手順 4 のみ。V1〜V4 は不要） |

### 1.2 `qm-ship`（出荷の範囲）

| # | 工程 | ひとことで |
|---|---|---|
| S0 | 受け付け | cut の依頼を受け、出荷の範囲（release の HEAD と含まれる変更の一覧）を確定し、深さ（D1〜D3）を決める |
| S1 | 範囲と土台 | release / base の HEAD と merge-base を固定し、含まれる変更ごとに独立レビューの記録と独立の成立を突合する |
| S2 | 検査の実測 | 出荷レーンの必須の検査が**走って**通ったかを context 単位で数える。失敗は外部要因か欠陥かをログで切り分ける |
| S3 | 記録の完備 | 判定記録の欠落 0 か、受容した負債・既知の不具合・未達の統制の一覧（保証の開示）があるかを突合する |
| S4 | 判定する | 止めるのは「出荷基準の未充足」と「記録の欠落」だけ。意見は異議として決裁者に渡す。戻せない操作は承認者の記録を待つ |
| S5 | 事後 | merge 後の整合（案件のブランチ規則が求めるもの）・health・「承認未実行」の残置を確かめる |

V0 / S0 と V6 / S5 を置く根拠は Dev と同じ（受け渡しの境目で事故が起きる。`research-ganbari-incidents.md` §まとめ: H と A が事故の形を決める）。V2 を独立の工程にしたのは、会社の型と GQ の欠けへの答えで、B 系列で「開いたか」を測る単位でもある〔推論〕。VQ は P-4（問い合わせは PR レビューの外でも起きる）〔推論〕。

## 2. 各工程の定義の書式

設計書 11 §2 と同じ 10 項目（工程の内部の段階 / 入る条件 / やること / 考え方 / 調査の範囲と深さ / 背景・目的が不明なとき / 矛盾するとき / 出る条件 / 成果物と受け渡し / 典型的な失敗）。手順表の行が「段階」に当たる工程はそう書く。**原則（§3）は 1 か所にだけ書き、工程の手順はその番号を参照する**（調査 §7 危険 (1): 工程を細かく書くほど規則で止める向きに戻る。GQ では規則を 5 回足しても再発率が変わらなかった、I-16）。

## 2b. 深さ（段に応じて工程を軽くする）

**原則**: 手順と成果物への投資は変更（または出荷）のリスクに比例させる〔実証〕DORA（設計書 11 §2b と同じ出典）〔GQ〕棚卸し 2 §8.2「どの PR を深く見るかの規定が無い」。段は V0 / S0 で決め、理由を 1 行残す（B-19）。割れたらいちばん重い軸に合わせる〔推論〕。

### 段の判定

| review の段 | ship の段 | 中身 | 出典 |
|---|---|---|---|
| R1 | D1 | 依存の定型更新・lockfile だけ・案件が標準変更とした種類。検査の集計だけで判定できる / 1 PR の出荷前、必須の検査の実測だけ | 〔GQ〕難易度の調査 §3.3 R1、#5078〜#5080 / §3.4 S1 |
| R2 | D2 | 差分の中で完結する変更。受入基準と差分の 1 対 1 で判定できる / release cut（複数 PR）。含まれる変更の一覧 × 判定記録の突合 | 同 §3.3 R2 / §3.4 S2 |
| R3 | D3 | 差分の外（呼び出し元・他の入口・同じ概念の別の場所）を読まないと正しさが言えない / 統合 PR の失敗の切り分け（外部要因か欠陥か） | 同 R3（#5007・#5008）/ S3（#5072） |

いちばん重い軸: 差分の種類（認証・認可・個人データ・金額・公開した挙動・戻せない操作に触れれば R3 以上）/ 広さ（複数モジュールなら R3）/ 履歴（同じ箇所に事故があれば 1 段上げる）〔推論〕設計書 11 §2b の軸を当てた。

## 4. 各工程の定義

### 4.V0 受け付け（qm-review）

**目的**: 自分宛ての変更を取りこぼさずに拾い、自分の決定権の中か・どのレーンか・どの深さで見るかを決め、1 回に 1 つだけ扱う。

| 段 | # | 手順 | 要点 | 出典 |
|---|---|---|---|---|
| **A1 拾う** | 1 | 受信箱を見る | レビュー待ち・問い合わせ・自分が止めたもの（HEAD が動いた）の 3 つを見る。空なら「空」と 1 行。PR を伴わない問い合わせは VQ へ | 〔GQ〕qm-session §セッション起動時〔事故〕I-20 |
| **A2 自分の仕事か** | 2 | 宛先の表を当てる | 付表 3a。R5 なら自分。R0〜R3・R7 なら**材料をそろえて渡すところまで**（Y3） | 〔GQ〕憲章 §4〔作法〕カタログ §3.2 R7（compass roles-responsibilities L756） |
| | 3 | レーンを判別する | base で判別し、レーンごとの必須の検査（アダプタ）を読む | 〔GQ〕qm-session §レビュー対象レーン |
| **A3 深さ** | 4 | 段を決める | R1〜R4 を §2b で決め、理由を 1 行（B-19）。いちばん重い軸に合わせる | 〔推論〕 |
| | 5 | 1 つずつ | 1 回に 1 つの変更。複数を一括で処理しない | 〔事故〕I-04〔GQ〕qm-session（1 Agent = 1 PR） |

- **入る条件**: 受信箱に自分宛てがある。**出る条件**: 宛先・レーン・段・理由が記録されている（Y13 冒頭メタ）
- **考え方**: 受信箱が空なのは経路が壊れている兆候であることが多い〔GQ〕label-mailbox §5。自分の決定権の外の依頼は、進めるのではなく材料をそろえて渡す（Y3）
- **調査の範囲と深さ**: ここでは差分を読まない。宛先・レーン・段を決めるのに要るもの（チケットの種類・base・変更パスの一覧・触れる領域）だけ
- **背景・目的が不明なとき**: チケットが無い・受入基準が無い PR は、V2 で「受入基準が曖昧」を所見にする前提で受ける（付表 3a R2）。レーンが判別できなければアダプタの既定（いちばん重い出荷レーン）で見て、そう書く〔推論〕
- **矛盾するとき**: 依頼の label と PR の内容が食い違う（レビュー依頼に見えて実は問い合わせ）→ 内容で判定し、label を正す〔GQ〕label-mailbox §3.1.1
- **成果物と受け渡し**: 判定記録の冒頭メタ（宛先・レーン・段・理由）。次の工程は自分
- **典型的な失敗**: 複数 PR の一括処理（I-04）/ 自分の決定権の外の依頼を進める（I-24。I-26 からは QM の宛先規則が生まれた）

### 4.V1 土台を固定する

**目的**: 判定の対象を「どの HEAD の、どの base に対する差分か」で固定し、見かけの緑に騙されない。手順 1〜4 が段階。

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | HEAD を固定する | `git ls-remote` で head の SHA を取り、以降の全確認で固定参照する（API の値は古いことがある） | 〔GQ〕qm-session §Authoritative HEAD |
| 2 | merge-base を測る | 空なら orphan（CI の全 pass は根拠にならない）。差分は three-dot で見る（two-dot は「まだ取り込んでいない」を「削除」と読ませる） | 〔事故〕I-23〔GQ〕qm-session §① |
| 3 | base 側も実物から読む | 作業ツリーでなく `git show origin/<base>:<path>` / API で取る | 〔GQ〕qm-session §base 側ファイル |
| 4 | Draft と未起動を確かめる | Draft は required が skip になり緑に見える。context 0 件は走っていない | 〔事故〕I-22〔GQ〕qm-session §Draft |

- **入る条件**: V0 の出る条件。**出る条件**: HEAD / base / merge-base が記録され、Draft でないことを確かめた（B-18）
- **考え方**: 読む対象を固定しないと、後の確認がそれぞれ別の状態を見る（I-13・I-23）。土台の固定は読む前に 1 回だけ行う〔GQ〕qm-session
- **調査の範囲と深さ**: HEAD・base・merge-base・Draft の 4 点だけ。差分の中身は V3
- **背景・目的が不明なとき**: base が判別できない（複数の候補、PR の base が案件のレーンに無い）→ 作成者に問い、仮の base で読み進めない〔推論〕
- **矛盾するとき**: `gh pr view` と `ls-remote` が割れたら ls-remote を採り fetch してから読む〔GQ〕qm-session §Authoritative HEAD
- **成果物と受け渡し**: HEAD・base・merge-base・Draft の有無を判定記録の冒頭メタに
- **典型的な失敗**: Draft のまま approve（I-22）/ two-dot で削除と誤読（I-23）/ 別の HEAD で検査（I-13）

### 4.V2 文脈を読む（GQ に無く、新設）

**目的**: 変更が何のためで、何に従うべきかを、作者の要約ではなく一次の文書（チケット・受入基準・設計書・決定記録）で知る。開いた一覧を証拠として残す（Y1 を V2 で当てる）。手順 1〜4 が段階。

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | チケットと受入基準を開く | PR が閉じるチケットの受入基準・採択条件・履歴（コメント・関連 PR）を開く。PR 本文の要約で代用しない（Y2）。決裁が要る PR はチケット側の条件と PR 側のブリーフを両方読む | 〔事故〕I-01・I-24〔GQ〕qm-session 手順 1 |
| 2 | 変更パスから設計書を引く | 変更したパスに対応する設計書・決定記録・入口の文書を**機械的に**引いて開く。対応表はアダプタ（GQ の例: `docs/CLAUDE.md` の更新ルール表、`pr-review` Step 0）。**対応表が無い案件の既定**: 変更パスの各ディレクトリの入口文書（CLAUDE.md / README）を開き、`docs/` を変更ファイル名・モジュール名・公開名で検索して当たった文書を開く。当たらなければ「対応する設計書なし」を未確認に書く。開いた一覧を判定記録に残す | 〔オーナー〕会社の型（対応表の無い新しい案件で起きた）〔GQ〕`research-inventory.md` §(2) 不足「手順 0」〔実証〕Bacchelli & Bird 2013（理解が中心）〔推論〕対応表が無いときの既定 |
| 3 | 決定記録の状態を見る（R3 以上） | 日付と状態（置き換え済みか）を確かめる。古い記録に基づく所見を書かない。コア機能では設計意図の記録の完備を確かめる | 〔作法〕Nygard（設計書 11 §4.1 手順 5）、compass G-6 基準 3 |
| 4 | 意図的な設計かを確かめる | 差分が設計書と食い違うとき、「設計書が古い」「意図的に変えた（決定の記録がある）」「逸脱」のどれかを決める前に、根拠（決定記録・チケットの合意）を探す | 〔GQ〕`research-inventory.md` §(2)（policy-compliance の段が PR ごとに無い） |

- **入る条件**: V1 の出る条件。**出る条件**: 開いた文書の一覧（パス・版）がある（B-1・B-2）。R1 で省くなら理由 1 行
- **考え方**: レビューの中心は欠陥の発見より「変更の理解」で、文脈の知識が有用率を倍にする〔実証〕Bacchelli & Bird 2013、Bosu ら 2015。差分だけを見るレビューは会社で実際に詰まった〔オーナー〕
- **調査の範囲と深さ**: 対応表が指す文書と、チケットから 1 ホップ（関連 PR・置き換えた決定）まで。それ以上は R3 の V3 手順 4 で広げる〔推論〕
- **背景・目的が不明なとき**: チケットの目的・受入基準自体が曖昧なら、推測で埋めずに「受入基準が曖昧」を所見にし、付表 3a R2（PO）へ回す。GQ にはこの規定が無かった〔GQ〕棚卸し 2 §8.2
- **矛盾するとき（文書と差分）**: 黙ってどちらかに合わせない。①食い違いを所見に書く ②意図的な変更の記録があるか探す ③無ければ「設計書の修正か差分の修正か」を作成者に返し、裁けないなら付表 3a R3（技術判断者）へ。GQ では「設計書同期なしはマージ不可」（pr-review F）と「3 類型に当たらなければ QM が直す」（憲章 §0）が食い違っていた〔GQ〕棚卸し 2 §8.2・§8.6。核は「食い違いの所見 + 裁定の経路」、どちらを採るかはアダプタ〔推論〕
- **成果物**: 開いた文書の一覧（判定記録の欄「開いたもの」）
- **典型的な失敗**: 設計書を読まずに差分だけでレビュー（会社の型）/ PR 本文の要約を仕様の代わりに読む（I-21 と同型）

### 4.V3 差分を読む

**目的**: 変更した全ファイルを自分の目で開き（Y1）、受入基準と 1 対 1 で照らし、作者の主張を実物で照合する（Y2）。R3 以上では差分の外に広げる。手順 1〜5 が段階。

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | 変更した全ファイルを開く | 差分の一覧を取り 1 ファイルずつ開く（テストも）。レビュー道具の「見た」印は自己申告で、ファイルが変わると外れる | 〔作法〕Google eng-practices（全行を見る）、GitHub Docs〔実証〕McIntosh ら 2014・2016、Spadini ら 2018 |
| 2 | 受入基準と 1 対 1 で照らす | 受入基準の項目ごとに、どのファイル・行で満たされるかを名指しする。満たされない項目は所見 | 〔GQ〕qm-session 手順 1〔作法〕compass G-6 基準 1 |
| 3 | 作者の主張を照合する（Y2 の対象） | 「直した」「N 件」「通した」「証跡を撮った」を、HEAD の中身・grep の件数・実行・証跡で確かめる。照合できないものは「未確認」。偽の主張（HEAD に無い修正、差分の前後で同一の証跡）は証跡の真正性の所見 | 〔GQ〕ADR-0004 §2、qm-session §Re-Review 4〔事故〕I-11・I-14 |
| 4 | 差分の外へ広げる（R3 以上） | 呼び出し元・他の入口・サーバー側の関門・秘密の値の経路・同じ概念の別の場所（並行実装）を開く。足りない回帰テストを示す | 〔GQ〕難易度の調査 §3.3 R3（#5007）〔実証〕Bacchelli & Bird、DoorDash [二次]（AI レビュアは構造の問題を見逃した） |
| 5 | 前提を疑う（R4） | 技術の選択・前提・戻しにくい決定の見落とし。「正しく作られているか」より「正しいものを作っているか」。技術の選択の問いは付表 3a R3 へ | 〔GQ〕難易度の調査 §3.3 R4〔作法〕compass G-3 |

- **入る条件**: V2 の出る条件。**出る条件**: 変更した全ファイルを開いた記録（B-3）。受入基準ごとの位置。主張ごとの照合結果（確認 / 未確認 / 偽）。R3 なら差分の外で開いたものの一覧
- **考え方**: 作者の主張は PR 本文の枕詞 1 つで検出を大きく下げる〔実証〕Mitropoulos ら 2026。主張を事実の代わりにしない（Y2）
- **調査の範囲と深さ**: R2 は差分の全ファイル。R3 は 1 ホップ（呼び出し元・同じ概念の別の場所）。R4 は前提の文書まで。それ以上は分割を求める（Y9）〔推論〕
- **背景・目的が不明なとき**: 差分の意図が読めない → 作者の説明を「主張」として扱い、実物で確かめられない部分は未確認に書く。意図を推測で補って承認しない〔推論〕
- **矛盾するとき**: 差分と受入基準が食い違い、どちらが正しいか分からない → 付表 3a R2。差分どうし（並行実装の片側だけ変更）→ 所見
- **成果物**: 開いたものの一覧、受入基準ごとの位置、主張の照合結果（Y13 の欄へ）
- **典型的な失敗**: 一部のファイルだけ見て全体を判定 / 主張を鵜呑み（I-14）/ 「文字列検索で N 件」で済ませる

### 4.V4 検証の証拠を読む

**目的**: 「通った」を主張でなく実測で確かめる（Y5）。手順 1〜5 が段階。

| # | 手順 | 要点 | 出典 |
|---|---|---|---|
| 1 | 検査を context 単位で数える | required の一覧（アダプタ）に対し、走ったか・通ったか・skip か・未起動かを 1 つずつ。まとめの検査が緑でも根拠にしない。再トリガ後の古い世代を今の結果と読まない | 〔事故〕I-22〔GQ〕qm-session §非 pass 行 0 は緑の証明にならない |
| 2 | 作者の検証記録を読む | 実行した手順・観測した結果・受入基準を満たすと考えた理由、の 3 要素があるか。無い変更は差し戻す。PR 本文の主張を証拠として読まない（Y2） | 〔作法〕compass G-6 基準 6、Claude Code best practices〔実証〕Mitropoulos ら 2026 |
| 3 | 証跡を開く | 画像・DOM・ログ・出力の記録を実際に開き、1 件ごとに具体の所見。**差分の前後で同一の証跡は偽装を疑う**（種類ごとの判定はアダプタ。GQ は画面の記録の blob SHA） | 〔GQ〕qm-session 手順 2・3〔事故〕I-01・I-11 |

- **入る条件**: V3 の出る条件（R2 以上では V2・V3 の後に行う。CI を先に見ると「CI 緑 = approve」に退行した: I-01）。**出る条件**: context ごとの結果の表（B-5・B-6）。作者の検証記録の有無。証跡ごとの所見。再実行したなら命令と出力
- **考え方**: Y5。緑は証拠であって判定ではない
- **調査の範囲と深さ**: required の一覧 + 作者の記録 + 証跡。自分で再実行するのは R3 以上か、主張が「全件」「N 件」の形のとき〔推論〕
- **背景・目的が不明なとき**: required の一覧が案件に無い → context 全部を required と読み、そう書く（§6 既定）
- **矛盾するとき**: 手順 4
- **成果物**: 「走らせたもの」の欄（context 表・再実行の命令と出力）
- **典型的な失敗**: skip を緑と読む（I-22）/ 証跡を開かずに所見（I-01）

### 4.V5 判定する

**目的**: 所見を書き（Y7）、止める理由の範囲で合否を決める（Y6）。権限外の問いは回す（Y3）。未確認を書き（Y8）、挙動を要約する（Y1）。手順 1〜8 が段階。

|---|---|---|---|

| 2 | 止める理由の範囲を当てる | Y6。「指摘ゼロ」は「レビューしたが指摘なし（何を見たか）」と書き、レビューしていないと区別する | Y6〔GQ〕ADR-0004 §1、事故 I-04 |
| 3 | 権限外の問いを回す | Y3・付表 3a | Y3 |

- **入る条件**: V2〜V4 の出る条件。**出る条件**: 判定（承認 / 差し戻し / 判定の案）と、Y13 の欄の入った判定記録
- **考え方**: 「問題を探せ」と言われたレビュアは必ず何か見つける。範囲を限る（Y6）〔作法〕Anthropic best practices〔実証〕Jin & Chen。所見の大半は欠陥ではなく、却下の主因は偽陽性・範囲外〔実証〕Czerwonka ら、Lin ら 2026（数値は付録 A）。「素晴らしい実装です」型の、根拠の無い肯定を書かない（echoing。adversarial-reviewer が禁じる）
- **調査の範囲と深さ**: ここでは新しく読まない。V2〜V4 で開いたものだけで書く。足りなければ V2〜V4 に戻る（X13 と同じ）
- **背景・目的が不明なとき**: 受入基準が曖昧で合否が決められない → V2 の背景不明へ（付表 3a R2）
- **矛盾するとき**: 指摘と作成者の主張が割れたら実物で照らす。2 周で収束しなければ Y12
- **成果物**: 判定記録（Y13）
- **典型的な失敗**: CI 緑を理由に承認（I-01）/ 権限外の問いに答える（会社の型）/ 書式の不備で止める（統合 PR を 4 日止めて顧客リスクは減らなかった、ADR-0004 改訂）

### 4.V6 返す

**目的**: 判定を残る場所に定型で書き（Y13）、届く経路で次の担い手へ渡す（Y11）。`verdict` に応じて最終の判定か判定の案かを分ける（Y10）。手順 1〜5 が段階。

|---|---|---|---|
| 1 | 判定記録を残る場所に | Y13 の冒頭メタ + 5 欄 | Y13 |
| 2 | 承認者を確かめる | 自分が作成者・作成の指示者でないこと（Y4、B-12）。承認の操作は判定者本体が行う（Y10、B-13） | Y4・Y10 |
| 3 | `verdict` に従う | `final`: approve / request-changes を自分で行う。`detection`: 判定の案と記録を書き、人の席の状態（アダプタ）に付け替えて記名を待つ。どちらでも欄は同じ | 〔オーナー〕Q3 |
| 4 | 状態を付け替える | 差し戻しは作成者（または fix）の受信箱の状態、承認は出荷判定（または merge）の状態。問い合わせは元の状態に戻す（Y11） | 〔事故〕I-18〔GQ〕label-mailbox |
| 5 | 再レビュー | 前回の所見ごとに HEAD で確かめる。「全件解消」は独立の grep で件数を突き合わせる。承認は承認した差分に対してだけ有効 | 〔事故〕I-14〔GQ〕qm-session §Re-Review〔作法〕compass G-6 L909 |

- **入る条件**: V5 の出る条件。**出る条件**: 判定記録が残る場所にあり、状態が次の受信箱に出ている
- **考え方**: 書いたかではなく相手の受信箱に出るかで伝達の成否が決まる（Y11）
- **調査の範囲と深さ**: 無し（記録と状態の操作だけ）
- **背景・目的が不明なとき / 矛盾するとき**: `verdict: detection` なのに人の席の状態がアダプタに無い → 判定の案のまま止め、PO へ回す（付表 3a R7）〔推論〕
- **成果物**: 判定記録 + 状態の付け替え
- **典型的な失敗**: 「approve に進みます」と書いて終了（I-15）/ 状態を外して次を付けない（I-18）/ 自分が指示した変更を承認（I-03）

- **矛盾するとき**: 含まれる変更の判定記録と release の内容が食い違う（記録のある PR が入っていない / 記録の無い PR が入っている）→ 記録の欠落として差し戻し。「多い・少ない」は異議〔作法〕compass G-7

- **組織の規定（1 回の判定では測らない）**: 出荷のチェックリストの各項目は過去の事故で裏付け、定期に棚卸しする〔作法〕Google SRE LCE。これは maintenance の仕事で、§6「出荷基準」の注記に置く

## 7. 評価計画への接続

評価計画は `27-qm-role-evaluation-plan.md`。

- **主な量 B（プロセス準拠）**: 調査 §5.1 の B-1〜B-16 に本版で **B-17**（判定者がレビュー対象を編集・commit・push していない。Y15）、**B-18**（判定の前に merge-base / HEAD 固定 / Draft 確認の呼び出しがある。V1）を足す。実装: `packages/pit-wall/src/graders/process/review-phases.mjs`（B-1・2・3・5・6・7・9a・9b・10・12・13・15・17・18、区切り = 最初の判定。判定の有無は偽 gh の効果 `state.gh`、位置は trajectory。位置の無い効果は判定不能 = null）。B-8（偽の主張の反証の観測）は課題ごとの check。B-9b（答えたか）は文の照合 + judge の併用で、単独で主張しない
