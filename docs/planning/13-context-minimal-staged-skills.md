# 13 文脈を小さく保ったまま、複雑で段階的なスキルの実行を保つには（研究計画）

作成: 2026-11-02 / 状態: **計画（未着手）**。セルはまだ作らない（設計書 11 の全工程の中身が揃ってから）

## 0. 発端と問い

- オーナー（2026-11-02）: 工程を細かく規定するとスキルが肥大化し、文脈を圧迫したり、細かい規則の読み落としでミス・手戻りを招いたりしないか。工程はフラットに並べるのがよいか、大工程を判定してから詳細を読むのがよいか（オーナーの見立てはフラット）。dev-research のような工程別スキルを作るべきか。続けて「二つ目の質問も実験で調べましょう。コンテキストを最小に維持しながら複雑かつ段階的なスキル実行の維持とはどうあるべきか研究したいです」
- **研究の問い**: 同じ中身（設計書 11 の工程定義）を、どんな構造と分け方でエージェントに渡すと、(a) 工程を飛ばさず (b) その工程の規定を守り (c) 長い作業・圧縮の後も保ち (d) 文脈の消費が小さいか
- 根拠の調査: `docs/research/research-process-structure-for-agents.md`（照合メモつき）。要点:
  - 調査の推奨は混合案（大工程の一覧と入る・出る条件だけを常に置き、工程の中身はフラットな手順にして、その工程に入るときに 1 階層だけ読む。工程の判定は状態ファイル・成果物の有無で）。確度は中: コーディングエージェントで直接比べた研究は無く、他分野からの類推
  - 害の主因は文脈の長さそのものより「選び間違い」と「無関係な内容」だった（202 スキルで最大 21% 低下、主因は選び間違いで文脈の大きさの影響はほぼゼロ: arXiv 2605.24050、要旨で照合）。段階的開示は 1 段なら効き、2 段目は効かず壊すこともある（2607.17598、題材は長文の質問応答、要旨で照合）
  - 反証もある: 詳しい外部チェックリストで 10/10、一般的な自己点検は 5/10（2607.17937）。粒度の差は小さく不確か（2605.31408）

## 1. 仮説（実行前に固定し、どれが外れても記録する）

| # | 仮説 | 外れたら |
|---|---|---|
| H1 | 混合案は、フラット案より工程の取りこぼしが少なく、文脈の消費も小さい | 構造の差は小さく、中身の具体性が効いている（2605.31408 と同じ向き）。フラット案（オーナーの見立て）を採る |
| H2 | 混合案は、エージェント自身が工程を判定する階層案より、誤った工程の詳細を読む回数が少ない | 状態ファイルの手間は不要。階層案を採る |
| H3 | 工程の中身を参照ファイルにするより、核から名指しで呼ぶスキルにした方が、圧縮の後に規定が保たれる（呼んだスキルは圧縮後も先頭が再添付される） | 参照ファイル＋「入るときと圧縮後に読み直す」規則で足りる |
| H4 | 自動で発火する工程別スキルは、呼ばれない・別のスキルが呼ばれる回が他の分け方より多い | 自動発火でも足りる（説明文の工夫で解ける） |
| H0 | どの構造・分け方でも差が出ない（天井、または課題に識別力が無い） | 課題を、長さ・引き継ぎ・圧力を持つものに作り直す（`research-ecological-validity.md`） |

## 2. 比べる条件（arm）

中身は同一（設計書 11 から機械的に生成し、文の追加・削除をしない）。違うのは構造と分け方だけ。

| arm | 構造 | 分け方 |
|---|---|---|
| F | フラット: 約 20 の工程を番号で 1 列 | 1 つの dev スキルに全文 |
| H | 階層: 核に大工程の表と判定の規則、工程の中身は工程ごと | 参照ファイル。工程の判定はエージェント自身 |
| M | 混合: 核に大工程の表・入る / 出る条件・致命的な規則。工程の中身はフラットな手順。判定は状態ファイル・成果物の有無 | 参照ファイル。入るときと圧縮後に読み直す規則 |
| M-skill | M と同じ | 工程の中身を、自動発火を切った工程別スキルにし、核から名指しで呼ぶ（オーナーの選択肢「核から名指しで呼ぶスキル」） |
| S | M と同じ | 工程別スキルを自動発火（dev-research 等）。説明文だけで選ばせる |
| 0 | ハーネスなし | 比較の基準 |

- 主な比較は 3 つに絞る（多重比較を避ける）: **M 対 F**（構造、H1）、**M 対 H**（判定の仕方、H2）、**M-skill 対 M 対 S**（分け方、H3・H4）
- 費用が足りなければ、S と 0 を後回しにする

## 2b. 使うモデル（オーナー 2026-11-02）

- オーナー:「最先端モデルだけで使えるスキル、ってなるとその時点で不安定な可能性があるので、スキルを正しく実行できているかどうかの評価では sonnet や haiku（そもそも不適切かも？）で検証したほうがいいかもしれないです。その方がよりどれくらいうまく構造化したスキルを検討するべきかわかりそうです」
- 方針: 構造と分け方の比較は、最上位のモデルではなく **Sonnet を主、Haiku を副**にする。最上位のモデルは天井に当たりやすく、構造の差が見えにくい〔推論〕。これまでの実験もすべて claude-sonnet-5-5
- 仮説 H5（実行前に固定）: 構造の差（取りこぼし・誤った工程の読み込み）は、Haiku の方が Sonnet より大きく出る。外れたら（差が同じ、または Haiku が全 arm で失敗）、Haiku はこの課題に不適切として外す
- Haiku が適切かは、骨組みの試走（§5 の 2）で先に確かめる: Haiku で 1 課題 × 3 arm × 3 回を走らせ、工程を 1 つも進められない（全 arm で床）なら主の比較から外し、その旨を記録する
- 根拠の調査: 指示の数が増えたときの遵守の落ち方はモデルによって違う（arXiv 2507.11538「How Many Instructions Can LLMs Follow at Once?」、題名を API で確認。小さいモデルほど落ち方が大きいかは要旨・本文で未確認）。実行前にこの論文の該当部分を照合する

## 3. 課題（セル）

- 事故由来の、複数の工程をまたぐ課題を 3〜4 本（`12-dev-role-evaluation-plan.md` §2 の候補から。古い base、偽の完了報告、名前の変更で修正が消える、再現テストが修正前に失敗すること）
- 各課題に入り方を 3 つ:
  - **頭から**（チケットだけ）
  - **途中から**（調査メモと失敗するテストが既にあり、本来は実装から始めるべき状態）: 工程の判定を試す
  - **急かす**（依頼文に「すぐ実装して」）: 工程の飛ばしを試す
- **圧縮を挟む**条件を 1 つ: 作業の途中で文脈の圧縮を起こす。Harbor（非対話）で圧縮を強制できるかは [未確認]。できなければ、長い前置きの作業（同じ種類の課題を連続）で自然に起こす

## 4. 測るもの（記録と成果物から決定的に）

| 量 | 定義 | 主 / 副 |
|---|---|---|
| 工程の取りこぼし | 出る条件の成果物（調査メモの必須項目、失敗したテストの実行記録、検証の記録）が無いまま、次の工程の行動（実装ファイルの編集など）が始まった回数 | **主**（実行前に登録） |
| 誤った工程の詳細を読む | その時点の正しい工程（状態・成果物から決まる）と違う工程の中身を読んだ回数。読むべき中身を読まなかった回数 | 副 |
| 工程内の遵守 | 各工程の手順のうち、成果物で確かめられる項目の充足率 | 副 |
| 圧縮の後の劣化 | 圧縮の前後の充足率の差。圧縮後に工程の中身を読み直したか | 副 |
| 文脈の消費 | 読み込まれたスキル・参照の文字数（トークン換算）、文脈の最大の大きさ、入出力トークン、所要時間 | 副（**問いの (d)**） |
| 呼ばれない・選び間違い | S・M-skill で、呼ぶべき工程のスキルが呼ばれなかった / 別の工程のスキルが呼ばれた回数 | 副（H4） |
| 事故の述語 | 課題ごとの害（`12` §2 の述語） | 副（中身の効果。arm 間で同じなら構造の差は効いていない） |

## 5. 進め方・回数・判定

1. **前提**: 設計書 11 の全工程の中身が揃っていること（構造の比較には複数の工程が要る）。arm を設計書から機械的に生成する道具（文の追加・削除をしないことを検査する）
2. **骨組みの試走**: 1 課題 × 3 arm（F・H・M）× 3 回。量が記録から機械的に取れるか、圧縮を起こせるかだけを確かめる（効果は見ない）
3. **本実行**: 主な比較 3 つについて、arm × 課題あたり 10〜12 回。判定は実験カードに実行前に固定する（主の量、Newcombe の 95% 区間、Fisher の正確確率、故障の除き方）。天井（全 arm で取りこぼし 0）なら H0 として課題を作り直す
4. 7 日枠の使用率 0.99 で止める。Harbor は並行させない。ホストの空きメモリ 6GB 未満では始めない
5. 費用の見積り [推論]: 骨組み 9 回 + 本実行（3 比較 × 2〜3 arm × 3〜4 課題 × 10 回）で 200 回前後。1 週の枠では足りない見込みが高いので、主の比較（M 対 F）を先に、残りは週をまたいで行う

## 6. 言わないこと（先に決めておく）

- 天井の結果から「構造はどれでもよい」と一般化しない（課題に識別力が無かった可能性を先に疑う）
- 1 つのモデル・1 つの版の Claude Code の結果を、他に広げない
- 中身を変えた比較（量を減らした版など）を、構造の比較と混ぜない
