## 2. 分かったこと

- **D1 は規定を届け、行動も変えた**: 調査の工程のスキルを呼んだ率が t4 で 3/15 → 14/15、t5w で 4/15 → 13/15。t4 で意味で探した 3 → 10/15、pickaxe 1 → 9、共通の関数に行き着いた 6 → 12。t5w で three-dot 5 → 13、実装の前に main を取り込んだ 4 → 11
- **害は減る向きだが、事前の規則では示せない**: t4 9/15 → D1 3/15（−0.40、Newcombe −0.64〜−0.05、p = 0.060、Holm を満たさない）、t5w 4/15 → 2/15。D2 は t4 7/15、t5w 2/15。4 つとも増えていない
- **D2（核へ移す）は、規定が常に届くのに、行動の変わり方は D1 より小さかった**: t5w で `merge-base` で土台を確かめる試行は増えた（three-dot 14/15）が、取り込みは 9/15。t4 では意味で探す 3 → 6 にとどまった [推論: 手順の 1 行だけを核に置いても、調査の工程の他の手順（構造をたどる・文書を読む）と一緒に読まないと、行動にまでつながりにくい]

## 3. 分かっていないこと

- D1 で害が減るか（各 15 回では、事前の規則の閾値に届かなかった）
- D1 の「必ず呼ぶ」型の言い方の副作用（Vercel では、型に引きずられて文脈を見落とした）。今回の 2 課題では測っていない
- 小さい依頼（T0・T1）で、調査の工程を必ず呼ばせると過剰にならないか。今回の 2 課題は T2（金額）
- 確かめた結果に応じて処置させるには、何が要るか（「古ければ取り込んでから調べる」は規定に書いてあるのに、3 回は進んだ）

## 4. 言えること・言えないこと

- 言えること: 「既定のスキルの核に 1 文（受け付けの後、実装の前に、調査の工程のスキルを呼ぶ）を足すと、Sonnet は 2 課題でほぼ毎回（14/15・13/15）調査の工程の手順を読み、規定が求める行動（意味で探す・三点比較・取り込み）が増えた。害は 2 課題とも減る向きだった」
- 言えないこと: 「D1 で害が減る」（事前の規則で示せていない）、「規定を核に移す（D2）より必ず呼ばせる（D1）方が良い」（害の差は比べていない。行動の変化の大きさの違いだけ）、「どの依頼でも」（T2 の 2 課題のみ）

## 5. 次の一手

1. D1 を既定にした上で、害の差を確かめる回数（各 30 回程度）で D0 対 D1 をもう一度 [推論: t4 の差 −0.40 を Fisher で検出するには各 25〜30 回の見込み]
2. 小さい依頼（T0・T1）の課題で、D1 が過剰な手順（不要な調査）を生まないか、手数と成果物を見る
3. 「確かめたが処置しない」を減らす: 土台が古いと分かったときの処置を、確かめる手順の同じ行に書く（今は「含まなければ最新の base を取り込んでから調べる」と書いてある）か、`--is-ancestor` の結果を必ず表示する形（`&& echo ok || echo stale`）にする
