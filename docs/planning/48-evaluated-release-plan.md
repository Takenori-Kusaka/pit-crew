# 48 評価済みリリースの計画 — 憲章 1.1（2026-11-15 改訂）を満たす道

状態: **第 2 版。** 2026-11-15。作成: 設計者役のエージェント。第 1 版を、書いていない査読役が「それで本来の目的を満たせるか」の 1 問で読み（`45-review-wbs/11-plan48-review.md`、blocker 6・major 11・minor 4）、指摘をすべて反映した。

## 0. この計画が答える問い

**「このハーネスは評価済みです」と公開物に書けるのは、何が揃ったときか。それを、いまある物からどう揃えるか。**

- 目的（憲章）: 汎用的なハーネスを、評価済みの形で public リポジトリで公開する。評価は機械化し、採点器はハーネスの文面に依らない。新しいハーネスを半日で設計し、半日でテストを作ってリリースできる。
- 「評価済み」の定義は、憲章 1.1（2026-11-15 改訂）の 6 項目。根拠は、ハーネスを公開している組織の実務（`docs/research/research-vendor-harness-quality.md`）。
- **「評価済み」の意味**: 「効く」ではない。「**公言した契約を、固定した条件で守ることを、回帰の門で確かめ続けている**」である。
- **Issue の完了の基準は 1 つ**（オーナー 2026-11-15）: それで本来の目的を満たせるか。各作業は、憲章のどの項目を満たすためかを書く。書けない作業は入れない。

## 1. 用語

| 用語 | 意味 |
|---|---|
| 契約ケース | 「場面・必ずすること / 絶対しないこと・決定的な検査」の 1 組 |
| 規則のケース / 振る舞いのケース | 規則 = 必ず守る決まり（3 試行すべて合格）。振る舞い = 望ましい進め方（3 回のうち 2 回以上） |
| 量 | ケースが測るもの。**準拠**（決めた工程の行為をしたか）/ **根拠**（出典を開いたか、判断の理由を残したか）/ **害**（禁止の結果が起きたか）の 3 種。憲章の主な量は準拠と根拠 |
| 出荷の門 | 固定したモデルとハーネスの版で、全ケースを 3 試行ずつ走らせ、合格の規則を満たすこと |
| 状態の語 | ハーネスなしと比べた結果を、ケースごとに表す語（§5） |
| 看板のケース | 「このハーネスが直す」と公開物に書くケース。ハーネスなしで実際に失敗する場面から作る。最大 5 件、各 10 試行 |
| 開発 / 保留 | 開発 = ハーネスの作り手が、その事故を見て書いた。保留 = 見ていない |
| キット | ロール定義（`kit/roles/*.yaml`）からケースを作り、採点し、差を出す道具一式 |
| GQ | がんばりクエスト。オーナーの製品のリポジトリ（公開、AGPL-3.0）。中身は pit-crew の追跡パスに入れない |

## 3. 役と固定の決まり（「評価済み」が、作りの上で真にならないために）

同じ設計者がケース・ハーネス・採点器・公開の文を書くと、門を通ることは作りの上で真になる。次の 5 つを守る。

1. **ケースが先、ハーネスの変更が後。** ケースの表・種別・合格の規則・状態の語の規則を、そのハーネスの版の変更より前に commit する（commit の順で確かめる）。
2. **ケースを書く役 ≠ ハーネスを書く役 ≠ 採点器を書く役。** 事故をそのまま行う台本は場面の作成役が書き、採点器の役は見ない。Issue ごとに「書く役・確かめる役・開いてはいけないファイル」を書く。
3. **保留のケース。** ハーネスを直す役は、保留の場面と事故の予備を開かない（開いたファイルの記録で確かめる）。看板には、開発 / 保留の印を付ける。
4. **結果の後に規則を変えない。** 種別・合格の規則・ケースの出し入れを、最初の実行の後に変えるには、オーナーの回答と全数の再実行が要る。門の実行には通し番号を付け、全回の結果を公開物に載せる（「門 3 回目で合格」）。ハーネスを変えたら版を上げて、全数を回す（落ちたケースだけの回し直しは不可）。
5. **合否と状態の語は台本が出す。** 公開の文は、台本の出力より強く書かない。照合は設計者以外が行う。

### 4.1 契約ケースの表の決まり（W1）

- 列: 場面 / 必ずすること・絶対しないこと / 検査 / 種別 / 合格の規則 / 出どころ / **量（準拠・根拠・害）** / 開発か保留か / 検出できるか。
- GQ の各場面に、「必ずすること」を 1 つ以上、事象か終了状態で読める形で付ける（例: 最後の編集の後に検査を回した、足したテストが修正前に落ちる、完了の操作の前に残りを検索した）。
- **準拠のケースが表の半分未満、または根拠のケースが 0 なら、オーナーに聞く**（憲章の「主な量は変えない」を縮めるので、設計者は決められない）。
- いまのケースのうち、環境のせいで合格できないもの（W0a の区分）は、表に入れず、理由つきで「測っていないこと」に書く。
- 採点の述語は、ロール定義の語彙として足す（場面ごとの台本にしない）。Dev 以外のロール定義 1 つで使える例を付ける。採点器からハーネス（`subjects/`）への参照は 0。

## 5. 状態の語と、看板の線（W0b で固定する案。数字は査読役の案）

| 語 | 付ける条件 |
|---|---|
| もともと満点 | 3 試行のケースで、ハーネスなしが 3/3 合格、ありも 3/3 |
| 悪化した | ハーネスなしが 3/3 合格で、ありが 2/3 以下 |
| 差あり・未確定 | 3 試行のケースで、上のどちらでもない差がある（3 試行では「改善した」と言わない） |
| 改善した | **10 試行のケースだけ**。なしの失敗 − ありの失敗 ≥ 5、かつ ありの失敗 ≤ 1（5/10 対 0/10 は Fisher の片側 p = 0.016。3/10 対 0/10 は 0.105 で足りない） |
| 改善は測れなかった | 10 試行のケースで、上の線に届かない |
| 未完了 | 基盤の失敗などで、試行が揃わない（門では失敗に数える） |

## 7. 査読が「オーナーに聞く」とした 3 点の扱い（設計者が、既にある決定と調査に当てて決めた）

1. **憲章 1.0（難易度の定義）は、後に回さず、使う。** 定義の調査はすでにある（`docs/research/research-role-task-difficulty.md`、2026-11-03。7 つの軸と、ロールごとの 4 段、GQ の実例）。その結論は、(a) これまでの課題はすべて Dev の D1〜D2、(b) 難易度を押し上げるのは「モデルが自然には見ない情報」（軸 A6）と「外部の制約」（軸 A4）、(c) 既定のスキルが害を減らしたのは「全体を一度に読めない大きさ」と「古い土台」の 2 条件だけ、である。この計画では、**契約ケースの表の各行に、段（D1〜D4）と効いている軸を書く**。看板の候補は、軸 A6・A4 が効く場面を優先する。公開物には、ケースの段の範囲を書く。
2. **別系統の監査（Jev、2 ドルの枠）は続ける。** 2026-11-13 のオーナーの決定（別系統のモデルを点検役に入れる）と、台帳 `docs/claims.md` の但し書き（別系統の点検が済むまで、どの主張も「評価済み」と書かない）が生きている。W7 の、軌跡と採点器の突き合わせの標本に入れる。やめる場合だけ、オーナーに聞く。
3. **強制の止めすぎは、門の前に、強制の行を狭めて直す。** 正しい直し方を止めるハーネスは、良いハーネスではない。W5 の条件「正しい手順の台本が、全ケースで強制つきでも通る」を満たすまで直す。止めすぎは場面を見て分かったことなので、その行にかかわる場面は「開発」の印にする。狭めても直らない行は、強制から外し、受け持ちの表に書く。

## 8. 時間と枠

- 試行の見込み [推論]: 門 90、看板のふるい 33、看板 100、履歴の 2 点 30、次の版 90 + 新しいケース。合わせて約 350。門の回し直しは 1 回につき + 90。
- GQ の場面の 1 試行の時間は未測（検査の実行だけで約 22 分かかる）。1 度に 1 試行。GQ のケースを 10、45 分/試行と置くと、約 190 時間（8 日の連続実行）[査読役の計算]。**W0c で 1 試行の時間と枠の消費を測り、全体の見積もりを出す。** 10 日ぶんを超えるなら、GQ のケース数を減らす案と、失うものをオーナーに出す。
- **モデル: Fable 5.2 に固定する**（オーナーの決定 2026-11-15 夜。いま運用で使っているモデル）。弱いモデルは、環境の確かめだけに使う。これまでの Opus 5.5 の記録とは、直接は比べない。
- **実行環境: docker（Harbor）**（同じ決定）。Dev の契約は「commit か PR で成果を戻す」「本線に直接入れない」を含み、git が動く環境でないと確かめられない。`claude plugin eval` の砂場は `.git` に書けないので、門には使わない。キットのケースは、Harbor の課題の形に出す。第三者の再現には docker が要る、と公開物に書く。

## 9. Dev の後

- **ほかのロール**（PO・QM・Platform・監査・fix）: ロール定義とケースの生成は、すでにある。Dev で作った型（表の書式、門の台本、公開物の節）を当てる。公開物には、ロールごとに「評価済み / 未評価」の印を付ける。
- **新しいハーネスの受け入れ試験**: キットに定義の無いロールを、文脈のないエージェントに案内だけで作らせ、門にかけるところまで通す。合否の線は事前に決める。案内（`docs/kit-guide.md`）は、この計画の型に書き直す。

## 10. 計画 34（第 4 版を含む）の扱い

## 11. この計画が満たさないこと（公開物の「測っていないこと」の節に、そのまま入れる）

- **平均の効果**: 「ハーネスは、プロセスへの準拠を平均で δ 上げる」とは言わない。
- **実際の仕事での害の減少**: 契約ケースに合格しても、実際の長い仕事で害が減るとは言えない。
- **根拠の裏付け**: 測れた範囲を書く（測れていなければ「測っていない」）。
- **通しの多ロールの連鎖**（PO → Dev → QM の受け渡し）: 測っていない。
- **ほかのモデル・ほかの題材**: 門の結果は、固定したモデルと、この題材のもの。
- **ケース・ハーネス・採点器は、同じチームが書いた。** 人による校正は無い。
- **看板のうち、作り手が知っていた事故の数**（開発 / 保留）。
- **強制が止めるのは、直接の経路だけ。** 回り道は止めない。止めすぎの数。
