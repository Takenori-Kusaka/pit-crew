## なぜ具体にするか

- いまの「同じ型を探す」は「同じ種類の誤りが他にないかを確かめ、検索した結果を残す」で、何で探すかを書いていない。EXP-23 では全 29 回が見えている式（90・99）を grep し、漏れた 17 回は名前も書き方も違う共通の関数 `round_tenth` を一度も開かなかった。文献も、修正漏れの多くは最初の修正と内容が似ておらず、文字列やクローンの一致では予測できないとする（Park ほか MSR 2012）
- いまの「土台を確かめる」は「three-dot で見る」と書くが、three-dot が何で、two-dot だと何が起きるか、土台が古いときに何をするかを書いていない。EXP-24 の害の 1 回は `git diff main`（two-dot）で比べ、rebase せずに進んだ

## 案

### A 原則（調査の考え方）

**いま**

- **1 つ見つけたら、同じ型を探す。** テストをすり抜けた不具合は、見落としていた視点を示している。同じ種類の誤りが他にないかを確かめ、検索した結果（件数と場所）を残す〔両氏〕同上（要旨）〔GQ〕dev-process/feature-change-lateral-spread

**案**

- **1 つ見つけたら、同じ型を探す。字面ではなく、何を計算・判断しているか（根本原因）で探す。** テストをすり抜けた不具合は、見落としていた視点を示している。次の 3 つで探し、検索した結果（件数・場所・使った検索）を残す。見えている式や文字列の grep だけで終えない。(1) 意味で探す: 誤りを言葉にし（例:「日付を UTC ではなく現地時刻で比べている」）、その概念の語・コメントの語・同じ計算の別の書き方で検索する (2) 構造で探す: 直す箇所の呼び出し元・呼び出し先と、同じ役割の関数（共通の helper を含む）を開いて確かめる (3) 履歴で探す: 誤りを入れた commit を特定し（`git log -L`・blame）、`git log -G<正規表現>` で同じ形の変更を探す〔両氏〕同上（要旨）〔GQ〕dev-process/feature-change-lateral-spread〔実証〕Park ほか MSR 2012（補足修正の多くは最初の修正と内容が似ておらず、文字列・クローンの一致だけでは漏れの場所を予測できない。漏れの多くは近く、または直接の呼び出し・参照の先にある）、Nguyen ほか ICSE 2010（同じ役割のコード code peers で繰り返す修正）、Yin ほか FSE 2011（同じ根本原因の箇所の直し忘れ）〔作法〕CodeQL の variant analysis（既知の欠陥を種に論理上の変種を探す）、Project Zero 2022（根本原因の分析が変種探しの前提）、git 公式（log -G / -L）。(1)〜(3) の組み合わせで見落としがどれだけ減るかは文献に無い〔推論〕

### B 調査の手順 2（土台）

**いま**

| | 2 | 土台を確かめる | どの branch・HEAD・環境を読んでいるかを記録する。他の branch との差は merge-base からの差（three-dot）で見る | 全部 | 〔事故〕I-12、I-23 |

**案**

| | 2 | 土台を確かめる | どの branch・HEAD・環境を読んでいるかを記録する。作業する branch が base（main 等）の今の先端を含むかを `git merge-base --is-ancestor <base> HEAD` で確かめ、含まなければ最新の base を取り込んでから調べる。自分の変更だけを見るときは `git diff <base>...HEAD`（three-dot: merge-base からの差）、自分の commit だけを見るときは `git log <base>..HEAD`。`git diff <base>` と `git diff <base>..HEAD`（two-dot）は 2 つの先端を直接比べるので、分岐の後に base に入った変更が、自分が消したかのように混ざる | 全部 | 〔事故〕I-12、I-23〔作法〕git 公式（git-diff: `A...B` は `git diff $(git merge-base A B) B` と同じ、`A..B` は 2 つの端点の比較。git-merge-base: --is-ancestor。git-log: `A..B` は B から届き A から届かない commit）。「混ざる」は定義からの推論〔推論〕 |

## 案で言えないこと

- (1)〜(3) を書くと見落としが減るかは、文献では示されていない（効果量は無い）。EXP-25 で確かめる
- 文献は 2004〜2012 年の C / Java の開発が対象で、AI エージェントの見落とし率の根拠にはならない
- two-dot の誤用がどれくらい起きるかの資料は無い。事故（I-12・I-23）と EXP-24 の 1 回だけ
