## 1. 何をしているか（1 段落）

役割分離のハーネス（PO / Dev / QM / Platform / Audit）を、新しい案件で使い始めるまでの手間を小さくする「汎用の核＋案件アダプタ」に作り直し、その良し悪しを数字で判定できる評価基盤（pit-wall）で確かめている。発端は、会社でロール別のスキルをゼロから作り直すのに時間がかかったこと。

## 2. 何が分かったか

### 評価基盤について
- 最終状態（ファイル・git・gh の呼び出し・作業後の検査）で決定的に採点できる。台本の対照（何もしない / 部分解 / 参照解 / 改ざん / 近道）で、セルが作ったとおりに区分を出すことを、モデルを呼ぶ前に毎回確かめている
- 偽判定を走らせる前か後に 6 回止めた: Status 行の書き換えの扱い（試走前に許容を決めた）、ファイル権限で変わる fixture、エージェント定義の欠落、同じ長さの書き換えの欠落、書き足しと書き換えの区別、採点の定義とセルの不一致（GitHub への投稿を求めていた）
- 保留セル（設計者が中身を見ない）を、別のエージェントに作らせ、別のエージェントに確かめさせる工程が動いた

### ハーネスについて
- **設計者が手作りした、小さく 1 回きりの課題では**、ハーネスなしの単一セッションも規律を守った: 文書の裁定、レビュー役の境界、解けない課題でテストを曲げない（どれも天井）。[2026-11-02 訂正] これを「今のモデルはすでに規律を守る」と一般化するのは言い過ぎ。オーナーの指摘: 本当にそうなら、がんばりクエストで各ロールのスキルは作られなかったはず。課題を汎用化・抽象化しすぎて、スキルが必要になった実際の条件（長い作業、複数セッション、実際の製品の複雑さ、実際に起きた失敗）を落としている疑いが強い（前提 P3: 小さな手作りのセルが関心のある振る舞いを測っているか）
- **差が出たのは「案件の決まりごと」だけ**: 書いてあれば守る。大きなリポジトリでは、入口（CLAUDE.md）から指されていない決まりごとは取りこぼされうる（EXP-09）
- **役割をまたぐと、決まりごとが上書きされる**: 主が決まりごとを読む前に委任し、既定の作法（commit するな）を委任の指示文に書き、さらに組み込みの git の指示で聞き返して終わる（EXP-10〜14）
- **効いた対策**: ①委任先の定義に案件の事実を含まない核の 1 文（決まりごとを委任の言葉より優先して報告する）で 4/10 → 10/10（p = 0.011、EXP-12）②決まりごとを CLAUDE.md に取り込む（@import）で 0/10 の取りこぼし（EXP-14）
- **保留セル 1 回目（EXP-13）では、上書きそのものが起きなかった**（0/30）。開発セルの失敗が、そのセルの条件に引き出されていたことを示した

## 3. 何が分かっていないか

- **核の 1 文が、題材の違う案件でも効くか**（EXP-13・15）: 保留セル 2 回とも、1 文が効くべき条件（委任の言葉が決まりごとを上書きする）が起きなかった。commit を要求する陽性対照でも 0/5。「効かない」ではなく「効くべき場面が、題材を変えると起きにくい」。1 文ありで悪くなった組はない
- **開発セルで上書きを引き出していた要素**: EXP-14 で「どうすれば消えるか」（決まりごとの取り込み、組み込みの git の指示を外す）は分かったが、「何が起こすか」は特定できていない（保留セルの陽性対照で再現しなかった）
- **v1 が v0 より良いとは、まだ言い切れない**（EXP-16）: dev に委任する案件で v1 10/10、v0 7/10。差 +0.30（Newcombe 95% −0.04〜+0.60、Fisher p = 0.21）。委任なしは両方 10/10。v0 の失敗 3 回はすべて既知の仕組み（無条件の「commit するな」）で、v1 ではその仕組みが働かなかった。差を確かめるには各 20〜30 回が要る
- 入口（説明文で正しい役割が呼ばれるか）、受け渡しの多段、移植（2 つ目の案件にアダプタだけ差し替えて動くか）、アダプタを埋める手間
- 別のモデル・別の版の Claude Code で同じことが言えるか（すべて claude-sonnet-5-5、Claude Code 2.1.316）
- 長い作業での決まりごとの劣化（調査では主因とされる）
