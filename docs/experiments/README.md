# docs/experiments/ — 探索期の実験の一覧（EXP-01〜47）

この一覧は、2026-10-31〜11-12 の探索期に回した実験のレポート 46 本を、1 実験 1 行にまとめたものである。番号は EXP-01 から 47 まであり、EXP-03 だけレポートが無い。

結論を先に書く。この期間に示せたのは、主に 2 つである。1 つは、開発に使った課題の上では、指示の書き方（構造・届け方）が作業の順序や特定の失敗を変える、ということ。もう 1 つは、既定の Dev スキルを入れると、ハーネスなしのときより、決めた工程を踏む割合が上がる、ということである。一方、「ハーネスを入れると、開発に使っていない課題でも結果の害が減る」ことは示せなかった。そういう課題では、ハーネスが無くても害がほとんど起きず、差を測る余地が無かった。さらに、fix ロール（レビューの指摘を直す役）の主張は採点器の誤りで取り下げ、QM ロール（レビューと出荷判定の役）の主張の一部も、後の監査で弱まった。

主張のいまの状態は [主張の台帳](../claims.md) が正である。**レポートの本文と台帳が食い違うときは台帳に従う。** 食い違った箇所は、この一覧の「いまの扱い」の列と「失敗から得たもの」に書いた。また台帳は、全部の主張に次の但し書きを付けている。点検をしたのは被験体と同じ系統のモデルで、人による校正は無く、別系統のモデルによる点検はまだ行っていない。このため、ここに並ぶどの結果も「評価済み」とは呼ばない。

## この一覧で使う言葉

| 言葉 | 意味 |
|---|---|
| ハーネス | AI エージェントに渡す指示のまとまり（スキルの本文、役割の定義、案件の決まりごとの文書など） |
| arm | 比べる条件の 1 つ。同じ課題を、ハーネスだけ替えて走らせる |
| ハーネスなし（vanilla） | 課題の文書だけを渡し、役割のハーネスを入れない arm |
| GQ の写し（v0） | 別プロジェクト「がんばりクエスト」のロール別ハーネスを、そのまま写した arm |
| v1 | このリポジトリが最初に作った汎用の役割ハーネス |
| 既定のスキル（default） | このリポジトリが設計した、ロールごとのスキル（Dev・QM・fix） |
| セル | 評価用の課題 1 つ（小さなリポジトリと依頼文と検査の組） |
| 開発セル / 保留セル | 開発セルは、設計者が中身を見て、ハーネスを直すのにも使った課題。保留セルは、設計者と別の役が作り、設計者が中身を見ていない課題 |
| 台本の対照 | モデルを呼ばず、決まった操作の台本を課題に流して、採点が意図どおりに出るかを確かめる実行 |
| 天井 / 床 | 天井は、ハーネスなしでも全部うまくいく状態。床は、どの arm でも全部失敗する（または害が 1 度も起きない）状態。どちらも arm の差を測れない |
| ふるい | 本実験の前に、少ない回数で天井と床のセルを外す実行 |
| 害の述語 | 「越えてはいけない線を越えた」を終了時の状態から機械で判定する規則 |
| B share | 決めた工程の先行関係（開いてから直す、失敗を見てから直す、など）のうち、満たした割合。0〜1 |
| RAISES / REDUCES / NOT SHOWN | 実行前に決めた規則での判定の語。上げた / 減らした / 示せなかった。NOT SHOWN は「差が無い」という意味ではない |
| 取りこぼし | Dev の構造の実験で、変更計画やテストを書く前に実装を編集した試行 |
| 偽 gh | 評価用に作った、GitHub の CLI の代役 |

統計の語は原文のまま使う。Fisher は Fisher の正確確率検定（両側）の p 値、Newcombe は 2 つの割合の差の 95% 区間、Holm は複数の比較をしたときの補正である。

## 生の記録について

各実験の実行は `runs/<日付>/<名前>/` に 1 フォルダずつある（EXP-01〜27 の対応表は [runs/README.md](../../runs/README.md)。EXP-28 以降のフォルダ名は `exp<番号>-` で始まる）。フォルダに残っているのは次のものである（何を残し何を外したかの全体は [runs/README.md](../../runs/README.md) の冒頭）。

- `report.md`: その実行の集計
- `records.json`: 試行ごとの判定と、エージェントの最後のメッセージ（長さを切り詰めてある）
- 実行によっては、台本の対照の結果 `controls.md`、害の集計 `harm.json`、判定器の再判定 `judge-*.json`

セッションの全手順（道具の呼び出しの記録）と、終了時のファイルの中身は入っていない。生ログは 2026-11-19 に git から外した。したがって、**公開リポジトリだけからは採点し直せない。** 下の表の数字は、レポートと台帳に書かれた値を写したもので、この一覧を作るときに計算し直してはいない。

## 失敗から得たもの

何が起きて、どう見つけ、何を変えたかの順に書く。全体の整理は [evaluation-know-how.md](../guides/evaluation-know-how.md) と [33-evaluation-process-v2.md](../planning/33-evaluation-process-v2.md) にある。

**採点器と述語の誤り**

- **fix の採点器が、文章の答えを「未回答」と読んでいた（EXP-45・46）。** 採点器は、既定スキルが使う判定語があるかで「所見に答えたか」を読んでいた。ハーネスなしと GQ の写しは、文章で説明して実際に直していても未回答に数えられた。修理役が保存記録を全件当て直して見つけ、手読み 50 試行・109 所見で照合した。見出しの主張（RAISES × 2）を取り下げた。根拠: [EXP-45](EXP-20261112-45-fix-process-conformance.md) の末尾、`experiments/fix/grader-repair-2.md`、台帳 F-1・F-2。
- **修理した後も、同じ種類の読み違いが残っていた（EXP-47）。** 本実験の前に、監査役が試走の 120 試行を全部再生した。「扱いが違う」とされた 24 試行は、24 件とも採点器の読み違いだった。30 回の本実験を回す前に、数が arm の間で比べられないと分かった。これを受けて、正しさは終了時の状態から取り、文面の読みは「書いたか」に限る、という方針にした。根拠: [EXP-47](EXP-20261112-47-fix-reject-pilot.md)、`experiments/fix/audit-exp47.md`、台帳 F-6。
- **害の述語が、正当なテストの書き換えを「検査を弱めた」と数えていた（EXP-44）。** 述語は「受け取ったテストの行が消えたか」という文字の規則だった。監査役が実走の記録を読むと、立った 83 件のうち真の弱化は 1 件だった。述語を、欠陥のあるコードに当てて検出力が落ちたかで決める形に直した。ふるいの区分は床 4 → 床 1 に変わった。根拠: [EXP-44](EXP-20261111-44-fix-sieve.md) の末尾、`experiments/fix/harm-audit.md`。
- **台本の対照が通っても、実走では誤る。** 上の 3 つと、別の害の述語 2 つの誤検出を合わせて、2026-11-12 の 1 日に 4 回見つかった。台本は 1 つの書き方しか作れないのが原因である。本実験の前に、各 arm の実走の標本を、採点器を書いた役とは別の役が読んで照合する手順を入れた。根拠: 台帳 M-1、[32-status-summary-fix.md](../planning/32-status-summary-fix.md)、[docs/log/2026-11-12.md](../log/2026-11-12.md)。
- **Dev の採点にも、道具の出力の書式に依存する読み落としがあった（EXP-32・33）。** 2026-11-12 の監査で全記録を再計算して見つけた。GQ の写しの 50 試行のうち 11 試行が「やったのに認識されず」だった。保留セルでの対 GQ の写しは弱まり、対 v1 は不安定になった。レポートの本文には、この訂正は書かれていない。根拠: 台帳 D-4・D-5、`experiments/audit-2026-11-12/dev-grader-audit.md`。
- **採点の項目が、スキルの語彙そのものだった（EXP-32 ほか）。** 「根拠の表」の項目は、既定スキルの arm で 98/100、ほかの arm で 0/294 だった。スキルが「書け」と指示した物の有無を数えていただけで、比較として成り立たない。根拠: 台帳 D-9。
- **評価用の代役（偽 gh）の作りが、arm の差を作っていた（EXP-42・43）。** 偽 gh が、出荷用の PR の本文を返さず、知らない番号には架空の PR を返していた。「既定スキルだけが判定記録を開く」は成り立たず、対 GQ の写しの主張は大きく弱まった。根拠: 台帳 Q-3・Q-4・M-3、`experiments/audit-2026-11-12/qm-grader-audit.md`。
- **採点の定義がセルと合っていなかった（EXP-05）。** 「差し戻し」を GitHub への投稿として定義したが、依頼文は投稿を求めていなかった。記録を読んで、12 回すべてが返答で正しく指摘していたと分かった。点数は変えず、セルを作り直しにした。根拠: [EXP-05](EXP-20261101-05-p2-boundary.md)。
- **順序の測り方が、命令の書き方を拾い落としていた（EXP-19〜21）。** エージェントが 1 回の Bash に読み書きをまとめる形や、置換式に `;` を含む `sed -i` を数えていなかった。集計の後に記録と突き合わせて見つけ、保存記録から計算し直した。数は変わったが、判定は変わらなかった。その後、最終状態と記録が食い違うと集計せずに止まる検査を足した。この検査は EXP-27 で実際に集計を止めた。根拠: [EXP-20](EXP-20261102-20-structure-m-vs-f.md) の追記、[EXP-21](EXP-20261102-21-structure-volume-and-placement.md)、[EXP-27](EXP-20261103-27-d1-confirm-small-action.md)。
- **故障の判定が、エージェントの回復できる誤りを「実行環境の故障」に数えていた（EXP-19・20）。** 故障とした 11 試行の記録を全部読むと、実行環境の故障は 1 つも無かった。判定の種類を分け、保存記録から計算し直した。根拠: [EXP-20](EXP-20261102-20-structure-m-vs-f.md) の追記。
- **検出器の形の指定が狭すぎた（EXP-39・40）。** 「自明:」という書き方だけを数え、さらに「最初の実装の編集」を `.gitignore` への書き込みで誤って区切っていた。結果を見た後に直した値も並べたが、判定は直す前の値で行い、結論は変わらなかった。根拠: [EXP-39](EXP-20261104-39-design-rule-delivery.md)、[EXP-40](EXP-20261104-40-decision-point-list.md)。

**課題（セル）の作り**

- **手作りの小さなセルは、ハーネスなしでもうまくいってしまい、差を測れない。** 天井、床、または「防ぐべき失敗が起きない」という形で、EXP-06・07・08・13・15・24・30・31・37・38 と、fix の 20 セルで繰り返し起きた。開発セルで効いた 1 文（EXP-12）は、保留セルでは防ぐべき失敗そのものが起きず、効果を測れなかった（EXP-13・15）。この後の時期に、課題の出どころを実際の失敗に変える計画に進んだ。根拠: 台帳 M-4・D-10、[evaluation-know-how.md](../guides/evaluation-know-how.md) §4。
- **スキルの開発に使ったセルでの大きな差は、保留セルでは再現しなかった（EXP-29）。** 開発セルでは 8/40 対 37/40 だったが、保留セルではどの arm も 2〜5/40 だった。事前の規則が「保留セルで REDUCES のときだけ主張する」と決めていたので、主張は出していない。根拠: [EXP-29](EXP-20261103-29-harness-comparison.md)。
- **規定の書き方を比べたつもりが、規定が読まれていなかった（EXP-25）。** 事後に、工程のスキルを呼んだ回数を数えて分かった。次の実験（EXP-26・27）で、先に「届け方」をそろえた。また実行前には、スキルの例文に課題の答えが入っていたのを読み直しで見つけ、差し替えている。根拠: [EXP-25](EXP-20261102-25-rule-content.md)。
- **スキルの指示が実行環境で実行できない形だと、そのスキルの arm だけが壊れる（EXP-45）。** 状態ファイルを shell で書く操作が、権限の設定で拒否されていた。記録の故障の内訳から見つけ、スキルで道具を指定して、拒否は 91 試行から 0/360 になった。根拠: [EXP-46](EXP-20261112-46-fix-skill-r1.md)、台帳 F-4。
- **台本の対照が、課題の作りの不具合を本実行の前に止めた例もある。** EXP-24 では、実行環境の git の既定のブランチ名が手元と違っていた。解けない課題のセルの最初の対照では、課題の組み立ての不具合が 8/8 で検出された。根拠: [EXP-24](EXP-20261102-24-structure-other-incident-types.md) の追記、[runs/README.md](../../runs/README.md) の `integrity-controls-1`。
