# EXP-20261101-04 基準点 v0 を「そのまま」と「入口つき」の 2 つで測り直す（前提 P9）

ラベル: 探索

問い: 役割のエージェント定義が使える状態で、v0 はこの課題でどう振る舞うか。入口（`/dev`）を付けると何が変わるか
この問いに依存する決定: v1 との比較に使う基準点を、v0 そのものにするか、入口つきの v0 にするか（両方持つか）。v1 の差を「入口の効果」と「中身の効果」に分けられるか

設計: arm 2 つ × セル 3 つ（A3 / A4 / A9）× 2 回 = 12 回。実行器はエージェント定義を配置する版（commit 6875548）
- arm 1: `path:subjects/ganbari-quest-v0`（そのまま）
- arm 2: `path:subjects/ganbari-quest-v0@/dev`（Dev として入る。issue の解決は Dev の仕事と v0 の Dev スキルに書かれているため。役割の選び方は設計者の判断で、他の役割は試さない）

主仮説 H1: 入口を付けると Dev の手順が読み込まれ、振る舞いが変わる（記録の作り方・受信箱の操作・コミットや PR の作法のどれかに差が出る）。値の判断（中身）は両 arm とも天井
対立仮説:
- H2: 入口を付けても振る舞いは変わらない（Dev の手順はこの 1 回きりの課題に当てはまらず、モデルは自分の判断で解く）
- H3: 入口を付けると悪くなる（Dev の手順が受信箱・ラベル・PR を前提にしていて、存在しない仕組みを探して迷う、ターンを使い切る）
- H4（測定の作り物）: 差は出るが、差の原因は手順ではなく、指示文の先頭に `/dev` が付いたこと自体（文の長さ・形）である。この試験では H1 と区別できない（限界として書く）
- H5（偶然）: 各 6 回なので、1〜2 回の違いは偶然と区別できない

予想:
| 仮説 | 記録に出るもの |
|---|---|
| H1 | arm 2 の記録に Dev スキルの本文の展開があり、arm 1 と行動の形（ラベル操作、PR、手順の順序）が違う |
| H2 | 両 arm の行動の形が同じ（調べる → 直す → 記録） |
| H3 | arm 2 で `gh` のラベル・PR 操作の失敗、存在しない docs の参照、ターン上限での打ち切りが増える |

反証の条件: arm 2 の 6 回で、行動の形が arm 1 と区別できない（H2）なら H1 を捨てる
この試験が H1 を落とせる理由: 入口の展開は記録で確かめられる。展開されても行動が同じなら H1 は落ちる
使う方法と偏りの向き: 最終状態の採点（中身・書式）＋記録の読み込み（行動の形の比較、設計者）。行動の形の判定は設計者 1 人
止める規則: 12 回で終える。追加はしない
失敗したらどうするか: H3 なら、v0 は入口つきでもこの課題に合わないので、基準点は「そのまま」を主にし、入口つきは参考にする。H2 なら基準点は 1 つでよい

---（実行後）

結果（`runs/2026-11-01/exp04-v0-baseline`、12 回、故障 0、7 日枠の使用率 0.66）:
- 2 つの arm とも 6/6 が中身 `decided`、書式 0/6（総合 `not-recorded`）
- `/dev` の arm は 6/6 で Dev スキルの本文が展開された（セッション記録で確認）。そのまま の arm では展開 0、Skill・エージェントの呼び出しも 0（エージェント定義は今回使える状態）
- 行動の形は両 arm で同じ: issue を見る → 調べる → 直す（A3 は 60 に戻す、A4・A9 は 100 のまま）→ 独自の書式で判断記録を書く → A4・A9 では ADR の Status 行を Superseded にする。道具の呼び出しは 3〜4 回で、Dev の手順（受信箱・ラベル・PR・pre-ready）に沿った操作は 1 回もない
計画からのずれ: なし
妥当性: 構成概念 = 「行動の形」は設計者が道具の呼び出しと最終状態から読んだもの。内的 = 同じセル・同じ実行器。外的 = 3 セルとも 1 回きりの依頼。結論 = 各 6 回、形が完全に同じなので差はない
解釈:
- **H1（入口で振る舞いが変わる）は反証された。H2（変わらない）が残る**。Dev の本文は読み込まれたが、この 1 回きりの課題には当てはまらず、モデルは自分の判断で解いた
- H3（入口で悪くなる）も当たらなかった
- 基準点は「そのまま」1 つでよい（この課題では入口の有無で差が出ない）。ただしこれは「1 回きりの依頼」という課題の形のせいかもしれない。受信箱を介した受け渡しのセルでは別に確かめる [事後]
