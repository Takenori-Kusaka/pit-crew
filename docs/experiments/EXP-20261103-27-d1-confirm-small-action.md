# EXP-20261103-27 D1 を確かめ切る: 害の確認のやり直し、小さい依頼、処置の書き方

ラベル: 確認（主: t4 の害 D0 対 D1、EXP-26 とは独立のやり直し）、副（t5w の害、検出力が足りない）、探索（小さい依頼での過剰な手続き、処置の書き方）
前提: EXP-26（D1 で調査の工程を呼ぶ率が 3/15 → 14/15 など、規定が届き行動も変わった。害は t4 9/15 → 3/15、t5w 4/15 → 2/15 と減る向きだが、事前の規則では示せなかった）。オーナーの決定で既定のスキルは D1（20 §7）
問い:
- ① D1 は D0 より t4 の害（修正漏れ）を減らすか（独立のやり直しで）
- ② 小さい依頼（軌道 T0・T1）で、D1 は設計書 11 §2b の工程 × 軌道の表が「不要」とする手続きを増やすか
- ③ 土台を確かめた結果を表示させ、処置を同じ行に書くと、「確かめたが取り込まない」が減るか
この問いに依存する決定: 既定のスキルを D1 のままにするか、処置の書き方を第 4 版に採るか

## ① 確認のやり直し（主）

- arm: D0 = MskillG、D1 = MskillD1（= `subjects/dev-skill-default`）。EXP-26 と同じファイル
- 課題: t4-scatter-big-start（手数の上限 24）、t5-stale-base-weak（手数の上限 12）。EXP-26 と同じ digest
- 回数: 各 arm × 各課題 30 回（5 回ずつ 6 巡）。**EXP-26 の結果とは合算しない**（結果を見てから回数を足して合わせると、有意になるまで続けたのと同じ偏りが入るため）
- 回数の根拠（`experiments/structure/power.mjs`、模擬試行 4,000 回、Fisher 両側 α = 0.05）:
  - t4: EXP-26 の率（0.60 対 0.20）が真なら、各 30 回で示せる確率 0.87。ただし EXP-26 の差は偶然大きく出た分を含みうる。真の差が 0.40 対 0.20 なら 0.29
  - t5w: 0.27 対 0.13 なら各 30 回で 0.17。示すには各 100 回を大きく超える回数が要る
- **主の比較は t4 の D0 → D1 の 1 つだけ**（多重比較の調整は要らない）。「減らす」= Newcombe 95% の上限 < 0 かつ Fisher 両側 p < 0.05
- 副: t5w の D0 → D1（検出力が足りないことを明記し、率と区間を書く。判定しない）。届いたかの確認（調査の工程を呼んだ率、意味で探した、共通の関数、three-dot / merge-base、main の取り込み）
- 読み: 「減らす」→ D1 のままにする根拠が強まる。示せない → D1 で害が減るとは言えない（届け方としての D1 の根拠は EXP-26 の行動の変化だけになる）。D0・D1 とも 0/30 → 天井、27/30 以上 → 床

## ③ 処置の書き方（探索）

## 結果（2026-11-03、`runs/2026-11-03/exp27-*`、08:2x〜10:42。台本の対照 3 suite とも ok。Claude Code 2.1.316・同じイメージ。故障 1（D1A の t5w、エージェントがイメージに無いコマンドを使い tool-unavailable、事前の規則どおり除外））

### 集計の前の検査で止まったことと直し方（結果を見た後、必ず読む）

1. **測り方の検査が止めた**: s1（T0 誤字）の D1 の 5 回で、課題は解けているのに記録から実装の編集が見つからなかった。原因は「実装 = bin/・lib/ への書き込み」という定義で、s1 で直すのは README.md だった。記録の見落としではなく、この課題に合わない定義。`phase-metrics.mjs` に課題ごとの実装のファイル（`IMPL_FILES`、s1 は README.md）を足し、当たる例・当たらない例のテストを足した。直した後、EXP-20〜27 の全 run が検査を通った（他の課題の数え方は変わらない）
2. **害の述語の突き合わせが止めた**: t5w の 5 回で、作業ツリーの statement は直っているのに課題が落ちていた。記録を読むと、5 回とも作業ブランチの上で 4 か所を直したが、依頼の「main に merge する」をせずに終えていた。課題の検査は main の木で採点するので、判定（task-failed）は課題の定義どおり正しい。突き合わせの「作業ツリー = main」という仮定が誤りだった。直し方: 作業ツリーの statement が直っていて課題が落ちたものは「直したが merge していない」として別に数え、食い違いとして止めるのは「statement が切り上げのままなのに課題が通った」場合だけにした。下の表で、害を「古い土台の害」と「merge していない」に分けて示す。主の判定（t4）には影響しない
3. 作業ツリーに statement が無かった 1 回（xZsoZEb、D1）は手で読んだ: `git merge --ff-only main` が取り込めておらず、statement に一度も手を入れていない。古い土台の害。同じ試行は状態ファイルを外すために `.git/info/exclude` に書いていた（EXP-21 の副作用が D1 でも 1 回）
