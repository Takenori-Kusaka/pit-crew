## 主の量と判定（実行前に固定）

主の量: 工程の取りこぼし = 実装の編集が、変更計画（notes/<ID>.md）またはテスト（tests/）の作成より前に起きた試行（`phase-metrics.mjs` の skippedMemo または skippedTest）。2 課題を合わせた率

主の比較は 4 つ。差（後者 − 前者）の Newcombe 95% 区間と Fisher の正確確率（両側、`experiments/structure/diff.mjs`）。**多重比較は Holm で調整する**（4 つの p を小さい順に 0.05/4、0.05/3、0.05/2、0.05 と比べる）

| # | 比較 | 答える問い |
|---|---|---|
| a | F 対 Mall | 量をそろえても構造で差が出るか |
| b | M 対 Mall | 構造をそろえても量（読み方）で差が出るか |
| c | M 対 H | 工程の判定の置き場所（H2） |
| d | M 対 M-skill | 工程の中身の置き場所（H3） |

- 「差がある」: Newcombe の区間が 0 をまたがず、かつ Holm で調整して有意
- 「差は確かめられない」: それ以外。**同等とは言わない**（各 20 回で区間の幅は ±0.2〜0.3 ある）

①の読み方（a と b の組み合わせ。事前に固定）:

| a（F 対 Mall） | b（M 対 Mall） | 読み |
|---|---|---|
| 差あり（Mall が少ない） | 差なし | 構造（案内）が効いている。量の寄与は確かめられない |
| 差なし | 差あり（M が少ない） | 必要なときに読むこと（量・読む動作）が効いている |
| 差あり | 差あり | 両方が効いている |
| 差なし | 差なし | 分けられない（Mall が中間、または検出力が足りない） |

- 注意（事前に書く）: Mall 対 M は「常時読む量」と「工程に入るときにファイルを読む動作（それ自体が区切りになりうる）」を同時に変える。この 2 つはこの実験では分けられない
- 天井: M・Mall・H・M-skill がすべて取りこぼし 0〜1 なら、c・d は「天井で比べられない」と書く。EXP-20 で M は 1/20 なので、c・d は H・M-skill が M より**悪い**場合にしか差を検出できない

副の量: 全部守った率（最終状態）、文脈の最大、工程の中身を読んだ回数（M-skill はスキルを呼んだ回数）、軌道の判定（記録の「軌道 T?」）、課題ごとの取りこぼし、EXP-20 と合わせた M 対 F

### 測り方の不具合と直し方（結果を見た後の変更。必ず先に読む）

集計の台本（commit 6d99b0e）で集計したあと、取りこぼしの判定を試行の記録で確かめたところ、`phase-metrics.mjs` の測り方に 2 つの不具合があった。
- 実装の編集の見落とし: 置換式の中に `;` がある `sed -i`（例: `sed -i 's|^total() .*|total() { echo $(( $1 * 110 / 100 )); }|' lib/sum_total.sh`）を実装と数えていなかった。t2 の修正の大半がこの形で、EXP-21 の Sonnet 100 回のうち 15 回で実装が「無し」になっていた。実装が無いと取りこぼしにならないので、**取りこぼしを少なく数える向き**の誤り。EXP-20 でも 40 回中 4 回あった
- テストの書き込みの見落とし: `sed -i '/^exit/e cat /tmp/l' tests/price_test.sh` のようにテストを書き足すと、テストが「無し」になり、**取りこぼしを多く数える向き**の誤り（M の 1 回）

直し方: ヒアドキュメントの本文と、引用符の中（パスだけの引用は残す）を伏せてから照合し、`sed -i`・`perl -i` の書き込みを置き場所（bin・lib / tests / notes）で数える。6 通りの命令の形で確かめた。**直した後、Sonnet の 100 回 + 入り方 30 回 + EXP-20 の 40 回のすべてで、変更計画・テスト・実装の 3 つが見つかる**（Haiku の「無し」は課題を解かなかった 4 回だけ）。直したのは測り方だけで、判定の規則・比較・回数は変えていない。事前に固定した測り方での結果も下に並べる

- **① の読み（事前の表）: a が差あり・b が差なし → 「構造（案内）が効いている。量の寄与は確かめられない」**。常時読む量を F とそろえた Mall で取りこぼしは 0/20（t1 0/10・t2 0/10）。F と Mall の差は課題ごとでも出た（t1 −0.80、−0.94〜−0.38、p = 0.0007 ／ t2 −0.70、−0.89〜−0.29、p = 0.003）
- 「構造」の中身は、この実験では分けられない。Mall と F の違いは、(1) 状態ファイルで工程を決める案内 (2) 入る / 出る条件を先頭にまとめて置く (3) 工程の中身を工程ごとにまとめる（F は段を 1 列の通し番号にする）(4) F の「工程 1 から順に進める。どの工程も飛ばさない」の 1 文、の 4 つを同時に含む
- c は向きとしては H が悪い（t1 で 1/10 対 6/10、t2 で 2/10 対 4/10）が、事前の規則（Holm）では差を示せていない
- d・b: M-skill と Mall はどちらも 0/20、M は 3/20。M の 3 回はどれも「修正の後に変更計画を書いた」型で、M が工程ファイルを読む動作とは関係が見えない。差は確かめられない
- **最終状態の差は無い**（全 arm で 19〜20/20 が全部守った）。差は EXP-20 と同じく、変更計画を実装の前に書くかという**順序**
- 全部守らなかった 2 回（M・Mall の t2 各 1）は、どちらも状態ファイル `.dev-state.md` を commit から外そうとして `.git/info/exclude` に書き込み、Claude Code の権限で拒まれ（harness-denied）、commit が残らなかった。**状態ファイルという仕組みの副作用**で、M 型の構造に固有の費用である（F・H には状態ファイルの案内が無い）
- 文脈の最大: Mall は F と同じ約 7 万、M・H・M-skill は約 4 万
