# ハーネスキットの使い方 — 新しいロールを半日で設計・半日でテストする

対象: 営業・企画・外部監査など、新しいロールのハーネスを足す人。キットの部品は `kit/` と `packages/pit-wall/src/kit/` にある。
進み具合の確かめ方: `node scripts/kit-check.mjs`。

## 考え方（3 行）

1. ロールの手順は、ハーネスの文面ではなく**ロールの決定権と開発プロセス**から、データ（`kit/roles/<role>.yaml`）として書く。
2. 採点器（`grader.mjs`）は手順の定義と、記録（transcript）・終了状態だけを読み、ハーネスを読まない。だからどのハーネスにも同じ採点器を使える。
3. ケースは手順の定義から自動で作る。手で書くのは「環境の部品」（小さなリポジトリと依頼）だけ。

## 半日で設計（目安 4 時間）

| 手順 | すること | 目安 |
|---|---|---|
| 1 | 出どころを決める。RACI でそのロールが A（決める）・R（実行する）の作業と、A でも R でもない作業を書き出す（`decision_rights`）。**RACI にそのロールの列が無いとき**は、役割の説明・任命の基準・受け渡しの規則など最も近い記述を出どころにし、決定権の欄の推測した箇所に `# 推測` と書く。既存のロールと名前が近いときは、下の「既存のロールとピットインの席」で別の席かを確かめる | 30 分 |
| 2 | `kit/templates/role-spec.yaml` を写し、**必要な行為**（`actions` + `procedure.required`）を書く。行為は「記録に残るもの」（コマンド・編集・gh の操作）に限る | 60 分 |
| 3 | **順序**（`order`、前後の組）と、どれか 1 つでよい行為（`any_of`）を書く | 15 分 |
| 4 | **禁止の行為**（`forbidden`）を書く。A でも R でもない作業がそのまま候補になる。各項目に、それをしたくなる一言（`lure`）を付ける | 45 分 |
| 5 | **上げるべき判断**（`escalations`）を書く。上げる先、上げたと見なす行為（`detect_escalated`）、その場面を作る一言（`prompt_variant`） | 45 分 |
| 6 | 各行為に正しくこなす例（`example`）を付ける。参照の台本はここから作られる。gh の操作を状態（`gh:` 述語）で検出する行為は、例にも `gh: [issue_comment]` のように効果を書く（書かないと参照の台本の状態に効果が入らず、正しい台本が fail する） | 30 分 |
| 7 | 検証: `node scripts/kit-check.mjs --spec kit/roles/<role>.yaml` が ok（必須の欄・行為の id の参照・出どころにハーネスが無いこと） | 15 分 |

書き方の決まりと検出の語彙は `kit/schema/role-spec.md`。記入例は `kit/templates/role-spec.example.yaml` と、`kit/roles/` の 6 ロール（dev / po / qm / platform / audit / fix）。
値に「: 」を含むときは `' '` で囲む（YAML の決まり。何度か誤った）。

### 新しいロールが既存のロールと同じ席になったとき

出どころをたどって既存のロールと同じ席になったら（例: 企画書の起案は価値責任者の作業で、po と同じ席）、別のロールとして書いてよい。席が同じでも、作業（扱う依頼・成果物・上げる判断）が違えば別の手順の定義になる。そのときは、定義の冒頭の注に「既存の <role> と同じ席。作業は <違い>」と書き、Δ の「あり」の側にその席のハーネスを使って、作業がずれることを time.json の notes に書く。作業まで同じなら、新しいロールは作らず既存の定義に足す。

### 環境の部品の規則のファイル

依頼文で「決まりどおりに」と書くなら、その決まりがエージェントから読める場所に要る。ハーネスなしの側にも同じ条件で見せたい規則（プロセスの規則・ラベルの意味など）は、部品の `files/` に置く（例: `files/docs/process.md`）。ハーネスにしか無い規則は置かない（置くと、ハーネスなしとの差が消える）。

### キットの中を読む必要があるとき

案内と schema で足りないときに読むのは次の 2 つだけでよい。`packages/pit-wall/src/kit/gen-cases.mjs`（ケースと台本の対照の作り方。`ok` の条件）、`packages/pit-wall/src/kit/grader.mjs`（検出の述語の解釈）。

## 半日でテスト（目安 4 時間）

| 手順 | すること | 目安 |
|---|---|---|
| 1 | 環境の部品 `kit/fixtures/<role>-basic/` を作る: `files/`（小さなリポジトリ）、`fixture.yaml`（依頼文 `prompt`、issue か `github_cache`、`task` の値、`tools`）。欄の書き方は `kit/schema/role-spec.md` の「環境の部品」。既存の部品（カートの JS）を流用すると早い | 90 分 |
| 2 | ケースを作る: `node packages/pit-wall/src/kit/gen-cases.mjs kit/roles/<role>.yaml kit/fixtures/<role>-basic kit/cases/<role> --result kit/results/<role>/gen-run.json` | 5 分 |
| 3 | 台本の対照を見る: gen-cases が最後に `ok` を出せば合格。`ok` の条件は、通常と誘いのケースで reference（正しくこなす台本）が pass、上げる判断のケースでも reference が pass（上げる判断の行だけで採点する）、全ケースで null（何もしない台本）の準拠が 0。`ok` でなければ手順 1 か設計の手順 6 に戻る。あわせて `kit/cases/<role>/evals/*/prompt.md` を目で読み、依頼文と部品の記録が食い違っていないか（例: 依頼文で名乗らせた人と、記録の判定者が同じになっていないか）を確かめる。gen-cases は文面の整合を見ない | 30 分 |
| 4 | `node packages/pit-wall/src/gates.mjs no-gq-content` が ok（題材のリポジトリの写しが混じっていない） | 5 分 |
| 5 | Δ を 1 回取る（WSL）: `bash kit/run-delta-wsl.sh <role> <harness dir> /<entry> 1`。ハーネスあり・なしの準拠の差が `kit/results/<role>/delta.json` に出る。「あり」の側は、そのロールのために書いたハーネス。無ければ最も近い席のハーネス（下の表）を使い、席がずれることを time.json の notes に書く | 60〜90 分（待ち） |
| 6 | かかった時間を `kit/results/<role>/time.json` に書き、コミット。欄は `role`・`design_hours`・`test_hours`（数値、時間）・`who`（だれがかけた時間か。人か AI か）・`notes`（「あり」の側の選び方、半日を超えた理由など）。新しいロールは、`kit/roles/` と `kit/fixtures/<role>-basic/` を置けば CI（kit.yml）のケース生成と植え込んだ誤りの検査に自動で入る。`scripts/kit-check.mjs` のマイルストーンは goal ごとの固定の一覧なので、新しいロールの検証は `--spec` で行う | 10 分 |

CI（`.github/workflows/kit.yml`）が採点器の自己テストと、全ロールのケース生成を毎回回す。

## Δ の読み方

- `conformance` は必要な行為・順序・禁止・上げる判断のうち満たした割合。`violations` は禁止の行為の数。
- 1 ケース 1 試行の記述にとどめる（強いモデル・少数試行。統計の主張には使わない）。
- 差が 0 のときは、ハーネスが手順を変えていないか、ケースが差を出せない作りかのどちらか。`delta.json` の `items[].events` と最後の発言を見て分ける。

## 6 ロールの Δ（2026-11-14、Opus 5.5、各ケース 1 試行。記述であり、優劣の主張ではない）

| ロール | ハーネス（あり の側） | ケース | 準拠 あり / なし | Δ | 違反 あり / なし |
|---|---|---|---|---|---|
| Dev | `subjects/dev-skill-default` | 9 | 0.889 / 0.869 | +0.020 | 23 / 7 |
| QM | `subjects/qm-skill-default` | 5 | 0.929 / 0.958 | −0.030 | 5 / 7 |
| fix | `subjects/fix-skill-default` | 5 | 0.588 / 0.804 | −0.216 | 13 / 10 |
| PO | GQ v0 の `/po` | 5 | 0.583 / 0.333 | +0.250 | 0 / 1 |
| Platform | GQ v0 の `/platform` | 4 | 0.333 / 0.833 | −0.500 | 0 / 2 |
| Audit | GQ v0 の `/audit` | 5 | 0.750 / 0.750 | 0.000 | 6 / 6 |

Platform の −0.500 は、ハーネスの決まりと手順の定義が食い違うことを示している。GQ の Platform には「検査を増やすことは今止めている」という決まりがあり、ハーネスありのエージェントは検査を足す依頼を実装せず、`status:on-hold` に戻した（4 ケース中 4）。手順の定義はピットインの 3.11.8（検査の追加は AI 維持管理者が A）から書いたので、これは準拠が低いと数えられる。どちらが正しいかは、採点器ではなくプロセスの持ち主が決めることである。キットはこの食い違いを見つけるところまでを受け持つ。

キットの目的（どのロールにも同じ仕組みでテストを作れること）に対しては、6 ロールすべてで「手順の定義 → ケース → 1 回の Δ」が同じ手順で通った、というのが結果である。数値の差は、下の限界のため読み込みすぎない。

## 採点し直し（2026-11-14、モデルを呼ばずに保存済みの記録で）

採点器と手順の定義の数え誤りを直し、`node packages/pit-wall/src/kit/regrade.mjs` で 6 ロールの保存済みの記録（`kit/results/<role>/delta.runs.jsonl`）を採点し直した。結果は `kit/results/regrade.json`。回帰テストは `packages/pit-wall/test/kit-regrade.test.mjs`（保存済みの記録そのものを読む）。

直したこと:
- 上げるべき判断のケースは、上げる判断の行だけで採点する（必要な行為の数で割らない）。直す前は、このケースを Δ の準拠から外していた。直した後は 0 か 1 で準拠に入る
- 正規表現の `.` が改行にも当たる（`s` 旗）。複数行の本文の gh コメントを数え落としていた（fix の回答、QM の差し戻し）
- Dev の秘密情報の読み取りは、ファイルの中身を読む命令に限る（`process.env` や `git log -- .env` を数えていた）
- Dev のテストの書き換えは、既存の assert / expect を減らす編集に限る（新しい述語 `removes`）。ただし保存済みの記録には編集の文面が無いので、今回の採点し直しでは数え方は変わらない（文面が無いときは数える）。これからの実行は文面を残す
- fix の部品が「指摘が仕様と食い違う」の旗を全ケースに立てていた。上げる判断のケースだけに立つよう直した

| ロール | 準拠 あり（前 → 後） | 準拠 なし（前 → 後） | Δ（前 → 後） | 違反 あり / なし（前 → 後） |
|---|---|---|---|---|
| Dev | 0.889 → 0.691 | 0.869 → 0.676 | +0.020 → +0.015 | 23/7 → 22/7 |
| PO | 0.583 → 0.667 | 0.333 → 0.267 | +0.250 → +0.400 | 0/1 → 0/1 |
| QM | 0.929 → 0.743 | 0.958 → 0.967 | −0.030 → −0.224 | 5/7 → 3/4 |
| Platform | 0.333 → 0.500 | 0.833 → 0.625 | −0.500 → −0.125 | 0/2 → 0/2 |
| Audit | 0.750 → 0.600 | 0.750 → 0.650 | 0.000 → −0.050 | 6/6 → 6/6 |
| fix | 0.588 → 0.750 | 0.804 → 0.643 | −0.216 → +0.107 | 13/10 → 8/6 |

読み方: 直す前と後では、上げる判断のケースを準拠に入れたかどうかも変わっているので、差は 2 つの変更の合計である（ケースごとの内訳は regrade.json の `changed`）。Dev の準拠が下がったのは、上げる判断の 2 ケースで両方の条件とも上げなかった（0 点）ため。fix の Δ の符号が変わったのは、ハーネスありの回答（複数行の対応表）を数え落としていたのが直ったため。数え方を直すだけで Δ の符号が 2 ロールで変わることは、1 試行の Δ を読み込みすぎない理由の 1 つである。

## 半日に収まるかの検証（2026-11-14、文脈のない別のエージェントで 2 回）

この案内とそこから参照されるファイルだけを渡した別のエージェントに、新しいロールを作らせた。記録は `kit/results/<role>/onboarding-log.md`、1 回目の詰まりへの対応は `kit/results/ext-audit/blockers-resolution.md`。

| 回 | ロール | 設計 / テスト（エージェントの時間） | 詰まった所 | うち案内の不足 | Δ（あり / なし、各 1 回） |
|---|---|---|---|---|---|
| 1 | 外部監査 `ext-audit`（監査担当、内部監査） | 合わせて約 4 分 | 12 | 10 | 0.726 / 0.683（+0.043。今の定義で採点し直すと +0.076） |
| 2 | 企画 `planning`（企画書の起案。価値責任者と同じ席） | 約 2 分 / 約 2 分 | 12 | 7 | 0.932 / 0.861（+0.071。「あり」は近い席の GQ v0 `/po`） |

分かったこと:
- 1 回目の後に案内を直したので、案内の不足による詰まりは 10 件から 7 件に減った。残りの 5 件（出どころのプロセス文書に席が無い、検出の語彙で文面の規則を書けない、など）は案内を直しても解けない
- 2 回とも、出どころのプロセス文書にそのロールの席が無かった（「外部監査」「企画」という名の席は無い）。新しいロールを足すときは、まず出どころ探しに時間がかかる。導入役の見立てでは、人なら 1〜2 時間（推測）
- 文書を書くロール（企画）の肝の規則（AI が作った顧客の声を観測に数えない、など）は、書いた文面に当てる述語が無いので禁止に書けない。採点できるのは手続き（読んだか、上げたか、渡し先）だけである
- **エージェントの時間は人の半日の裏付けにならない**。人が初めて使ったときの時間は、まだ測っていない

## 植え込んだ誤りで採点器を確かめる

`node packages/pit-wall/src/kit/perturb.mjs`（自己テストは `packages/pit-wall/test/kit-perturb.test.mjs`、CI で回る）は、各ロールの通常のケースの正しくこなす台本に、誤りを 1 つずつ植え込む: 禁止の行為を足す、必要な行為を抜く、順序の組を入れ替える。採点器はそれぞれを検出し、元の台本は pass しなければならない。人の判定もモデルも使わない。

新しいロールを足したら、テスト手順 3 のあとにこれを回す。植え込みの台本は、禁止の行為の検出（`gh`・`changed`・`path` など）から自動で作る。命令の正規表現だけで書いた禁止は自動で作れないので、その禁止には `example` を付ける。

最初に回したとき（2026-11-14、7 ロール）、採点器が見逃した植え込みが 4 件あった。どれも、ある行為の検出が別の行為の文面に当たっていた（fix のコメントの本文の「npm test 通過」を、テストを走らせたと数えた。PO の未確定の印の grep を、仕様を読んだと数えた。外部監査の所見の本文の `records/` を、記録を開いたと数えた）。検出を、命令の先頭や読む命令に限るよう直した。保存済みの記録の採点は、この修正では変わらなかった。

## 測れなかったこと（限界）

測り方の問題のうち、上の「採点し直し」で直したもの以外は、直さずにここに書いて進めた。

1. ~~上げるべき判断のケースは、正しい台本でも準拠が低い~~ → 「採点し直し」で直した。上げる判断の行だけで採点する。
2. **ハーネスが書く作業ファイルが範囲外の編集として数えられる**（Dev の既定のスキルが `.dev-state.md` と `.gitignore` を書く）。範囲（`task.scope`）にハーネス固有のファイルを足すと、採点器がハーネスに依存してしまうので足していない。
3. **`claude plugin eval` の砂場では `git commit` が失敗することがある**（`.git` が読み取り専用に見えた）。「戻す」行為はハーネスあり・なしの両方で達成できない場合がある。
4. **Dev の「テストを変える必要がある」ケースの部品は、既存のテストと実際には矛盾していない**。上げる場面として弱い。
5. **gh の操作は代役（shim）が答えるだけで、効果は実行したコマンドから推定している**。コマンドの書き方が想定外だと見落とす。
6. **時間の記録はエージェントのもので、人がかけた時間ではない**。文脈のない別のエージェントで 2 回確かめた（設計・テストとも数分）が、読む速さも、出どころの文書を探す手間も人とは違う。人が初めて使うときの半日は、まだ測っていない。
7. **各ロール 1 ケース 1 試行**なので、Δ は偶然の揺れと区別できない。
8. **採点器の妥当性は、植え込んだ誤りの検出（機械的な検査）までしか確かめていない**。植え込みは手順の定義の検出から作るので、定義の検出そのものが的外れ（そもそも違う行為に当てている）な場合は見つけられない。実際のエージェントの書き方で当たるかは、保存済みの記録の回帰テストでいくつか確かめただけである。
9. **検出は正規表現なので、数えすぎ・数え落としが残る**。植え込んだ誤りの検査で、ある行為の検出が別の行為の文面に当たる型を 4 件見つけて直した。観測した 3 つ（fix の回答、Dev の秘密情報の読み取り、Dev のテストの書き換え）は「採点し直し」で直したが、ほかの書き方（`--body-file` で本文をファイルから投稿する、別名の命令で読む）は数え落とす。テストの書き換えは、編集の文面が記録に無い Write（全体の上書き）では、足しただけか減らしたかを見分けられないので数える。
10. **文書を書くロールの中身の規則は採点できない**（企画で分かった）。書いた文面に当てる述語が無く、gh のラベルの効果も名前を持たない。採点できるのは手続き（読んだか、上げたか、どこへ渡したか）だけである。
11. **新しいロールの出どころが、プロセス文書に無いことが多い**。2 回とも、その名の席は無く、最も近い記述と推測で決定権を書いた。採点器は定義どおりに数えるので、定義の推測が誤っていれば評価も誤る。

## 公開の前提

`kit/results/publish-precheck.json`（goal 2 では `publish-precheck-2.json`）に、CI が緑・秘密情報の検査 0 件・識別子の検査 0 件を記録してから、オーナーに承認を求める（`approval-request.md` / `approval-request-2.md`）。公開の push はオーナーの承認のあとに限る。
