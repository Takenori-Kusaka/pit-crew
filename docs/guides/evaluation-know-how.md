# エージェントのハーネスを評価するときのノウハウ（第 1 版、成果物 2.3）

この文書は、pit-crew が 2026-10-31〜11-13 に実際に誤り、見つけ、直したことから書いた。一般論ではなく、ここで起きたことに出典（ファイルと行）を付ける。主張の状態は `docs/claims.md` が正、進め方の正は `docs/planning/33-evaluation-process-v2.md`。

**この文書が言わないこと**: 「この手順に従えば評価は正しい」とは言わない。進め方 v2 はまだ 1 つのロールも端から端まで通っていない。通った後に、門が実際に何を止めたかを足して第 2 版にする。

## 1. 数を使う前に、計器を受け入れ検査する

**起きたこと**: 1 日（11-12）に採点器と害の述語の誤りが 4 回見つかった。どれも、台本の対照（両方向）は通っていた。

| 誤り | 台本で見えなかった理由 | 見つけた方法 |
|---|---|---|
| 害の述語 H2（検査の弱化）が 82/83 で誤検出 | 台本は「行を消す」形でしか弱化を作らなかった。モデルは assertion を同値の形に書き換えた | 監査役が実走の記録を全件読んだ（`experiments/fix/harm-audit.md`） |
| H7・H4 が語だけで判定 | 台本の文は判定語を使っていた | 同上（`harm-audit-exp45.md`） |
| 「所見に答えたか」を既定スキルの判定語で読んでいた | 台本は表で答えた。モデルは文章で答えた | 修理役が保存記録を全件当て直した（`grader-repair-2.md`）。見出しの主張を取り下げた |
| 修理後も、文章の答えを読み違えた（24/24） | 修理の検査は、修理役が思いついた書き方だけだった | 本実験の前の試走で、監査役が 120 試行を全部再生した（`audit-exp47.md`） |

**教訓**:
- 採点器・述語・代役は、**被験体の実走の記録で**照合するまで「未検証の計器」として扱う。台本の対照は 1 つの書き方しか作れない（`research-practice-gap.md` §0 の 4）
- 照合は、計器を書いた人と別の役が、**arm ごとに同じ数**の標本で行う。読み違いが arm の間で偏ることが、最も害が大きい（決まった形で答えさせるハーネスほど正しく読まれる）
- 監査役そのものの精度も測る（黙って既知の誤りを混ぜ、検出率を出す）。同じ系統のモデルどうしでは、誤りが相関しうる（`research-next-steps-small-n.md` 要点 5）

## 2. 「何をしたか」は文面ではなく、行為と終了状態から読む

- 返信の文面から行為を読む採点は、ハーネスの指示の文面と採点の基準が同じ文になりやすい。差は「指示されたから書いた」だけになる（`research-process-evidence-evaluation.md:15`、Dev の根拠の表の比較は成り立たなかった: `claims.md` D-9）
- 採点の項目ごとに、読むものを **T（道具の呼び出しの事実）/ S（終了状態）/ W（文面）** で宣言する。W は「書いたか」だけに使い、正しさと主な量に使わない（進め方 v2 の G2）
- それでも、道具の出力の書式や呼び出しの粒度に依る読み落としは残る（1 回のコマンドで失敗→修正→成功をまとめると認識されない: `dev-grader-audit.md`）。形の不変性の対照は、試走に実際に出た形から機械で数えて作る

## 3. 評価用の代役（偽の gh など）も計器である

- QM の評価では、偽の gh が全フィールドを返す・未知の番号に架空の PR を返す・裏のファイルが作業木から読める、の作りが、arm の間の差を作っていた（`qm-grader-audit.md`、`claims.md` Q-3・Q-4）
- 代役は、実物の記録済みの出力と突き合わせる test を、**エージェントが走る image の中で**回す。記録に無い問いには答えを作らず、明示の失敗を返して数える（進め方 v2 の G4）

## 4. 課題は、強いモデルが落ちうるものから作る

- 手作りの小さな 1 回きりの課題は、ハーネスなしでも天井になった（fix の 20 セル、`claims.md` M-4）。天井はモデルの性質ではなく、セルの性質（`research-ecological-validity.md` 要点 6）
- 弱いモデルを強いモデルの代わりにする先例は見つからなかった（`research-practice-gap.md` §3.3）。弱いモデルの実行は、環境の確認にだけ使う（オーナー 11-12）
- 先例に沿う課題の出どころ: 実際の失敗（issue と修正 PR の組）、実際の記録の切り出し、散らかり度の条件（METR の 16 項目）。EXP-48 は GQ の公開履歴から機械のふるいで作った（725 → 19 件、`experiments/exp48/task-author-report.md`）
- 実際の失敗にも偏りがある。GQ では 19 件中 18 件の issue が直すファイルを名指ししており、「調査」の工程に余地が少ない。主張の範囲に書く

## 5. 少ない課題・少ない試行で言えること

- 検出できる最小の差は課題数で決まる。試行を増やしても、課題 × 条件の交互作用の床が残る（10 課題 × 3 試行で標準偏差の 0.5〜0.8 倍: `research-graded-quality.md` §D）
- この規模では「差は無い」は言えない。「上げる」は区間の下限 > 0 かつ追う差の下限以上、それ以外は「この範囲では決められない」と書いて止まる（`34-review-g5.md` §5.4）
- 結果を見た後に課題を足さない。足すなら規則を先に書く（EXP-48 はオーナーの決定で 1 回だけ）

## 6. 役を分け、独立は物で守る

- 「設計者はセルを読まない」と決めたとき、読む役を誰にも割り当てなかったことが、11-12 の誤りの根にあった（`research-practice-gap.md` §0 の 3(a)）
- 独立は申告では守れない。条件 B の文書の書き手が、読んではいけない採点項目を誤って表示した（11-13）。隔離したフォルダで書き直させ、2 つの版を比べた（出どころの重なり Jaccard 0.33。同じ指示でも書き手で選び方が違う: `experiments/exp48/arm-b-v1-not-used/README.md`）
- 導き直し役が 3 分で終えたとき、一致を信用しなかった（`docs/log/2026-11-12.md`）。作業の時間と道具の呼び出しの記録も、独立の証拠として見る

## 7. 調査の結論が、次の計画を縛るようにする

- 調査の勧告 329 行のうち、fix の段で守られたのは 15%。残ったのは手続き（先に固定・途中で見ない）、落ちたのは測定の妥当性の点検（`research-practice-gap.md` §1）
- 計画は前の計画から写さず、調査の行を「採る / 落とす（理由）/ 食い違う行を探した結果」で埋めた点検表を付け、書いた本人と別の役が査読する（進め方 v2 の G5）
- 方針に関わる同意・提案にも、照合した調査の行を付ける。オーナーの発言に照合せず同意し、指摘されて訂正したことがある（`docs/planning/00-owner-statements.md` 11-12 の訂正）

## 8. 計算資源も事前に見積もる

- 候補ごとに docker の image を作って C: を満杯にし、WSL が起動しなくなった（11-13）。仮想ディスクの置き場（C:）を確かめていなかった。image は作る → 確かめる → 消すを 1 件ずつ、空きの下限で止まる検査を build の台本に入れた（`experiments/exp48/README.md` のディスク予算）
- ホストのメモリ不足で、検証の台本が止められた。待機している補助のエージェントの数もメモリを使う。終わったものは止める
- 進め方 v2 の G4 の点検項目に、ディスクとメモリの見積もりと置き場の確認を足す（未反映）

## 9. 誤りと訂正を消さない

- 取り下げた主張も、訂正の履歴と一緒に台帳に残す（`docs/claims.md`）。前の数と後の数を並べ、どう誤りと分かったかを書く
- 公開物は台帳から書き、台帳に無い主張を書かない
