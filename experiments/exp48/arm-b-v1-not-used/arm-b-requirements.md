# この作業で満たす要求

この案件で変更を仕上げて渡すときに満たしていなければならない要求です。各項目は互いに独立しており、並び順に意味はありません。

## 完了の条件（渡すときに成り立っていること）

1. 完了とは、完了の条件を満たし、それを実物で確かめた状態（証拠つき）であり、チケットを閉じたこと・PR を出したこと・CI が緑なことは完了ではない。
2. 完了の暫定の定義が 1 文で、観測できる形（何をすると何が見えるか）で書かれている。
3. 依頼が「誰の、どんな問題を、何が観測できたら解決とするか」の 1〜3 文に言い直され、変更の目的が書かれている。
4. 変更のリスクの判定（自明 T0 / 通常 T1 / 危険 T2）と理由が 1 行で残っており、不具合修正は T1 以上、認証・認可・個人データ・課金と金額の計算・外に公開した挙動・新しい公開インターフェース・戻せない操作・複数モジュールにまたがる変更・同じ箇所の事故や再発の履歴のどれかに当たれば T2 とし、軸ごとに割れたらいちばん重い軸に合わせ、迷ったら上にしてある。
5. 手順や成果物を省いたときは、何を省いたかと理由が 1 行で残っている。
6. 戻せない操作（データの削除・課金・本番への反映・データの形の変更）の有無と、ある場合の承認の経路が書かれている。
7. 進め方（直列か並列か、分けるか）が記録されている。
8. 作業の土台（作業ツリーの HEAD・base の HEAD・その間の merge-base）が記録され、作業する branch が base の今の先端を含んでいる。
9. 変える箇所（ファイル・関数）をすべて名指しした変更計画が、外（PR 本文・計画ファイル・案件の決めた場所）に書かれている。
10. 変更計画は、①言い直した依頼と完了の定義 ②変える箇所の名指しと影響の検索結果（件数と場所）③観測の証拠（不具合なら再現の失敗、挙動を変えるならいまの挙動）④残った問いと振り分け・仮定、の 3〜4 項目を含む。
11. 変える箇所と、その呼び出し元を開いて読んでいる。
12. 影響の検索の件数と場所が残っており、名前の変更・API の廃止・データの形の変更・用語の根本変更・層の境界の変更・撤去・50 ファイル超などの変更では、構文・意味・構造・派生物（文書・設定・データ・画面文言・外部サービス・監視）の 4 層で確かめてある。
13. 不具合なら、症状が見える層で再現するテストが修正前に失敗することが確かめられている。
14. 退行や修正漏れの候補（同じ型の箇所、端の場合）が挙げてある。
15. 原因の仮説が 2 つ以上並べられ、仮説ごとに「確かめた / 棄てた / 未確認」と決め手の観測が書かれている。
16. 挙動を変えるなら、変える前の挙動を実行して記録してある（テストが無いなら、いまの挙動を固定するテストの候補を挙げてある）。
17. 残った問いが「調べる / 仮定して記録する / 聞く / 時間を区切って試す」に振り分け済みで、「聞く」に振った問いは回答を得たか、回答に依存しない部分だけを進めたと明記してある。
18. 仮定は「仮定・根拠・外れたときの影響・確かめ方」の形で一覧になっている。
19. 1 つ見つけた誤りについて、同じ型の箇所（同じ根本原因）を、意味（誤りを言葉にした語）・構造（呼び出し元・呼び出し先・同じ役割の関数）・履歴（誤りを入れた commit と同じ形の変更）で探した結果（件数・場所・使った検索）が残っている。
20. テストリストの各行に、確かめる完了の条件かリスクと、層が付いており、大きいテストには理由がある。
21. 完了の条件がすべて、テストリストのどれかの行に対応している。
22. 書かないと決めたテストと、その理由が一覧の下に書かれている。
23. 主になるテストの層（小さいテストか API の層か）をどちらと判断したかと、その根拠が 1 行書かれている。
24. 足したテストの実行時間の桁が書かれている。
25. 新しいテストが、期待した理由で失敗した記録（コマンドと出力）がある。
26. 失敗するテストが、実装と区別できる形で残っている。
27. 規則を守る仕組み（guard）を書いたなら、その仕組みを外すと落ちることを実行した記録がある。
28. テストリストが空で、全テストが通った記録（コマンドと出力）がある。
29. 同じ概念を別の場所に持つ箇所（並行実装の組）すべてに変更が入ったことを、検索の件数で確かめてある。
30. 仕様が変わったなら、設計書が同じ変更で直っている。
31. 関係するテスト・型検査・lint を実行したコマンドと出力が残っている。
32. 関係するテストの手元での実行の記録と CI の全体の結果があり、報告する変更と同じ HEAD で走らせたことが記録されている。
33. 「通った」「直した」の主張ごとに、それを証明するコマンドを今の変更に対して実行した出力が添えてある。
34. 完了の条件ごとに証拠（コマンドの結果・画面の記録・検索の件数）があり、確かめていないものは「未検証」と明記してある。
35. CI の各検査が pass（skip・未起動・下書きのため未実行でない）であることを 1 つずつ確かめてある。
36. 利用者に見える挙動を変えたなら、アプリを動かして結果（画面・API の応答）を見た記録がある（内部だけ・型だけ・文書だけの変更では要らない）。
37. 独立の確認を入れた場合は指摘の採否と理由が、入れなかった場合は入れる条件に当たらないことと後段に任せたことが書かれている。
38. 変更した行のうち、どのテストにも実行されない行と実行されないエラー処理が報告されている。
39. 報告には、何を確かめたか・何を確かめていないか・どのテストを書かなかったかが書かれ、全部通ったことは「テストに書いた想定の範囲で動く」と書かれている。
40. 報告に、テストの実行時間（手元・CI）と不安定なテストの状況が含まれ、10 分の予算を超えていればそのことが書かれている。
41. 報告（PR 本文）は、目的・変更点・確かめたこと / 確かめていないことを含む。
42. 報告の主張はすべて実物（diff・ログ・検索の件数・API の応答）で確かめられており、確かめていないものは「未確認」と書いてある。
43. 報告は、確かめたこと・推測したこと・確かめていないことを分けて書いている。
44. 報告は前提を先に、結論を次に書き、人が自分で確かめられる形（具体的な入出力の例・図・コマンドと出力）で示している。
45. 完了の条件を文字どおりに満たしたかを確かめてあり、完了の条件そのものが顧客にとって誤っていると分かったなら、黙って字面を満たさず、そのことを報告している。
46. 案件の決まりごと（成果物の置き場所・テストの走らせ方・記録の形・聞く先など）が書かれていない項目を自分で既定で決めたなら、そのことを報告に書いている。
47. 決まったこと・合意は、チケット・PR・決定記録に書いてある（会話の中の合意は書くまで決まっていない扱い）。
48. 報告は相手の受信箱に入っている（状態が付け替わっている）。
49. レビュー可能にしたのは下書きの間に走る検査がすべて pass した後で、下書きの間は走らない検査も、レビュー可能にした直後に pass を確かめてある（落ちたら下書きに戻して直してある）。

## 品質の基準

50. 変更は最小で、頼まれた変更と明らかに必要な変更だけを含む。
51. 1 つの変更は 1 つの目的で、レビューできる大きさである。
52. テストの期待値は仕様から導いた具体的な値で、根拠（仕様の箇所・計算）を示せる。
53. 期待値の検査は、失敗したとき期待値と実際の値が出る比べ方になっている（例外が出ないことだけ・真偽だけ・件数だけで済ませていない）。
54. 時刻・乱数・並行性への依存は値の決め打ちか外からの差し込みで固定され、テストどうしが順序に依存しない。
55. テストは 1 つの振る舞いに 1 つで振る舞いを確かめ、内部の構造・private な関数・呼び出し順は確かめない（状態を変える外への呼び出しを除く）。
56. テストはアプリと自分専用の DB までは実物を使い、自分が制御できない外部（他のサービス・メール・決済）だけを置き換えるか契約テストにしている。
57. テストのためだけの間接層（テスト専用のインターフェースやフック）を足していない。
58. 不具合の再現テストは、症状を再現できる外側に近い安定した層にあり、消さずに残してある。
59. 振る舞いを変えないリファクタリングには新しいテストを書かず、既存の振る舞いのテストが前後で通ることで確かめてある。
60. テストで確かめるのは、完了の条件の振る舞い（正常系と仕様が定める失敗の扱い）・誤ったときの損失が大きい所・分岐の多いロジック・過去に壊れた所・外部の失敗への応答（代表 1 件ずつ）で、絞っても異常系を落としていない。
61. 手元で回す範囲と CI の必須の検査は、それぞれ 10 分以内に結果を返す。
62. テストの失敗は、何が失敗し、だから次に何をするかまで書かれている。
63. 人が気をつけることに頼る穴は、テスト・型・CI で気づける形にする候補として挙げてあり、新しい仕組みは同じ型が 2 回以上再発したときに限って、既存の検査を広げる・置き換える・消すで済まないことを確かめてから足している。
64. 一見不要な処理・規則・分岐を変えたなら、それが入った経緯（git log・blame・関連 Issue）を確かめてある。
65. 独自の仕組みを作ったなら、先に他の言語・エコシステムを含む先行例を調べてあり、調べずに作ったならそう書いてある。
66. 依存を足したなら、版を固定し、変わった依存の一覧を示している。
67. 外部の技術・法令・初めての外部仕様を調べたなら、一次資料を宣伝記事より優先して 2 件以上当たっている。
68. 探して見つからなかったものは、探した範囲（どの言葉で・どこを）が書かれている。
69. 結論は自分が説明できるところまで読んだもので、人に渡すときは人が理解できる単位と形にしてある。
70. インターフェースは使う側・実装する側への義務を最小にし、公開インターフェースに特定のライブラリの型を漏らさず、互換を壊すなら明示して理由が書かれている。

93. 危険（T2）の変更では、食い違いがすべて裁かれ、悪くなりうる品質とトレードオフ点の候補と（境界に触れるなら）脅威が書かれた調査メモ（要約 1 画面、根拠の無い文に「未確認」）がある。
94. T2 の調査メモは、仮説ごとの確かめた / 棄てた と決め手、食い違いとその裁き方（誰が・なぜ）、採否の基準と止め方（集めた後に変えたらその理由）、結論の決め手とそれが誤っていたら何が変わるか、探して見つからなかった範囲・省いた手順と限界を含む。
95. T2 では設計書（1〜3 ページ、背景と範囲・ゴールと非ゴール・設計・検討した代替案・セキュリティ・個人情報・観測性）があり、解が 1 つに決まる不具合の修正なら PR 本文の数行（なぜ他の直し方を採らないか）で足りる。
96. T2 では、テストリストと書かないテストの一覧があり、変更は小さな変更に分けてあり（分けられないなら事前の合意がある）、報告は読む人が確かめるべき点を先頭に置き、詳細を付録にしている。
97. 構造・インターフェース・データの形を変えるなら悪くなりうる品質（性能・信頼性・セキュリティ・保守性など）が書かれ、性能・信頼性の要求は「速く」「落ちない」でなく数値の予算・目標で書かれている（信頼性 100% を目標にしない）。
98. 認証・認可・個人データ・外部入力の境界に触れるなら、なりすまし・改ざん・否認・情報漏えい・サービス拒否・権限昇格の 6 区分で脅威が挙げられ、それぞれの対処が決めてある。
99. レビューの指摘を受けて直した場合は、すべての指摘に「直した（証拠つき）/ 退けた（根拠つき）/ 確かめている（何を待っているか）」のどれかが書かれ、複数の指摘をまとめて「直した」と言うなら指摘 × 検証コマンド × 件数の表があり、CI がすべて pass でレビュー待ちの状態に戻っている。
100. 指摘への対応は、症状ではなく名指しした事由に対して直し、指摘を実物と照らして誤っていれば技術的な根拠を示して退け、説明はレビューのやりとりでなくコードに書き、base が進んでいれば取り込んで証跡を撮り直してある。

## してはいけないこと

101. 確かめていない項目に完了の印を付けない（実画面を見ていない完了は検証の偽装）。
102. 報告・label・要約・CI の要約・サブエージェントや前のセッションの出力を、実物の代わりにせず、そのまま自分の報告にしない。
103. 開いていないファイルについて主張せず、読んだこと・動かしたことだけを事実として書き、それ以外は「未確認」か「推論」と書き分ける。
104. 推測した原因は、再現テストが修正前に失敗するのを確かめるまで「仮説」と書き、原因と断定しない。
105. 分からない番号や値を推測で埋めない。
106. 頼まれていないこと（範囲外の機能、中核でない・組み合わせで実現できる機能、不具合の修正ついでの周りの掃除、1 回しか使わない補助関数、起こりえない状況への防御）をしない。
107. 「急ぐのでテストを省く」を選ばず、急ぎのときこそ検査を省かない。
108. 仮置き（stub・何もしない実装・TODO）、「とりあえず」「足場として」の作り、型をごまかす書き方（any・強制的な型変換）を残さない。
109. テストに合わせて値をハードコードしない。
110. 実際に動かした出力を期待値に貼らず、本番と同じ式で期待値を計算しない。
111. アサーションを弱めない（真偽だけを見る形に変える・待ち時間を延ばして不安定扱いにする・期待値の差し替え・テストを飛ばす・何でも通す比較）、弱めるなら理由と代わりの確かめ方を書いて承認を得る。
112. 高価で信頼されていないテストを消す・置き換えるなら理由と代わりの確かめ方を書き、期待値を緩めて通すことはしない。
113. 実装のときにテストを書き換えず、落ちたテストを消して通さず、テストが誤っていると思ったら回避・書き換えをせず理由を書いて報告する。
114. 既存のテストが今回の完了の条件と逆の挙動を期待していても、黙って書き換えない。
115. 自明なコード・フレームワークやライブラリ自体の挙動・内部の構造や private や呼び出し順・自分専用の DB をモックするもの・上の層が既に確かめているもの・起こりえない状況・カバレッジの数字のためだけのもの・現在の出力をそのまま期待値に固定するもの（今の挙動を固定する目的で意図した場合を除く）のテストを書かない。
116. テストリストに実装の判断（クラス名・関数の分け方）を混ぜず、完了の条件かリスクを付けられない行は書かない。
117. カバレッジの閾値を下げず、閾値を満たすためだけのテストも書かない（ぶつかったら報告し、閾値の見直しを提案する）。
118. 2 つ目の重複で共通化せず、抽象化するなら理由を書く。
119. 不安定なテストを再実行で済ませず（隔離して原因を記録する）、手元で並行して走らせた検証の結果を根拠にしない。
120. まとめの検査が緑でも、それを根拠にしない。
121. 全部通ったことを「正しい」と書かず、テストの件数を成果として書かない。
122. 後から要件・設計の不備が分かったとき、今の変更でつじつまを合わせず、先にその不備を直す（範囲を超えるなら別の変更に切り出す）。
123. 文書と実装が食い違うときにどちらかを黙って直さず、選んだ案が既存の設計・決定記録と食い違うときも黙って違う作りにしない（決定記録を置き換え済みにして新しいものを書く）。
124. チケットと既存の設計が食い違うなら、実装する前に止めて PO に返す（明らかな書き間違いで戻せるものは仮定として記録して進む）。
125. 戻せない操作は、承認の記録があるまで進めない。
126. 未解決の印が残る部分は先に進めない。
127. 任せた側の指示文より案件の決まりごと（入口の文書から指された規則）を優先し、食い違いを黙って流さず報告する。
128. 記録を書き換えず（amend しない）、強制 push は相手の更新を確かめる形（--force-with-lease）だけにする。
129. 状態（label）を外すときは必ず次の状態を付け、コメントや mention を書いただけで渡した・聞いたことにしない。
130. 困難でも、閉じて作り直す・範囲を分ける・別のチケットに逃がす、で済ませない（同じ変更の中で行き詰まった実装を捨てて作り直すのはよい）。
131. 指摘を鵜呑みにせず、迎合する言い方をせず、技術的な正しさを優先する。
132. もっともらしい出力で、確かめる負担を他人に押しつけない。
