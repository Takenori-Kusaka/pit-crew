この作業を引き渡す時点で、次がすべて成り立っていること。

- 変更のリスクの区分（自明 / 通常 / 危険）とその理由が 1 行で残っている。
- 区分は、差分の言い表し・種類・戻せるか・影響の領域・広さ・履歴の軸のうちいちばん重い軸に合わせてあり、不具合修正は通常以上になっている。
- 自明とするのは、差分を 1 文で言えて範囲が明確で、誤字・文言・ログ 1 行・名前の変更などの種類で、すぐ戻せて、影響がリスクの低い領域だけで、1〜2 ファイルに収まる変更に限られている。
- 進め方が不確か・妥当な設計が複数ある・新しい機能や新しい公開インターフェース・戻せない操作・認証／認可／個人データ／課金と金額の計算（価格・請求・税）／外に公開した挙動に触れる・複数モジュールや多数のファイルに及ぶ・同じ箇所に事故や再発の履歴がある、のどれかに当たる変更は危険の区分になっている。
- 迷ったときは上の区分にしてあるが、危険の区分は上の具体的な項目に当たるときに限られており、迷っただけで全部を危険にしていない。
- 作業中に、読んだ事実が依頼の前提と食い違った・影響が想定より広かった・同じ問題への修正が続けて外れた・戻せない操作が要ると分かった、のどれかが起きた場合は区分を上げてあり、区分を下げた場合はその理由が書いてある。
- 省いてよいとされたものを省いた場合は、何を省いたかとその理由が 1 行で残っている。
- 成果物の総量は、自明なら PR 本文の数行だけ、通常なら PR 本文と短い変更計画まで、独立の文書（調査メモ・設計書）は危険の区分のときだけであり、これを超える成果物を作っていない。
- すべての変更を同じ手続きに通しておらず、この変更で要る手順と成果物だけにしてある。
- 完了の暫定の定義が 1 文で書かれており、通常・危険の区分では変更の目的も書かれている。
- 戻せない操作の有無と、ある場合はその承認の経路と承認者が書かれている。
- 進め方（直列か並列か、分けるか）が記録されている。
- 並列に進めたのは、触るファイルが重ならない・並行実装の組に触れない・データの形を変えない・設計書の同期が独立・重大でない・単独で完了できる、を全部満たすときだけで、それ以外は 1 件ずつ直列に進めてある。
- 作業を分割したのは、1 回では不可能・各部分が独立して出せる・各部分で顧客に見える進みがある・承認がある、をすべて満たすときだけである。
- 計画ファイルは、1 セッションで終わらない作業・別の担い手に渡す作業・危険の区分の作業のときだけ作られており、1 セッションで終わる自明・通常の作業では作られていない。
- 受け取ったこと・渡したことが相手の受信箱の状態（label 等）に表れており、古い状態を外したときは必ず次の状態が付いている。
- 変える箇所とその呼び出し元を開いて読んであり、開いていないファイルについて主張していない。
- 完了の定義が、何をすると何が見えるかという観測できる形で言える。
- 残った問いが「調べる / 仮定して記録する / 聞く / 時間を区切って試す」に振り分け済みで、聞いた問いは回答を得たか、回答に依存しない部分だけを進めたと明記してある。
- 未解決の印が残る部分は先に進めていない。
- 通常以上の区分では、変える箇所（ファイル・関数）をすべて名指しした変更計画が PR 本文・計画ファイルなどの外に書かれており、退行や修正漏れの候補（同じ型の箇所、端の場合）が挙げてある。
- 通常の区分の変更計画は 3〜4 項目で、言い直した依頼と完了の定義・変える箇所の名指しと影響の検索結果（件数と場所）・観測の証拠（不具合なら再現の失敗、挙動を変えるならいまの挙動）・残った問いと振り分けと仮定を含む。
- 自明の区分では、何を変えるかとどこを読んだかが PR 本文に 1〜2 行で書かれている。
- 影響の検索の件数と場所が残っており、「文字列検索で N 件」だけで影響範囲の調査を終えたことにしていない。
- 名前の変更・API の廃止・データの形の変更・用語やプランの根本変更・層の境界の変更・画面の説明文や法務文書や用語辞書の改訂・50 ファイル超・撤去に当たる変更では、区分が通常以上で、影響範囲を構文・意味・構造・派生物（文書・設定・データ・画面文言・外部サービス・監視）の 4 層で確かめてある。
- 公開している挙動を変える場合は、契約に書いていない利用者も数えてある。
- 不具合では、症状が見える層で再現するテスト（またはスクリプト）が修正前に失敗することが確かめられており、修正前に通った場合はテストの誤りか原因の理解不足を疑って調べ直してある。
- 通常以上の区分では、原因（または方針）の仮説が 2 つ以上並べられ、仮説ごとに「確かめた / 棄てた / 未確認」と決め手の観測が書かれている。
- どの仮説とも整合する観測を判断の根拠にしていない。
- 挙動を変える場合は、変える前の挙動を実行して記録してあり、テストが無ければいまの挙動を固定するテストの候補が挙げてある。
- 自前で仕組みを作る場合は、使えるライブラリや他の言語・エコシステムの先行例を調べてあり、調べずに作ったなら「先行例を調べていない」と書いてある。
- 依存を足す場合は、考え方を借りることとは別に判断してあり、版の固定と更新の費用も比べてある。
- 危険の区分では、要約が 1 画面に収まる調査メモがあり、通常の 4 項目に加えて、仮説ごとの確かめた / 棄てた と決め手・食い違いとその裁き方（誰が・なぜ）・悪くなりうる品質とトレードオフ点の候補と脅威・探して見つからなかった範囲と省いた手順と限界が書かれている。
- 危険の区分（または通常で文書・外部資料の食い違いがあるとき）では、食い違いがすべて「裁いた（根拠つき）/ 条件によって両方正しかった / 顧客への約束を変えるため上げた」のどれかになっている。
- 危険の区分で構造・インターフェース・データの形を変える場合は、悪くなりうる品質について測れる形の要求が数本、(重要度, 難しさ) を高 / 中 / 低で付けて挙げてあり、品質が逆向きに動く点は候補として設計に渡してあり、通常の区分では悪くなりうる品質が 1 行書かれている。
- 認証・認可・個人データ・外部入力の境界に触れる場合は、区分によらず、なりすまし・改ざん・否認・情報漏えい・サービス拒否・権限昇格の 6 区分で起こりうることが並べてあり、それぞれへの対処が決めてある。
- 読んでいる branch・HEAD・環境が記録されており、作業する branch が base の今の先端を含むこと（ok / stale）が確かめてあり、stale だった場合は最新の base を取り込んだ後の土台で調べ直してある。
- 分岐の後に base に入った変更を自分が消したかのように扱ったり、古い土台で見えた存在しない削除や矛盾を事実として扱ったりしていない。
- 読んだこと・動かしたことだけが事実として書かれ、それ以外は「未確認」か「推論」と書き分けてある。
- 他の人やサブエージェントの報告、label、CI の要約を実物（diff・ログ・検索の件数・API の応答・実行結果）の代わりにしておらず、分からない番号を推測で埋めていない。
- 一見不要な処理・規則・分岐を変える場合は、それが入った経緯（git log・blame・関連 Issue）を確かめてある。
- 問いは一般論ではなく、この製品の前提（実行基盤・顧客・開発体制・段階・制約）と顧客に害が出る失敗の型から立ててある。
- 結論を覆しうる観測を 1 つ挙げてそれを取りに行ってあり、他社の事例を決定の根拠にしていない。
- 推測した原因は、再現テストが修正前に失敗するまで「仮説」と書いてある。
- 通常以上の区分では、1 つ見つけた誤りと同じ型の箇所を、字面ではなく何を計算・判断しているか（根本原因）で、意味（誤りを言葉にした語での検索）・構造（呼び出し元・呼び出し先・同じ役割の関数を開く）・履歴（誤りを入れた commit と同じ形の変更）の 3 つで探してあり、件数・場所・使った検索が残っている。
- 同じ型の探索を、見えている式や文字列の grep だけで終えていない。
- 人が気をつければ防げる穴を見つけた場合は、注意書きを足すより、テスト・型・CI で検出できる形にすることが候補として挙げてある。
- 入口の文書・チケットとその履歴（コメント・関連 PR）・変更箇所と呼び出し元・既存のテスト・同じ概念を別の場所に持つ箇所を読んであり、通常以上では変える箇所に関係する設計書・決定記録の日付と状態（置き換え済みか）も確かめてある。
- 名前・用語・データの形を変える場合は、全出現箇所の検索結果が件数と除外理由つきで残っており、データの形は定義・作成・移行・既存データの移し替え・テスト用の初期データまで確かめてある。
- 外に見えるものを変える場合は、画面の文言・説明ページ・販促文・料金表に同じ訴求がないか確かめてある。
- 不具合の場合は、同じ箇所の過去の不具合と修正を確かめ、再発していないか・同時期の名前の変更で修正が古いパスにだけ入っていないかを見てある。
- 外部の技術・法令・初めての外部仕様を調べた場合は、一次資料を 2 件以上当たり、一次資料を宣伝記事より優先し、自分で読んである。
- 探して見つからなかったものには、探した範囲（どの言葉で・どこを）が書いてあり、試す作業には始める前に時間枠が決めてある。
- 完了に要る問いに答えられた後も調べ続けたり、存在しない資料を探し続けたり、単純な問いに過剰に調べたりしていない。
- 材料の採否・重み付けの基準と止め方が集める前に書いてあり、集めた後に変えた場合はそのことと理由が書いてある。
- 値の正しさは文書の格ではなくその値を支える根拠の強さで比べてあり、結論は種類の違う 2 つ以上の出所・方法で支えてある（写しは 1 つと数える）。
- 品質の優先は変更の事業上の目的から導いてあり、案件の品質の優先表があればそれに従っている。
- セキュリティと運用の健全性をトレードオフの対象にしておらず、譲る場合は決定記録と承認がある。
- 性能・信頼性の要求は「速く」「落ちない」ではなく数値の予算・目標で書かれており、信頼性 100% を目標にしていない。
- 速さのために内部品質（保守性）を下げることや「急ぐのでテストを省く」ことを前提にしておらず、下げる・省く場合は判断と返済が記録してある。
- 結論の決め手が名指しされ、それが誤っていたら何が変わるか・何が見えたら見直すかが書いてある。
- 調査を縮めた場合は、省いた手順とそれによる限界、止めた基準（答えが揃った / 新しい材料が出ない / 上限 / 網羅）が書いてある。
- リポジトリ・チケット・既存の文書・履歴から答えが得られる問いを聞いていない。
- 妥当な既定値があり外れても戻せるものを仮定して進めた場合は、仮定一覧に「仮定・根拠・外れたときの影響・確かめ方」が書いてある。
- 「お任せ」と言われたことには、推奨を示して明示的な確認を取ってある。
- 回答を待っている問いがある場合は、それに依存する部分を進めておらず、何を待っているかが書いてある。
- 文書と実装が食い違うとき、どちらかを黙って直しておらず、いまの挙動をテストで固定し、食い違いを記録し、どちらが正かを裁定して、決めた側に合わせてもう一方を直してある。
- 文書どうしの食い違いは、文書が宣言する優先順位があればそれに従い、なければ各値の理由・経緯を調べて顧客から見た根拠の強い方を採り（前提が消えた根拠は外し、根拠が無い値は世の中の標準から定め直し、両方成り立つなら古い顧客への約束を採る）、文書を直して根拠を残す形で裁いてある。
- 上げて止まることを既定にしておらず、上げたのは顧客への約束を変える結論でそれが顧客の気にする水準のときだけである。
- チケットと既存の設計が食い違う場合は、実装の前に止めて PO に返してあり、明らかな書き間違いで戻せるものは仮定として記録して進めてある。
- 後になって前の段階（要件・設計）の不備が分かったとき、今の作業でつじつまを合わせておらず、元を先に直してあり、今の範囲を超えるものは別の変更に切り出してある（範囲の拡大か設計の欠陥か迷ったものは触っていない）。
- 出所どうしが食い違いどちらも決め手にならない場合は、仮説を見分ける観測を新たに取りに行ってあり、取れなければ「条件によって両方正しい」可能性とその条件が書いてある。
- 比べる双方の HEAD を揃えずに比較していない。
- 調査の要約は PR 本文（またはチケット）に、詳細はリポジトリ内のファイルに置いてある。
- 書かなかった項目は対象外とみなし、「対象外」とその理由を項目ごとに書き並べていない。
- 会話の中の合意・決定はチケット・PR・決定記録に書かれており、根拠・目標・制約は決めたその場で書かれている。
- 調べさせたりレビューさせたりした結論も、自分が説明できるところまで読んであり、人に渡すものは人が理解できる単位と形になっている。
- 推奨案と、捨てた案とその理由が書かれており、設計を書かないと判断した場合はその理由が 1 行書かれている。
- 通常の区分では、解が 1 つなら設計を書かず、妥当な案が複数あるなら PR 本文に数行（推奨と、捨てた案 1 つと理由）が書かれている。
- 危険の区分、新しい公開インターフェース、新しい機能では、背景と範囲・ゴールと非ゴール・設計・検討した代替案・セキュリティ・個人情報・観測性の節を持つ 1〜3 ページの設計書があり、ただし解が 1 つに決まる不具合の修正では、なぜ他の直し方を採らないかを PR 本文に数行書けば足りる。
- 新しいデータの形・新しいインターフェース・セキュリティ・課金・外部資源の追加・数日以上の作業では設計が書かれている。
- 代替案の無い実装手順書を設計書と呼んでいない。
- トレードオフ点（1 つの選択で品質が逆向きに動く点）をどちらに倒したかとその理由が書かれている。
- 案は、どの案でも満たせる基準を外したうえで、順位つきの判断基準（品質の順位と事業上の目的）で比べてある。
- 別のエージェントや人に実装を渡す場合は、計画が数分単位のタスクに分かれ、各タスクに触るファイルと確かめ方が付いている。
- 合意が要るもの（戻せない操作や、決める席が他にある判断）は、着手前に承認を取り、その記録が GitHub 上（コメント・label・決定記録）にある。
- 将来のための仕組みを作らず、フレームワークの機能を包まずに使い、抽象を足しておらず、破った場合は理由が書いてある。
- 実行時の検査を足す前に、型・列挙・値の型で不正な値を作れなくできないかを考えてあり、外から入る値は境界で早く失敗させてある（型で保証していても外からの値には実行時の検査を残す）。
- 時刻・乱数・外部 I/O は外から差し込める形になっており、テストのために設計を変えた場合は責務が単純になっている（複雑になっていない）。
- インターフェースは使う側・実装する側への義務を最小にしてあり、公開インターフェースに特定のライブラリの型を漏らしておらず、既存の仕組みとの互換を壊す場合は明示して理由が書いてある。
- 複雑さは内部の作りの数ではなく、使う人から見た複雑さで比べてある。
- 2 つ目の重複で共通化しておらず、似た仕組みが 3 つ目になったときに共通の型を当てない場合はその理由が 1 行書いてある。
- 1 つの変更（PR）に 2 つ以上の目的を混ぜておらず、途中の段階を出す場合も各段階が単独で動く形になっている。
- 決定記録（文脈・決定・状態・結果）は、後から覆すときに背景の理解が要る重要な決定・既存の決定記録と矛盾する新しい判断・機械で強制できない判断原則のどれかのときだけ書かれ、それ以外の決定は PR 本文の 1 段落に書かれている。
- 選んだ案が既存の設計・決定記録と食い違う場合に黙って違う作りにしておらず、古い記録を消さずに置き換え済みにして新しい記録を書いてある。
- 中核でないもの、他と組み合わせて実現できるものを足しておらず、足さない理由が書いてある。
- 自明の区分では新しいテストを原則書かず、既存のテストを変更の前後で走らせた記録がある。
- 通常の区分では数行のテストリストがあり、危険の区分ではテストリストと書かないテストの一覧がある。
- テストリストの各行に、確かめる完了の条件かリスクが付いており、付けられない行は書かれていない。
- テストリストに実装の判断（クラス名・関数の分け方）を混ぜていない。
- テストリストの各行に層が付き、実ネットワーク・ブラウザ・複数サービスにまたがる大きいテストには 1 本ずつ理由がある。
- 書かないと決めたテストとその理由が、テストリストの下に書かれている。
- 完了の条件がすべて、テストリストのどれかの行に対応している。
- テストで確かめる対象は、完了の条件に書かれた振る舞い（正常系と仕様が定める失敗の扱い）・誤ったときの損失が大きい所（お金・データの消失・権限・個人情報）・分岐の多いロジック・過去に壊れた所や間違えやすい所・外部の失敗（タイムアウト・相手のエラー・制約違反）への応答の代表 1 件ずつに限られている。
- テストを絞るときに異常系（外部の失敗への応答）を落としていない。
- テストの層は比率ではなく、確かめるものとコードの種類ごとに選んであり（ドメインのロジックはプロセス内の小さいテスト、つなぎのコードは自分専用の DB を実物にした公開 API の層、自明なコードは書かない、分岐も依存も多いコードはテストの前に分割を考える）、製品の主になる層をどちらと判断したかと根拠が 1 行書いてある。
- アプリと自分専用の DB までは実物を使い、自分が制御できない外部だけを置き換えるか契約テストにしてあり、内部の構造・private な関数・呼び出し順は（状態を変える外への呼び出しを除いて）確かめていない。
- 不具合では、症状を再現できる外側に近い安定した層の再現テストが最初の 1 本になっており、振る舞いを変えないリファクタリングでは新しいテストを書かず既存の振る舞いのテストが通り続けることで確かめてある。
- 自明なコード・フレームワークやライブラリ自体の挙動・内部の構造や private や呼び出し順・自分専用の DB をモックする・上の層のテストが既に確かめていて足しても場所の特定も速さも増えない・起こりえない状況・カバレッジの数字のためだけ・現在の出力をそのまま期待値に固定する（意図して今の挙動を固定する場合を除く）テストを書いていない。
- 技法（同値分割・境界値・決定表・状態遷移）は、損失が大きい・分岐が多い・過去に壊れた箇所にだけ当ててある。
- 手元で回す範囲と CI の必須の検査がそれぞれ 10 分以内に結果を返し、足したテストの実行時間の桁が書いてあり、超えそうなら足す前に遅いテストを速くする・まとめる・消すを考えてある。
- 変更が触れる領域に、重い検査でしか見つからない不具合の履歴がある場合は、関係する重い検査を手元で走らせてある。
- 既存のテストが今回の完了の条件と逆の挙動を期待している場合に、それを黙って書き換えておらず、どちらが正かを裁定してある。
- カバレッジの閾値を下げておらず、閾値を満たすためだけのテストも書いておらず、閾値と書かないテストがぶつかった場合はそのことを報告して閾値の見直しを提案してある。
- 人と一緒に進める作業では、実装の前にテストリスト（テストのコードではなく一覧）が見せてある。
- 完了の条件をテストできる形にできなかった場合や期待値を仕様から導けなかった場合は、根拠の無いまま値を決めておらず、仮定を記録するか聞いてある。
- 完了の条件を満たすテストが設計では書けない場合に、そのまま進めておらず設計を直してある。
- テストが期待した理由で失敗した記録（コマンドと出力）があり、最初から通るテストで確かめたことにしておらず、予期しない理由で失敗した場合はテストか理解を直してある。
- テストの期待値は仕様から導いた具体的な値で、根拠（仕様の箇所・計算）を示せる。
- 実際に動かした値を期待値に貼っておらず、本番と同じ式で期待値を計算していない。
- 期待値の検査を、例外が出ないことだけ・真偽だけ・件数だけで済ませておらず、失敗したときに期待値と実際の値が出る比べ方になっている。
- 時刻・乱数・並行性に依存するテストは値を決め打ちするか外から差し込んであり、テストどうしは順序に依存しない。
- 1 つの振る舞いに 1 つのテストで、テストのためだけの間接層（テスト専用のインターフェースやフック）を足しておらず、準備のコードは読みやすさを損なわない範囲で共有してある。
- 内側の小さいテストは、外側のテストを通す途中で複雑なロジックが要ると分かったときにだけ足してある。
- 規則を守る仕組み（guard）を書いた場合は、その仕組みを外すとテストが落ちることを実行して記録してある。
- 失敗するテストは実装と区別できる形で残してあり、実装のときにテストを書き換えていない。
- テストに合わせて値をハードコードしていない。
- アサーションを弱めて（真偽だけを見る形に変える・待ち時間を延ばして不安定扱いにする・期待値の差し替え・テストを飛ばす・何でも通す比較）いない、弱める場合は理由と代わりの確かめ方を書いて承認を得てある。
- 高価で信頼されていないテストを消す・置き換える場合は、理由と代わりの確かめ方が書いてあり、期待値を緩めて通すことはしていない。
- テストは既存のテストの書き方と補助（fixture・ヘルパ）に合わせてある。
- テストリストが空で、全テストが通った記録（コマンドと出力）がある。
- 並行実装の組（同じ概念を別の場所に持つ箇所）すべてに同じ変更が入ったことを、検索の件数で確かめてある。
- 仕様が変わった場合は、設計書の更新が同じ変更に入っている。
- 仮置き（stub・何もしない実装・TODO）が残っておらず、any や強制的な型変換で型をごまかしていない。
- 変更は最小で、通す変更と整理を混ぜていない。
- 頼まれた変更と明らかに必要な変更だけをしており、不具合の修正で周りを掃除しておらず、1 回しか使わない処理に補助関数を作っておらず、起こりえない状況の防御を書いていない（検査は外との境界で行う）。
- 範囲外の機能を足しておらず、足したいものは別のチケットとして提案してある。
- 範囲外の問題に気づいた場合、軽く同じ目的なら同じ変更で直し、目的が混ざるなら別の変更にして直してあり、チケットにしたのはいま直せないと分かったときだけで、そのチケットには理由と担当が書いてある。
- 依存を足した場合は版を固定し、変わった依存の一覧が示してある。
- 人と一緒に進める作業では Red / Green / Refactor の段階ごとに記録（コミット）が分かれている。
- 整理（Refactor）は通った状態のまま、今の作業に必要な範囲だけで行ってあり、抽象化した場合は理由が書いてある。
- 「負債」を雑なコードの言い訳にしておらず、「後で直す」と書いた箇所にはチケットがあり、作らないものは今直してある。
- 整理の後に、手元で走らせられる範囲のテストを走らせて通った記録がある。
- 利用者に見える挙動（画面・API の応答）を変えた場合は、単体テストと型検査で終えずにアプリを動かして結果を見てある。
- 設定・文言・純粋な削除・依存の定型更新・振る舞いを変えない機械的なリファクタリングでは、既存のテストを変更の前後で走らせてあり、テストが無ければ変更の前にいまの挙動を固定してある。
- テストが誤っていると思った場合に、回避や書き換えをしておらず、理由を書いて報告してある。
- 同じ仮説での修正が続けて外れた（3 回）場合に、手当たり次第に直し続けておらず、仮説と設計を疑って戻ってある。
- 変更（PR）そのものを閉じて別に作り直した場合は、その理由が変更に残してある。
- 困難を理由に、閉じて作り直す・範囲を分ける・別のチケットに逃がす、で済ませていない。
- 触ったコードの書き方が古いと気づいて直した場合は、一次資料 2 件以上で確かめてある。
- 規則を字面どおりに当てはめて、動いている検査を消していない。
- 本番に必要な設定を配らずに起動時の検査を足していない。
- 例外を許さない規則は文で書くだけでなく仕組みで強制してあるが、手順・規則・仕組みを足したのは、それが無かったら起きる事故を言え、同じ型が 2 回以上再発したときに限られ、足す前に既存の検査を広げる・置き換える・消すで済まないかを確かめてある。
- 完了の条件ごとに証拠（コマンドの結果・画面の記録・検索の件数）があり、確かめていないものは「未検証」と明記してある。
- 完了の条件が複数あるとき・「全部」と主張するとき・危険の区分のときは、完了の条件 × 証拠の表があり、「全部」と書く前に全範囲を検索してある。
- 関係するテスト・型検査・lint を実行したコマンドと出力が残っている。
- 「通った」「直した」の主張ごとに、それを証明するコマンドを今実行して出力を読んであり、その出力が報告に添えてある。
- 関係するテストの手元での実行の記録と CI の全体の結果があり、検査した作業ツリーの HEAD が報告する変更の HEAD と同じであることが記録されている。
- CI の各検査が pass（skip・未起動・下書きのため未実行ではない）であることを 1 つずつ確かめてあり、まとめの検査が緑であることを根拠にしていない。
- 変更を PR として出す場合は、下書き（Draft）のまま始め、下書きの間に走る検査がすべて pass したのを確かめてからレビュー可能にしてあり、下書きの間は走らない検査はレビュー可能にした直後に pass を確かめ、落ちたら下書きに戻して直してある。
- 独立の確認を入れたのは、危険の区分・後段に人や QM のレビューが無い・同じ文脈で作ったものを同じ文脈で完了とし複数の条件を「全部できた」と主張する、のどれかのときだけで、入れる前に後段のどの検査と重なり何を後段に任せるかが書いてある。
- 独立の確認を入れた場合は、作業の文脈を持たない確認者に仕様と照らした正しさの欠落だけを報告させてあり、指摘ごとの採否と理由が書いてあり、仕様と食い違う指摘は根拠を示して退けてある。
- 独立の確認を入れなかった場合は、入れる条件のどれにも当たらないことと、後段に任せたことが書いてある。
- 不安定なテストを再実行で済ませておらず、隔離して原因を記録してあり、手元で並行して走らせた検証の結果を根拠にしていない。
- 変更した行のうちどのテストにも実行されない行と、実行されないエラー処理を探して報告してある（全体のカバレッジの数字は目標にしていない）。
- テストの効き目を疑った場合は、変更行を 1 か所わざと壊してテストが落ちるかを確かめてある。
- 全部通ったことを「正しい」とは書かず、「テストに書いた想定の範囲で動く」と書いて範囲外は未検証としてあり、テストの件数を成果として書いていない。
- 何を確かめたか、何を確かめていないか、どのテストを書かなかったかが書いてある。
- テストの実行時間（手元・CI）と不安定なテストの状況が報告に含まれ、10 分の予算を超えていればそのことが書いてある。
- 手元では通り CI で落ちる（またはその逆の）場合は CI を正とし、差の原因（環境・負荷・版）を調べてある。
- 自分の変更が原因でない CI の失敗を「原因調査中」「自分のせいではない」で放置しておらず、原因を特定してその場で直す変更を出してある。
- テストの結果は、何が失敗し、だから次に何をするかまで書いてある。
- 急ぎのときでも検査を省いていない。
- レビューの指摘・差し戻しに対応した場合は、すべての指摘について「直した（証拠つき）/ 退けた（根拠つき）/ 確かめている（何を待っているか）」のどれかが書いてある。
- 複数の指摘をまとめて「直した」と言う場合は、指摘 × 検証コマンド × 件数の表がある。
- 指摘に対応した後は、CI がすべて pass で、差し戻しの状態を外してレビュー待ちの状態が付いている。
- 指摘を鵜呑みにせずコードの実態と照らしてあり、誤っている指摘は技術的な根拠を示して退け、確かめられない指摘には何が無いと確かめられないかと、調べる / 聞く / 進めるのどれにするかが書いてある。
- 意図の分からない指摘を推測で直しておらず、着手前に相手の受信箱で確かめてある。
- 直したものは症状ではなく事由を名指ししてから直してあり、挙動の不具合の再現テストは消さずに残してある。
- 指摘への説明は、レビューのやりとりではなくコード（明確な書き方、足りなければコメント）に書いてある。
- base が進んだら指摘を待たずに取り込んであり、取り込んだ後は証跡（画面の記録など）が撮り直してある。
- 記録を書き換えて（amend して）おらず、強制 push は相手の更新を確かめる形（--force-with-lease）だけにしてある。
- 前回の差し戻しの事由が今の HEAD に反映されていることが確かめてある。
- 同じ指摘が 2 周続いた場合に 3 周目の直し合いに進んでおらず、何と何が食い違っているかを名指しして裁定し、裁定に合わせて設計書を直す変更を先に出してある。
- 迎合する言い方（「素晴らしい指摘です」等）をせず、技術的な正しさを優先してあり、合意できない点は技術的な事実で議論して差分を放置していない。
- 書式の必須項目を埋めるためだけに空回りしていない。
- 報告の主張（「直した」「通った」「N 件」）がすべて実物（diff・ログ・検索の件数・API の応答）で確かめてあり、確かめていないものは「未確認」と書いてある。
- サブエージェントや前のセッションの報告を、そのまま自分の報告にしていない。
- 報告では、確かめたこと・推測したこと・確かめていないことが分けて書かれている。
- 完了の条件を文字どおり満たしていない項目、確かめていない項目に完了の印を付けておらず、チケットを閉じたこと・PR を出したこと・CI が緑なことを完了としていない。
- 完了の条件そのものが顧客にとって誤っていると分かった場合は、黙って字面を満たさず、そのことが報告してある。
- 報告は何を前提にした結論かを先に書き、結論を次に書いてあり、人が自分で確かめられる形（具体的な入出力の例・図・コマンドと出力）で示してあり、長い説明で理解した気にさせていない。
- 報告の量は、自明なら 1〜3 行（何を変え、何で確かめたか）、通常なら PR 本文（目的・変更点・確かめたこと / 確かめていないこと）、危険ならそれに加えて読む人が確かめるべき点を先頭に置き、詳細を付録にしてある。
- 報告は相手の受信箱に入っており（状態が付け替わっており）、コメントや mention だけで届いたことにしていない。
- 誰に渡すべきか決まらない場合は、受け付けた経路を逆にたどり、それでも決まらなければ宛先の決まっていないものとして PO の受信箱に入れてある。
- 自分の報告と他者の報告・CI の結果が食い違う場合に、報告どうしを比べて決めておらず、実物を測り直してある。
- 報告に「〜に進みます」と書いたことを実行しないまま終えていない。
- もっともらしい出力で、確かめる負担を他人に押しつけていない。
- 案件の決まりに書かれていない事項を既定で決めた場合は、既定で決めたことが報告に書いてある。
- 自分が決めてよいこと（承認された設計の中の判断・局所の設計・テストの書き方・命名・着手順・確立した直し方のある不具合の直し方・既存の仕組みの範囲の変更）は聞かずに決めて理由を残してある。
- 上に上げたのは決める席が他にあるときだけで、戻しにくい技術の選択（データストア・認証・課金・公開 API の形・基盤）と基盤の制約・費用のトレードオフは技術判断者に、顧客に見える文言・UX・価格の方針・backlog の順序・機能仕様と実装計画の承認・範囲の約束・リスクの受容は PO に聞いてあり（技術判断者がいなければ PO）、聞く先は 1 つにしてある。
- 聞いたのは、範囲・セキュリティ／個人情報・顧客に見える挙動に大きく効き、解釈が複数あり、妥当な既定値が無いものだけで、優先は範囲 > セキュリティ／個人情報 > 顧客に見える挙動 > 技術の細部の順である。
- 未解決の印は最大 3 で、質問は 1 回に 1 問、各問に「なぜ重要か」・選択肢・推奨が付いている。
- 問いや判断の依頼をチケットのコメントにだけ書いて「聞いた」ことにしておらず、相手の受信箱に届く経路で聞いてある。
- データの削除・課金・本番への反映・データの形の変更（スキーマ変更）といった戻せない操作は、承認の記録があるまで進めていない。
- 作業を任されたとき、任せた側の指示文より案件の決まりごと（入口の文書から指された規則）を優先してあり、食い違いがあればそれを報告してある。
- チケットどうしの優先度の食い違いを自分で決めておらず、PO に受信箱で返してある。
